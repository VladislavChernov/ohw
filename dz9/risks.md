# Риски и ограничения методологии

Документ фиксирует ограничения контрольного прогона из
[`example_metrics_run.md`](example_metrics_run.md). Это не баги: пайплайн
считает метрики корректно. Это ограничения **методологии**, из-за которых
числа нельзя воспринимать как строгий бенчмарк.

Кратко: один hold-out split без кросс-валидации, пропуски в Pima не
импутируются, гиперпараметры не подбираются.

## 1. Один hold-out split без кросс-валидации

**Что сделано.** Данные один раз делятся на train/test в пропорции 80/20 с
`random_state=42`. Модель учится на train, метрики считаются на одном test.

**Почему это проблема.** Метрика на одном split — случайная величина. Она
зависит от того, какие именно объекты попали в тест. Если тест «удачный»,
модель покажет выше; если «неудачный» — ниже. Особенно это заметно на
маленьких выборках и при дисбалансе классов.

**В нашем прогоне.**

| Датасет | Test | Цена одной ошибки в accuracy |
|---|---|---|
| `breast_cancer` | 114 объектов | ≈ 0.0088 |
| `pima_indians` | 154 объекта | ≈ 0.0065 |

Отсюда:

- `breast_cancer`: LR 0.982 против Perceptron 0.956 — разница 0.026, то есть
  **около 3 объектов** из 114;
- `pima_indians`: LR 0.714 против Perceptron 0.727 — разница 0.013, то есть
  **около 2 объектов** из 154.

Грубая оценка стандартной ошибки accuracy при `n=154` и `p≈0.72` — около
0.036 (3.6 п.п.). Разница 1.3 п.п. находится глубоко внутри этой
погрешности. То есть вывод «перцептрон лучше на Pima» по одному split
**статистически не обоснован**.

**Что даёт кросс-валидация.** Stratified k-fold (обычно 5 фолдов):

1. Данные делятся на 5 частей с сохранением пропорции классов.
2. Модель обучается 5 раз: каждый раз один фолд — валидация, остальные 4 —
   обучение.
3. Итог — среднее и стандартное отклонение метрики по фолдам.

Преимущества:

- оценка устойчивее и использует все объекты;
- видно разброс (`0.72 ± 0.04`), а не одно число;
- можно сравнить модели по среднему и проверить, перекрываются ли интервалы.

Для корректности тест всё равно держат отдельно: кросс-валидацию делают
**на train**, а финальный test трогают один раз. Если подбирать
гиперпараметры, нужна вложенная CV (nested CV): внешняя — для оценки,
внутренняя — для подбора.

Стоимость для наших моделей минимальна: логистическая регрессия и
перцептрон обучаются за миллисекунды, 5 фолдов — вопрос секунд.

## 2. Пропуски в Pima не импутируются

**Что сделано.** `pima_indians.csv` содержит нули в физиологически
невозможных местах. Пайплайн читает их как обычные числовые значения `0.0`
и не заменяет.

**Где именно нули:**

| Признак | Нулей | Доля | Комментарий |
|---|---|---|---|
| `feature_1` (pregnancies) | 111 | 14.5% | 0 — валидное значение |
| `feature_2` (glucose) | 5 | 0.7% | 0 невозможен |
| `feature_3` (blood pressure) | 35 | 4.6% | 0 невозможен |
| `feature_4` (skin thickness) | 227 | 29.6% | 0 невозможен |
| `feature_5` (insulin) | 374 | 48.7% | 0 невозможен |
| `feature_6` (BMI) | 11 | 1.4% | 0 невозможен |
| `feature_7`, `feature_8` | 0 | 0% | — |

**Почему это проблема.** Ноль здесь — не измерение, а **маркер отсутствия
данных**. Модель этого не знает и учится на нём как на реальном значении:

- почти половина колонки `insulin` — это одна и та же константа `0`,
  которая не отражает реальный уровень инсулина;
- линейная граница и коэффициенты смещаются, потому что «нулевые» пациенты
  образуют искусственную группу;
- recall и precision занижаются не из-за слабости модели, а из-за качества
  признаков.

**Что такое импутация.** Это замена пропуска на правдоподобное значение:

- медиана/среднее по train;
- самое частое значение;
- KNN-импутация (похожие объекты);
- итеративная (MICE);
- отдельный признак-индикатор «здесь был пропуск».

Для Pima разумный минимум:

1. Заменить `0 → NaN` **только** в glucose, blood pressure, skin thickness,
   insulin, BMI. Для pregnancies 0 оставить: это валидное значение.
2. Поставить `SimpleImputer(strategy="median")` **до** `StandardScaler`
   внутри `Pipeline`.
3. Обучать импутер только на train — иначе утечка данных из test.
4. Сравнить метрики с импутацией и без неё на одной CV-схеме.

Важно: импутация не гарантирует рост качества. Иногда медиана «размывает»
сигнал, и лучше работает модель, устойчивая к пропускам (например,
градиентный бустинг). Но текущие числа для Pima — это качество на данных с
49% пропусков в инсулине, а не предел модели.

## 3. Гиперпараметры не подбираются

**Что сделано.** Используются значения scikit-learn по умолчанию,
зафиксированы только `random_state` и `max_iter=5000`:

- `LogisticRegression(C=1.0, penalty="l2", solver="lbfgs", class_weight=None)`;
- `Perceptron(alpha=0.0001, max_iter=1000, tol=1e-3, class_weight=None)`.

**Почему это проблема.** Дефолты — разумная отправная точка, но не оптимум:

- **`C`** управляет силой регуляризации. Маленький `C` — простая модель
  (риск недообучения), большой — гибкая (риск переобучения).
- **`class_weight`** важен при дисбалансе. На Pima классы 500/268; без весов
  модель смещается в сторону мажоритарного класса, что и видно по невысокому
  recall (0.52–0.59).
- **Порог классификации** по умолчанию 0.5. При дисбалансе оптимальный порог
  часто другой: можно поднять recall, пожертвовав precision.
- **Перцептрон** чувствителен к `alpha`, `eta0`, числу эпох и перемешиванию.

**Почему сравнение моделей от этого страдает.** Мы сравниваем «LR с
дефолтами» и «Perceptron с дефолтами», а не «лучшую LR» и «лучший
Perceptron». Вывод «LR лучше на breast_cancer» может измениться, если
подобрать `C` или `class_weight`.

**Как подбирать правильно.**

1. Сетка/рандом по гиперпараметрам **только на train**:
   - LR: `C ∈ {0.01, 0.1, 1, 10}`, `penalty ∈ {l1, l2}`,
     `class_weight ∈ {None, balanced}`;
   - Perceptron: `alpha ∈ {1e-4, 1e-3, 1e-2}`,
     `class_weight ∈ {None, balanced}`, `early_stopping`.
2. `GridSearchCV` / `RandomizedSearchCV` с `StratifiedKFold(5)`.
3. Выбор метрики — из задачи: `recall`, если нельзя пропускать больных;
   `precision`, если дороги ложные тревоги; `f1` или `balanced_accuracy`
   как компромисс.
4. Финальная оценка — на отдельном test, который не участвовал в подборе.
5. Для честной оценки — nested CV, иначе метрика после подбора будет
   оптимистичной.

На наших объёмах (569 и 768 строк) полный перебор небольшой сетки занимает
секунды, так что это легко добавить.

## Сводка

| Ограничение | Что искажает | Эффект | Стоимость исправления |
|---|---|---|---|
| Один hold-out split | устойчивость и сравнение моделей | разница в 2–3 объекта выглядит как вывод | низкая: `StratifiedKFold(5)` |
| Нет импутации Pima | качество на Pima | до 49% одного признака — фиктивные нули | низкая: `SimpleImputer` в Pipeline |
| Нет подбора гиперпараметров | потенциал моделей и честность сравнения | модели сравниваются «из коробки» | средняя: `GridSearchCV` + nested CV |

## Что уже сделано для честности

- Фиксированный `random_state=42` для split и обучения.
- Стратифицированный split: пропорции классов сохраняются.
- `StandardScaler` находится **внутри** `Pipeline`, поэтому при
  предсказании применяются те же преобразования, что при обучении.
- Test не участвует в обучении; метрики считаются только на нём.
- Fail-safe `0.0` для precision/recall при нулевом знаменателе.

## Вывод

Для учебного ДЗ текущая реализация корректна и достаточна: она показывает
полный цикл «данные → обучение → метрики → графики» и явно фиксирует
ограничения. Но числа из `example_metrics_run.md` — это **иллюстративный
прогон**, а не научный бенчмарк.

Если проект будет использоваться для реальных выводов, начинать надо с
кросс-валидации и импутации Pima — они дают наибольший прирост доверия к
результатам при минимальных трудозатратах.
