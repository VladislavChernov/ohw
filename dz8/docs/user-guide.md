# User Guide — лаборатория проверки LLM

Лаборатория встроена в рабочее место Dz2 отдельной страницей
**«Проверка модели»**. Она отвечает на два вопроса:

1. **Можно ли доверять модели?** Не выдумывает ли она требования, URL,
   сущности и результаты тестов; стабильно ли она работает при повторе;
   не деградировала ли она после смены модели, квантования или параметров.
2. **Цел ли пайплайн вокруг модели?** Правильно ли клиент понимает HTTP API
   Ollama, коды ошибок и параметры запросов; не сломается ли генератор
   артефактов Dz2, если модель начнёт вести себя иначе.

Лаборатория не заменяет тесты Dz2 и не оценивает «красоту» ответов. Она
измеряет **повторяемые, проверяемые свойства**: структуру, трассируемость,
стабильность и контракт API.

---

## 1. Где это находится

| Что | Где |
|---|---|
| UI | `http://localhost:8501` → sidebar **«Страница»** → **«Проверка модели»** |
| Код | `dz8/src/llm_degradation` |
| CLI | `llm-lab` (в контейнере `dz2-ui-1`: `/app/.venv/bin/python -m llm_degradation`) |
| Конфиг | `dz8/config.toml` |
| Отчёты | `dz8/output/<run_id>/` (на хосте), `/data/dz8-output/<run_id>/` (в контейнере) |
| Golden-данные | `dz8/golden/` |
| Baseline | `dz8/golden/baseline/llama3.json` |

Нового приложения, порта и постоянного контейнера нет: используется
существующий стенд `ohw-ollama` + `dz2-ui-1`.

```
dz2 UI (8501)
  └─ «Проверка модели»
       ├─ Стенд ──────────────► health: /api/version, /api/tags
       ├─ Галлюцинации ───────► probes/hallucinations.py + golden/probes
       ├─ Согласованность ────► probes/consistency.py (серия прогонов)
       ├─ API ────────────────► probes/api_contract.py (API-01…API-12)
       ├─ Канарейка ──────────► probes/canary.py (LLM vs детерминированный нормализатор)
       ├─ Деградация ─────────► degradation.py (baseline vs candidate)
       ├─ Последний прогон ───► report.py (самый свежий report.json)
       └─ Отчёты ─────────────► report.py (список и просмотр)
```

## 2. Быстрый старт

1. Поднимите стенд (Docker Desktop должен быть запущен):

   ```powershell
   cd D:\Otus\ohw\dz2
   .\scripts\up-gpu.ps1     # или .\scripts\up-cpu.ps1
   ```

   Linux/macOS (только CPU):

   ```bash
   cd ohw/dz2
   ./scripts/up-cpu.sh
   ```

2. Откройте `http://localhost:8501` и переключите страницу на
   **«Проверка модели»**.

3. Проверьте подключение: в боковой панели нажмите **«Обновить список
   моделей»**, выберите модель (по умолчанию `llama3`) и нажмите
   **«Проверить связь»**. Успех — зелёная строка `Ollama 0.33.3`.

4. Запускайте вкладки в рекомендованном порядке (раздел 4).

5. Результат каждого запуска появится на вкладке **«Последний прогон»** и
   сохранится в `dz8/output/<run_id>/`.

> Первый запрос после старта контейнера загружает модель в память. На GPU это
> может занять до ~2–3 минут; дальше ответы идут секунды. Это не зависание.

## 3. Параметры боковой панели

Эти параметры общие для всех вкладок.

| Параметр | По умолчанию | Смысл |
|---|---|---|
| Base URL | `http://ohw-ollama:11434` | адрес Ollama |
| Модель из `/api/tags` | — | выбор из списка моделей |
| Модель (ручной ввод) | `llama3` | имя модели, если списка нет |
| timeout, с | `600` | таймаут одного HTTP-запроса |
| temperature | `0.7` | температура генерации |
| Фиксировать seed | включено | использовать `seed` |
| seed | `42` | зерно генерации |
| num_ctx | `4096` | размер контекста |
| num_predict | `512` | максимум новых токенов |
| max_retries | `3` | повторы при ошибке валидатора |
| output_dir | `/data/dz8-output` | куда писать отчёты |

Полное описание каждого параметра и всех ключей отчёта — в
[глоссарии](glossary.md).

## 4. Рекомендованный порядок проверок

Порядок выбран так, чтобы дешёвые проверки отсекали проблемы до дорогих
прогонов.

| Шаг | Вкладка | Кнопка | Зачем именно здесь |
|---|---|---|---|
| 1 | [Стенд](tabs/stand.md) | **«Проверить стенд»** | Убедиться, что Ollama доступна и модель есть |
| 2 | [API](tabs/api.md) | **«Проверить API»** | Убедиться, что транспорт и коды ошибок в порядке |
| 3 | [Канарейка](tabs/canary.md) | **«Запустить»** | Проверить, что модель может аккуратно скопировать текст |
| 4 | [Галлюцинации](tabs/hallucinations.md) | **«Запустить»** | Проверить, что модель не выдумывает факты |
| 5 | [Согласованность](tabs/consistency.md) | **«Запустить»** | Проверить стабильность на серии прогонов |
| 6 | [Деградация](tabs/degradation.md) | **«Сравнить»** | Сравнить baseline и candidate на серии |

После каждого нажатия результат появляется прямо под кнопкой, а полный отчёт
— на вкладках [«Последний прогон»](tabs/last-run.md) и
[«Отчёты»](tabs/reports.md). Пошаговые инструкции «куда смотреть» есть в
описании каждой вкладки.

Если шаг 1–3 падает, запускать шаги 4–6 обычно бессмысленно: результаты
будут отражать не качество модели, а сломанный стенд или промпт.

## 5. Как читать отчёт

Каждый запуск создаёт каталог:

```
output/<YYYYMMDDTHHMMSSZ>-<id>/
  manifest.json     окружение, вход, промпт, параметры
  normalized.md     нормализованный вход
  prompt.txt        фактический промпт
  runs/             сырые прогоны (request/response/metrics)
  raw/              полные ответы модели по каждому вызову
  report.json       машиночитаемый отчёт (pydantic, extra="forbid")
  report.md         человекочитаемая версия
```

`raw/` — отдельная подпапка с полными ответами модели. Для `consistency` и
`degradation` там лежат `attempt-NN.txt` + `attempt-NN.json` на каждую
попытку (включая отклонённые валидатором), для `canary` — `request.json` и
`run-01.txt`, для `hallucinations` — `probes/<id>/run-XX/request.json` и
`response.txt`. Корневой `prompt.txt` содержит только user-промпт; system и
user целиком — в `request.json` соответствующего вызова. Подробная схема —
в [описании вкладки «Отчёты»](tabs/reports.md#подпапка-raw).

`report.md` состоит из разделов:

1. **Шапка** — `run_id`, время, вердикт, модель, digest, версия Ollama,
   параметры.
2. **Вход** — файл, кодировка, URL, список `BR-N`, хэш промпта, тип и `count`.
3. **Вердикт** — причины, если вердикт не `pass`.
4. **Прогоны** — таблица по каждому прогону: валидатор, попытки, кейсы,
   `positive`/`negative`, покрытие `BR`, задержка.
5. **Сводка** — все метрики запуска (раздел 6 и
   [глоссарий](glossary.md)).
6. **Файлы** — что лежит рядом.

Пример реального baseline (`consistency`, `llama3`):

```
Вердикт: fail
Причины:
- validator_pass_rate 0.50 < 0.90
- count_match_rate 0.50 < 1.00
- br_coverage_min 0.29 < 0.80

Сводка:
runs 10 | pass_at_1 0.0 | pass_all 0.5 | br_coverage_mean 0.4285
br_coverage_min 0.2857 | invented_br_total 0 | invented_url_total 0
identical_runs 20 | unique_artifacts 2 | self_consistency 0.6984
```

Важно: `fail` здесь — **фактическое поведение модели**, а не сбой
лаборатории. `llama3` стабильно проходит валидатор только в половине
прогонов и не покрывает все `BR` в худшем прогоне.

## 6. Вердикты

| Вердикт | Значение |
|---|---|
| `pass` | все обязательные условия выполнены |
| `warn` | обязательные условия выполнены, но есть предупреждение |
| `fail` | нарушено хотя бы одно обязательное условие |
| `regressed` | candidate хуже baseline (деградация) |
| `improved` | candidate лучше baseline |
| `unchanged` | значимых изменений нет |
| `insufficient_data` | меньше 5 прогонов в ячейке, сравнивать нельзя |

Что считается «обязательным условием», зависит от вкладки; пороги сведены в
[глоссарии](glossary.md#8-пороговые-значения).

---

## 7. Хранение и очистка

- Каждый запуск пишется в отдельный каталог `output/<run_id>/`.
- `output/` не коммитится.
- Хранятся только последние `reports.keep_runs` запусков (по умолчанию `3`).
  Старые каталоги с валидным `report.json` удаляются после записи нового
  отчёта.
- Переопределение: флаг `--keep-runs N` или env `LLM_LAB_KEEP_RUNS`.
- Baseline в `golden/baseline/` под очистку **не** попадает.
- Каталоги без `report.json` (например, прерванный прогон) автоматически не
  удаляются — их можно убрать вручную.

## 8. CLI

CLI полезен для CI и для проверки без UI. Внутри `dz2-ui-1`:

```bash
/app/.venv/bin/python -m llm_degradation health --model llama3 --json
/app/.venv/bin/python -m llm_degradation api-check --model llama3 --json
/app/.venv/bin/python -m llm_degradation canary --model llama3 --input /opt/dz8/golden/inputs/catalog.md --json
/app/.venv/bin/python -m llm_degradation hallucinations --model llama3 --runs 3 --json
/app/.venv/bin/python -m llm_degradation consistency --model llama3 --input /opt/dz8/golden/inputs/catalog.md --runs 10 --seed 42 --json
/app/.venv/bin/python -m llm_degradation degradation \
  --baseline-model llama3 --candidate-model llama3 --input /opt/dz8/golden/inputs/catalog.md \
  --runs 5 --json
/app/.venv/bin/python -m llm_degradation report --list --json
```

С хоста:

```powershell
docker compose -f D:\Otus\ohw\dz2\compose.yaml exec -T ui `
  sh -c "/app/.venv/bin/python -m llm_degradation health --model llama3 --json"
```

Коды выхода:

| Код | Значение |
|---|---|
| `0` | успех |
| `2` | ошибка конфигурации, входа или отчёта |
| `3` | Ollama недоступна или модель не найдена |
| `4` | проверка вернула `fail` / `insufficient_data` |
| `5` | деградация при `--fail-on-regression` |

Общие флаги: `--config`, `--base-url`, `--model`, `--timeout`, `--input`,
`--temperature`, `--seed`, `--num-ctx`, `--num-predict`, `--max-retries`,
`--keep-runs`, `--preset`, `--output-dir`, `--json`, `--quiet`.

## 9. Ограничения

- **Одна модель за раз.** Лаборатория не сравнивает модели автоматически,
  кроме вкладки «Деградация», где baseline и candidate задаются явно.
- **Golden-данные фиксированы.** Галлюцинации и канарейка проверяют модель
  на `golden/inputs/catalog.md` и `golden/inputs/no-cart.md`; это не
  универсальный бенчмарк.
- **Ключевые проверки — эвристики.** Запрещённые слова, маркеры отказа и
  регулярные выражения ловят типовые галлюцинации, но не понимают смысл
  ответа.
- **`num_predict=512`.** Длинные артефакты могут обрезаться; в метриках есть
  флаг `truncated`.
- **Температура и seed.** Для честных сравнений фиксируйте `seed` и
  используйте `temperature=0` там, где проверяется воспроизводимость.
- **CPU медленно.** Полный набор integration-тестов на CPU занимал десятки
  минут; на GPU (`RTX 2070 SUPER`, полный оффлоад) — около 2,5 минут.
- **Отчёты — снимок момента.** При смене модели, квантования, версии Ollama
  или параметров старый baseline перестаёт быть сопоставимым.

## 10. Типичные проблемы

| Симптом | Что проверить |
|---|---|
| `Модель недоступна` | `docker ps`, `docker exec ohw-ollama ollama list` |
| Долгий первый ответ | модель загружается в VRAM; дождитесь завершения |
| `Не удалось получить модели` | Base URL, сеть `ohw_net`, доступность Ollama |
| `Canary` падает с `parse_error` | модель не вернула Markdown; смотрите `raw` |
| `insufficient_data` в деградации | нужно ≥ 5 прогонов в каждой ячейке |
| Отчёт не появился | смотрите ошибку в UI; каталог мог не создаться |
