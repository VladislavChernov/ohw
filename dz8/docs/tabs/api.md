# Вкладка «API»

[← User Guide](../user-guide.md) · [Глоссарий](../glossary.md)

## Что это и зачем

Проверка **контракта HTTP API Ollama**, а не качества модели. Лаборатория
вызывает реальные эндпоинты и проверяет, что клиент правильно понимает
ответы, коды ошибок и параметры запросов.

Зачем:

- отличить «модель плохая» от «транспорт сломался»;
- заметить изменения в Ollama до того, как они испортят генерацию артефактов;
- убедиться, что таймауты, JSON-режим, стриминг и конкурентность работают
  так, как ожидает лаборатория.

Проверка не оценивает текст ответа: важно, что вернулся корректный HTTP-ответ
с нужными полями.

## Как запустить в UI

1. Откройте страницу **«Проверка модели»** → вкладку **«API»**.
2. Отдельных полей нет: проверьте `Base URL`, модель и `timeout` в боковой
   панели.
3. Нажмите **«Проверить API»** и дождитесь окончания 12 проверок.
4. Смотрите таблицу: `id`, `status`, `http_status`, `latency_ms`, `detail`.
   Начинайте с критичных `API-01`…`API-08` и `API-10`; `warn` у `API-09`,
   `API-11`, `API-12` вердикт не валит.
5. Полный отчёт — на вкладках **«Последний прогон»** и **«Отчёты»**.

## Входные параметры

Отдельных полей у вкладки нет. Используются:

| Параметр | Влияние |
|---|---|
| `Base URL` | адрес Ollama |
| `Модель` | модель для `chat`-запросов и `/api/show` |
| `timeout, с` | таймаут обычных запросов |

Несуществующая модель для API-06 задана константой
`llm-lab-model-does-not-exist:latest`.

## Методика проверки

Выполняются 12 проверок подряд; каждая пишет `status`, HTTP-код, задержку,
`detail` и, где нужно, сырой ответ.

| ID | Запрос | Условие успеха | Критичная |
|---|---|---|---|
| `API-01` | `GET /api/version` | `200`, непустой `version` | да |
| `API-02` | `GET /api/tags` | `200`, у каждой модели есть `name`, `model`, `digest`, `size`, `details` | да |
| `API-03` | `POST /api/show` | `200`, есть `details` и `model_info` | да |
| `API-04` | `POST /api/chat`, минимальный | `200`, непустой `message.content`, `done=true`, `eval_count > 0` | да |
| `API-05` | `POST /api/chat`, `format=json` | `200`, `message.content` парсится как JSON | да |
| `API-06` | `POST /api/chat`, неизвестная модель | `404` и непустой `error` | да |
| `API-07` | `POST /api/chat`, битый JSON | `400` (не `500` и не `200`) | да |
| `API-08` | `POST /api/chat`, `temperature`/`seed`/`num_predict` | `200`, `prompt_eval_count > 0`; `warn`, если `eval_count > 32` | да |
| `API-09` | `POST /api/chat`, `stream=true` | `200`, каждая непустая строка — валидный JSON (NDJSON) | нет |
| `API-10` | `POST /api/chat`, `timeout=0.001` | запрос **обязан** упасть по таймауту | да |
| `API-11` | `GET /api/ps` | `200` или `404` (эндпоинт опционален) | нет |
| `API-12` | 3 параллельных `chat` | все три вернули `200` | нет |

Особенности:

- `API-03` не требует `digest`: в Ollama ≥ 0.12 он приходит из `/api/tags`, а
  не из `/api/show`.
- `API-08` намеренно просит короткий ответ; предупреждение появляется только
  при `eval_count > 32`, то есть при явном игнорировании `num_predict`.
- `API-09` проверяет именно NDJSON: одна JSON-строка на чанк.
- `API-10` — единственная проверка, где ошибка транспорта является успехом:
  так подтверждается, что таймаут реально применяется.
- `API-11` и `API-12` не валят вердикт, а только предупреждают.

## Метрики

`summary` содержит один ключ `checks` — массив из 12 объектов.

| Поле | Значение |
|---|---|
| `id` | `API-01` … `API-12` |
| `name` | название проверки |
| `status` | `pass` / `warn` / `fail` |
| `http_status` | HTTP-код или `null` |
| `latency_ms` | длительность |
| `detail` | пояснение |
| `raw` | сырое тело ответа |
| `critical` | влияет ли провал на вердикт |

## Вердикт

- **fail** — провалилась хотя бы одна критичная проверка;
- **warn** — критичные прошли, но есть `warn` среди опциональных;
- **pass** — всё зелёное.

Если все проверки упали с `http_status=null` (Ollama недоступна), CLI
возвращает код `3`, а не `4`.

## CLI

```bash
/app/.venv/bin/python -m llm_degradation api-check --model llama3 --json
```

Код выхода: `0` для `pass`/`warn`, `4` для `fail`, `3` при недоступной
Ollama.

## Как читать результат

- `API-01`/`API-02` упали — стенд или сеть, а не модель.
- `API-06` вернул `200` — Ollama не отличает неизвестную модель; это
  потенциально опасно для пайплайна.
- `API-07` вернул `500` — ошибка клиента маскируется под ошибку сервера.
- `API-08` дал `warn` — модель или сервер игнорирует `num_predict`.
- `API-09`/`API-11`/`API-12` дали `warn` — вердикт `warn`, но не `fail`.

## Ограничения

- Проверяется контракт, а не качество текста.
- Набор эндпоинтов зафиксирован; новые возможности Ollama не проверяются.
- `API-10` может быть нестабилен на очень быстром локальном сервере, но
  таймаут `0.001 с` практически гарантирует срабатывание.
- `API-12` — базовая проверка конкурентности, без замеров производительности.
- Версия Ollama и её поведение могут отличаться; отчёт фиксирует
  `environment.ollama_version`.
