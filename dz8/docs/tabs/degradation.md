# Вкладка «Деградация»

[← User Guide](../user-guide.md) · [Глоссарий](../glossary.md)

## Что это и зачем

A/B-сравнение двух состояний: **baseline** и **candidate**. Обе ячейки
прогоняются на одном входе, одном промпте и одной серии, после чего
сравниваются метрики.

Зачем:

- проверить, не стала ли модель хуже после смены версии, квантования или
  параметров;
- сравнить две модели на одинаковой задаче;
- получить не только «стало хуже», но и статистическую оценку: интервалы
  Уилсона, размер эффекта и bootstrap.

Это единственная вкладка, где сравниваются **два источника**, а не один
запуск сам с собой.

## Как запустить в UI

1. Откройте страницу **«Проверка модели»** → вкладку **«Деградация»**.
2. Заполните `Вход`, `Тип артефакта`, `count` и `runs` (прогонов в каждой
   ячейке).
3. Выберите `Baseline`: **«Сохранённый отчёт»** (быстро) или
   **«Живая модель»** (честнее, дороже). Для сохранённого отчёта выберите
   файл в списке `Отчёт baseline`.
4. Укажите `Baseline-модель` (для живой модели) и `Candidate-модель`.
5. При необходимости включите `fail-on-regression`.
6. Нажмите **«Сравнить»** и дождитесь окончания прогресса.
7. Смотрите вердикт и блок сравнения: изменения метрик, интервалы Уилсона и
   bootstrap. `regressed` — candidate хуже baseline.

## Входные параметры

| Параметр UI | По умолчанию | Смысл |
|---|---|---|
| Вход | `golden/inputs/catalog.md` | документ требований |
| Тип артефакта | `testcases` | `testcases`, `qareport`, `coveragematrix` |
| count | `5` | число кейсов |
| runs | `5` | прогонов **в каждой** ячейке |
| Baseline | «Сохранённый отчёт» | отчёт или живая модель |
| Отчёт baseline | первый из списка | `golden/baseline/*.json` или `consistency`-отчёт |
| Baseline-модель | — | если выбран режим «Живая модель» |
| Candidate-модель | `llama3` | вторая модель |
| fail-on-regression | выключен | вернуть код `5` при `regressed` |

Общие параметры (temperature, seed, …) берутся из боковой панели.

### Два режима baseline

1. **Сохранённый отчёт** — берётся готовый `report.json` из
   `golden/baseline/` или из прошлых `consistency`-запусков. Быстро, но
   отчёт должен быть совместим с текущим промптом.
2. **Живая модель** — baseline-серия запускается прямо сейчас. Дороже, но
   гарантирует одинаковые условия.

Совместимость сохранённого отчёта проверяется по:

- `prompt.prompt_sha256`;
- `prompt.artifact_type`;
- `prompt.count`;
- наличию `summary`.

Если хоть что-то не совпало — ошибка, сравнение не выполняется.

## Методика проверки

1. Вход нормализуется, промпт собирается один раз.
2. Запускается baseline-ячейка:
   - из сохранённого отчёта — берутся `summary` и число прогонов;
   - живая — выполняется серия `consistency` с текущими параметрами.
3. Запускается candidate-ячейка — такая же серия `consistency`.
4. Для каждой ячейки считаются `pass_at_1`, `br_coverage_mean`,
   `invented_br_total`, `valid_json_rate`, `mean_attempts`.
5. Строится `comparison`:
   - `pass_at_1` с 95 % интервалами Уилсона и флагом `overlap`;
   - разницы остальных метрик;
   - `effect_size_h` (Cohen's h);
   - `relative_diff`;
   - `bootstrap_pass_at_1`.
6. Проверяются правила регрессии/улучшения.

Минимум для сравнения — **5 прогонов в каждой ячейке**. Иначе вердикт
`insufficient_data`.

## Метрики сравнения

| Ключ | Что означает |
|---|---|
| `pass_at_1.baseline` / `candidate` | доля успехов с первой попытки |
| `pass_at_1.diff` | `candidate − baseline` |
| `pass_at_1.ci_baseline` / `ci_candidate` | 95 % интервалы Уилсона |
| `pass_at_1.overlap` | интервалы пересекаются |
| `invented_br_total` | выдуманные требования: было / стало / разница |
| `br_coverage_mean` | покрытие `BR`: было / стало / разница |
| `valid_json_rate` | валидный JSON: было / стало / разница |
| `mean_attempts` | среднее число попыток: было / стало / разница |
| `effect_size_h` | размер эффекта Cohen's h |
| `relative_diff` | `diff / baseline_pass_at_1` |
| `bootstrap_pass_at_1` | bootstrap-интервалы среднего |

Подробные формулы — в [глоссарии](../glossary.md#7-деградация).

## Вердикт

Сначала проверяется объём данных:

- меньше 5 прогонов в baseline или candidate → **insufficient_data**.

Затем собираются признаки регрессии:

| Условие | Признак |
|---|---|
| `pass_at_1` упал на `≥ 0.20` **и** интервалы Уилсона не пересекаются | регрессия |
| `invented_br_total` вырос на `≥ 2` | регрессия |
| `br_coverage_mean` упал на `≥ 0.10` | регрессия |
| `valid_json_rate` упал на `≥ 0.20` | регрессия |
| `mean_attempts` вырос на `≥ 1.0` | регрессия |

Признаки улучшения — зеркальные.

Итог:

1. есть хотя бы одна регрессия → **regressed**;
2. иначе есть хотя бы одно улучшение → **improved**;
3. иначе → **unchanged**.

Важно: падение `pass_at_1` учитывается только при **непересекающихся**
интервалах. Небольшое падение внутри шума не считается регрессией.

## Как читать результат

- `summary` в отчёте деградации — это сводка **candidate**, а не сравнение.
  Сравнение лежит в `comparison` и в разделе `## Degradation` файла
  `report.md`.
- `overlap=true` — разница `pass_at_1` статистически не убедительна.
- `effect_size_h`: `0.2` — малый, `0.5` — средний, `0.8` — большой эффект.
- `invented_br_total` может измениться на 1 без вердикта: порог — `2`.
- `insufficient_data` — это не «плохо», а «мало данных».

## CLI

Сохранить baseline:

```bash
/app/.venv/bin/python -m llm_degradation consistency \
  --model llama3 --runs 10 --seed 42 --json
cp output/<run_id>/report.json golden/baseline/llama3.json
```

Сравнить с сохранённым отчётом:

```bash
/app/.venv/bin/python -m llm_degradation degradation \
  --baseline-report golden/baseline/llama3.json \
  --candidate-model llama3 --runs 5 --json
```

Сравнить две живые модели:

```bash
... degradation --baseline-model llama3 --candidate-model qwen2.5:7b-instruct --runs 5
```

С падением на регрессии:

```bash
... degradation --baseline-report golden/baseline/llama3.json \
  --candidate-model llama3 --runs 5 --fail-on-regression
```

Коды выхода:

| Код | Когда |
|---|---|
| `0` | `unchanged` / `improved` / `regressed` без флага |
| `4` | `insufficient_data` |
| `5` | `regressed` с `--fail-on-regression` |

## Ограничения

- Нужно минимум 5 прогонов в каждой ячейке; на CPU это дорого.
- Сравнение корректно только при одинаковом входе и промпте.
- Сохранённый baseline проверяется по `prompt_sha256`; любое изменение
  шаблона или пресетов делает его несовместимым.
- `pass_at_1` — грубая метрика; интервалы Уилсона и bootstrap помогают, но
  не заменяют большего числа прогонов.
- При сравнении одной и той же модели ожидаемо `unchanged` или шум.
- Вердикт `regressed` без `--fail-on-regression` не валит CI.
