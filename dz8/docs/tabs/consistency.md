# Вкладка «Согласованность»

[← User Guide](../user-guide.md) · [Глоссарий](../glossary.md)

## Что это и зачем

Проверка **стабильности**: один и тот же вход и промпт прогоняются несколько
раз, а результаты сравниваются между собой. Хорошая модель при фиксированном
seed должна выдавать близкие артефакты; плохая — каждый раз новый набор
тест-кейсов, требований и заголовков.

Зачем:

- понять, можно ли воспроизвести артефакт;
- увидеть, как часто валидатор Dz2 пропускает результат;
- получить baseline для вкладки [«Деградация»](degradation.md);
- оценить покрытие `BR` и трассируемость на серии, а не на одном удачном
  ответе.

## Как запустить в UI

1. Откройте страницу **«Проверка модели»** → вкладку **«Согласованность»**.
2. Выберите `Тип артефакта`, задайте `count` и `runs` (для baseline берите не
   меньше 5, лучше 10).
3. Нажмите **«Запустить»** и дождитесь окончания прогресса.
4. Смотрите вердикт и сводку: `pass_at_1`, `pass_all`, `br_coverage_mean`,
   `br_coverage_min`, `self_consistency`. Расшифровка — в разделе
   [«Как читать результат»](#как-читать-результат).
5. Этот запуск можно сохранить как baseline для вкладки
   [«Деградация»](degradation.md).

## Входные параметры

| Параметр UI | По умолчанию | Смысл |
|---|---|---|
| Вход | `golden/inputs/catalog.md` | документ требований |
| Тип артефакта | `testcases` | `testcases`, `qareport`, `coveragematrix` |
| count | `5` | сколько кейсов просить |
| runs | `10` | сколько раз повторить генерацию |

Общие параметры (temperature, seed, num_ctx, num_predict, max_retries) берутся
из боковой панели.

## Методика проверки

1. Вход нормализуется детерминированным нормализатором Dz2.
2. Один раз собирается промпт по шаблону и пресетам.
3. Выполняется `runs` одинаковых запросов с одинаковыми параметрами.
4. Каждый ответ проходит валидатор и метрики артефакта.
5. Метрики агрегируются по серии:
   - доли (`pass_at_1`, `valid_json_rate`, …);
   - средние и минимумы (`br_coverage_mean/min`);
   - попарные Jaccard-сходства;
   - число одинаковых артефактов.
6. Строится вердикт по порогам.

Ключевой момент: сравниваются **артефакты между прогонами**, а не с эталоном.
Эталон здесь не нужен — важна воспроизводимость.

## Метрики

| Ключ | Что означает |
|---|---|
| `runs` | число прогонов |
| `pass_at_1` | доля успехов с первой попытки |
| `pass_all` / `validator_pass_rate` | доля прогонов, прошедших валидатор |
| `valid_json_rate` | доля валидного JSON |
| `count_match_rate` | доля прогонов с нужным числом кейсов |
| `balance_match_rate` | доля сбалансированных прогонов (pos/neg) |
| `br_coverage_mean` / `br_coverage_min` | среднее и худшее покрытие `BR` |
| `invented_br_total` | сумма выдуманных `BR-N` |
| `invented_url_total` | сумма выдуманных URL |
| `tc_jaccard_mean` / `tc_jaccard_min` | сходство наборов `TC-*` между прогонами |
| `heading_jaccard_mean` / `heading_jaccard_min` | сходство заголовков |
| `title_jaccard_mean` | сходство токенов заголовка |
| `identical_runs` | число **пар** полностью одинаковых ответов |
| `unique_artifacts` | число уникальных ответов |
| `mean_attempts` | среднее число попыток |
| `mean_latency_ms` | средняя задержка |
| `self_consistency` | интегральная стабильность |

Полные определения и формулы — в
[глоссарии](../glossary.md#5-согласованность).

## Вердикт

Проверяются только те условия, которые применимы к типу артефакта.

| Условие | Вердикт |
|---|---|
| `validator_pass_rate < 0.90` | **fail** |
| `br_coverage_min < 0.80` | **fail** |
| `count_match_rate < 1.00` (testcases) | **fail** |
| `tc_jaccard_mean < 0.40` (testcases) | **fail** |
| `temperature == 0.0` и `identical_runs == 0` | **warn** |
| иначе | **pass** |

`heading_jaccard_mean_min = 0.70` объявлен в конфиге и попадает в
`verdict.thresholds`, но в текущей логике вердикта не участвует.

## Как читать результат

- `pass_at_1 = 0` при `pass_all > 0` означает, что модель проходит валидатор
  только после повторов — первый ответ ненадёжен.
- Большой разрыв между `br_coverage_mean` и `br_coverage_min` — результат
  нестабилен: в худшем прогоне потеряна часть требований.
- `unique_artifacts = 1` — все ответы идентичны; `unique_artifacts = runs` —
  все разные.
- `identical_runs` считает пары, поэтому может быть больше `runs`.

Пример реального baseline `llama3`:

```
runs 10, pass_at_1 0.0, pass_all 0.5,
br_coverage_mean 0.4285, br_coverage_min 0.2857,
identical_runs 20, unique_artifacts 2
```

Это значит: модель проходит валидатор в половине прогонов, но всегда не с
первой попытки; в худшем прогоне покрыто только 2 из 7 требований; при этом
ответы группируются в два устойчивых варианта.

## Baseline

Отчёт этой вкладки можно сохранить как baseline:

```bash
llm-lab consistency --model llama3 --runs 10 --seed 42 --json
```

Затем скопировать `output/<run_id>/report.json` в
`golden/baseline/llama3.json`. Этот файл использует вкладка
[«Деградация»](degradation.md).

## CLI

```bash
/app/.venv/bin/python -m llm_degradation consistency \
  --model llama3 --input /opt/dz8/golden/inputs/catalog.md \
  --artifact-type testcases --count 5 --runs 10 --json
```

Код выхода: `0` для `pass`/`warn`, `4` для `fail`.

## Ограничения

- Дорогая проверка: время растёт линейно с `runs`; на CPU 10 прогонов могут
  занять десятки минут.
- При `temperature > 0` разброс ожидаем; для проверки воспроизводимости
  ставьте `temperature=0`.
- `num_predict=512` может обрезать длинный артефакт; смотрите `truncated`.
- Сравнение идёт между ответами одной модели, а не с «правильным» ответом.
- `self_consistency` — агрегат, а не отдельный порог; вердикт по нему не
  ставится.
