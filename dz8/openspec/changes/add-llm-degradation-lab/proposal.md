# Proposal: лаборатория глюков и деградации LLM

## Почему

В ДЗ8 нужно проверить локальную LLM на галлюцинации, согласованность и
корректность API. У нас уже есть стенд Dz2: детерминированный нормализатор
требований, внешние промпты и пресеты Dz7, валидаторы артефактов, клиент
Ollama и общий контейнер `ohw-ollama`. Но в нём нет:

- детерминированных probe-ов на галлюцинации (выдуманные `BR-N`, URL,
  сущности, результаты прогонов);
- серий прогонов и метрик стабильности (один прогон при `temperature=0.7`
  ничего не доказывает);
- проверки контракта Ollama HTTP API (коды, схемы, `seed`, `num_ctx`,
  `num_predict`, `format=json`);
- сравнения baseline/candidate с доверительными интервалами;
- канарейки, которая ловит расхождение LLM-нормализации с детерминированным
  эталоном до генерации артефакта.

Добавлять это внутрь страницы генерации Dz2 нельзя: смешаются две разные
задачи — генерация артефактов и измерение модели. Но и отдельное приложение
не нужно: рабочее место уже есть, а проверки должны использовать те же
нормализатор, шаблоны, пресеты и валидаторы.

## Что делаем

- **Новый код в `dz8`**: пакет `llm_degradation`, CLI `llm-lab`, тесты,
  golden-набор, страница `ui/page.py`.
- **Страница в UI Dz2**: в sidebar рабочего места появляется переключатель
  «Генерация артефактов» / «Проверка модели». Вторая страница вызывает
  `llm_degradation.ui.page.render_page()`.
- **Тонкий адаптер в Dz2**: radio, защищённый импорт, mount `../dz8` и env в
  `compose.yaml`, тест переключателя. Существующая страница генерации не
  меняется.
- **Никаких новых контейнеров**: используем `ohw-ollama` из `infra/`,
  `ohw-python:3.13` и существующий `dz2-ui-1`. Нет порта 8502, нет
  `dz8/compose.yaml`, нет `llm-lab-ui`.
- **Нормализация как контракт входа**: каждый документ проходит
  `ai_testgen.normalizer`; в отчёт пишутся `source_sha256`, `text_sha256`,
  `prompt_sha256`, кодировка, `BR-N`, URL и настройки нормализатора.
- **Галлюцинации**: golden-набор probe-ов с детерминированными проверками
  (точное число, отсутствующая сущность/URL/цена, трассировка `BR`, отсутствие
  выдуманных `TC-NN`, запрет вердиктов без данных прогона).
- **Согласованность**: серия N прогонов одного промпта; `pass@1`, `pass@all`,
  `count_match_rate`, `br_coverage`, pairwise Jaccard `TC-id`, заголовков и
  текста; пороги и вердикт.
- **API**: контракт `/api/version`, `/api/tags`, `/api/show`, `/api/chat`,
  включая `format=json`, `stream=false`, `seed`, `num_ctx`, `num_predict`,
  ошибки 400/404, таймаут и параллельные запросы.
- **Канарейка**: LLM нормализует тот же документ; сравнение ID, порядка, URL,
  заголовка и тела с детерминированным нормализатором. Результат канарейки не
  попадает в генерацию.
- **Деградация**: baseline и candidate на одном `prompt_sha256`; Wilson CI для
  долей, bootstrap CI для средних, effect size, вердикт
  `regressed/improved/unchanged/insufficient_data`; `--fail-on-regression` →
  код 5.
- **Отчёты**: `dz8/output/<run_id>/` с `manifest.json`, `normalized.md`,
  `prompt.txt`, `runs/run-NN/{request,response,metrics}`, `report.json`,
  `report.md`; JSON валидируется pydantic, MD генерируется из JSON.
- **Тесты**: ≥ 60 unit-тестов без Ollama на `httpx.MockTransport` и
  записанных ответах; integration-тесты с маркером `integration`; UI AppTest.
  Всё запускается в существующем `dz2-ui-1` с временным venv в `/tmp`.

## Чего не делаем

- Не меняем `dz2/src`, кроме UI-адаптера и тестов.
- Не меняем `dz2/prompts`, `dz2/presets`, `dz2/normalizer.toml`.
- Не поднимаем второй Ollama и не добавляем GPU-оверлей.
- Не создаём новый контейнер/сервис/порт для Dz8.
- Не обучаем и не файнтюним модель.
- Не используем LLM-судью текста промпта для деградации.
- Не делаем автоматический `ollama pull` в тестах.
- Не проверяем реальный сайт и не ходим в бэкенд.
- Не пишем baseline-числа руками.

## Альтернативы

### Отдельное приложение на 8502

Плюс: полная изоляция, Dz2 не меняется. Минусы: второй UI и порт; на демо
нужно объяснять, куда идти; проверки всё равно используют Dz2, то есть
изоляция только визуальная. Отклонили после обсуждения: пользователь хочет
страницу в рабочем месте.

### Вкладка внутри страницы генерации

Плюс: минимум изменений в навигации. Минусы: пять вкладок генерации
смешиваются с восемью вкладками измерений; страница становится перегруженной;
пользователь просил отдельную страницу. Отклонили.

### Код проверок внутри Dz2

Плюс: не нужен mount. Минусы: нарушает требование «новая домашка в dz8»;
Dz2 начинает зависеть от тестовой инфраструктуры; сложнее удалить/оценить
отдельно. Отклонили.

### Свой Ollama в compose Dz8

Плюс: изоляция. Минусы: дублирует `ohw-ollama`, занимает порт 11434, ломает
требование «не строить новый стенд». Отклонили.

## Влияние

- Новые файлы — в `dz8/`; в `dz2/` — только UI-адаптер, compose mounts,
  тесты и README.
- Новый порт не появляется; UI остаётся на 8501.
- Новые отчёты — в `dz8/output/` (не коммитятся, кроме baseline).
- `llama3` занимает место в `ohw-ollama` (~4.7 ГБ).
- Время integration-тестов на CPU — десятки минут; поэтому маркер.
- Если `dz8` не смонтирован, UI Dz2 работает, страница показывает подсказку.

## Проверка

- `pytest -m "not integration"` — ≥ 60 passed без Ollama.
- `pytest -m integration` — зелёный на живом `llama3`.
- `docker compose exec ui python -m llm_degradation health --model llama3 --json`
  → 0.
- `... api-check --model llama3 --json` → 0.
- `... hallucinations --model llama3 --runs 3` → отчёт.
- `... consistency --model llama3 --runs 10 --seed 42` → отчёт.
- `... canary --model llama3` → отчёт.
- `... degradation --baseline-model llama3 --candidate-model llama3 --runs 5`
  → отчёт с CI.
- UI 8501: страница «Проверка модели», восемь вкладок, health, запуск проверки,
  прогресс и скачивание отчёта.
- UI 8501: «Генерация артефактов» работает как раньше.
