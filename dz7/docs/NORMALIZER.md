# Нормализация требований

Нормализатор — входной шаг рабочего места Dz2. Он приводит произвольный
документ требований к каноническому виду с заголовком, URL и явными
идентификаторами `BR-N`, не обращаясь к модели.

Реализация: [`dz2/src/ai_testgen/normalizer.py`](../../dz2/src/ai_testgen/normalizer.py).
Спека: [`dz2/openspec/changes/add-requirement-normalizer/`](../../dz2/openspec/changes/add-requirement-normalizer/).

## Зачем

Генератор промптов опирается на `BR-N`:

- правило трассировки в `prompt.py` включается только при наличии `BR-N`;
- тест-кейс обязан заполнить `requirement`, а матрица покрытия — ссылаться на
  реальные требования;
- чек-лист, тест-план и QA-отчёт ссылаются на номера требований.

Если во входном тексте нет `BR-N`, всё это молча вырождается: кейсы остаются
без ссылок, матрица — без строк требований. Нормализатор закрывает разрыв между
«текстом, который есть» и «форматом, который ждёт генератор».

Дополнительно он снимает проблему кодировок: выгрузки бывают в cp1251 и cp866,
а `load_docs` без нормализации читает только UTF-8.

## Канонический формат

```markdown
# <заголовок>

**URL:** https://example.com/path

<вступление: всё, что было до первого требования>

## Requirements

### BR-1
<текст требования>

### BR-2
<текст требования>
```

- Заголовок — первый `#`, иначе короткая первая строка, иначе `Требования`.
- URL — `--url`/поле в UI, иначе первая ссылка в тексте. Если ссылки нет,
  строка `**URL:**` не пишется, а в предупреждениях появляется запись.
- Вступление сохраняется: цель и контекст полезны модели.
- Раздел называется `## Requirements`, потому что на него ссылаются шаблоны
  Dz7 («from the Requirements section») и правило `BR-N`.
- Повторная нормализация уже канонического текста ничего не меняет.

## Определение кодировки

Порядок:

1. BOM: UTF-32, UTF-16, UTF-8.
2. Строгий UTF-8.
3. cp1251 и cp866 — побеждает вариант с большим числом русских букв и меньшим
   числом мусорных символов; при равенстве выбирается cp1251.

Эвристика нужна из-за пары cp1251/cp866: байты `84 AE AA E3 AC A5 AD E2 A0 E6
A8 EF` в cp1251 дают `„®Єг¬Ґ­в жЁп`, а в cp866 — `документация`.

Ложное срабатывание возможно на очень коротком неоднозначном тексте; в этом
случае в предпросмотре видно результат, а кодировка показана явно.

## Порядок извлечения требований

Стратегии пробуются по порядку; используется первая, давшая хотя бы одно
требование. Смешивать источники нельзя: документ с таблицей-сводкой и
подробными разделами `BR-N` должен читаться по разделам, а не задваиваться.

| Приоритет | Что распознаётся | Пример |
|---|---|---|
| 1 | заголовки `BR-N` | `## BR-1 Вход по email` |
| 2 | Markdown-таблица с колонкой ID | `\| ID \| Описание \|` |
| 3 | список под разделом «Требования»/«Requirements» | `- вход по email` |
| 4 | строки, начинающиеся с `BR-N` | `- BR-1: вход` |
| 5 | абзацы (fallback) | обычный текст |

Fallback всегда сопровождается предупреждением: структура не распознана,
результат нужно проверить.

### Идентификаторы

- Существующие `BR-N` сохраняются: на них уже могут ссылаться артефакты.
- Требованиям без ID выдаются следующие свободные номера в порядке появления.
- Дубли ID отбрасываются (остаётся первое вхождение).
- Требование с пустым текстом отбрасывается.

Оба последних случая попадают в предупреждения.

## CLI

```bash
# только записать нормализованные файлы; модель и -n не нужны
uv run ai-testgen --normalize-only --input-dir docs --output-dir output

# нормализовать в памяти перед генерацией
uv run ai-testgen -n 10 --normalize
```

| Флаг | Поведение |
|---|---|
| `--normalize` | декодировать и нормализовать каждый входной файл в памяти; в промпт идёт канонический текст |
| `--normalize-only` | только записать нормализованные файлы (`<output-dir>/normalized/<stem>.md`) и выйти; `-n` не требуется |
| `--normalized-dir DIR` | другой каталог для `--normalize-only` |

`--normalize` не пишет файлы в `output/`: выходной каталог принадлежит
артефактам прогона. Для аудита «что именно ушло в модель» используйте
`--normalize-only`.

В консоль печатаются определённая кодировка, число требований, стратегия и
предупреждения:

```
normalized: output/normalized/doc.md (cp1251, 7 requirements, strategy: table)
```

## Рабочее место

На вкладке «Требования»:

1. файл загружается и декодируется с определением кодировки;
2. кнопка «Нормализовать» строит канонический текст;
3. показываются кодировка, число требований, стратегия и предупреждения;
4. вкладки «Исходный»/«Нормализованный» дают предпросмотр;
5. переключатель «Использовать нормализованный текст в промптах» решает, какой
   текст уйдёт в генератор; результат сверяется с текущим текстом по sha256,
   поэтому правка после нормализации помечает его устаревшим.

Если в тексте нет ни одного `BR-N`, интерфейс предупреждает о потере
трассировки — это основной сценарий, ради которого нужна кнопка.

## Детерминизм

- Никаких обращений к LLM, сети, времени и случайности.
- Одинаковые байты и аргументы дают одинаковый результат.
- Формулировки требований не переписываются: меняются только раскладка,
  пробелы, переводы строк и Markdown-структура (вложенный заголовок внутри
  требования становится жирной строкой, чтобы не ломать границы разделов).

## Ограничения

- Нормализатор не решает, является ли абзац требованием: в fallback он лишь
  предлагает разбиение и предупреждает.
- Очень короткие неоднозначные тексты могут дать неверную кодировку; проверьте
  предпросмотр.
- Нумерация не «уплотняется»: если в источнике были `BR-3` и `BR-7`, они
  сохранятся, а новым требованиям достанутся свободные номера.
