# Рабочее место: от требований до артефакта

Документ описывает Streamlit-интерфейс, который связывает ДЗ7 (промпты) и
ДЗ2 (стенд с Ollama) в один сценарий: выбрать требования, собрать промпт из
шаблона и пресетов, сгенерировать артефакт, доработать его диалогом и
оценить по рубрике.

## Зачем интерфейс

CLI рассчитан на батч: «все файлы из `docs/` → все артефакты в `output/`».
Для демонстрации и отладки промптов нужно другое:

- видеть **готовый текст промпта** до отправки в модель и править его;
- переключать тип артефакта и пресеты, не переписывая front-matter;
- сравнивать версии одного артефакта, а не файлы в каталоге;
- фиксировать оценку промпта рядом с прогоном.

Интерфейс не дублирует логику: он вызывает `ai_testgen.service.generate_artifact`
— то же ядро, что и CLI (сборка промпта из шаблона, вызов Ollama, валидация,
retry с замечаниями, рендер markdown).

## Запуск

```bash
cd dz2
uv sync --dev            # streamlit входит в dev-группу
uv run ai-testgen-ui     # http://localhost:8501
```

Streamlit — опциональная зависимость `ui`:

```bash
uv sync --extra ui       # без dev-группы
```

В Docker рабочее место живёт в том же образе, что и CLI (`ohw/dz2:local`,
extra `ui` добавляет только Streamlit), и поднимается вместе с общим ollama:

```powershell
cd dz2
.\scripts\up-gpu.ps1          # Windows, GPU; up-cpu.ps1 — CPU
./scripts/up-gpu.sh           # Linux / macOS
# http://localhost:8501
```

Скрипты используют общий базовый образ `ohw-python:3.13` и компоненты из
`../infra`; отдельный образ под UI не собирается. Контейнер получает `./docs`
(только чтение), `./input`, `./output` (запись: артефакты и `output/quality`),
`./prompts` и `./presets`; адрес Ollama — `OLLAMA_BASE_URL`
(`http://ohw-ollama:11434` в общей сети).

Открывается `ai-testgen-ui`. В боковой панели — подключение к модели, которое
можно настроить двумя способами:

- адрес Ollama: готовые варианты (`localhost`, `ohw-ollama` в общей
  Docker-сети, `host.docker.internal` для Docker Desktop) или «Свой адрес»;
- модель: кнопка «Загрузить модели» (`GET /api/tags`) заполняет список
  скачанных, а «Другая модель» оставляет поле для ручного ввода.

Там же, в блоке «Параметры генерации», — температура и таймаут запроса (для
CPU — 600–1200 с). Значения по умолчанию берутся из `OLLAMA_BASE_URL` /
`OLLAMA_MODEL`, затем из `ai-testgen.toml` — так же, как в CLI.

## Вкладки

### 1. Требования

- Файлы загружаются через `st.file_uploader` (`.md`/`.txt`, можно несколько) —
  каталог указывать не нужно, как в `QA_RAG_Studio`.
- Если файлов нет, вкладка показывает подсказку и не роняет приложение;
  остальные вкладки подсказывают, что делать.
- Загруженный файл выбирается в списке; текст можно править прямо в
  интерфейсе: правка живёт в текущей сессии и не пишется обратно в файл,
  а имя файла используется в именах артефактов.
- Файл не в UTF-8 показывается ошибкой, а не падением.
- URL подставляется из текста (`https://…`); поле можно переопределить.
- Метрики: количество уникальных `BR-N`, найденный URL, длина текста.

### 2. Промпт

- Тип артефакта: тест-кейсы, чек-лист, тест-план, QA-отчёт, матрица покрытия.
- Число тест-кейсов (1–50) — для markdown-типов игнорируется, как и в CLI.
- Пресеты: показываются только те, чьи `types` включают выбранный тип.
  Выбор пресета добавляет блок «Additional instructions» в `{extra}`.
- Промпт отображается целиком и редактируется; кнопка «Собрать промпт заново»
  возвращает версию из шаблона. Правка действует на текущий запуск, а не на
  файл шаблона.
- «Скачать промпт» сохраняет `.txt` — его можно передать в Dz2 через
  `--prompt-dir`.

### 3. Результат

- «Сгенерировать» отправляет **отредактированный** промпт в Ollama.
- Нарушения формата показываются как предупреждения: модель исправлялась
  после конкретных замечаний, номер попытки виден.
- Готовый артефакт показывается тремя способами: отрендеренный markdown,
  исходный markdown, отправленный промпт.
- «Скачать .md» и «Сохранить в output» (`<stem>.<type>.md`).

### 4. Чат с LLM

Чат — совещательный: он не меняет артефакт сам по себе.

1. Вопрос отправляется вместе с требованиями, текущим артефактом и исходным
   промптом.
2. Ответ показывается в переписке и сохраняется как «ожидающая правка».
3. Кнопка «Применить как новую версию» прогоняет ответ через ту же валидацию,
   что и генерацию. Только после этого артефакт заменяется; при нарушении
   формата показываются конкретные замечания, а текущая версия остаётся.

Так исключается типичная проблема чат-интерфейсов: необработанный ответ
модели молча становится «документом».

### 5. Оценка

Оценку ставит LLM, а не человек: кнопка «Оценить через LLM» отправляет
**текст промпта** (не артефакт) отдельными запросами с `temperature=0.0` —
по одному на каждый критерий, со своей рубрикой. Судья возвращает балл 1–5 и
комментарий с цитатой из промпта; UI показывает их и сразу пишет JSON:

```json
{
  "artifact": "testcases",
  "run_id": "20261031T091703123456Z",
  "source": "llm",
  "model": "qwen2.5:7b-instruct",
  "presets": ["boundary-values"],
  "count": 10,
  "judge_version": 4,
  "judge_temperature": 0.0,
  "prompt_sha256": "…",
  "prompt_chars": 2450,
  "generated_artifact": {
    "path": "requirements.testcases.md",
    "sha256": "…",
    "bytes": 5120,
    "modified_at": "2026-10-31T09:17:03+00:00"
  },
  "scores": {
    "readability": 5,
    "context": 5,
    "goal": 4,
    "coverage": 5
  },
  "comments": {
    "readability": "«Generate exactly 10 test cases» — структура ясная",
    "context": "URL, требования и формат заданы",
    "goal": "формат JSON задан, но разделы не перечислены",
    "coverage": "есть позитивные, негативные и граничные сценарии"
  },
  "summary": "Сильный контекст; покрытие полное, формат можно уточнить.",
  "note": "",
  "average": 4.75,
  "created_at": "2026-10-31T09:17:03+00:00"
}
```

Файл — `output/quality/<type>[-<preset>]-<run-id>.json`, где `run_id` —
UTC-метка прогона; поэтому две оценки одного типа больше не затирают друг
друга. `generated_artifact` ссылается на артефакт, который оценивался:
относительный путь внутри `output/`, sha256, размер и время изменения.
`prompt_sha256` фиксирует, что оценивался именно текущий промпт,
`judge_version` — какой версией рубрики, а `source` отличает оценку модели от
ручной.
Ниже кнопки остаются слайдеры: если человек не согласен с судьёй, он может
выставить баллы сам — файл перезапишется с `"source": "human"`. Из этих файлов
собирается таблица в [`prompt-quality.md`](prompt-quality.md); оценки не
выдумываются заранее.

Почему критерии оцениваются по одному вызову: первая версия просила все четыре
балла одним JSON-ответом и давала пример заполнения. Локальная 7B-модель
возвращала ровно эти примерные числа на всех десяти промптах — то есть не
оценивала, а копировала образец. Отдельный вызов на критерий, рубрика без
числовых примеров и поле `comment` перед `score` убирают и копирование, и
«усреднение» всех критериев в одну оценку.

Тот же судья доступен из CLI: `--evaluate` собирает промпт и пишет JSON, не
запуская генерацию (см. `dz2/README.md`).

## Что проверено тестами

`dz2/tests/test_ui_app.py` (Streamlit `AppTest`):

- приложение рендерится, требования загружаются файлами и заполняют промпт;
- загруженные файлы можно переключать; не-UTF-8 показывается ошибкой;
- без загрузки вкладки подсказывают, что делать, и не падают;
- пресет адреса подставляет URL Ollama, список моделей загружается и
  выбирается, ручной ввод модели тоже работает;
- смена типа пересобирает промпт;
- выбранный пресет добавляет инструкции в промпт;
- генерация с подменённым клиентом даёт валидный артефакт;
- прогон всех пяти типов: каждый сохраняется в `output/`, а матрица получает
  TC-id из только что сгенерированных кейсов;
- оценка LLM сохраняется в `output/quality/<type>[-<preset>]-<run-id>.json`
  (`source=llm`), ручная — с `source=human`.

Тесты вызывают `OllamaClient.chat_messages` через monkeypatch, поэтому
живой сервис для них не нужен.

## Границы

- Интерфейс не пишет в `docs/`: правки требований живут только в сессии.
- Один артефакт на сессию: версии складываются в список, но отображается
  последняя применённая.
- Матрица покрытия берёт номера кейсов только из набора `testcases` этого же
  файла. Пока кейсы не сгенерированы, промпт честно говорит, что их нет, и
  требует `—`/`Not Covered` вместо придуманных `TC-NN`.
- Чат не хранит историю между перезапусками (session state Streamlit).
- Одновременная работа нескольких пользователей не поддерживается — это
  локальный инструмент, а не сервис.
