# Журнал обмена с LLM — что это, где включается и зачем

**Статус:** реализовано 2026-09-30. Отдельный документ, потому что режим нельзя объяснить
одной строкой в таблице конфигурации: у него четыре уровня, и выбор уровня — это решение о
том, попадает ли текст документа в лог.

## Зачем он нужен

Пользовательский интерфейс показывает ответ модели в потоке, и из этого видно, что ответ
неполный — обычное дело, а не редкий сбой. Из ingest обмена видно не было ничего: при обрыве
по длине текст, на котором JSON не закрылся, исчезал вместе с исключением. Вопрос «что именно
модель пишет в ответ» требовал нового прогона каждый раз, а прогоны на стенде дорогие.

Журнал решает именно это и ещё одно: он даёт **расход токенов по факту**. До него расход не
снимался вовсе, поэтому вопрос «кто жёт токены — промпт или ответ» не имел ответа.

## Уровни

Переменная `LLM_EXCHANGE_LOG`, четыре значения. Дефолт — `off`, и это не осторожность, а
следствие того, что полный обмен — это потенциально весь документ в логах.

| Уровень | Что пишется | Текст документа | Для чего |
|---|---|---|---|
| `off` (дефолт) | ничего | нет | обычная работа |
| `meta` | модель, стадия, поток, расход токенов, причина завершения, длины, ошибка | нет | «сколько стоило и чем кончилось» |
| `response` | плюс **текст ответа** | нет | «что модель выдаёт» без раздувания журнала |
| `full` | плюс **промпт и системная инструкция** | **да** | разбор «что модель получила и что она сделала» |

Неизвестное значение даёт `off`, а не «писать всё»: опечатка в настройке не должна
превращаться в полный слив текстов в лог.

### Почему «ответ без промпта» — это отдельный уровень

В извлечении текст чанка лежит **внутри промпта**. Поэтому «ответ без промпта» — это ровно
«запись без текста документа», и отдельная настройка «исключить текст чанка» не нужна:
достаточно не писать промпт. Дублировать текст документа отдельным полем «чанк» нельзя по
двум причинам: файл раздувается вдвое, и появляется второй источник правды о документе,
который со временем разойдётся с первым.

**Что попадает в запись вместо текста чанка:** идентификаторы. В ingest это `source_url` и
`chunk_id` (`labels`), плюс `stage=extract`. По ним записи соединяются с документом, и без
них следующая обработка получает строки, которые нечем сгруппировать. Отдельно отмечено:
решение о том, нужны ли в логе сами чанки, принимается при проектировании ingest — сейчас
их там нет.

## Настройки

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `LLM_EXCHANGE_LOG` | `off` | уровень: `off` / `meta` / `response` / `full` |
| `LLM_EXCHANGE_LOG_FILE` | пусто | путь к JSONL-файлу; пусто — писать в stdout |
| `LLM_EXCHANGE_LOG_MAX_CHARS` | `8000` | усечение текста в записи; `0` — не резать |

В stdout пишется одна JSON-строка на вызов через `logging` (`graphrag_proto.llm.exchange`),
то есть в тот же конвейер, что и остальные логи (`docs/06` §2). Файл — случай «хочу посмотреть
глазами весь обмен по конкретному прогону»: такой объём в индекс класть не нужно.

## Формат записи

Одна строка JSON на вызов, поля стабильные и аддитивные:

```json
{
  "ts": "2026-09-30T12:00:00+00:00",
  "model": "qwen2.5-3b-instruct-q4_k_m",
  "stage": "extract",
  "stream": false,
  "finish_reason": "length",
  "usage": {"prompt_tokens": 812, "completion_tokens": 4096, "total_tokens": 4908},
  "prompt_chars": 3120,
  "response_chars": 4096,
  "error": "LLMResponseError",
  "duration_ms": 41230,
  "labels": {"source_url": "s://a.md", "chunk_id": "chk:1"}
}
```

Правила, которые держат записи пригодными для последующей обработки:

- **`truncated` обязателен и честен.** Если текст усечён, рядом лежит `prompt_chars` /
  `response_chars` — полная длина. Иначе следующая обработка примет обрезку за полный ответ
  и посчитает выводы по неполным данным. На уровне `response` ключа `prompt` нет, поэтому и
  признака усечения промпта нет: ключ не выдумывается.
- **Сбой пишется до повторного выброса.** Запись с `error` появляется даже тогда, когда вызов
  упал, и содержит сырой ответ (`response`) — именно это и было недоступно раньше.
- **Ошибка записи журнала не ломает разбор.** Если файл недоступен, пишется предупреждение в
  обычный лог и работа продолжается: включённая диагностика не должна ронять джобы, ради
  которых включена.

## Как пользоваться

**Посмотреть, во что обошёлся разбор** (без содержимого):

```yaml
environment:
  LLM_EXCHANGE_LOG: "meta"
```

**Посмотреть, что модель выдаёт** (текст документа не попадает):

```yaml
environment:
  LLM_EXCHANGE_LOG: "response"
  LLM_EXCHANGE_LOG_FILE: "/var/lib/graphrag/llm-exchange.jsonl"
```

**Разобрать конкретный прогон целиком** (осознанно, текст документа уходит в лог):

```yaml
environment:
  LLM_EXCHANGE_LOG: "full"
  LLM_EXCHANGE_LOG_FILE: "/var/lib/graphrag/llm-exchange.jsonl"
  LLM_EXCHANGE_LOG_MAX_CHARS: "0"
```

Включается на том сервисе, который зовёт модель: `ingestion-api` — для извлечения,
`query-service` — для генерации ответа. В журнале это различается полем `stage`.

## Чего журнал не делает

- **Не заменяет паспорт извлечения.** Паспорт — это данные (модель, температура, бюджет,
  расход токенов, отпечаток инструкции), и он лежит в БД. Журнал — это журнал: строчный, append-only и включаемый. Данные для отчётности берутся из паспорта, глазами смотреть —
  в журнал.
- **Не собирает метрики.** Регулярный сбор `usage` в Prometheus — отдельная работа (этап B
  в `docs/06` §2). Журнал включают на время прогона, а не постоянно.
- **Не пишет чанки.** Идентификаторы — да, текст — нет.
