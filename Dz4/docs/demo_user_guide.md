# Демо GraphRAG: руководство пользователя

Браузерное демо графовой RAG-платформы: за < 10 минут загрузить документ
(txt/md), задать вопрос на русском и получить ответ со ссылками на источники —
без написания кода и знания REST-контрактов.

Уровень: пользователь/оценщик. Для эксплуатации (перезапуск, отладка, e2e-прогон)
есть отдельный [runbook](./demo_runbook.md).

---

## 1. Что это

Демо-контур вех M0–M2 прототипа платформы, собранный в Docker Compose:

| Слой | Что делает |
|------|-----------|
| **UI (Streamlit, `:8503`)** | Вкладки «Документы» и «Запросы»: всё управление в браузере |
| **Config Service** (`:8001`) | Профили доменов (it, library, film, финансы…), словари |
| **Ingestion API** (`:8002`) | Пайплайн загрузки документа 9 этапов → реальный COMMIT в граф |
| **Graph** (Neo4j, `:7474`) | Граф знаний: документы → чанки → эмбеддинги |
| **Query API** (`:8000`) | Асинхронный контур: очередь задач → воркер → SSE-стрим ответа |
| **LLM** (llama.cpp, `:8080`) | Локальная генерация ответа (OpenAI-совместимый `/v1`), ничего в интернет не уходит |

Честные границы текущей вехи: эмбеддинги — детерминированные (тестовые векторы),
ранжирование top-k (реранкер появится в M3). LLM — реальный локальный
Qwen2.5-Coder-7B через llama.cpp.

---

## 2. Что нужно

| Компонент | Требование |
|-----------|-----------|
| Docker | Desktop (Windows 10/11, WSL2) или Engine + Compose на Linux, Engine ≥ 24, Compose ≥ 2.20 |
| Память | **≥ 16 ГБ ОЗУ** (Neo4j ограничен 1.5 ГБ JVM; суммарно стек ~6–8 ГБ) |
| Диск | ~4–6 ГБ под Docker-образы + место под модель (~5 ГБ) |
| GPU | NVIDIA (CUDA) — рекомендуется, генерация в разы быстрее; строго не обязателен для запуска |
| git | Для получения кода |

**Модель для генерации (GGUF, ~4–5 ГБ)** — единственный внешний артефакт.
Подойдёт любая сборка `Qwen2.5-Coder-7B-Instruct-abliterated-GGUF` `Q4_K_M`
(например, уже загруженная LM Studio). По умолчанию демо ищет её в
`D:/progs/AI Models/lmstudio-community/Qwen2.5-Coder-7B-Instruct-abliterated-GGUF`.

## 3. Скачивание

1. **Код.** Склонируйте репозиторий (внутренний/учебный — используйте свой доступ),
   проект — папка `dz4` монорепо:

   ```bash
   git clone <адрес-репозитория>
   cd ohw/Dz4/prototype     # дальше все команды отсюда
   ```

   Если код уже есть — обновите: `git pull`.

2. **Модель.** Загрузите GGUF (см. §2). Если файл лежит в другом каталоге —
   укажите его при запуске переменной окружения (см. §4, опция модели).

3. Docker-образы демо собираются автоматически при первом старте (локальная
   сборка, ~5–15 минут).

## 4. Запуск

```bash
docker compose --profile config --profile graph --profile ingestion --profile llm up -d --wait
```

Проверка состояния:

```bash
docker compose ps          # ожидаемо: Up ... (healthy), ohw-llm — с прогревом до ~2 минут
```

Откройте **http://localhost:8503**. Ключ API по умолчанию — `changeme` (одноимённая
переменная `GRAPH_AUTH_API_KEY` при старте стека); адреса и ключ редактируются в
sidebar UI.

**Модель в другом месте** — переопределите путь/файл:

```powershell
$env:LLM_GGUF_HOST_DIR = "X:/path/to/models"; $env:LLM_GGUF_FILE = "modelfile.gguf"
```

### Режим без LLM (заглушка FakeLLM)

**Зачем он нужен.** Воркер умеет выдавать полный ответ без всякой модели и GPU:
адаптер `FakeLLM` детерминированно стримит фиксированный текст
«Ответ прототипа: детерминированный фейк без LLM.» и возвращает `done` со
`sources`, не обращаясь к `llm:8080`. Весь остальной контур при этом настоящий:
загрузка → 9 этапов пайплайна → COMMIT в Neo4j → retrieval → SSE-стрим в UI.
Это нужно, когда:

- оценивается **поток и UX**, а не качество ответа (демо заказчику с одного лаптопа — не установка GGUF);
- на машине **нет GPU или диска** под модель (~5 ГБ) — например, бюджетный ноутбук или CI-smoke;
- нужно **воспроизводимое** демо: ответ и timings всегда одинаковые, не зависят от настроения модели.

Отличие от запуска «просто без контейнера `llm`» (обычный стек из §4): там
генерация падает в событие `error`, а здесь задача доходит до `done` с текстом и
источниками. Эмбеддинги в обоих случаях детерминированные, реранкер `noop` —
заменяется только последний шаг (шаблонный текст вместо генерации).

**Как включить.** В `prototype/infra/compose.yaml` у сервисов `query-api`
(~строка 246) и `query-worker` (~строка 288) заменить:

```yaml
      LLM_ADAPTER: openai   -->   LLM_ADAPTER: fake
```

Затем поднять стек:

```bash
docker compose --profile config --profile graph --profile ingestion --profile llm up -d
```

Замечания:
- `up -d` без `--wait`: контейнер `llm` может не стартовать (нет модели/GPU) —
  это ожидаемо и не блокирует ничего: при `LLM_ADAPTER=fake` воркер его не вызывает;
- демо-документы и весь сценарий в браузере (раздел §5) работают без изменений,
  просто ответ всегда шаблонный;
- вернуть настоящий LLM — заменить `fake` на `openai` и поднять стек с готовой моделью.

Готовые демо-документы уже лежат в репозитории: `prototype/infra/samples/`
(`big_o.md`, `b_tree.txt`, `graph_traversal.md`, `war_and_peace_ru.md`) — можно
загружать их без подготовки своих.

## 5. Сценарий в браузере

**Шаг 1 — загрузить документ.** Вкладка «Документы» → выбрать домен → выбрать файл
txt/md (PDF не входит в демо: JSON-контракт Ingestion не несёт бинарного контента)
→ «Загрузить». UI показывает стадии журнала загрузки до терминального статуса
`succeeded`.

**Шаг 2 — задать вопрос.** Вкладка «Запросы» → текст вопроса → «Отправить запрос».
Пойдёт живой стрим: `status (processing) → token* (токены генерации) → done`.
Итог: **текст ответа**, таблица **sources** (`source_url`, `relevance`),
время генерации `generation_time_s`.

Пример вопроса к `war_and_peace_ru.md` (домен literature): *«За что НОСТРА
отвечает по дебиторской задолженности?»* — а к `big_o.md` (домен it): *«Что такое
O(log n)?»*.

**Шаг 3 — управление.** Во вкладке «Документы» можно **удалить документ
(soft-delete)** — он снимается с поиска: следующий запрос вернёт тот же ответ без
него в `sources`. Во вкладке «Запросы» есть **отмена задачи** в процессе генерации.

## 6. Как это работает (внутри)

```
Браузер (Streamlit :8503)
  ├── POST /api/v1/ingestion/documents  → Ingestion API :8002
  │      → пайплайн 9 этапов (нормализация → чанкинг → эмбеддинги → COMMIT в Neo4j)
  │      → job_id; UI поллит журнал стадий до succeeded/failed
  └── POST /query                        → Query API :8000
         → задача в очередь (valkey :6379) → воркер
         → retrieval:  top-k по эмбеддингам → контекст
         → LLM: llama.cpp :8080 (/v1/chat/completions) стримит токены
         → SSE-стрим  GET /query/tasks/{task_id}/stream
         → конверт {type, task_id, ts, payload}:  status → token* → done{text, sources, generation_time_s}
```

Поток генерации ответа, стадии и отмену хорошо видно прямо в UI — каждая задача
отражается в истории сессии с текущим статусом.

Портфолио:

| Сервис | Порт |
|--------|------|
| Demo UI | 8503 |
| Query API | 8000 |
| Config Service | 8001 |
| Ingestion API | 8002 |
| Glossary Service | 8003 |
| Neo4j Browser | 7474 |
| llama.cpp (LLM) | 8080 |

## 7. Устранение неполадок

| Проблема | Причина/решение |
|----------|----------------|
| UI не открывается (`:8503`) | Стек не поднят или `demo-ui` ещё прогружается: `docker compose ps`, дождаться `healthy` |
| Запрос завершается `error` | Нет доступа к LLM: проверьте `docker logs ohw-llm`, путь к GGUF, наличие GPU-билда |
| Контейнер `llm` падает/не стартует | Неверный `LLM_GGUF_HOST_DIR` или `LLM_GGUF_FILE` — переопределите env при старте |
| Ответ не возвращает добавленный документ | Детерминированные top-k эмбеддинги: возможен кэш/мусор в графе. Полный сброс — `docker compose down -v` + up |
| Нехватка памяти / OOM | Закройте тяжёлые приложения; Neo4j зажат в 1.5 ГБ JVM |
| Автоматический e2e-прогон | `bash infra/scripts/run_demo_e2e.sh` (сбрасывает volumes — предусловие детерминизма; детали в runbook) |
