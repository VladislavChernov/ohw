# Документация: Эксплуатационные требования

> **Версия:** v6 (итерация поверх базы v5)
> **Последнее обновление:** 2026-09-05
>
> Сводит требования, отложенные на продакшен экспертами (`docs/expert_reviews.md`,
> «Не критично для прототипа»), и операционные задачи жизненного цикла платформы.
> Регламенты текущей фазы — в `docs/06_operations_and_risks.md`.

## 1. Резервное копирование и восстановление

| Что | Как (продакшен) | Частота (рекомендация) |
|-----|-----------------|------------------------|
| Граф + векторные индексы | Единый дамп Neo4j (или snapshots выбранной СУБД) | Ежедневно |
| Document Registry + Config (DOMAIN_PROFILE, адаптеры) | Backup конфиг-хранилища (SQLite/Postgres) + git-папка профилей | Ежедневно |
| Веса моделей (LLM/эмбеддинги) | Не копировать в backup (перекачиваются); проверить наличие точного состава в volumes | При обновлении |

- Восстановление (RPO/RTO) фиксируется при вводе в эксплуатацию; целевые: RPO ≤ 24 ч,
  RTO ≤ 4 ч для прототипных сред.
- Точки восстановления тестируются: минимум 1 контрольный restore в квартал.

## 2. Retention-политика для старых версий графа

- Superseded версии Document Registry (ADR-014) и чанки устаревших версий удаляются по правилу:
  «старее N версий или старше T дней» — параметры `N`, `T` настраиваются в Config Service
  (namespace, добавляется при реализации).
- Сущности без активных источников (все `source_ids` = deleted/superseded): фоновый
  cleanup-job пересчитывает их статус; политика:
  - Сущность остаётся в графе, если подключена к активной сущности (не изолированный узел).
  - Изолированные сущности без активных источников удаляются.
- Удаление — не в hot-path (ADR-014), выполняется фоном в окно простоя.

## 3. Reconciliation с внешними системами

- Целевые интеграции: TMS, GitLab, CI/CD (акторы `CI/CD / CRON` — `docs/00` §1).
- Сверка по подписи документа (content hash / `doc_id`): при расхождении — переиндексация
  изменённого источника (ADR-014) и отчёт о расхождениях.
- Формат отчёта: документ/список `{source_url, expected_version, actual_version, action}`.
- Асинхронный, выполняется по расписанию, не блокирует чтение.

## 4. Мониторинг, алертинг и аудит

- Метрики Prometheus: перечень — `docs/06 §2` (все с лейблом {domain}).
- Алертинг-правила:
  - GPU VRAM/температура через DCGM Exporter — порог безопасного уровня;
  - объём очереди Query Tasks (лимит задержки ответа);
  - процент ошибочных джоб ingestion;
  - скорость роста `graphrag_graph_nodes_total` (аномальный прирост — риск мусора графа).
- **Аудит действий:** журнал операторских действий (смена адаптера, активация домена,
  удаление источника) в отдельном логе; недоступен для просмотра рядовым аналитиком.
- **Ротация API-ключей:** по событию утечки или раз в 90 дней; процедура — новый ключ →
  подтверждение работы → деактивация старого (Config API).

## 5. A/B-тестирование при смене моделей

- Смена модели/промпта выполняется через runtime config (`namespace: adapters`, `extraction`, `llm`).
- Сравнение качества — методология `docs/05_adr_log.md` ADR-015 (eval-датасет, метрики, lift-отчёт).
- Требование выпуска: groundedness и coverage не ниже baseline при допустимой задержке (ADR-015,
  «валютное» правило). После выпуска — мониторинг задержки и ошибок на живом трафике.

## 6. Runbook и запуск прототипа (отложено)

Решено: **runbook (симптом → причина → фикс), инструкция запуска и системные требования
собраны в требованиях к прототипу** — `docs/prototype_requirements.md` (заглушки
User Guide и Runbook, приложения A/B). До реализации прототипа отдельный
эксплуатационный runbook не создаётся.

Ориентиры внутри `docs/prototype_requirements.md`:
- §3 «Системные требования» (GPU, VRAM, память, диск, ОС);
- §6 «Веха 0» (инфраструктура: compose, сети) — откуда начинается запуск;
- Приложение B «Runbook» — таблица «симптом → причина → фикс», заполняется на М0–М4.
