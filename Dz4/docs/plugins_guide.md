# Гайд: свой адаптер или свой плагин

В проекте **два разных механизма расширения**, и они отвечают на разные вопросы. Путаница между
ними — источник почти всех споров о том, «как добавить своё», поэтому сначала разводим их.

| | **Адаптер** | **Плагин** |
|---|---|---|
| Что меняет | **инфраструктуру**: какая БД, какая модель | **поведение**: какая стратегия, какое смешение |
| Кто выбирает | платформа, при развёртывании | прикладной код, по имени в конфигурации |
| Где объявляется | `infra/config/namespaces.yaml` + переменная окружения | `pyproject.toml` плагина, группа entry points |
| Как находится | слот и каталог, разрешаются при сборке пайплайна | `importlib.metadata.entry_points(group=…)` при обращении |
| Неизвестное имя | `ValueError` при сборке | `PluginMissingError`, затем ошибка вызывающего |
| Гайд | [adapters_guide.md](./adapters_guide.md) | этот документ |

**Критерий выбора — один вопрос.** Разворачиваете ли вы обязательную часть стенда или подменяете
способ что-то считать?

- «Какую векторную БД использовать», «какой LLM» → **адаптер**. Это инфраструктура; её выбирает
  оператор развёртывания, и её отсутствие ломает стенд.
- «Как смешивать графовую и векторную ось», «как резать документ» → **плагин**. Это политика;
  её меняют, не трогая ядро.

Смешивание осей — плагин. Добавление чтения текста чанка — адаптер. В одном бандле встречаются
оба, и это нормально: см. `openspec/changes/graph-vector-mix-plugin/`.

## Слои: контракт и загрузка — это разные вещи

Слово «плагин» отвечает на вопрос **как поставляется**, а не **что он умеет**. Контракт всегда
описан абстрактным классом, независимо от способа загрузки:

```
контракт (ABC)  ←  что обязано уметь: Chunkerr, Reranker, VectorStoreProvider
загрузка        ←  откуда берётся: встроенная реализация ИЛИ entry point
```

Ошибка считать их одним и тем же приводит к двум бедам: либо добавляют новую реализацию
хардкодом в фабрику (и её больше нельзя расширить без правки ядра), либо пишут новый ABC там, где
достаточно существующего. Ниже — оба слоя по отдельности.

## Часть 1. Свой адаптер

Адаптер реализует **существующий** порт. Файлы в `src/graphrag_proto/retrieval/adapters/`:

| файл | что там |
|---|---|
| `base.py` | абстрактные классы: `Embedder`, `VectorStoreProvider`, `GraphStoreProvider`, `LLM`, `Reranker` |
| `inmemory.py` | реализации для тестов и локального прогона |
| `neo4j.py` | реализация поверх Neo4j |
| `deterministic.py`, `bge.py`, `llm.py`, `reranker.py` | прочие реализации |
| `factory.py` | слоты, каталог и разрешение |

### Порядок действий

1. **Реализуйте нужный ABC** в новом модуле. Методы, которые хранилище не умеет, **не поднимайте
   исключение**: у портов есть заглушки с безопасным поведением по умолчанию. Например
   `list_chunk_ids_of_source()` в `base.py` возвращает пустой список, а `verify_projection()`
   возвращает `True`. Это сделано намеренно: неподдерживаемая возможность — это «не могу», а не
   «сломалось».
2. **Закрепите возможности честно.** Если ваша БД не умеет транзакцию, верните
   `consistency_capability() == "best_effort"`, а не `"atomic"`. На этом строятся решения
   пайплайна об откате.
3. **Добавьте имя в каталог** `infra/config/namespaces.yaml`. Это **единственный** источник
   правды о допустимых именах; фабрика проверяет по нему.
4. **Почините фабрику.** Здесь важное: пока новое имя не добавлено в сборщик, оно не заработает —
   `_build_*` содержит явные ветви. Это и есть тот дефект, ради которого расширение переносится на
   плагины: **каждое новое имя сегодня требует правки ядра**.
5. **Переменная окружения** для слота — только если нужно переопределять при развёртывании.
6. **Тесты.** Обязательно: реализация на InMemory и на Neo4j проходит общий контракт. Порт без
   второй реализации — это не порт, а обход пайплайна.
7. **Каталог проверяется тестом.** Неверное имя в `namespaces.yaml` должно ломать гейт.

### Про вендорскую привязку

Привязка появляется ровно тогда, когда код пайплайна начинает знать про конкретную БД. Правило:
**в пайплайне не должно быть ни одного упоминания Neo4j, Qdrant или иной БД.** Всё, что нужно от
хранилища, запрашивается через порт. Тогда замена хранилища — это новая реализация порта, а не
переписывание пайплайна.

Практическая проверка: если чтобы прочитать текст чанка по его идентификатору пришлось бы написать
запрос в Neo4j прямо в пайплайне — привязка уже есть. Правильный ход — добавить метод порта и
реализовать его в обеих реализациях.

## Часть 2. Свой плагин

Плагин — это **пакет с заявленной точкой входа**. Ядро о нём не знает и меняться не должно.

### Как это работает в проекте

Механизм один — `src/graphrag_proto/plugin_registry.py`:

| функция | что делает |
|---|---|
| `map_plugins(group)` | все объявленные точки входа группы как `{имя: entry_point}` |
| `list_plugins(group)` | отсортированные имена |
| `load_plugin(group, name)` | импорт модуля и **вызов точки входа**, возвращает фабрику |
| `clear_cache(group=None)` | сброс кэша (только для тестов) |
| `PluginMissingError` | имя не зарегистрировано ни в одной установленной точке входа |
| `PluginLoadError` | точка входа нашлась, но её импорт или вызов упал |

Группы в проекте: `graphrag.chunkers`. Объявление группы — в `pyproject.toml` **плагина**,
а не ядра:

```toml
[project.entry-points."graphrag.chunkers"]
my_strategy = "my_package.chunking:build_chunker"
```

Точка входа указывает на **фабрику**, а не на класс. Фабрика принимает то, что передаёт
вызывающий.

### Обязательный контракт ошибок

Это самая частая ошибка, поэтому вынесено отдельно. Здесь важен не только запрет на молчаливый
откат, но и **разделение случаев**: их три, и у них разные последствия.

| случай | что означает | что происходит |
|---|---|---|
| **имя не найдено** | политики нет | откат: порядок как в векторе, вклад графа сохраняется |
| **загрузка сорвалась** | политика есть, но не загрузилась | откат, в логе названа причина сбоя |
| **работа сорвалась** | политика отработала неверно | откат целиком; **частичный результат не используется** |
| **отработала** | — | отвечает за свой результат сама, гарантии порядка нет |

Последняя строка важнее прочих: **гарантия «порядок не изменится» относится только к тому, что
случилось до работы плагина.** Установленная реализация может вернуть что угодно, и это её
ответственность.

### Откат — это реализация, а не ветка в коде

Самое частое нарушение здесь выглядит безобидно: в коде появляется `try/except` с возвратом
«просто вектор». Формально отказ стал явным, а на деле появилась **вторая политика ранга**
рядом с первой — в ядре и в плагине. Дальше они расходятся, и выигрывает та, что молчаливее.
Это уже происходило в проекте: подъём оценки на константу не смог починить порядок, который
задавался приоритетом оси.

Правильный вид: откат — **зарегистрированная реализация в той же группе**, и подставляет её
разрешение, а не обработчик исключений. Тогда путь один.

### Откат обязан быть виден в трёх местах

Лог, ответ и артефакт прогона. Только лога недостаточно: отчёт о прогоне читают без логов, и
откат, видимый лишь в логе, даёт прогон, в котором «граф не дал вклада», хотя графа не было.

В артефакте пишутся **оба имени** — запрошенное, которое не нашлось, и применённое. Иначе отчёт
показывает политику, которую никто не просил.

**Причины различаются, а не сводятся в одну.** «Смешивание не применилось», «проекция не готова»
и «обход пуст» — три разных состояния с одинаковым внешним видом «остался вектор». Сведённая
причина делает прогон нечитаемым ровно в тот момент, когда его нужно читать.

### Чек-лист

1. Своя группа точек входа или существующая — решайте сами, но **группа на одно назначение**.
2. Фабрика в `pyproject.toml` плагина.
3. Реализация ABC из `base.py` или из места, где живёт контракт.
4. Ошибки — по контракту выше.
5. Тест на **подставной** точке входа: имя находится, фабрика вызвана. Так проверяется путь
   загрузки, не дожидаясь установки настоящего пакета.
6. Тест на несуществующее имя: применяется откат, он **зарегистрирован как реализация**, и в
   артефакте видны оба имени — запрошенное и применённое.
7. Тест на упавшую реализацию: откат применяется **целиком**, частичный результат не попадает
   в выдачу.
8. Если результат влияет на выдачу — **запишите применённую реализацию и её параметры в ответ и
   в артефакт прогона**. Реализация, применённая к прогону, не восстанавливается из коммита:
   конфигурация меняется на лету.

## Часть 3. Как это уже сделано в проекте

Готовый образец — чанкер. Он же показывает, почему порядок важен:

- контракт — `Chunker` в `chunker.py`;
- загрузка — группа `graphrag.chunkers` через `plugin_registry`;
- перечисление — `list_chunkers()`, которое **склеивает** встроенные имена и имена плагинов;
- неизвестное имя — `ValueError` с перечислением допустимого (`chunker.py:358`).

Тот же контракт, другой способ загрузки — реранкер: `Reranker` в `adapters/base.py`, но
`_build_reranker()` перечисляет ровно два имени. Пока это перечисление в коде, добавить третью
реализацию без правки ядра нельзя. **Это и есть разница между адаптерным слотом и плагином на
практике.**

## Часть 4. Правила, которые не обсуждаются

1. **Неизвестное имя — ошибка.** Молчаливый откат читается как успех.
2. **Применённая реализация записывается в артефакт.** Имя, параметры, что ушло в значение по
   умолчанию.
3. **Плагин не имеет права терять provenance.** Сведения о том, какими осями и путями найден
   документ, читаются при расчёте метрик; их потеря делает отчёт недостоверным, а не беднее.
4. **Ядро не знает про реализации.** Новое имя не должно требовать правки ядра — иначе это не
   плагин.
5. **Порт без второй реализации — обход, а не порт.**

## Часть 5. Быстрый выбор

| Хочу | Делай |
|---|---|
| хранить чанки в другой БД | адаптер: реализация `VectorStoreProvider` |
| звать другую модель эмбеддингов | адаптер: реализация `Embedder` |
| иначе переупорядочивать результаты | плагин: своя группа точек входа |
| иначе резать документы | плагин: `graphrag.chunkers`, уже поддерживается |
| иначе смешивать граф и вектор | плагин: контракт смешения, загрузка через `plugin_registry` |
| иначе генерировать ответ | адаптер: реализация `LLM` |

Полный разбор ролей и прав — [adapters_specification.md](./adapters_specification.md).
