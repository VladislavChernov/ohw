# GraphRAG: Документно-агностичная концепция (v4) — АРХИВ

> **High-Level Architecture Diagram:** [Смотреть](./docs/assets/high_level_architecture.png)

## 1. Назначение системы

GraphRAG — доменно-агностичная гибридная (графовая + векторная) RAG-платформа. Объединяет граф знаний (сущности, связи, контракты) с векторным поиском по чанкам документов. Генерация ответа — через локальную LLM (Ollama, Qwen 2.5 7B), без внешних API.

Базовый профиль (поставляется из коробки) — ИТ-домен: требования, понятия, контракты, конфликты, ограничения. Но архитектура не привязана к ИТ: тот же движок может быть сконфигурирован для литературы (авторы, произведения, жанры, мотивы), кино (фильмы, режиссёры, актёры, жанры, рейтинги), науки (теоремы, эксперименты, методы) или любого другого домена.

Принцип: ядро системы (пайплайн, ретривер, сервисы) — фиксировано. Доменная специфика (онтология, глоссарий, промпты, правила валидации) — конфигурируется через Domain Profile.

## 2. Архитектурные решения (кратко)

- **Хранилище:** Neo4j Community (GPLv3) — граф + native vector index.
- **LLM:** Qwen 2.5 7B Instruct через Ollama (генерация + extraction).
- **Эмбеддинги:** bge-m3 (мультиязычные, RU/EN, 1024 dim).
- **Реранжирование:** bge-reranker-base на CPU (не конкурирует за GPU).
- **Развёртывание:** Docker Compose, профили (embeddings/llm/graph/...).
- **Конфигурация:** YAML (база) + Config Service (runtime overrides).
- **Глоссарий:** YAML (база) + Glossary Service (runtime CRUD).
- **Доменная конфигурация:** Domain Profile (YAML) — онтология, промпты, правила валидации, глоссарий [НОВОЕ].
- **Очередь ingestion:** синхронно (прототип) -> Redis/RabbitMQ (фаза 3).
- **Масштабирование векторов:** Neo4j (прототип) -> Qdrant (рост).

Подробное обоснование — в ADR (раздел 15).

## 3. Архитектура доменов [НОВЫЙ РАЗДЕЛ]

### 3.1. Принцип разделения

```
+----------------------------------------------------------+
|                    ЯДРО СИСТЕМЫ (fixed)                   |
|                                                           |
|  Ingestion Pipeline (9 этапов)                            |
|  Retriever (Graph + Vector + Reranker + Context)         |
|  Services (Query, Config, Glossary, Embeddings, Ingestion)|
|  Storage (Neo4j + vector index)                          |
|  Observability (Prometheus + Grafana + Loki)             |
+----------------------------------------------------------+
                                 |
                                 | настраивается через
                                 v
+----------------------------------------------------------+
|                DOMAIN PROFILE (configurable)              |
|                                                           |
|  Ontology Schema (типы узлов, типы рёбер)                 |
|  Extraction Prompt Template (доменный промпт)              |
|  Validation Rules (правила семантической валидации)      |
|  Glossary Content (синонимы, канонизация, Unicode)       |
|  Chunking Strategy (стратегия разрезания по типам источника)|
|  Context Assembly Template (формат сборки промпта)        |
+----------------------------------------------------------+
```

Ядро не знает, с каким доменом работает. Domain Profile определяет:
- Какие типы узлов и рёбер существуют
- Какие правила валидации применять
- Какой промпт использовать для извлечения
- Как канонизировать имена сущностей
- Как разрезать документы на чанки
- Как собирать контекст для LLM

## 4. Ингестиционный конвейер (Ingestion Pipeline)

### 4.1. Динамический ingestion pipeline (9 этапов)

Движок последовательно прогоняет данные через этапы:
DataSource -> Document Registry -> Chunker (стратегия из профиля) -> Embeddings -> Extraction (доменный промпт из профиля) -> Normalizer v3 -> Graph Writer -> Validator v2 (Cypher-правила из профиля) -> Registry Update.
