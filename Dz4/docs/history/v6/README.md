# Dz4: Мультиязычная Асинхронная Платформа Enterprise GraphRAG (v6.0.0)
===============================================================================

> **Отношение версий:** v6 — **следующая итерация** концепции и документации поверх базы v5.
> Базовый SSOT v5 остаётся в корне проекта: [CONCEPT.md](../../../CONCEPT.md) и [docs/](../../../docs/README.md).

Гибридная (графовая + векторная) RAG-платформа корпоративного уровня. 
Предназначена для семантического поиска, анализа контрактов и выявления логических 
противоречий в технической документации без использования внешних коммерческих API. 

Движок является полностью доменно-агностичным (Fixed Core). Настройка на конкретную 
предметную область (ИТ, кино, литература) осуществляется динамической подгрузкой Domain Profile (YAML).
Слой программных адаптеров в сочетании с Topology Orchestrator полностью изолирует код 
бизнес-логики от вендор-зависимости и изменений инфраструктуры на фазах масштабирования.

## 1. Минимальные системные требования
--------------------------------------------------------------------------------
* **ОС:** Linux (Ubuntu 22.04+), macOS (M1/M2/M3), Windows 11 (через WSL2).
* **CPU:** Минимум 4 ядра (рекомендуется 8 ядер для эффективного локального реранкинга).
* **RAM (Системная ОЗУ):** Строго от 16 ГБ. (СУБД Neo4j программно зажата в лимит 1.5 ГБ JVM).
* **GPU (Видеопамять):** NVIDIA RTX 2070 Super и выше (Минимум 8 ГБ VRAM под инференс).
* **Зависимости:** Docker Engine v24.0+, Docker Compose v2.20+, Python 3.11+ (slim).

## 3. Быстрый старт и развертывание
--------------------------------------------------------------------------------

### Шаг 1: Проверка CUDA-окружения и прав доступа
Для запуска требуются права администратора и поддержка контейнеризированного GPU.
```bash
# Проверка версий Docker
docker --version
docker compose version

# Проверка проброса GPU внутрь Docker-контекста
docker run --rm --gpus all nvidia/cuda:12.0.0-base-ubuntu22.04 nvidia-smi
```

### Шаг 2: Запуск изолированной инфраструктуры
```bash
# Запуск конфигурационных сервисов, очередей и СУБД графа
docker compose --profile config --profile graph up -d

# Проверка статуса сетевых контейнеров
docker compose ps
```

### Шаг 3: Корректная остановка системы
```bash
# Остановка с сохранением локальных весов LLM и индексов графа в volumes
docker compose --profile config --profile graph down

# Полная зачистка и удаление орфанных контейнеров
docker compose down --remove-orphans
```

## 4. Управление рантайм-конфигурацией (API Спецификация)
--------------------------------------------------------------------------------

### 4.1. Смена предметной области (Domain Profile API)
Динамическое переключение домена выполняется без перезапуска контейнеров через Config Service (Порт `8001`):
* **Запрос:** `POST http://localhost:8001/api/v1/config/domain/activate`
* **Тело запроса:** `{"profile": "library"}`
* **Успешный ответ (Код 200 OK):**
```json
{
  "status": "activated",
  "active_domain": "library",
  "previous_domain": "it",
  "loaded_at": "2026-09-05T17:15:00Z"
}
```

### 4.2. Переключение инфраструктурных плагинов (Adapters Management API)
* **Запрос:** `PUT http://localhost:8001/api/v1/config/adapters`
* **Тело запроса:** `{"storage": "qdrant"}`
* **Успешный ответ (Код 200 OK):** Изменение стратегии персистентности на лету (Runtime Swap).

### Стандартизированные коды системных ошибок API:
* `400 Bad Request` — Нарушение синтаксиса YAML-профиля или дублирование `unique_key`.
* `422 Unprocessable Entity` — Ошибка логической валидации онтологии (связи ссылаются на фантомные узлы).
* `500 Internal Server Error` — Критический сбой СУБД или инфраструктуры очередей при накате транзакции коммита.

## 5. Базовый Troubleshooting (Устранение неполадок)
--------------------------------------------------------------------------------
* **Сбой:** Контейнер графового движка (Neo4j) падает сразу после старта с кодом `137`.
  * *Причина:* Локальный демон ОС (OOM Killer) принудительно гасит процесс из-за дефицита ОЗУ на хост-машине.
  * *Решение:* Завершите фоновые тяжелые процессы или уменьшите объем страничного кэша Java в `infra/compose.yaml`.
* **Сбой:** Пайплайн загрузки уходит в бесконечный таймаут при расчете эмбеддингов.
  * *Решение:* Проверьте изоляцию сети `docker network inspect ohw_net`. Убедитесь, что Embeddings Service запущен и доступен по внутреннему порту `8004`.
