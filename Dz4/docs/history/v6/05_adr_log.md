## ADR-013: Переход на асинхронную Task Queue архитектуру и введение Topology Orchestrator (ВЕРСИЯ 6.0)

**Статус:** Accepted  
**Контекст:** В v5 синхронный HTTP-контур Query API создавал риски блокировки потоков и падения системы при пиковых нагрузках, а жесткое переключение адаптеров требовало ручной координации.  
**Решение:** 
1. Ликвидировать синхронный блокирующий контур Query API. Принимать запросы моментально с возвратом статус-кода `202 Accepted` и уникального `task_id`, сразу разрывая сетевое соединение.
2. Использовать оперативную среду очередей рантайма на базе Valkey / Redis Streams.
3. Реализовать пул асинхронных обособленных обработчиков `Query Workers` для асимметричного забора задач без блокировок входных веб-потоков.
4. Выделить внутри Config Service управляющий компонент `Topology Orchestrator` (Паттерн "Фабрика"), который считывает конфигурационный файл `infra_topology.yaml` и динамически подменяет InMemory-классы на сетевые драйверы (Redis/RabbitMQ/vLLM) на лету, полностью изолируя кодовую базу бизнес-логики.

**Последствия:**
- + Высокая отказоустойчивость при пиковых нагрузках (веб-потоки Query API свободны)
- + Инфраструктурная изоляция: код бизнес-логики очищен от деталей сетевой топологии
- + Результаты доставляются асинхронно через WebSockets или Server-Sent Events (SSE), привязанные к стейту `task_id`
- - Усложнение отладки из-за распределенного жизненного цикла задачи поиска
- - Необходимость дополнительного мониторинга состояния оперативных очередей рантайма
