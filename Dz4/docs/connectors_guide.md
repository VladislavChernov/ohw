# Гайд: Создание коннектора внешнего источника данных

> **Версия:** v1.0
> **Последнее обновление:** 2026-09-11
> **Статус:** планируемый слой. Коннекторы в коде отсутствуют; гайд описывает, **как их
> создавать** и как встроить без переписывания ядра. См. также [proposal бандла](../openspec/changes/add-source-connectors/proposal.md),
> [ADR-018](./05_adr_log.md) (Ingestion API), [ADR-021](./05_adr_log.md) (канонический документ),
> [ADR-014](./05_adr_log.md) (жизненный цикл источников), [`docs/02`](./02_pipeline_and_normalizer.md).

---

## 1. Зачем нужен этот гайд

Ingestion API (:8002) принимает источники по **push-модели** (`POST /documents`, ADR-018):
клиент шлёт содержимое + метаданные (`source_url`, `domain`, `doc_type`). Текущий реестр
ридеров поддерживает `txt`, `md`, `pdf` (`registry.py::factory`, ADR-021). Пайплайн из
9 этапов (INGEST→COMMIT) работает **только с каноническим документом** и источник-агностичен.

Вы хотите загружать в систему данные из **внешних систем**: Jira, Test Management Systems
(TestRail, Zephyr…), корпоративные вики (Confluence, Wiki.js…), GitLab и т.п.
Для этого нужен **коннектор** — код, который вытаскивает данные из внешней системы по её
API и приводит их к виду, который уже понимает пайплайн. Этот гайд — пошаговая инструкция.

**Главное:** коннектор живёт **вне ядра**. Пайплайн, реестр ридеров, Document Registry,
soft-delete и версии источников (ADR-014) менять **не нужно**. Встраивание безболезненное
по построению — точка подключения находится до пайплайна.

---

## 2. Две ответственности, которые нельзя смешивать

| Слой | Отвечает за | Контракт |
|------|-------------|----------|
| **Коннектор / фетчер** | Транспорт: HTTP-клиент, auth, пагинация, экспорт | `fetch(...) -> bytes/material` |
| **Ридер (`DocumentReader`)** | Формат: `Path` → канонический `Document` (ADR-021) | `read(source: Path, source_url, domain) -> Document` |

> **Правило (зафиксировано в бандле `add-source-connectors`):** не «поглощать» транспорт
> в `DocumentReader`. Ридер остаётся источник-агностичным парсером; вся логика внешней
> системы (эндпоинты, креды, пагинация, фильтры) — в коннекторе.

## 3. Два варианта подключения

### Вариант A — materialize-first (рекомендуется, работает уже сейчас)

Коннектор сводится к «фетчеру, который приводит данные к файлу». Дальше используется
существующий код без единой правки:

```
Внешняя система ──fetch──► коннектор ──materialize──► local file / content
                                                          │
                                     POST /documents {source_url, domain, doc_type, content}
                                                          ▼
                                Ingestion API :8002 ──► ридер (registry) ──► пайплайн INGEST→COMMIT
```

Конкретно:
1. Коннектор вызывает API внешней системы (Jira JQL, TestRail API, Confluence export…).
2. Приводит результат к текстовому/структурированному виду.
3. Передаёт в Ingestion API вызываем `POST /api/v1/ingestion/documents` с полями
   `source_url`, `domain`, `doc_type` и `content` (`docs/api_reference.md` §5).
   Если нужен **новый** `doc_type` — добавьте ридер в `registry.py` (паттерн PDF, см. §5).

### Вариант B — контракт `SourceProvider` (задел, планируется)

Интерфейс-заготовка для будущей реализации (не входит в текущие вехи, помечен в
`openspec/changes/add-source-connectors/tasks.md` как `[ ]`):

```python
# ingestion_service/connectors/base.py (будущая реализация)
class SourceProvider(ABC):
    @abstractmethod
    def fetch(self, source: SourceRef, creds) -> bytes:
        """SourceRef = {source_url, domain, doc_type}; транспорт — ответственность коннектора."""
```

Опционально (поздняя эволюция) — слот `source` в топологии (`infra_topology.yaml` +
Adapters Management API) для переключения активных источников на лету, по аналогии
с слотами `graph_store`/`vector_store` (M3).

## 4. Как создать коннектор — пошагово

### Шаг 1. Выберите `doc_type` и изучите API внешней системы

- `doc_type` — строковый идентификатор формата/системы (например `jira`, `testrail`,
  `confluence`, `gitlab`). Записывается в канонический `Document` и сохраняется в
  Document Registry.
- Определите, какой API даёт система и что из него реально нужно:
  - **Jira** — REST `/rest/api/3/search?jql=...` (задачи, комментарии, связанные тест-кейсы);
  - **TestRail** — `/index.php?/api/v2/get_cases/...`, `get_results_for_case/...`;
  - **Confluence / Wiki** — REST `/rest/api/content?...` или HTML/модуль экспорта в Markdown;
  - **GitLab** — `/api/v4/projects/:id/repository/tree` + blob-чтения.

### Шаг 2. Напишите фетчер (транспорт)

Отдельный модуль **вне ядра** (например `connectors/jira.py` рядом с `ingestion_service`):
- HTTP-клиент к внешнему API; timeout'ы и ретраи обязательны;
- аутентификация: токен/пароль **только** из env или секретохранилища (никогда не в коде
  и не в логах — `docs/security.md` §3);
- пагинация/курсоры; отсечение лишнего, если система отдаёт «сырьё» (binary attachments и пр.).

### Шаг 3. Приведите данные к «понятному» виду (материал)

- Хороший тон — отдать текст/Markdown аккуратно оформленными блоками (заголовки, код-блоки),
  это улучшает CHUNK и EXTRACT.
- Структурированные данные (cases, issues) можно сериализовать в JSON/Markdown **со стороны
  коннектора**; ядро данные не декорирует.
- Не забудьте `source_url`: это идентичность источника (ADR-014). Один «физический»
  объект системы (задача, тест-кейс) — один стабильный URL.

### Шаг 4. Передайте в Ingestion API (или файл → executor)

```bash
curl -X POST http://localhost:8002/api/v1/ingestion/documents \
  -H 'X-API-Key: changeme' \
  -d '{
    "source_url": "https://jira.corp/rest/api/3/issue/PROJ-123",
    "domain": "qa",
    "doc_type": "jira",
    "content": "# PROJ-123: не работает экспорт...\n..."
  }'
```

Ответ `202 {job_id, status, created_at}` — дальше пайплайн сам выполнит 9 этапов.
Повторная передача того же источника с тем же содержимым **идемпотентна** (`content_hash`
по каноническому виду, ADR-014): дублей не будет.

### Шаг 5. Новый `doc_type` → добавьте ридер (только если нужен новый формат)

Если `doc_type` уже покрыт существующим ридером (`txt`/`md`/`pdf`) и коннектор отдаёт
Markdown/text — ничего делать не надо. Если формат новый — следуйте паттерну PDF:

1. Класс-наследник `DocumentReader` (`readers/base.py`), поле `doc_type`.
2. `read(source, source_url, domain) -> Document`: блок — `Block(type, page, order, data)`;
   `content_hash = compute_content_hash(domain, blocks)`.
3. Регистрация в `registry.py::factory` (словарь ридеров) и добавление в `ALLOWED_DOC_TYPES`
   (`app.py`), если идёте через `POST /documents`.
   Пример — `readers/pdf.py`: реализация с lazy-импортом библиотеки, реестр не ломается
   при её отсутствии.

> `.json`-ридер был вне скоупа M1 (ADR-021) — это про **объём** M1, а не запрет: добавление
> ридера под нужды конкретного коннектора — нормальная, самодостаточная правка.

### Шаг 6. Тесты коннектора

Контрактные проверки того же уровня, что и у адаптеров (ADR-012 — по духу):
- `fetch` для типового запроса возвращает данные; для пустого — пустой материал без ошибки;
- прошедший через ридер материал даёт `Document` с корректным `source_id` и
  непустыми блоками;
- повторный INGEST того же `source_url`/`content_hash` не создаёт дублей (проверка
  по Document Registry, ADR-014);
- при недоступности внешней системы коннектор падает с понятной ошибкой и **не валит**
  пайплайн целиком (исключение ловится на уровне джоба).

## 5. Чек-лист «коннектор готов»

- [ ] Транспорт в отдельном модуле вне ядра; в ядро — ноль правок пайплайна.
- [ ] `source_url` стабилен и уникален для каждого объекта внешней системы.
- [ ] Креды — только из env/секретохранилища; в логах — красакция.
- [ ] Материал приводится к text/md-виду (или добавлен ридер нового `doc_type` по PDF-паттерну).
- [ ] Идемпотентность проверена повторным INGEST.
- [ ] `X-API-Key` при обращении к Ingestion API (L5-01).
- [ ] Контрактные тесты зелёные; `uv run pytest -q`, `ruff`, `mypy` — чистые.

## 6. Частые вопросы (FAQ)

**Нужно ли менять пайплайн для нового источника?** Нет. INGEST в пайплайне получает
только канонический `Document` (ADR-021); коннектор существует до пайплайна.

**Можно ли переключать источники на лету, как адаптеры в M3?** В текущих вехах — нет,
это задел: интерфейс `SourceProvider` и (опционально) слот `source` в топологии помечены
как планируемые в `openspec/changes/add-source-connectors/`.

**А если источник — тот же PDF, но из некой системы?** Тогда коннектор просто скачивает
файл и передаёт как `doc_type=pdf` — существующий `PdfReader` подхватит без правок.

**Это входят в скоуп ДЗ?** Не входит в M3–M5; это отдельная запланированная веха
(см. `docs/prototype_requirements.md`, веха «Внешние источники (коннекторы)»).
