> **Версия:** v9 (ADR-001 — ADR-039)
> **Последнее обновление:** 2026-10-01
>

> серия с теми же номерами: ADR-010…013 совпадали, а с 014-го расходились — под ADR-014 здесь
> было версионирование источников, а там точки роста. Из-за этого «ADR-014» без указания
> файла означало два разных решения, и одна из записей ссылалась сама на себя в чужой серии.

> authoritative журнал.** Новые решения продолжают серию этого файла.
>
> **Статусы ADR:** `Accepted` — действует; `Draft` — прорабатывается, исполнению не
> подлежит; `Superseded от <дата> (ADR-NNN)` — заменён другим решением, текст сохранён

> Пункт «Accepted» у записи означает, что она **прямо действует**: если решение отменено
> корректирующими записями, это видно из них, а в самой записи может стоять текст,
> расходящийся с действующим.
>
> **Сводка решений ADR-014+:** жизненный цикл источников (ADR-014), методология оценки (ADR-015),
> JSON-Schema событий стриминга (ADR-016), набор MCP-инструментов (ADR-017), контракты

> (ADR-019), язык Query API Gateway на этапе прототипа — Python/FastAPI (ADR-020). Закрывают
> открытые вопросы expert_reviews и api_reference. **Сводка обрывается на ADR-020** и не
> покрывает 021–038; это заметное неудобство навигации, а не отсутствие записей: полный
> перечень — заголовки `## ADR-NNN` ниже по файлу.
> Сводные справочники: `docs/security.md`, `docs/operations_requirements.md`
> (нормативные правки требований — ADR-035).

## ADR-001: Выбор Neo4j в качестве единого хранилища для прототипа

**Статус:** Accepted  
**Контекст:** Нужно выбрать хранилище для графа знаний и векторных чанков.  
**Решение:** Neo4j Community (GPLv3, native vector index, Cypher).  

**Последствия:**
- + Один источник правды, нет JOIN между БД
- + Cypher для графовых запросов
- - GPLv3 лицензия (приемлемо для internal use)
- - Vector index деградирует на >1M чанков → Qdrant (фаза 2)

**Уточнение:** Для митигации рисков падения по OOM (Out of Memory) на 16 ГБ системной ОЗУ, лимиты памяти Java Virtual Machine жестко зажимаются через Docker Compose: max heap 1G, initial heap 512M, pagecache 512M.

**Корректирующая запись (2026-09-28):** запись была неполной по сравнению с копией из `CONCEPT.md`, обе внесены в журнал при сведении двух серий. Цель выбора была шире зафиксированной — не связать ядро с вендором. Независимость обеспечивается не самим фактом выбора Neo4j, а косвенностью: `GraphStoreProvider` и `VectorStoreProvider` допускают независимые реализации, поэтому смена backend не требует правок ядра. Статус Accepted относится к прототипу, а не к обязательству production — последующие решения (ADR-022, ADR-031) уже заменили LLM- и graph-контуры. Формулировка «единого хранилища» означает «один источник правды» (плюс в последствиях), а не запрет отдельного векторного хранилища.

## ADR-002: Обеспечение LLM для extraction и генерации

**Статус:** Superseded от 2026-09-26 (ADR-022)  
**Контекст:** Нужно обеспечить локальный LLM для extraction и генерации, без внешнего API.  
**Прежнее решение:** Qwen 2.5 7B Instruct через Ollama.

**Почему заменено:** ADR-022 перенёс локальный LLM-контур на llama.cpp с
`Qwen2.5-Coder-7B-Instruct-abliterated-Q4_K_M.gguf`. Ollama остался возможным, но не
обязательным вариантом, поэтому «через Ollama» перестало быть частью решения.

**Что сохраняется по существу:** конкретная модель и хост — это конфигурация развёртывания,
а не архитектурное решение. Ядро обращается к LLM только через контракт `LLMInference`
(инвариант L4-01), поэтому подойдёт любой endpoint с OpenAI-совместимым `/v1/chat/completions`:
llama.cpp, Ollama, vLLM, LM Studio, внешний провайдер. Выбор конкретной модели не должен
попадать в ADR — его место в конфигурации стенда.

**Что было правильного в исходной постановке (не потеряно):**
- + Умещается в 1 GPU (8 ГБ VRAM достаточно)
- + Русский язык, instruction-tuned
- - 7B показал слабую точность на Validator + слиянии эмбеддингов

**Как выбирается фактически сейчас:** стенд поднимает `llama.cpp` (сервис `llm`, `:8080`),
модель закреплена в `prototype/Dockerfile.llm` по ревизии и SHA-256, подключение идёт через
`LLM_BASE_URL`, адаптер в `infra_topology.yaml` — `llm: openai`. Смена модели или хоста
не требует правок кода.

## ADR-003: Выбор bge-m3 для эмбеддингов

**Статус:** Accepted  
**Контекст:** Нужны мультиязычные (RU/EN) эмбеддинги, 1024 dim.  
**Решение:** bge-m3 (BAAI, Apache 2.0).  

**Последствия:**
- + 1024 dim, мультиязычный, хорошее качество на русском
- - 2.3 GB весов, ~4 GB VRAM
- - Не может работать одновременно с Qwen 7B на одном GPU
- Принцип размерности: default 1024 — фактический выхлоп модели; смена модели
  требует выравнивания `EMBEDDING_DIMENSIONS` в сервисе, mock-режиме и адаптере
  (при несовпадении — 503/fail-fast, ось L2-04).

## ADR-004: Разделение LLM и Python в пайплайне

**Статус:** Accepted  
**Контекст:** LLM 7B хорошо извлекает сырые триплеты, но плохо выполняет дедупликацию и нормализацию.  
**Решение:** LLM — только экстракция. Python — дедупликация, канонизация, семантический вывод.  

**Последствия:**
- + Стабильное качество (детерминированный Python)
- + Меньше вызовов LLM
- - Normalizer сложнее (4 подэтапа)

## ADR-005: Двухступенчатая векторная дедупликация

**Статус:** Accepted  
**Контекст:** Один порог 0.92 отсекает явные дубли, но пропускает пограничные случаи.  
**Решение:**
- Ступень 1: cosine >= 0.92 → авто-merge
- Ступень 2: 0.75 <= cosine < 0.92 → LLM (SAME/DIFFERENT)
- Ступень 3: cosine < 0.75 → пропустить

**Последствия:**
- + Выше точность
- - Доп. нагрузка на GPU для ступени 2

## ADR-006: Иерархия Contract-узлов

**Статус:** Superseded от 2026-09-26 (ADR-031)  
**Контекст:** JSON-схемы ссылаются друг на друга через $ref и allOf.  
**Прежнее решение:** Добавить связи EXTENDS и REFERENCES между :Contract.  

**Последствия:**
- + Граф знает структуру вложенных схем
- + Graph Retriever обходит дерево одним Cypher
- - Extraction-промпт сложнее

**Корректирующая запись (2026-09-28):** копия из `CONCEPT.md` внесена в журнал при сведении двух серий. ADR-031 перевёл ingest на generic context nodes/edges, и ADR-006 остаётся историческим описанием typed-подхода: одна метка `ContextNode` вместо `:Contract` с типами, виды рёбер не задаются онтологией — `CONTAINS`/`MENTIONS` технические, остальные приходят из экстракции. Имена `PARENT`/`RELATED` в обходе больше не используются: фильтр по виду ребра снят, `expand()` идёт по любому виду и возвращает фактический вид прыжка (`docs/data_model.md` §3.1). Инструмент замены — corrective change `add-lightweight-context-graph`, он назван в статусе ADR-031.

## ADR-007: Контекстно-зависимая канонизация строковых представлений

**Статус:** Accepted  
**Контекст:** LLM создаёт дубли из-за пробелов, регистра, форматирования (O(V^2) vs O(v^2) vs O(V ** 2)).  
**Решение:** Контекстно-зависимая канонизация:
- complexity: 4 слоя (Unicode → функции → структура → glossary)
- algorithm: 2 слоя (Unicode → glossary)
- data_type: 1 слой (glossary only)
- прочие: trim + нижний регистр

Таблицы замен хранятся в Glossary Service (расширяемые без кода).

**Последствия:**
- + Меньше дублей, чище поиск
- + Правила расширяются через YAML, без деплоя
- - Канонизация может быть агрессивной (edge cases)
- - Нужна поддержка таблиц в Glossary Service

## ADR-008: Семантическая валидация графа

**Статус:** Superseded от 2026-09-26 (ADR-031)  
**Контекст:** Структурной валидации недостаточно. Система должна блокировать логические противоречия на этапе ingestion.  
**Прежнее решение:** Validator v2 проверяет:
- REQUIRES_CONSTRAINT без цели → warning
- CONTRADICTS внутри одного требования → error
- REQUIRES + CONTRADICTS одновременно → error
- SIMILAR_TO без обратной связи → auto-fix

**Последствия:**
- + Ошибки ТЗ ловятся до продакшена
- - Может давать false positives → нужен ревью отчётов

**Корректирующая запись (2026-09-28):** копия из `CONCEPT.md` внесена в журнал при сведении двух серий. Здесь снятая валидация описана как семантическая (Validator v2 с правилами REQUIRES_CONSTRAINT / CONTRADICTS / SIMILAR_TO), в копии CONCEPT.md — как hard ontology validation, блокирующая primitive ingest и произвольные tags. Это два описания одного снятого слоя; **что осталось в runtime, в журнале не было записано, а это и есть полезная часть копии**: runtime сохраняет только технические проверки endpoint/provenance, а `_validate_ontology` и profile Cypher validation rules **не являются** ingest gate. Инструмент замены — corrective change `add-lightweight-context-graph` (ADR-031).

## ADR-009: LLM-fallback для канонизации сложности

**Статус:** Accepted  
**Контекст:** Слои 1-3 (Unicode, синонимы функций, структурное сжатие Big-O) работают детерминированно, но не покрывают все случаи человеческих записей формул.  
**Решение:** Добавить LLM-fallback через **LLM Adapter** с обязательной проверкой результата регулярным выражением (Regex) по строгому паттерну o(...). При сбое Regex-валидации — автоматический fallback на исходную строку + warning в лог.

## ADR-011: Переход к доменно-агностичной архитектуре платформы (ВЕРСИЯ 4.0)

**Статус:** Accepted  
**Контекст:** Жесткая привязка кода к ИТ-домену ограничивала масштабируемость.  
**Решение:** Реализовать концепцию Domain Profile (YAML). Вся онтология, промпты, правила валидации на Cypher и канонизация вынесены в конфиги. Ядро системы абсолютно агностично. Смена домена происходит на лету через Config Service API.

**Примечание (2026-09-27).** Решение остаётся Accepted, но фраза «вся онтология… вынесена в
конфиги» описывает намерение, а не рантайм. По факту из профиля читаются `chunking`,
`extraction.prompt_template` и канонизация, а `ontology.node_types[].unique_key` имеет
единственного потребителя `GraphStoreProvider.ensure_schema()`, который не вызывается из ingest
path, и `ontology.edge_types` не читается нигде; Cypher-правила из `validation.rules` не
исполняются. Рабочие и инертные ключи перечислены в `docs/01_ontology_and_domain_profile.md` §1.1.
Ядро при этом действительно доменно-агностично — это решение ADR-011 и оно не отменялось;
не исполняется только перечисленная часть.

**Последствия:**
- + Один движок — множество доменов
- + Новый домен = новый YAML, без кода
- + Переключение домена в runtime (Config Service API)
- + Сообщество может создавать свои профили
- - Качество extraction зависит от промпта (нужно калибровать)
- - Мультидоменность в одной инсталляции — перспектива (namespace)
- - Валидация Domain Profile при загрузке (синтаксис, ссылки)

## ADR-012: Введение слоя адаптеров для изоляции инфраструктуры (ВЕРСИЯ 5.0)

**Статус:** Accepted  
**Контекст:** В v4 ядро системы было жёстко привязано к конкретным технологиям (Neo4j, Ollama, bge-m3 HTTP Service, bge-reranker). Замена любого компонента требовала изменения кода ядра. Это ограничивало гибкость и создавало vendor lock-in.  
**Решение:** Ввести слой адаптеров — программные интерфейсы (GraphStoreProvider, VectorStoreProvider, LLMInference, Embedder, Reranker), изолирующих ядро от конкретных технологий. Конкретная реализация выбирается через runtime config (namespace: adapters) и загружается динамически при старте. Сторонние адаптеры регистрируются через entry_points (Python setuptools).

**Последствия:**
- + Замена инфраструктуры — правка одного конфига, без переписывания ядра
- + Поддержка множества хранилищ (Neo4j, Qdrant, Memgraph), LLM (Ollama, vLLM, OpenAI), эмбеддингов (bge-m3, sentence-transformers), реранкеров (bge-reranker, NoOp, Cohere)
- + Сторонние разработчики могут создавать свои адаптеры без изменения кода ядра
- + Снижение vendor lock-in риска
- + Возможность выбора оптимального стека под задачу (лёгкая инсталляция, замена хранилища, облачный LLM)
- - Увеличение сложности архитектуры (дополнительный слой абстракции)
- - Необходимость контрактных тестов для каждого адаптера
- - Небольшой оверхед на вызов через интерфейс (незначительный)

## ADR-013: Разделение интерфейсов графового и векторного хранилищ (уточнение ADR-012)

**Статус:** Accepted  
**Контекст:** Монолитный интерфейс `GraphStorage`, введённый в ADR-012, концептуально неверно моделировал гибрид. Чисто векторный поиск ложно зависел от логики графового движка, а `QdrantStorageAdapter` (только векторы) не мог корректно реализовать графовые операции. Это нарушало принцип разделения интерфейсов (ISP) и блокировало независимое масштабирование осей.  
**Решение:** Аннулировать `GraphStorage`. Ввести два изолированных ABC-контракта: `GraphStoreProvider` (логика связей, Cypher, обход графа) и `VectorStoreProvider` (косинусный поиск чанков). Гибридный ретривер обращается к ним параллельно, соединяя результаты только на этапе Context Assembly. В прототипе обе реализации смотрят на Neo4j (native graph engine + native vector index); при росте `VectorStoreProvider` бесшовно заменяется на `QdrantVectorStore` без изменения графовой логики.

**Примечание (2026-09-27).** Решение остаётся Accepted: разделение интерфейсов и вывод
`QdrantVectorStore` действительно реализованы. Не реализована часть про порядок вызова —
«обращается к ним параллельно, соединяя результаты только на этапе Context Assembly». По
`L1-04` и `L3-03` фактический порядок другой: сначала vector search, затем bounded graph
expansion по `context_ids`, а Context Assembly получает уже сведённый bounded контекст. Графовая
ось при этом optional, а не симметричная второй оси, и её вклад измеряется парным прогоном.
Ось не «соединяется» в Context Assembly, а расширяет набор источников до сборки контекста
(`docs/03_retriever.md` §1). Двойник этого решения в `CONCEPT.md` ADR-013 приведён к факту.

**Последствия:**
- + Соответствие ISP: граф и вектор — две независимые оси.
- + Бесшовная миграция векторов на Qdrant подменой одной реализации; Cypher-пайплайны графа не затрагиваются.
- + Qdrant больше не «притворяется» графовым хранилищем; гибридность сохраняется.
- - В Query Workers необходимо инициализировать два отдельных клиента хранилища.
- - Кросс-правка всех упоминаний `GraphStorage` в спецификациях (SSOT).

## ADR-014: Жизненный цикл источников (UPDATE / DELETE, версионирование)

**Статус:** Accepted  
**Контекст:** Не зафиксированы правила обработки изменений и удаления источников: что происходит с
Source, Chunk и доменными сущностями при re-ingest одного и того же `source_url` и при удалении
документа (пробел expert_reviews «Обработка удаления источников: is_deleted, source_ids»). Document
Registry (`docs/data_model.md` §2) имеет поле `status`, но его допустимые значения не определены.

**Решение:**
1. **Идентичность источника:** источник идентифицируется по `source_url` (+ `domain`) в пределах
   активного профиля. Идемпотентность INGEST: если контент не изменился (content hash совпадает) —
   повторная загрузка является no-op и не плодит версии.
2. **Обновление (re-ingest):** при изменении контента существующего `source_url` создаётся новая
   версия документа. Versioning: старая версия метится в Document Registry (`status: superseded`),
   новые Chunk-узлы и сущности пишутся с актуальным `extractor_version`. Версия не удаляется
   физически — живёт до срабатывания retention-политики (`docs/operations_requirements.md`).
3. **Удаление — soft delete:** `DELETE /api/v1/ingestion/documents/{doc_id}` переводит Source в
   `status: deleted` и снимает чанки с оси поиска. Доменные сущности не удаляются в hot path:
   их `source_ids` сохраняются, но ретривер фильтрует чанки/сущности по активным источникам.
4. **Переиндексация:** повторный INGEST удалённого `source_url` реактивирует источник
   (новая версия), сущности продолжают работу через `source_ids`.

**Последствия:**
- + Гибкое обновление контента без потери графа: дедупликация и сущности переживают re-ingest.
- + Нет хард-удаления в горячем пути — нет гонок с ретривером и транзакционных проблем.
- + Идемпотентность: повторные загрузки одного URL не засоряют граф.

**Корректирующая запись (2026-09-28).** Пункт 2 выше не говорит, что происходит с

Дополняется, а не переписывается:

1. **Устаревшие рёбра при re-ingest не удаляются.** Причина не в экономии, а в
   необратимости: после удаления нельзя ответить, что утверждала предыдущая версия, а
   именно это нужно для сценария, ради которого версионирование и затевалось (например,
   переговорные итерации договора, где требуется показать, что было согласовано на

2. **«Текущее представление» — фильтр на чтении.** Ребро считается текущим, если у него

   выше «ретривер фильтрует по активным источникам», реализованное фильтром по
   `chunk_ids` вместо соединения с реестром.
3. **Физическая уборка** рёбер и узлов без активных источников — отдельная фоновая задача

    возвращает факт с `planned_*` и `removed_*` раздельно. Первая версия маршрута передавала в
    `run_orphan_cleanup` объект `DocumentRegistry`, тогда как `record_orphan_cleanup` живёт на
    `JobStore`, — вызов падал бы ровно на записи факта, то есть удаление прошло бы, а след
    остался бы нет. Тест на маршрут нашёл это сразу. Параметр переименован `registry` →
    `fact_store`, потому что старое имя и провоцировало ошибку.
32. **Правило впервые проверено на живом графе.** Прогон `docs/test_plan.md` §7.2 от 2026-09-29:
    `run_valid: true`, T1–T6 и T8 `pass`, T7 `not_evaluated` по замыслу (без конкурентного
    ingest `planned` и `removed` обязаны совпасть, и схлопывание неотличимо от корректности).
    Артефакт: `test_artifacts/e2e-cleanup/20260929-170440-49ffb23/`. Многоисточниковая связь,
    державшаяся на двух документах, пережила ревизию одного из них — это и есть T4, единственный
    провал, означающий потерю живых данных.

**Почему эта находка не отменяет ничего, а уточняет.** Пункты 16–19 не переписываются: признак
жизни, дискриминатор, порядок и требование факта верны и теперь работают. Меняется утверждение о
статусе: было «правило написано, но не вызвано», стало «правило было написано, но и не имело
предмета отбора; теперь вызвано и проверено». Отдельно помечено, что автоматический триггер по
прежнему не планируется (пп. 26–27 пятой записи в силе), а уборка по-прежнему обязана идти вне
hot path (п. 3). Найдено прогоном, а не чтением кода, — и это само по себе довод за то, что
E2E нужен: правило, написанное в ADR и продублированное в тестах, оказалось мёртвым.

## ADR-015: Методология оценки (eval) платформы

**Статус:** Accepted  
**Контекст:** Нужно доказать, что гибридный граф+вектор подход даёт прирост к качеству ответов по
сравнению с vector-only (пробел expert_reviews «Eval-датасет и метрики»). Без измеримой цели смена
моделей/промптов остаётся неконтролируемой.

**Решение:**
1. **Eval-датасет:** файлы `prototype/infra/eval/{domain}/questions.jsonl` — записи
   `{ query, golden_sources: [source_url], golden_facts: [строка факта] }`. Разметка вручную,
   минимум 50 вопросов на домен для базового среза; расширяется при каждом выпуске.
2. **Метрики ретрива (K=5):** Recall@K, Precision@K, MRR, nDCG@K — по `golden_sources`.
3. **Метрики генерации:** groundedness (доля утверждений ответа, подтверждаемых источниками),
   coverage (доля golden_facts, покрытых ответом), `hallucination_rate` (утверждения без
   источника; в коде — обратная к groundedness по тем же утверждениям, 1.0 при пустом ответе).
4. **Сравнение (lift-отчёт):** baseline = vector-only; optional graph experiment = vector +
   bounded graph expansion. Отчёт фиксирует delta по каждой метрике; инженерное решение о
   выпуске принимается по «валютному» правилу: groundedness, coverage и hallucination_rate не ниже
   baseline при приемлемом времени ответа. Неизмеренная метрика попадает в delta как `null`, а не
   как 0; при живом судье и отсутствии метрик вердикт = `invalid`, а не `pass`.
5. **Прогон:** eval-скрипт в составе пайплайна при смене `extractor_version` / модели / словаря;
   результаты — с метаданными `{run_id, model, prompt_version, date}`.

**Последствия:**
- + Измеримое обоснование ценности optional graph experiment и смены моделей.
- + Регрессионный барьер при смене промптов/моделей (нельзя незаметно ухудшить качество).
- - Трудозатраты на разметку eval-датасета (фиксируется в `operations_requirements.md` как
  регулярная задача).
- - Метрики groundedness требуют доработки LLM-as-judge шага (оценочный прогон на той же модели,
  что и генерация, — риск системной ошибки, учитывается в отчёте).

**Delta (эксперимент «вклад графа», 2026-09-22, см. design.md §4):**
Формат вопроса расширяется **опциональными** полями `v2` (обязательные — прежние:
`id, query, golden_sources, golden_facts`; старые наборы остаются парсибельными):

| Поле | Значение |
|---|---|
| `reasoning_type` | `single-hop`, `cross-document`, `temporal-cross-document`, `contradiction`, `causal-risk`, `multi-hop` (обратно совместимы пилотные `historical-fact`, `conditional`, `evidence-boundary`, `insufficient-evidence`) |
| `answerability` | `answerable` / `unanswerable` (пилот: `partial`) |
| `as_of` | дата среза знаний, ISO (`2026-09-17`) |
| `evidence_sections` | список разделов документов-свидетельств |
| `evidence_policy` | `joint` / `any` / `graph_required` (пилот: `alternatives`) |
| `rubric` | инструкция для проверяющего |
| `golden_graph_evidence` | `true` — факт требует графового пути/оси |

Правила:
- `golden_facts` — атомарные утверждения: одна строка ≈ один проверяемый факт.
- `evidence_policy=graph_required` **влечёт** `golden_graph_evidence: true` (валидируется).
- Вопросы, где граф нужен для полноты, помечаются `golden_graph_evidence` — вклад графа
  измеряется только на этом срезе (design.md «Критерии»); остальные — шум, не интерпретируются.
- `done.sources` дополнен аддитивным полем `axis ∈ {graph, vector}` (формат события `done`
  в ADR-016 остаётся обратно совместимым: `relevance`/`source_url` без изменений).

## ADR-016: JSON-Schema контракт событий стриминга (WebSockets / SSE)

**Статус:** Accepted  
**Контекст:** Открытый контракт в `docs/api_reference.md` §3.3 («Точный JSON-Schema событий
стриминга требует фиксации в ADR»). Доставка результата асинхронного Query API выполняется по
WebSockets и SSE — нужен единый конверт события для обоих транспортов.

**Решение:** Единый конверт события с дискриминатором `type`:

```
EventEnvelope:
  type:   "status" | "token" | "done" | "error"
  task_id: string
  ts:     string (RFC 3339)
  payload: объект по типу
```
- `status`: `payload: { "stage": "embedding" | "graph" | "vector" | "rerank" | "llm" }`
- `token`: `payload: { "delta": "<фрагмент текста>" }`
- `done`: `payload: { "text": "...", "sources": [{ "source_url": string, "relevance": number }], "generation_time_s": number }`
- `error`: `payload: { "code": string, "message": string }`

Транспорты:
- **SSE:** событие с именем `type` (`event: done`), тело — JSON в `data:`. Однострочный JSON.
- **WebSockets:** один JSON-объект конверта на фрейм.

**Последствия:**
- + Один контракт для обоих транспортов — Go/Rust-контур и Python-контур стримят одинаково.
- + Добавление полей backward-compatible (только расширение); ломающие изменения — новая
  мажорная версия контракта (`v2` и далее).
- - Фиксирует схему рано: возможны мелкие правки полей в ходе прототипирования (допустимы при
  статусе контракта `v1-draft` на время сборки прототипа).

## ADR-017: MCP-инструменты (Query API Gateway как MCP-шлюз)

**Статус:** Accepted  
**Контекст:** Открытый вопрос из `docs/api_reference.md` §3.4 («Набор MCP-tools не зафиксирован —
требует спецификации в ADR»). Query API Gateway совмещает роль MCP-шлюза для автономных ИИ-агентов.

**Решение:** Минимальный набор инструментов v6 (расширяется по необходимости):
- `graphrag.query` — RAG-запрос; принимает `{query, metadata}` → `task_id`; клиент подписывается на
  стриминг (тот же контракт ADR-016).
- `graphrag.get_active_domain` — имя активного профиля.
- `graphrag.resolve_term` — перевод тега в канонический ряд через Glossary Service (`canonical_name`).
- `graphrag.get_sources` — чтение списка источников / содержимого по `source_url` (access к графу).

Правила:
- Транспорт — MCP Protocol (JSON-RPC), те же порт/шлюз :8000 и `X-API-Key`.
- Сервисы, отличные от обработки запросов (правка профилей, конфигурации), агенту не
  предоставляются: шлюз ориентирован на чтение графа и выполнение поиска.
- Ответ машинному агенту — тот же стриминг, что и браузерному клиенту (ADR-016).

**Последствия:**
- + ИИ-агенты получают стабильный способ чтения графа без веб-аутентификации человека.
- + Минимальный охват снижает поверхность атаки (только чтение + запросы).
- - Агенты могут активно дёргать `graphrag.query` — требуется rate-limiting (Policy,
  `docs/security.md`).

## ADR-018: Контракты Ingestion API и Glossary API (стандартизация)

**Статус:** Accepted  
**Контекст:** `docs/api_reference.md` §5–§6 помечают контракты Ingestion и Glossary как
«рекомендуемые / требует фиксации в ADR». Нужен формально зафиксированный контракт для
реализации прототипа.

**Решение:**

*Ingestion API (:8002):*
- `POST /api/v1/ingestion/documents` — multipart-файл либо JSON `{url, domain, doc_type}`.
  Ответ `202` с `{job_id, status, created_at}`. ID-политика источника и идемпотентность — ADR-014.
- `GET /api/v1/ingestion/jobs` — список джоб (поддержка пагинации: `page`, `page_size`).
- `GET /api/v1/ingestion/jobs/{job_id}` — статус: `{job_id, status, stage}`.
- `DELETE /api/v1/ingestion/jobs/{job_id}` — отмена джобы (освобождение GPU).
- Жизненный цикл джобы: `queued → running (stage: INGEST|CHUNK|EMBED|EXTRACT|NORMALIZE|DEDUP|CONTRACT|VALIDATE|COMMIT) → succeeded | failed | cancelled`.

*Glossary API (:8003):*
- `GET /api/v1/glossary/{domain}` — словарь профиля (`glossary.{profile}.yaml`); домена нет — `404`.
- `POST /api/v1/glossary/resolve` — тело `{term, domain?}` → `{canonical_name, variants}`.
  `domain` опционален: если не указан, сервис берёт активный профиль через
  `GET /api/v1/config/domain/active` (pull-модель, fallback `it`).
- `POST /api/v1/glossary/validate` — тело `{domain?}` → `{valid, duplicates}`;
  проверка уникальности словаря по запросу.

Общие правила: аутентификация `X-API-Key`, стандартные коды ошибок (`docs/api_reference.md` §2).

**Последствия:**
- + Контракт фиксирован — прототип можно реализовывать параллельно по сервисам.
- + Из api_reference убирается статус «рекомендуемый».
- - Ранняя фиксация контрактов до первой реализации: возможны мелкие коррективы полей.
- - Раздельная обработка multipart и JSON усложняет унификацию приёма файлов; допускается
  нормализация к общему внутреннему представлению документа.

## ADR-019: Topology Orchestrator выделен в отдельный сервис с собственным GUI

**Статус:** Accepted  
**Контекст:** Topology Orchestrator (фабрика провайдеров по `prototype/infra_topology.yaml`) был
зафиксирован «внутри Config Service» (ADR-013, v6; C4 Level 2, CONTAINER 7 «Config, Glossary &
Topology Orchestrator»). При подготовке к прототипированию пересмотрено: это отдельная сущность
(инфраструктурный контур, а не доменная онтология), с другой аудиторией и жизненным циклом.
Отдельный экран в конфигураторе смешивает две ролевые и управленческие области в одном UI.

**Решение:**

1. **Отдельный сервис** — `Topology Orchestrator Service`: читает `prototype/infra_topology.yaml`,
   управляет пулами соединений (InMemory → сетевые драйверы Redis/RabbitMQ/vLLM) и runtime
   переключение адаптеров. Перестаёт быть частью Config Service.
2. **Отдельное GUI-приложение** — Topology UI (Streamlit): экран «Топология инфраструктуры»
   переезжает из `Web UI (Streamlit, :8501)` в отдельное настроечное приложение.
   Конфигуратор (Web UI :8501) остаётся только с экраном «Бизнес-онтология».
3. **Ролевая граница:** Topology UI доступен роли `operator` (`docs/security.md` §1);
   конфигуратор онтологии — роли `configurator`/`analyst`. Каждый UI аутентифицируется
   собственным `X-API-Key` к своему сервису.
4. **Порты:** Config Service :8001 (без динамики топологии), Topology Orchestrator Service —
   новый порт :8005, Topology UI — :8502. Конфигуратор :8501 без экрана «Топология».
5. **Профили Docker:** сервис и UI входят в один новый профиль `topology` (не в `config`);
   конфигуратор остаётся в `config`. Профиль `topology` активируется только оператором.

**Последствия:**
- + Чистая ролевая изоляция: топология (rare, рискованно, операторы) отделена от онтологии
  (часто, бизнес-аналитики); каждая поверхность аутентифицируется отдельным ключом.
- + Независимый деплой и жизненный цикл: инфраструктурные изменения не затрагивают
  конфигуратор и наоборот; изоляция сбоев (недоступность GPU/топологии не роняет онтологию).
- + Согласованность: раз сервис отдельный — отдельный и его контур управления.
- - Два процесса Streamlit вместо одного: дублирование каркаса аутентификации и композ-сервиса.
- - Меняется карта портов (добавляются :8005/:8502) — правится `docs/04` §1,
  `infrastructure_stack.md` §2 и прототип-требования.

## ADR-020: Query API Gateway на Python (FastAPI) на этапе прототипа

**Статус:** Accepted  
**Контекст:** Query API Gateway (:8000) принимает `POST /query` → `202 + task_id`, обеспечивает
SSE/WS-стриминг (ADR-016), MCP-мость (ADR-017), rate-limiting и `X-API-Key`-auth. Легенда `docs/00`
приписывала сетевому контуру Go/Rust. При выборе языка для прототипа: вклад шлюза в гипотезы
прототипа отсутствует (eval-гейт, домен-агностичность, переключение адаптеров — не про язык
границы); шлюз — это I/O-обвязка без тяжёлой логики; железо прототипа (RTX 2070 Super, 16 ГБ RAM)
не ограничивает ни один из вариантов — Go/Rust не потребляют GPU и занимают десятки МБ ОЗУ.
Решающий фактор — гомогенность и скорость итераций.

**Решение:**

1. На этапе прототипа Query API Gateway реализуется на **Python 3.11 + FastAPI** — того же языка,
   что и остальной ИИ-контур (Config/Glossary/Ingestion/Workers/адаптеры).
2. **Язык границы — заменяемый.** Веб-слой связан с системой только на-проводными контрактами:
   HTTP/SSE/WS (ADR-016), MCP JSON-RPC (ADR-017), HTTP к Config/Glossary (ADR-018), сообщения
   Task Queue (Valkey/Redis Streams). Смена языка границы не затрагивает ядро, очередь,
   хранилища и профили Docker — процедура в `docs/web_layer_replacement.md`.
3. Переход на Go/Rust на :8000 возможен как отдельное решение фазы 2 (реальная нагрузка
   стриминга, продакшен-граница) — без переделки остальных частей.

**Последствия:**
- + Гомогенный Python-контур: один язык, одна авторизация, один каркас деплоя; быстрые итерации.
- + Замена веб-слоя в будущем не трогает ядро — документация процедуры (`docs/web_layer_replacement.md`).
- + ADR-016/017/018 остаются единственными контрактами границы, язык им безразличен.
- - Легенда `docs/00` уточнена: сетевой контур прототипа — Python; Go/Rust — фаза 2.

## ADR-021: DocumentReader и канонический формат документа

**Статус:** Accepted  
**Контекст:** ADR-018 фиксирует управление джобами Ingestion (:8002) и типы входов
(`.txt/.md/.pdf/.json`), но **не определяет, какой формат INGEST обязан отдать пайплайну**
(CHUNK→…→COMMIT) после чтения источника. Без этого загрузчик негласно связан с типом
источника: подключение OCR / нового ридера / нормализации потребовало бы правки всех
этапов. Для книги по алгоритмам PDF — смешанный контент (текст + код + графики),
терять его на этапе извлечения нельзя. Требуется контракт «источник → канонический
документ», источник-агностичный, обеспечивающий идемпотентность (ADR-014, L2-06).

**Решение:**

1. **Канонический формат документа** (выход этапа INGEST):

   ```json
   Document {
     source_id, source_url, domain, doc_type,
     content_hash,               // sha256 по сериализации нормализованного канонич. вида
     blocks: [ { type, page, order, data } ]  // type: text | code | image
   }
   ```

   - `type: text|code|image`; порядок блоков — `order` (поток чтения).
   - `content_hash` считается **с канонического вида**, а не с байтов источника:
     переносы склеены, whitespace стабилен. Идемпотентность (ADR-014) становится
     источник-независимой и устойчивой к черновому извлечению.
   - `type: image` хранит `data.ref` (указатель), смысл картинки в M1 не индексируется.

2. **Интерфейс `DocumentReader`:** единственный контракт «источник → канонический
   документ». Реализации по `doc_type` (txt/md/pdf). Новый ридер или OCR — это НОВАЯ
   реализация интерфейса, а не правка этапов.

3. **Инвариант (в `docs/invariants.md`, L-запись):** этапы CHUNK…COMMIT читают ТОЛЬКО
   канонический `Document`; доступ к исходным байтам/файлу допустим только внутри
   `DocumentReader`.

4. **PDF-ридер в M1:** текст (склейка переносов `-`/`\n`), детект кодовых блоков
   (моноширинный шрифт/маркеры) → `type:code`, извлечение изображений → `type:image`
   без OCR. OCR/распознавание — M3 (реализация того же интерфейса).

5. **`.json`-ридер** в скоул M1 не входит (нет структурированных источников);
   добавить — отдельная реализация интерфейса.

**Последствия:**
- + Пайплайн не зависит от источника; OCR/новые ридеры — точечные изменения.
- + Идемпотентность (L2-06/ADR-014) на каноническом виде: стабильна при черновом извлечении.
- + Код/графики в PDF не теряются структурно уже в M1.
- - Нужна нормализация (переносы/whitespace) до вычисления `content_hash`.
- - Image-блоки на первых порах без смысла (до OCR) — осознанный компромисс M1.

5. Контейнер `llm` — профиль `llm`, GPU (поочерёдно с bge-m3, гейтинг L4-01 — ограничение

## ADR-023: Task Queue прототипа (Valkey / Redis Streams) и доставка событий задач

**Статус:** Accepted
**Контекст:** Асинхронный контур Query API (v6, L3-05/ADR-016): `POST /query` → `202 Accepted` +
`task_id`, обработка пулом Query Workers, доставка результата подписчику стримом SSE. Нужна
очередь запросов и надёжное хранение per-task потока событий для подписчика, пришедшего позже
старта обработки (история должна догоняться). Kafka — боевой вариант (вне прототипа); для
прототипа достаточно Valkey (drop-in Redis, BSD; актуальная стабильная ветка 9.x). Pub/sub не
подходит: нет истории событий и consumer-group для пула воркеров.

**Решение:**

1. **Очередь запросов** — Redis Stream `query:tasks`: `XADD` при приёме (`POST /query`),
   `XREADGROUP` `consumer_group=query-workers` при заборе воркером, `XACK` после успеха.
   task_id — `q_<hex8>`.
2. **Доставка событий подписчику SSE** — Stream `query:events:{task_id}`: `XADD` воркером по
   мере генерации, `XRANGE`/`XREAD` подписчиком. История события доступна даже после завершения
   задачи: поздний подписчик дополучает полный поток (`status` → `token*` → `done`).
3. **Интерфейс `TaskQueue`** (submit / claim / ack / fail / publish / events /
   is_cancelled / cancel) с двумя
   реализациями: `RedisStreamTaskQueue` (env `QUERY_QUEUE=redis`) и `InMemoryTaskQueue`
   (env `QUERY_QUEUE=inmemory`) — контрактно-эквивалентная, для контрактных тестов и автономного
   демо без Valkey. Выбор транспорта — конфигурация, не архитектура (L1-02). Воркер ack'ает
   entry (XACK) только после полной обработки; при отмене до старта entry ack'ается в claim.
4. **Task store** — SQLite `query_tasks` (task_id, status, stage, created_at, error); lifecycle
   `queued → running → succeeded | failed | cancelled`. Valkey — только транспорт; канонический
   статус живёт в SQLite (аналог связки ADR-014/DocumentRegistry: очередь не является БД).
   Терминальные статусы не перезаписываются: переходы защищены на уровне UPDATE.
5. **SSE-путь** — `GET /query/tasks/{task_id}/stream`; конверт — ADR-016
   (`{type, task_id, ts, payload}`, `event: <type>`, однострочный JSON в `data:`).
   Разрыв соединения клиента не отменяет задачу: worker читает очередь независимо от HTTP-подписчика.
6. **WebSockets в M2 не вводятся** (OQ1): результат доставляем по SSE тем же конвертом ADR-016;
   WS подключится вместе с MCP-шлюзом (M5).
7. **Векторный поиск M2** — косинусная близость по свойству `embedding` в Cypher (без native
   vector index; native index — M3), фиксация OQ2.

**Последствия:**
- + История событий хранится при задаче; подписчик SSE не привязан к жизненному циклу воркера.
- + Consumer-group позволяет горизонтально расширять пул воркеров без дублей выполнения.
- + InMemory-реализация даёт контрактные тесты без внешнего Valkey и демо на «чистом» стеке.
- - Ещё один stateful сервис в компоузе (Valkey), активен только в `llm`-профиле.
- - Формат событий — `v1-draft` (ADR-016): поля допускают мелкие правки до фиксации контракта.

## ADR-024: Атомарность COMMIT ограничена одним движком; разнородные пары — best-effort + компенсация

**Статус:** Draft (закрывает замечание A-2, `review_team.md:40-42`; бандл
`openspec/changes/architecture-atomic-commit/`)
**Контекст:** Инвариант L2-04 заявлял «атомарность COMMIT», но `CommitStage._write`
открывал две независимые транзакции (граф и вектор, `orchestrator.py`): между ними есть
окно частичного коммита. Вендор-независимое ядро (L1-02/L1-03, ADR-012/013) не может
«свести всё к одной Cypher-транзакции» для разнородных СУБД — общего транзакционного
координатора у них нет. Честный ответ — не притворяться атомарным, а декларировать
capability провайдера и поведение ядра по нему.

**Решение:**

1. **Capability-контракт** `consistency_capability()` у `GraphStoreProvider`/
   `VectorStoreProvider`: `"atomic" | "best_effort"` (дефолт `best_effort`).
   Плюс `engine_key()` — ключ движка/инстанса (ядро сравнивает только равенство пары).
2. **Атомарная пара** = обе оси `"atomic"` **и** общий `engine_key()` → обе оси пишутся
   **в одной транзакции движка** (для Neo4j-пары — один `session.begin_transaction()`
   через `atomic_batch()`; для InMemory-пары — вложенные `transaction()`-контексты
   единого процесса, общий откат). Классификация — автоматическая, по паре провайдеров.
3. **Любая другая пара — best_effort**: последовательный commit графа → вектора;
   при сбое второй оси граф компенсируется существующими операциями удаления
   (`delete_node` по id из плана записи, чанки; Source/Entity сохраняются), джоба
   завершается `failed` с пометкой «компенсировано»; повтор той же джобы идемпотентен
   (L2-06, регистр уже знает версию → no-op).
4. **Никакого 2PC** (распределённой транзакции): нет общего координатора, координация
   между движками не вводится.
5. **SSOT**: декларации capabilities в `infra/config/adapters.yaml` и `namespaces.yaml`
   (namespace `adapters`), контракт закрыт `tests/test_adapter_catalog_ssot.py`
   (декларация == `consistency_capability()` реализации).

**Последствия:**
- + L2-04 становится честным: атомарность ровно там, где её обеспечивает движок.
- + Разнородные пары (Neo4j + Qdrant и т.п.) получают явный best-effort + компенсацию
  вместо тихого «двух транзакций под видом атомарности».
- + Поведение ядра остаётся вендор-независимым: никакого Cypher в `orchestrator.py`.
- - Компенсированная джоба оставляет источник в реестре активным без чанков в хранилищах
  (оси согласованы, но query-слой не находит контент) — оператору видно `failed`,
  повторная загрузка с изменённым контентом перепишет оси.
- - Оператор обязан выбирать `atomic`, когда это критично (обе оси на одном инстансе
  Neo4j): автоматического объединения разнородных движков нет и не будет (отказ от 2PC).

## ADR-025: Semantic Cache на Valkey — TTL-инвалидация как допущение, режимы сброса

**Статус:** Accepted (2026-09-14; бандл `add-semantic-cache`, M3; порождён решением по свежести
`docs/prototype_requirements.md` §Веха 4-хвост, 2026-09-13; статус переведён из Draft после
закрытия замечаний команд ревью по fail-open, `clear()`/`stats()`, поле id)
**Проблема:** повторные семантически близкие запросы к Query-контуру гоняют полный цикл
retrieval + LLM (деньги/латентность). Кэш по embedding (cos-порог) закрывает повторы, но
требует политики свежести: данные обновляются при индексации, реестр документов версионится
(ADR-014), а query-слой в M3 не получает сигналов об изменениях.

**Три решения с одной целью:**

1. **TTL (реализовано)**: HASH `query:sc:<domain>` в Valkey/Redis, поле
   `sc:<sha256(repr(embedding))>` (полный digest, коллизионная перезапись исключена),
   payload JSON `{embedding,text,sources,ts}`.
   Записи с `now - ts > TTL` при сканировании не отдаются и HDEL-атся. Дефолт
   `SEMANTIC_CACHE_TTL_S=3600`; `0` = бессрочно (решение оператора). Косинусная
   близость ≥ `SEMANTIC_CACHE_THRESHOLD` (дефолт `0.85`, inrange отриц. нет).
   На сам HASH ставится EXPIRE = TTL при каждом `store()` (закрыто S4/T4: брошенный
   домен не держит ключ вечно; `0` = без EXPIRE). Соединение: `socket_timeout=2s`
   (fail-fast). **Fail-open:** сбой подключения/команды
   в `lookup` → miss (запрос идёт полным циклом), в `store` → no-op; кэш не роняет
   пользовательский запрос (закрыто замечание команд ревью R6-4/R6-7, S3).
2. **`clear()` (реализовано)**: SCAN (match `query:sc:*`) + DEL — полный сброс кэша без
   опоры на in-process счётчики; покрывает и записи, и meta-ключи счётчиков. `stats()`
   считает `entries` через HLEN (реальное состояние Redis), `hits`/`misses` — из HASH
   `query:sc:<domain>:meta` (shared-счётчики, HINCRBY; закрыто S2 ревью №7: переживают
   рестарт/несколько воркеров, никаких in-process накопителей).
   (закрыто R6-5, R6-8; добавлены тесты `test_redis_clear_removes_all_keys`,
   `test_redis_stats_uses_hlen`, `test_redis_shared_counters_persist_across_restart`).
3. **Epoch-bump (план, не реализуется в M3)**: пространство ключей `query:sc:<rev>:<domain>`;
   ревизия данных (Веха 4-хвост) при bump атомарно переводит запросы на новый префикс,
   старый кэш умирает по TTL сам. Отменяет ручные акты в пункте 2, но требует механизма
   доставки ревизии в query-контур — решение принято отложить до M4/M5.

**Не реализуется:** инвалидация по конкретным источникам (полный граф источников по
эмбеддингу в каждой записи), согласованность «как в индексе» (для неё нужен
cache-aside + инъекция обновлений из ingestion-контура). Внекэшный loop LLM не
маскируется: плохие ответы не складируются (см. `should_cache_text`).

**Последствия:**
- + Повторные запросы (cos ≥ порог) отдаются из Redis за миллисекунды: статусы
  `embedding` → `cache{hit:true}` → `done`, LLM не вызывается, `token` не шлётся.
- + Тривиальная операционная модель TTL+`clear()` без новой инфраструктуры поверх Valkey.
- + Сбой Valkey не роняет запросы: fail-open (lookup → miss, store → no-op), таймауты 2s.
- - Fail-open означает возврат полного цикла (retrieval + LLM) при сбое кэша — деградация
  цены/латентности вместо ошибки; попадаемость падает до 0 до восстановления Valkey.
- - Записи могут быть слегка устаревшими относительно индекса (до TTL) — гарантия
  «немедленной» актуализации становится задачей оператора (bump ревизии, пункт 3).
- - Двоякие границы порога/деменций на практике калибруются под домен (M4).

## ADR-026: Ревизия данных в query-контуре — гранулярность, источник, доставка (Веха 4-хвост)

**Статус:** Accepted, реализовано (2026-09-15; Веха 4-хвост, `docs/prototype_requirements.md` §Веха 4-хвост;
аналитика — `analitic/revision/data_revision_analytics.md`)
**Проблема:** семантический кэш живёт на TTL+`clear()` (ADR-025, допущение), у «актуального
контекста ответа» нет fingerprint-а данных, Eval (ADR-015) не может зафиксировать ревизию
знаний в срезе. Инвалидация по конкретным источникам и «как в индексе» — не реализуются
(ADR-025). Нужна ревизия данных домена в query-контуре.

**Три решения (зафиксировано):**

1. **Гранулярность — по-доменная.** У каждого домена своя `rev<domain>`. Кэш
   (`query:sc:<domain>`), профили/словари, ingestion и Eval-датасеты
   (`prototype/infra/eval/{domain}/`) уже по-доменные; мультидоменная переиндексация
   изолирована (апдейт `it` не сжигает кэш `legal`). Глобальная ревизия отклонена:
   ломает изоляцию доменов (L1-01) и размерность остального контура.
2. **Источник rev — fingerprint активного сета DocumentRegistry**:
   `rev<domain> = sha256(sorted((source_url, content_hash) активных документов домена))`.
    Идемпотентен (повторный INGEST того же `source_url` и `content_hash` = no-op,
    ADR-014 → fingerprint не меняется), честно отражает реальный набор источников
    (коллекции из 1..N книг на домен, разные URL/языки/переводы учитываются как
    отдельные пары),
   переиспользует существующие поля ADR-014 — **без новой параллельной модели ревизии**.
   Монотонный counter отклонён: не идемпотентен относительно no-op и не является
   отпечатком содержимого (нельзя сравнить «одинаковые ли данные» у двух срезов).
3. **Доставка — `GET /api/v1/ingestion/revision?domain=` + поллер в worker.**
   Ingestion-контур отдаёт `{"revision": <sha256>, "updated_at": ...}` (X-API-Key, L5-01);
   query-воркер опрашивает по аналогии с `_topology_rebuilder`
   (`TOPOLOGY_POLL_INTERVAL`), задержка = интервал поллинга. Паттерн уже доказан,
   работает в inmemory-режиме, retry/доставка бесплатны. Redis pub/sub отклонён:
   второй транспорт, потеря событий при перезапуске, не работает в inmemory.

**Ключ кэша:** epoch-bump префикс в поле HASH — пространство ключей `query:sc:<rev>:<domain>`;
при bump запросы атомарно переходят на новый префикс, старый кэш умирает по TTL сам
(planned upgrade из ADR-025, п.3).

**Последствия:**
- + У ответа появляется fingerprint «по каким данным собран» → воспроизводимый Eval-срез
  (ADR-015) и явный bounded staleness (L2-07, «ответ не старее ревизии R»).
- + Ручные акты оператора `clear()` для значимых индексаций больше не нужны.
- + Нет новой инфраструктуры поверх Valkey/очереди: переиспользованы ADR-014 поля
  (content_hash/status) и паттерн поллера топологии.
- - Допущение ADR-025 «записи устаревают до TTL» сужается: свежесть гарантируется
  до момента смены ревизии (задержка ≤ интервал поллинга).
- - Ревизия по-доменная → поллер должен знать список доменов или опрашивать по домену.

**Затрагиваемые компоненты:** `DocumentRegistry` (+`data_revision(domain)`), ingestion API
(+endpoint), query worker (поллер), `SemanticCache` ABC/ключи, `QueryPipeline` (прокидывание
rev), M4-Eval (фиксация rev знаний в срезе).

## ADR-027: Переквалификация GPU-гейтинга — инвариант → ограничение среды прототипа

**Статус:** Accepted (2026-09-15; порождено системным ревью №7, находки S10/S9д; принято
решением по правилу п.6 шапки `invariants.md` — изменение инвариантов отдельным решением)
**Проблема:** L4-01 формулировал «эмбеддинги и LLM разделяют одну видеокарту → поочерёдный
инференс через гейтинг» как платформенный инвариант. По определению шапки invariants.md
инвариант обязан выполняться при любых изменениях стека, но совместное размещение моделей —
свойство стенда прототипа (одна RTX 2070 Super 8 ГБ): LLM выносится на внешний
OpenAI-совместимый endpoint (ADR-022) без изменения кода ядра, а стадия «GPU 2 (параллельно)»
из docs/06 §4 формально нарушала инвариант.

**Решение:**
1. Инвариантом остаётся только контрактный уровень: доступ к инференсу исключительно через
   `LLMInference` (уже гарантирован L1-02); ядро локация-агностично.
2. «Одна видеокарта → гейтинг по фазам (композ-профили)» переносится в прототипные доки как
   ограничение среды: `prototype_requirements.md` §3 (целевое железо), `demo_runbook.md`
   §GPU-гейтинг (операционная процедура), `docs/06` §5 риск №1 (уже есть). Дублирование
   в `invariants.md` снимается.
3. Триггерная модель масштабирования — `docs/06` §4 (см. handoff
   2026-09-14_team-2_patch-docs06-scaling-triggers.md): стадии роста не требуют изменения
   инвариантов, т.к. смена размещения LLM — это конфигурация адаптера (`namespace: adapters.llm`).

**Последствия:**
- + Таблица стадий роста (`docs/06` §4) перестаёт конфликтовать с инвариантами.
- + Вынос LLM на отдельный хост/GPU перестаёт быть «нарушением» и становится
  конфигурационной сменой (T2 из ревью №7 §2.1).
- - Из перечня инвариантов уходит одно «дешёвое для проверки» утверждение; проверка гейтинга
  остаётся в приёмке прототипа (runbook), а не в контрактных тестах.

**Затрагиваемые компоненты:** `docs/invariants.md` (L4-01), `docs/06_operations_and_risks.md`
(§4 примечание к стадии «Рост: GPU 2», §5 риск №1), `docs/history.md`. Код и композ-профили
не меняются — гейтинг остаётся рабочей процедурой прототипа.

## ADR-028: Политика конкурентной записи COMMIT — retry transient + детерминированный порядок

**Статус:** Draft (2026-09-19; порождено находкой полного eval M5 —
`Neo.TransientError.Transaction.DeadlockDetected` при `INGEST_MAX_CONCURRENT=2`;
бандл `concurrent-ingest-write-policy`, стадии S1→S2 закрыты, S3 — очередь ingestion)

**Проблема:** концепция не декларировала, как конкурентные ingestion-джобы пишут в общий
граф: при параллельном `MERGE` общих сущностей Neo4j фиксирует deadlock-циклы
(transient-класс драйвера). Сигнал — deadlock-находка M5; временным обходом S1 стало
`INGEST_MAX_CONCURRENT=1` (ограничение среды, паттерн ADR-027), что не является
платформенным решением.

**Решение:**
1. `_write_atomic`, `_write_best_effort`, тело `soft_delete_source` оборачиваются в
   `_with_commit_retry(stores, fn)`: `N_RETRY_COMMIT` — число **повторов** после первой
   попытки (дефолт 3, всего `N_RETRY_COMMIT + 1`; `0` — ровно одна попытка); backoff
   `0.2*2^i + jitter(0.1)`; env-параметры (`N_RETRY_COMMIT`, `RETRY_BASE_S`, `RETRY_JITTER_S`)
   валидируются при старте fail-fast (отрицательные/нечисловые — ошибка конфигурации).
2. Transient-классификация — через декларации провайдеров (`transient_aware()` +
   `is_transient(exc)`, включая развёртку `__cause__`; контракт L1-02). Повтор только если
   transient; non-transient — немедленный fail.
3. **Компенсация best_effort — после исчерпания повторов, не на первом transient** (UC12-02);
   причина ошибки сохраняется цепочкой `__cause__` (`raise ... from exc`) — обёртка
   `CommitStageError` не ломает классификацию.
4. **Детерминированный порядок записи** (UC12-07): `CommitStage._write` и `_upsert_nodes`/
   `_upsert_edges` (neo4j.py) сортируют `nodes`/`edges` по контрактным ключам
   (`node_id`, `(from_id, to_id, type)`). Порядок **снижает вероятность** deadlock-циклов,
   но не исключает их — retry остаётся обязательным (см. L3-06).
5. **Согласованность soft-delete** (§2а спеки, UC12-06): при окончательном отказе удаления
   в хранилищах реестр возвращается в `active` компенсирующим действием
   `registry.rollback_soft_delete`; повторный вызов после частичного удаления безопасен
   (идемпотентность L2-06).
6. Границы: **без 2PC** (ADR-024), без single-writer на S2; очередь ingestion (S3,
   `docs/06` §4) — N воркеров пишут по правилам этого решения.

**Последствия:**
- + Конкурентная запись становится честно наблюдаемой и восстанавливаемой: транзиентные
  deadlock/сеть ретраятся с backoff, компенсация — только после исчерпания повторов.
- + Soft-delete не оставляет рассинхрон «реестр deleted при живых данных осей».
- + Инвариант L3-06 фиксирует контракт без ложного заявления «deadlock невозможен».
- - Нагрузка на движок при повторах (ограничена `N_RETRY_COMMIT`, работаем с транзиентами).
- - Формально не закрывает все источники deadlock (другие операции движка) — не заявляем.

**Затрагиваемые компоненты:** `retrieval/adapters/{base,neo4j,inmemory}.py` (контракт
transient), `ingestion_service/pipeline/orchestrator.py` (retry-loop, сортировка,
компенсации), `ingestion_service/storage/registry.py` (`rollback_soft_delete`),
`tests/test_{commit_stage,retry_compensation,transient_classification}.py`,
`docs/invariants.md` (L3-06), `docs/06_operations_and_risks.md` (§5 риск №7), `docs/history.md`
(Этап 14), `openspec/changes/concurrent-ingest-write-policy/*`.

## ADR-029: Методика эксперимента «вклад графа» (Draft)

**Статус:** Draft (2026-09-22; typed-ontology часть superseded corrective change
`add-lightweight-context-graph`, ADR-031; baseline/target eval сохраняются)

**Контекст:** ADR-015 фиксирует *что* мерим (recall/groundedness/coverage) и валютное
правило гейта, но не *как атрибутировать* прирост компоненту. Известные пробелы:
(1) абсолютный recall не доказывает, что прирост дал граф; (2) вопросы, где граф не нужен
для полноты, размывают агрегат шумом; (3) прогон без артефактов не перепроверяем —
парность веток восстанавливается по памяти; (4) полный прогон с LLM-судьёй дорогой,
блокирует быстрый итерационный цикл.

**Решение:**
1. **Парный прогон как операция** (§3.1 design.md): ветки отличаются **только** фактором
   `graph_enabled`, на **одной ревизии** (`revision_fingerprint` в манифестах совпадает).
   Правило парности: манифесты различаются не более чем в одном поле фактора
   (`mode`/`graph_enabled`); больше → «прогоны не парные», разность метрик не является
   вкладом компонента, вердикт `invalid` (`run_eval.py --compare-with`).
2. **Критерий необходимости:** вклад графа измеряется **только на срезе**
   `golden_graph_evidence=true`: метрики `necessity` (доля golden-источников, принесённых
   только графовой осью), `delta_recall` (recall_hybrid − recall_vector) и per-axis recall
   (`recall_graph`/`recall_vector`) + `evidence_recall_graph`. Вопросы вне среза
   (`mode="not_measured"`) не интерпретируются — это шум для вопроса «нужен ли граф».
3. **Запрет интерпретации без осей:** `done.sources` несёт аддитивное поле
   `axis ∈ {graph, vector}` (формат ADR-016 обратно совместим); без атрибуции оси вклад
   графа измерим нулём, поэтому журнал пар обязан включать `axis` у каждого источника.
4. **Judge-less как fast-loop:** послойные артефакты (`<out>/run_manifest.json`,
   `<out>/qa_log.jsonl`, `<out>/lift_report.json`+`.md`) обязательны **во всех режимах** —
   включая `--no-judge` и `--retrieval-only`; их полнота **не зависит от наличия судьи**
   (инвариант L5-05). Без судьи groundedness/coverage = `n/a` и не участвуют в вердикте
   гейта (`verdict="n/a"`). Retrieval-уровень и атрибуция осей считаются **всегда**, поэтому
   fast-loop не зависит от дорогого судьи. Диагностическая трасса `<out>/trace.jsonl`
   (слой 4) — по требованию (`--trace`) и не подменяет слои 1–3.

**Последствия:**
- + Прогон оставляет перепроверяемый след; парность доказуема по файлам, а не по памяти.
- + Быстрый итерационный цикл (retrieval-only / no-judge) без LLM-судьи сохраняет все
  артефакты и уровни 1 и 3 (recall, атрибуция осей).
- + Вклад графа измеряем честно: necessity + per-axis recall на размеченном срезе.
- - Требует ручной разметки `golden_graph_evidence`/`evidence_policy=graph_required`
  (фиксируется как регулярная задача, ADR-015).
- - Выводы об ограниченности: измеряется только срез `graph_required`; остальные вопросы
  в этот эксперимент не попадают.
- - Draft: live-приёмка на живом Neo4j-стеке (стадия 7) ещё не выполнена; температура судьи
  в `build_judge` не детерминирована — учитывается в отчёте (пункт «условия прогона»).

**Затрагиваемые компоненты:** `infra/eval/run_eval.py` (классы артефактов, правила парности,
режимы `--no-judge`/`--retrieval-only`/`--trace`/`--compare-with`), `src/graphrag_proto/eval/
metrics.py` (`graph_contribution`, `lift_report` c verdict n/a), `src/graphrag_proto/retrieval/
pipeline.py` (`done.sources[].axis`, `done["trace"]`), `infra/eval/{it}/questions{,_graph}.jsonl`,
`docs/test_plan.md` (§5–§6), `docs/invariants.md` (L5-05), `docs/history.md` (Этап 15),
`openspec/changes/eval-graph-contribution-experiment/*`.

## ADR-030: Жизненный цикл graph/vector-проекций (Draft)

**Статус:** Draft (2026-09-25; решение о переносе полной реализации на M6-Growth)

**Контекст:** graph и vector — независимые адаптеры; Neo4j является выбранным backend
прототипа, но не архитектурной обязательностью. Для роста системы изменение профиля,
онтологии, chunker или embedding должно перестраивать соответствующие проекции без
смешивания поколений. В прототипе COMMIT синхронный, а registry отслеживает только
`content_hash`; автоматический reindex после смены профиля не реализован.

**Решение:**
1. Полноценные transactional outbox, dual-generation и миграция проекций отложены на
   **M6-Growth / pre-connectors** — после текущего M4-эксперимента и до подключения
   внешних коннекторов.
2. До этой стадии профиль/ontology и pipeline-контракт загруженного корпуса считаются
   неизменными; повтор того же `content_hash` остаётся no-op. Автоматическая смена
   профиля не объявляется поддерживаемой операцией ingestion.
3. На M6-Growth вводятся независимые `vector_fingerprint` и `graph_fingerprint`, outbox
   проекций, построение новой generation рядом со старой и переключение active manifest
   только после успешной проверки. Запросы используют одну зафиксированную revision.
4. Это решение не относится к optional graph experiment: baseline и experiment должны
   использовать одну ревизию, chunking/embedding-контракт и отличаться только включением
   готовой graph projection.

**Последствия:**
- + Текущий prototype остаётся простым и пригодным для проверки ускорения graph-осью.
- + Сохраняется независимость graph/vector backend и отсутствие фиктивного общего ACID.
- - Онлайн-изменение ingestion-профиля до M6-Growth требует ручного clean rebuild и не
  входит в поддерживаемый lifecycle.
- - До M6-Growth нельзя утверждать наличие автоматической миграции проекций или безопасного
  обновления индекса при смене ontology.

**Затрагиваемые компоненты:** `openspec/changes/add-lightweight-context-graph/*`,
`docs/prototype_requirements.md`, `docs/06_operations_and_risks.md`, `docs/operations_requirements.md`,
`docs/history.md` (Этап 15).

## ADR-031: Primitive ingest и lightweight context graph

**Статус:** Accepted (2026-09-25; corrective change `add-lightweight-context-graph`)

**Контекст:** текущий typed-ontology эксперимент усложняет primitive ingest и ограничивает
динамические tags. Цель проекта — измерить вклад лёгкой графовой связности, а не внедрить
тяжёлую академическую ontology или Neo4j schema ownership.

**Решение:**
1. Document ingest, chunking, embeddings и registry не требуют profile, LLM, tags или links.
2. Ручные tags/links и AI suggestions — optional enrichment одного dynamic graph; сохраняются
   `tag_id`, `canonical_name`, aliases, origin, confidence и provenance. Projection может строиться
   inline после vector commit или отдельным offline replay.
3. `tag_id` стабилен в пределах domain; multilingual aliases разрешаются через optional glossary/AI,
   неоднозначные кандидаты не объединяются молча.
4. `_validate_ontology`, `ensure_schema`, typed labels, edge whitelist и runtime Neo4j constraints
   удаляются из ingest path. `Source`/`Chunk` остаются technical anchors.
5. Vector-only baseline выполняет vector search с metadata и не вызывает graph. Optional graph
   experiment после готовой inline/offline projection делает bounded expansion по chunk
   `context_ids` и применяет boost; unavailable/stale graph даёт degraded baseline.

**Последствия:**
- + Прототип соответствует optional user/AI workflow и позволяет построить graph experiment
  во время ingest или офлайн, не блокируя vector-only MVP.
- + Мультиязычные aliases и custom context properties не требуют heavy ontology migration.
- - Старые typed-узлы/constraints в существующей Neo4j базе не удаляются автоматически.
- - До M6-Growth изменение профиля не запускает автоматическую reindex проекции.
- - Пока projection не готова, graph experiment нельзя считать доказанным.

**Затрагиваемые компоненты:** `openspec/changes/add-lightweight-context-graph/*`,
`CONCEPT.md`, `docs/01`, `docs/02`, `docs/03`, `docs/data_model.md`, `docs/glossary.md`,
`docs/invariants.md`, `prototype/src/graphrag_proto/ingestion_service/*`,
`prototype/src/graphrag_proto/retrieval/*`.

## ADR-032: Гранулярность сброса LLM-слоя и различение причин деградации

**Статус:** Draft (заведён 2026-09-27; решение по гранулярности **не принято**)
**Контекст (на момент заведения):** optional-экстракция в ingestion работает в режиме
`optional_failure=True` (`orchestrator.ExtractStage`, прод собирает этот режим в
`app.py`). Тогда при **любом** исключении `ctx.entities` и `ctx.entity_edges`
очищались, ставился `enrichment_degraded`, и пайплайн уходил в детерминированный
fallback. Документация (ADR-031 §2) требует, чтобы optional enrichment не блокировал
документ, — это выполняется. Но граница отказа не совпадала с границей потери.

**Что с тех пор изменилось в коде (для читателя этого ADR, а не для журнала):** ловится
теперь ровно `ExtractionConfigError` и `ExtractionModelError`, дефект кода падает; флаг
потери ставится по факту исчезнувших записей; потеря инвалидирует вердикт прогона. Сброс
слоя целиком **остался** — предмет этого ADR не изменился, изменилось только то, что
вокруг него измеряется. Ниже «любое исключение» и «срабатывание пути сброса» описывают
состояние на момент заведения.

**Решено сейчас (не ждёт продолжения ADR):**

1. **Поведение неприемлемо при проектировании промышленного ingest.** Потеря необратима:
   повторная загрузка того же `content_hash` — no-op (`CommitStage.try_noop`), поэтому
   простая перезагрузка файла не перезапустит экстракцию. Одна транзиентная ошибка LLM
   навсегда оставляет документ без LLM-слоя. Зафиксировано в риске №7
   `docs/06_operations_and_risks.md` и комментарием в коде на месте сброса, чтобы
   ограничение не исчезло вместе с этим ADR.
2. **Оба факта измеряются раздельно и одним каналом.** `enrichment_degraded` (документ
   обработан хуже) и `llm_layer_dropped` (потерян слой) приходят полем `signals` в
   ответе джобы, а не текстом сообщения. Причина деградации остаётся текстом в message
   стадии — ей больше негде жить, но счётчики от неё не зависят.
3. **Причины разведены поимённо (реализовано 2026-09-27).** `ExtractionConfigError`
   (наш конфиг/профиль) и `ExtractionModelError` (модель, адаптер, форма ответа) больше не
   сводятся в один флаг: причина попадает в `enrichment.cause` как имя
   (`profile_unavailable` / `profile_invalid` / `model_error`). Широкий `except Exception`
   в `ExtractStage` убран: дефект нашего кода теперь падает громко вместо деградации,
   которая выглядела бы как «модель не справилась».
   **Позднее уточнено (2026-09-27):** транспорт до модели разведён отдельно —
   `model_unavailable` / `model_timeout` / `model_http_error`, потому что «поднять стенд» и
   «поправить промпт» — разные ремонты, а раньше это было одно число. Типы ошибок адаптера
   и порядок `except` (`TimeoutError` перед `OSError`) — часть решения, а не деталь
   реализации; классификация идёт по цепочке `__cause__`.
4. **`llm_layer_dropped` теперь означает «факты исчезли», а не «сработал сброс».** Размер
   потери считается в момент сброса и пишется числами (`lost_entities`/`lost_edges` в
   `job_enrichment`); сброс до первого ответа модели теряет ноль и флага не ставит.
   Прежнее поведение было верхней границей и завышало потерю.
5. **Объём LLM-слоя пишется на каждой джобе, прошедшей EXTRACT** (`llm_records`,
   `llm_edges`), потому что это знаменатель для «записей на документ». Знаменатель
   ограничен джобами, где стадия EXTRACT фактически выполнялась (свидетель — `job_stages`),
   и при нулевом знаменателе доля не выводится вовсе, вместо `0%`.
6. **Промпт запрещает модели `tag_id`** (`domain_profile.it.yaml`): идентичность
   считает платформа (L1-05), поле не восстанавливается из текста.
7. **Смещение измеряемо, и прогон с потерей слоя не получает `pass`** (2026-09-27).
   `run_eval.build_ingest_quality` даёт `lift_report.ingest_quality.loss`, и
   `metrics.build_lift_report` ставит `verdict = "invalid"` с названной причиной в
   `verdict_reasons`. Проверяются обе стороны пары: потеря в baseline смещает базу
   сравнения так же, как потеря в target. Основание — смещение одностороннее (пропавшие
   факты нельзя ни найти, ни вспомнить), поэтому недооценка оси гарантирована, и «pass» по
   таким числам утверждал бы о системе то, чего измерение не проверяло. Деградация **без
   потери** вердикт не инвалидирует. Контракт — `docs/06_operations_and_risks.md` §2.2.
   Побочный эффект: первая же настоящая цифра по потере получается только вместе с
   решением, читать её как «сколько стоит починка» по-прежнему рано — потеря по-прежнему
   сбрасывается целиком (п. «Не решено»).

**Не решено (гранулярность):** потерян весь LLM-слой документа вместе с `entity_edges`,
то есть теряются и узлы-якоря, и сами гипотезы связей. Это четвёртый, неназванный
вариант рядом с «отбросить одно ребро / карантин / автослияние по порогу», и он грубее
любого из трёх.

| Вариант | Сохраняем | Цена |
|---|---|---|
| сбросить слой (сейчас) | предсказуемость: нет полу-состояний | теряем всё; необратимо |
| отбросить одно ребро | чистоту графа | падает recall; нужна гранулярная обработка |
| карантин ребра | и чистоту, и связь | ревью-путь и его инфраструктура |
| автослияние по порогу | много связей | ложные рёбра; порог надо мерить |

**Порядок: сначала измерить, потом решить.** Инкременты стоят в точках выставления
флагов. Первый прогон даст `llm_layer_dropped_documents`; **ноль означает, что вопрос
отпадает**, и это лучший исход — решение выносится числом, а не спором.

**Точность счётчика (устарело, заменено п.4):** прежнее `llm_layer_dropped` означало «путь
сброса отработал», а не «потеряно ровно столько-то». Теперь флаг ставится по факту
исчезнувших записей, а размер потери идёт отдельными числами.

**Последствия:**
- + Поведение-прототип больше не выглядит продуманным хорошим решением: запрет записан
  в реестре рисков и в коде, независимо от судьбы этого ADR.
- + Счётчик потерь не зависит от формата сообщения, а два факта не смешаны в одном числе.
- + Дефект кода больше не маскируется под сбой модели; стоимость потери известна числом.
- - До решения сохраняется риск необратимой потери на каждом прогоне, где сработал сброс
  с непустым слоем.
- - Отдельная работа, не сделанная: различать причины деградации (ошибка модели, таймаут
  LLM, дефект собственного резолва) — теперь сделано, но не различия «сбой адаптера» и
  «сбой модели» внутри `ExtractionModelError`: оба приходят одним именем.

**Затрагиваемые компоненты:** `prototype/src/graphrag_proto/ingestion_service/*`,
`prototype/src/graphrag_proto/ingestion_service/storage/registry.py`,
`prototype/infra/eval/run_eval.py`, `docs/06_operations_and_risks.md` §2 и §5.

## ADR-033: Точки роста фиксируются как названные швы, без заготовок в коде

**Статус:** Accepted (перенесено из `CONCEPT.md` 2026-09-28; текст не менялся, кроме ссылок)
**Контекст:** Проект изначально закладывался «как в бою, но без оверинжиниринга». ADR-001
уже ввёл нужный приём: вендоронезависимость через `GraphStoreProvider` / `VectorStoreProvider`
и отложенную фазу с явным порогом («>1M чанков → Qdrant»). Развитие обнаружило, что этот приём
применён к хранению, но не к трём другим осям, и что «подготовить точку роста» в коде —
это то, что уже однажды привело к потере (бандл read-time ключей: конфиг без потребителя).

Обоснования: четыре золотых сигнала (latency/traffic/errors/saturation) из *Site Reliability
Engineering*, Google, 2016; RED (Rate/Errors/Duration) для сервисов; конвенции именования
Prometheus (`_total` для счётчиков, `_seconds` для длительностей, базовая единица в имени).
Разделение «emit против store» — суждение автора ADR, не заимствованная практика.

**Решение:** Три оси получают названный шов и явный триггер. Кода на этот этап не пишется.

1. **Транспорт событий джоб.** Шов — сторона записи `JobStore` (`update_stage`, `finish`,
   `note_stage`): это события, и именно они пойдут в транспорт, если он появится. Сторона
   чтения (`stages`, `is_cancelled`) швом **не** является: это запрос о состоянии, который
   лог доставки не отвечает в принципе, ему нужна отдельная проекция состояния. Следствие:
   замена SQLite на брокер — это **добавление транспорта**, а не подмена класса, и
   «переписать проект» ей не требуется.
   *Триггер:* нужен второй потребитель событий ингеста, либо джобы должны переживать потерю
   хоста с реплеем.
2. **Эмиссия метрик.** Шов — точка записи результата: значение метрики эмитится там, где оно
   уже вычислено, а не извлекается потом из БД. Правило: **данные, которые лежат только в
   SQLite, недоступны ни Prometheus, ни Забиксу** — их придётся переделывать, тогда как
   эмит — это конфигурация. Контракт имён уже задан в `docs/06_operations_and_risks.md` §2.
   *Триггер:* первый вопрос «почему ингест медленный», на который нужно ответить вне
   eval-прогона. (Он фактически уже возникает: таймаут ожидания не даёт увидеть, где встало.)
3. **Перенос обвязки с PowerShell.** Скрипты запуска написаны на PowerShell, что расходится
   с требованием «скрипты работают на любой системе». Решающий довод — тестируемость:
   PowerShell-обвязку **невозможно покрыть тестами by construction**, поэтому дефект
   передачи аргументов ждал прогона на стенде; скрипт на Python проверяется обычным pytest
   и ловится мгновенно.
   *Триггер:* следующая домашка, где скрипт запуска понадобится на другой ОС.

**Известная зависимость для п. 2 — закрыта 2026-09-28.** Запись утверждала, что метрика
`graphrag_ingestion_duration_seconds{stage, domain}` прописана, но данных для неё нет, и
предлагала `duration_ms` на стадию. Данные появились: `job_stage_durations` измеряет
длительность в момент перехода, а не восстанавливает её из перезаписанных `ts`
(см. `docs/06_operations_and_risks.md` §2.1, ADR-014). **Потребитель метрик при этом
по-прежнему отсутствует** — `prometheus_client` не подключён, `/metrics` не выставлен, поэтому
п. 2 не исполнён: данные лежат только в SQLite, то есть ровно то, чего правило п. 2 запрещает.

**Последствия:**
- + Три точки рота описаны и не потеряны; у каждой есть триггер, а не только намерение.
- + Стоимость «подготовки» — текст, а не код: абстракции не появляются и не требуют поддержки.
- + Появляется аргумент за уход с PowerShell, не основанный на вкусе, а на тестируемости.
- - Транспорт, если он понадобится, придётся добавлять вместе с проекцией состояния, а не
  «переключить одну строку»; решение зафиксировано заранее, чтобы это не было сюрпризом.
- - Метрики по стадиям не появятся, пока не будет `/metrics`; данные есть, потребителя нет.

## ADR-034: Дисциплина точки роста — шов, а не заготовка

**Статус:** Accepted (перенесено из `CONCEPT.md` 2026-09-28; текст не менялся, кроме ссылок)
**Контекст:** ADR-033 вводит точки роста. Без правил ведения такой реестр деградирует двумя
способами: запись либо не появляется вовремя, либо превращается в отговорку, которой откладывают
баги. Оба исхода уже наблюдались в проекте.

Обоснование: правило «плагин при двух реализациях, а не при одной» — общий опыт проектирования
расширяемых систем, а не заимствованный источник. Категоризация находок как «дефект / ограничение
измерения / точка роста» — суждение автора.

**Решение:**

1. **Плагин — при двух реализациях, не при одной.** Одна реализация обслуживается функцией.
   Плагинная механика до появления второй реализации — это поддержка пустой инфраструктуры.
2. **У каждой точки роста есть триггер и kill-критерий.** Триггер отвечает «когда строить»;
   без kill-критерия триггер может быть выполнен по плохой причине («мы растём»), и работа
   всё равно случится.
3. **Категоризация находок.** «Точка роста» — проектное намерение, живёт в ADR и
   `docs/06_operations_and_risks.md`. «Дефект» — сломанный код, чинится сразу: «это же точка
   роста» аргументом не является. «Ограничение измерения» — данные есть, но не той точности;
   мешает интерпретации, ничего не ломает.
4. **Личный рабочий фильтр:** «это понадобится в реальных условиях?» — надёжнее, чем
   «это боевая практика?». Первое отсекает cargo cult автоматически, второе — нет.
   Позиция проекта: «как в продакшене, но без оверинжиниринга».

**Последствия:**
- + Реестр точек роста остаётся проверяемым: у каждой записи есть проверяемое условие.
- + Дефекты перестают маскироваться под «точку роста».
- + Фильтр из п. 4 — сознательный и одинаковый во всех домашках, а не интуитивный.
- - Требует дисциплины: триггер без kill-критерия придётся дописывать, иначе п. 2 выродится
  в декларацию.

### Corrective note 2026-09-27: четвёртая категория — нерешённый продуктовый выбор

**Статус ADR не меняется: Accepted.** Ниже — дополнение к п. 3, а не замена.

П. 3 перечисляет три категории: точка роста, дефект, ограничение измерения. Их
недостаточно для находки, придуманной 2026-09-26 про `tag_id`
(`Ingest/analitic/node_identity_who_owns_tag_id.md`): рассуждение шло от кода и пришло
к двум противоположным ответам — «инвариант L2-01 требует стабильный `tag_id`» и
«профиль объявляет `unique_key: canonical_name`».

**Дополнение к п. 3 — четвёртая категория:**

> **Нерешённый продуктовый выбор** — расхождение между двумя артефактами проекта, где
> каждая сторона по отдельности согласована, а вместе они задают разное поведение, и
> правильного ответа нет без решения владельца. Лечится не кодом, а фиксацией выбора.
> До решения категория «дефект» к находке **не применяется**: назначение «дефект»
> санкционирует правку, а правка здесь выбирает сторону конфликта молча.

**Правило, обязательное для любой категории:** находка называет артефакт **поимённо и
цитатой**. Формулировка «инвариант говорит X» берётся из документа, а не из имён
функций рядом с ним.

**Как проверялось на самой себе, 2026-09-27.** Категория пригодилась, но применять её
следовало не по памяти, а после чтения `docs/invariants.md`. Прочтённый `L1-05` гласит:

> Детерминированность критичных шагов (tag identity, dedup policy, context assembly,
> bounded expansion, вытеснение) обеспечивается Python-кодом; LLM допускается только на
> optional enrichment и пограничных предложениях

`tag identity` назван прямо. Значит приоритет ответа модели в `_context_node_id` был
**нарушением L1-05**, то есть находка обычный дефект, а четвёртая категория к ней не
относится. Первая формулировка («документация говорит, что идентичность задаёт canonical
key») была ложной; вторая, зеркальная («запрет сломает L2-01»), оказалась ложной тоже:
L2-01 требует **существования и стабильности** `tag_id`, а не его происхождения, и
вычисленный `tag:{domain}:{_identity_key(canonical_name)}` этому требованию
удовлетворяет. Обе ошибки — одна и та же форма: утверждение о документе, выведенное не
из документа.

Дефект устранён 2026-09-27 (коммит `5b25363`): `tag_id` из ответа модели не копируется в
сущность, идентичность считает платформенный код по `canonical_name`, ручной `tag_id`
сохранён, запрет внесён и в промпт. Проверяющие тесты — в `prototype/tests/test_typed_graph.py`.
Прошедшее время здесь существенно: пока дефект был жив, категорию «нерешённый продуктовый
выбор» назначить было нельзя, и этот текст нельзя читать как описание текущего кода.

**Что из этого следует для п. 3.** Категория «нерешённый продуктовый выбор» реальна и
нужна, но её **нельзя назначать по признаку «артефакты расходятся»** — расхождение
инварианта с кодом чаще оказывается дефектом, и решается чтением инварианта, а не
созданием новой категории. Назначение категории без цитаты — та же ошибка, что и
назначение «дефекта» без цитаты.

## ADR-035: Требования приводятся в соответствие с решениями и кодом

**Статус:** Accepted
**Контекст:** `docs/operations_requirements.md` — нормативный документ: следующая сессия
читает его как указание, а не как описание. Ревизия 2026-09-28 проверила каждое его
утверждение по трём источникам — код, этот журнал, `CONCEPT.md` — и нашла одиннадцать
расхождений. Из них **семь меняли смысл требования**: четыре утверждали механизмы, которых
в проекте нет, одно прямо противоречило действующей политике версий, одно пропускало
состояние в backup, одно предлагало метод, который не может работать по построению.

| Прежнее утверждение | Почему неверно | Что теперь в требованиях |
|---|---|---|
| §2: хранить версии «старее N версий или старше T дней» | прямо противоречило политике «только актуально» (ADR-014, третья корректирующая запись) | §2 переписан датированной поправкой: архив не хранится, при перезагрузке документа его версии, векторы и структурные рёбра удаляются |
| §3: при расхождении подписи профиля нужна переиндексация | механизма нет, и §6 того же файла это признавал | §3: расхождение **обнаруживается** и не исправляется; починка отнесена в заделку |
| §5: смена промпта — способ A/B на уже загруженном корпусе | без переиндексации сравниваются два одинаковых графа, то есть метод заведомо не различает варианты | §5: названо требование пересборки знаний; A/B возможен только на пересобранном корпусе |
| §4: журнал операторских действий с разграничением доступа | нет ни журнала, ни разграничения; есть in-memory список событий проекции | §4 описано фактическое состояние, требование оставлено открытым |
| §4: деактивация ключа через Config API | такого API нет, при этом `docs/security.md` отсылал к требованиям, замыкаясь в круг | §4: механизм помечен несуществующим; круговая ссылка разорвана |
| §4: правила алертинга как действующие | `/metrics` не выставлен, счётчиков нет, потребителя Prometheus нет | §4: перечень назван **контрактом** — что появится вместе с `/metrics` |
| §1: backup без БД состояния проекций | потеря состояния при restore | §1: добавлена строка `projection.db` |

**Решение.** Требования приводятся в соответствие с кодом и принятыми решениями, а
отсутствующие механизмы **называются отсутствующими**, а не описываются как работающие.
Формулировка «механизма нет» в нормативном документе полезнее, чем правдоподобное
описание: первое останавливает, второе уводит в реализацию несуществующего.

**Что это решение НЕ делает.** Оно не создаёт ни одного из перечисленных механизмов и не
переносит их в задолженность молча. Каждый отсутствующий механизм — это отдельная работа с
владельцем: переиндексация, operator audit log, Config API для ротации ключей, `/metrics`
и его потребитель. Таблица соответствий и что именно требует решения — в
`docs/operations_requirements.md` §8.1–8.2.

**Последствия:**
- + Документ требований перестал быть источником противоположных указаний: сессия, читая
  §2, получает «удаляем», а не «храним N версий»
- + Расхождение требований с кодом больше не может накапливаться незамеченным — §8
  содержит разбор с датой и ссылками на источники
- + Круговая ссылка `security.md` → требования → Config API разорвана явным «такого API нет»
- - Часть требований остаётся невыполненной, и это теперь видно в самом документе, а не
  обнаруживается при эксплуатации
- - Правки нормативного текста требуют ревью владельца: автоматическая сверка «код vs
  документ» невозможна, документ проверяется чтением

**Ключевое из этого решения.** Требование, противоречащее коду, опаснее отсутствующего
требования: отсутствие молчит, противоречие даёт следующей сессии ложное основание для
решения. Поэтому расхождение фиксируется явно и датированно, даже когда починка отложена.

**Не входит в это решение.** Сведение двух серий ADR (ADR-033/ADR-034) и проверка
ADR-006/ADR-008 по коду — отдельная работа, оформленная корректирующими записями к
соответствующим ADR и §8.1–8.2 требований.

## ADR-036: Глубина обхода — параметр запроса, потолок 6, ветвление считается по узлу

**Статус:** Accepted (2026-09-29; решение владельца)
**Решение владельца:** глубина обхода приходит запросом, а не живёт в профиле как
константа. Для прототипа — ползунок 1..6, дефолт 3 (середина диапазона), с пояснением
во всплывающей подсказке. В следующих итерациях — пользовательские настройки окна
диалога в духе настроек opencode; до них прототипу хватает одного ползунка.

**Контекст.** Три расхождения, найденные при обсуждении, и все три — одного класса:
объявленное не равно сделанному.

1. `docs/01` §2 фиксирует партономию: цепочка переменной длины **4..6**, от дома до
   страны **пять** хопов, и там же сказано, что `retrieval.max_depth` как константа
   «неверен по форме» и должен стать параметром запроса. Код при этом держал
   `MAX_EXPANSION_DEPTH = 3`, то есть **потолок был ниже минимальной длины
   документированной цепочки**: вопрос «в чём содержится этот дом» и DAG с несколькими
   административными родителями были недостижимы по построению. Онтология обещала то,
   что код не мог отдать.
2. `max_fanout` читался из Config Service и в обоих адаптерах значил **разные вещи**:
   `inmemory.py` сбрасывал счётчик на каждом узле (не больше 8 соседей от каждого),
   `neo4j.py` считал по ключу `seed` (не больше 8 строк суммарно на стартовую точку).
   При глубине больше 1 второй вариант почти не давал эффекта: промежуточные узлы
   разветвлялись как угодно, и слайдер менял форму фронтира, а не объём ответа.
3. Ни профиль, ни запрос не задавали глубину — она целиком определялась кодовым
   фолбэком, то есть не была ничьим намерением.

**Решение.**

| Что | Значение | Почему так |
|---|---|---|
| Порядок разрешения | запрос → Config Service → профиль → кодовый фолбэк | запрос — единственное, что знает про конкретный вопрос |
| `MAX_EXPANSION_DEPTH` | 3 → **6** | покрывает максимум документированной цепочки (5 хопов); страховка от разворачивания сохраняется |
| `retrieval.max_depth` в профилях | **3** | середина диапазона; дефолт 3 партономию **не** открывает, и это названо явно |
| Кодовый фолбэк | 2 (без изменений) | профиль не загрузился — лучше меньше контекста, чем больше |
| Превышение потолка | зажим + объявление | не ошибка запроса; молчать нельзя, см. ниже |
| `max_fanout` | **по узлу** в обоих адаптерах | один параметр должен значить одно; счёт по seed делал глубину почти бесполезной |
| Потолок в UI | импортируется из кода | второе число в разметке — это снова расхождение |

**Почему зажим, а не отказ.** В проекте уже оба стиля, и в разных местаях: конвейер
зажимает и пишет `depth_clamped` в трассировку, а профиль с отрицательным значением
отвергается ошибкой. Для параметра запроса выбран зажим с объявлением
(`max_depth_effective`, `depth_clamped` в `effective_retrieval` и в трассировке
`graph_expansion`): ползунок физически не даст выйти за границу, значит отказ был бы
недостижимым шумом, а молчаливый зажим — это ровно тот класс лжи, который сегодня
вычищался трижды. Отказ остаётся только на негодном значении (не целое, меньше 1),
и проверяется он **до** эмбеддинга, чтобы ошибка не стоила обращения к модели.

**Побочное следствие, которое пришлось починить.** Тест
`test_expansion_depth_cap_is_identical_in_both_adapters` держал цепочку из 5 узлов при
потолке 3 и потому проходил на зажиме. После подъёма потолка до 6 цепочка стала короче
него, ограничителем перестал быть потолок — и тест стал бы проходить **даже с полностью
отключённым ограничением**, то есть проверял бы не то, что заявлял. Цепочка теперь
строится длиннее потолка, а длина проверяется утверждением, поэтому вырождение теста
больше не может пройти незаметно.

**Не входит в это решение.** Ползунок в `demo-ui` (отдельным заходом, границы берутся
из константы); полноценные пользовательские настройки окна диалога; E2E-сценарий на
обход в глубину как отдельный сценарий executor'а; служба достижимостей (growth point,
`docs/01` §2).

**Последствия для отчётности.** `run_eval.py` уже кладёт `effective_retrieval` в отчёт,
поэтому действующая глубина в манифесте появляется сама. Отдельно проверить в E2E, что
сравнение прогонов разной глубины не смешивается — для этого сценарий обязан фиксировать
запрошенную и действующую глубину, а не только число найденных документов.

## ADR-037: Неизвестный конец связи — отложенная ссылка, а не отказ

**Статус:** Accepted (2026-09-30; решение владельца). Исполнено частично: форма объекта связи —
да, запись факта — нет. **По своему предмету решение покрывает все атрибутируемые отказы:** все
деградации, у которых есть журнал обмена, вызваны неразрешёнными концами и ничем иным.
Уточнения от 2026-09-30 — в блоках «Что прототип может проверить на самом деле», «Два разных
вопроса», «Вырожденные рёбра» и «Уточнение после сверки».

**Решение владельца:** начать с формы объекта связи в инструкции; неизвестный конец связи
перестаёт быть отказом и становится отложенной ссылкой; показывать модели, что уже есть в
графе; общий резолвер отложенных ссылок, фоновая очередь и «умный» подбор нод для промпта
**не делаются сейчас** — но ссылки хранятся так, чтобы резолвер потом добавился без миграции.

**Контекст.** Найдено пробником извлечения (`test_artifacts/llm-probe/`). Модель на
настоящем тексте отдаёт годный JSON и связи, но связи приходят без поля `kind` и ссылаются
на имена, которых нет среди объявленных в этом же ответе. `_validate_edges` требовал оба
конца среди сущностей того же чанка и поднимал `ExtractionModelError`; по риску №7
(`docs/06`) это сносило LLM-слой документа целиком.

**Почему прежнее правило было неверным по сути.** Требование «оба конца среди сущностей
этого же фрагмента» исходит из молчаливого предположения, что чанк — смысловая граница.
Это не так: связь может идти на код (упомянутый в методичке), между сущностями соседних
фрагментов и между разными документами. Разбиение на чанки — артефакт retrieval, а не
граница онтологии. Правило, нарушаемое маленькой моделью систематически, нельзя
использовать как критерий корректности ответа.

**У правила всё же есть rationale, и его надо назвать.** Висячее ребро в Neo4j хранить
нельзя: `MERGE (a)-[r]->(b)` создаст и `b`, то есть молча изобретёт целевую ноду. Текущая
проверка защищает именно от этого. Значит неверно не правило, а средство — снос LLM-слоя
документа вместо записи самой ссылки.

**Отсюда решение владельца: неразрешённая ссылка — это запись, а не отказ.** Вместо
уничтожения слоя остаётся факт «ссылка от A на имя B не разрешена». Если позже, при загрузке
другого документа, нода B появится — ссылка может быть материализована; если не появится,
её удалит **отдельная джоба уборки**, а не документ падает сам. Отдельная джоба в проекте
уже есть в образце (`POST /api/v1/maintenance/orphan-cleanup`, ADR-014), то есть формат
существует и новый вид работы не изобретается.

**Почему резолвера в прототипе нет вообще.** «Ссылка закроется, когда появится нода» — это
не отдельный механизм, а следствие того, что факт переживает загрузку. Собственный резолвер,
очередь и повторные попытки понадобятся позже и только когда корпус вырастет; в прототипе
они были бы дороже, чем проблема, которую решают.

**Три случая для конца связи** — их и надо различать, сегодня они сведены в одну ошибку:

| случай | что это | поведение прототипа |
|---|---|---|
| 1. Объявлен в этом ответе | сущность есть среди извлечённых | обычное ребро |
| 2. Уже есть в домене | сущность загружена раньше: документ Б ссылается на А | ребро в существующую ноду |
| 3. Нигде нет | **прямая ссылка вперёд**: А упоминает Б, которого ещё нет | **отложенная ссылка**, не отказ |

**Пример третьего случая.** Документ А загружается в пустую БД и прямым текстом говорит:
«эта часть рассматривается в документе Б». Модель при загрузке А не может знать ноды Б — их
ещё нет. Что должно получиться: А создаёт ноду-плейсхолдер и связь в неё, помеченную как
неразрешённая. Позже приходит Б, и если его извлечение объявляет ноду с совпадающим ключом
идентичности, ссылка закрывается.

**Почему качество таких связей определяется не моделью.** Модель физически не видит чужих
нод. Поэтому склейку решает резолв идентичности, а не извлечение: для идентификаторов вроде
`DEDUP_STAGE` он работает (NFKC + casefold), для «требования к памяти» против
«memory requirements» — нет, и это ровно та роль, которая закреплена за глоссарием
(`docs/06` §2.4): косинусная дедупликация отклонена владельцем, глоссарий — единственный
путь склейки написаний.

**Что прототип может проверить на самом деле, а что нет.** Таблица выше различает три случая,
но проверка в коде отвечает только на один вопрос: **объявлено ли это имя среди имён, которые
ответил сам же ответ**. Документа стадия не видит и доступа к ней не имеет, поэтому случаи 2 и 3
для неё неразличимы — оба дают одно и то же: имя не найдено среди объявленных.

Отсюда правило именования и содержания факта: он записывает **«не найдено в этом ответе»**, а не
«не существует». Имя таблицы обязано это отражать (`endpoint_missing_in_response`, ADR-038), иначе
следующий читатель примет факт за доказательство отсутствия ноды в домене — а это ровно тот вывод,
которого факт не поддерживает. Расхождение «не найдено в ответе» и «нет в домене» максимально,
и оно не в пользу безопасности: отсутствие в домене куда вероятнее, чем присутствие.

**Следствие для будущей джобы уборки — это ограничение, а не план.** Джоба, которая удаляет факты
по признаку «не найдено в этом ответе», обязана сначала проверить домен, иначе она удалит ссылки
на ноды, которые существуют, то есть случай 2. Пока такой проверки нет, джоба не может быть
написана вовсе. Это честнее, чем написать её неправильно: неверная джоба уборки отнимает данные
безвозвратно, а отсутствующая — заметна.

**Два разных вопроса, и в коде реализован только один.** Проверка концов спрашивает «объявлено ли
имя в этом ответе». Grounded-оценка спрашивает «встречается ли имя в тексте документа». Это
разные вопросы, и они расходятся в обе стороны: в expC два конца (`CACHE_LIMIT`, `CACHE_EVICTION`)
взяты из примера в инструкции и в документе отсутствуют — но объявлены, поэтому разрешаются, и
деградации не было. Обратное тоже верно: `DedupStage` и `DEDUP_STAGE` оба разрешимы и оба
объявлены, расходятся только написанием.

Практическое следствие для этого ADR: **случай 3 никогда не увидит расхождение написаний.**
`DedupStage` и `DEDUP_STAGE` дают разные ключи идентичности, а `_entity_node_id` выводит `node_id`
из ключа — то есть в графе это две ноды одной сущности. Но обе объявлены, валидация проходит, и
факта не будет. Такой дубль лечится алиасом глоссария и к отложенным ссылкам отношения не имеет;
путать эти два ремонта опасно, потому что один пишет факт, а другой правит данные.

**Вырожденные рёбра — отдельный предмет, записанный здесь по решению владельца (2026-09-30).**
Это не про отложенные ссылки, но джоба уборки у них одна, а решение о хабах принято в том же
разговоре, поэтому запись здесь, а не в новом ADR. Измерения — в
`test_artifacts/llm-probe/*/grounding_verdict.json` и в разборе серии
`test_artifacts/llm-probe/README.md`.

Три формы, все посчитанные: петля `A → A`, хаб (большинство рёбер сходятся в одну ноду) и
взаимная пара (оба направления присутствуют, причём с видом, для которого `edge_types` объявляет
направленное правило).

**Главное свойство: всё это проходит валидацию молча.** Петля удовлетворяет проверке, потому что
оба конца — одна и та же объявленная сущность; хаб и взаимная пара — потому что оба конца
объявлены. `degraded` остаётся `False`, и ни один гейт этого не увидит. Отсюда правило: счётчик
на тихом дефекте надёжен ровно настолько, насколько надёжен код под ним, поэтому каждому такому
счётчику нужна ручная проверенная константа, и «0» в его выводе нельзя принимать, пока константа
не проверена.

**Решение владельца (2026-09-30): хабы копим и чистим джобой, а не подрезаем при извлечении.**
Порог «слишком много входящих» выбрать честно нельзя: на имеющихся прогонах значения
fan-in-share разнесены так, что любой разрез проходит между «хабом» и «не хабом», то есть это
критерий, написанный по итогу. Джоба уборки в проекте уже есть, и она переиспользуется. Первая
версия **только считает и пишет факт**; удаление — после того, как порог обоснован накопленным
распределением. Петли и взаимные пары в джобу не идут: признак двоичный, накопления не
требуют, ремонт локальный — это правила на этапе извлечения рядом с `_validate_edges`, и их надо
держать отдельно, иначе дешёвый локальный ремонт уедет в дорогую нелокальную задачу.

**Связь с выдачей, измеренная.** `max_fanout = 8` по умолчанию, и его дефект уже зафиксирован в
`docs/test_plan.md`: счёт по узлу берёт первые восемь соседей в порядке ответа Cypher, поэтому узел
с множеством извлечённых соседей вытесняет ребро цепочки. Хаб в одном из прогонов — ровно 8
входящих рёбер, то есть один узел съедает весь бюджет выдачи. Значит порог уборки и лимит выдачи
должны браться из одного накопленного распределения, а в финальном виде `max_fanout` должен
считаться по узлу за вычетом вырожденных рёбер: иначе уборка и выдача лечат и портят одно и то
же. Отдельное решение по `max_fanout` не принято, заведено как `BLG-03`.

**Требование «структура графа корректна» остаётся открытым и без владельца.** Петли, хабы и
взаимные пары измерены; ремонт для хабов намечен, для петель и взаимных пар определён. Владельца
у самого требования нет, и оно не выполняется — но и не объявлено невыполненным, а это худшее
состояние. Сузить ли обещание пользователю — решение владельца продукта, и оно не выводится из
того, что ремонта нет. Аналитика финального вида джобы: `BLG-A03`.

**Что делает прототип сейчас.** Случай 3 не отвергается, а записывается как факт
неразрешённой ссылки: имя конца, `source_url`, `chunk_id`, `job_id`. Ребро в графе не
создаётся — его и нельзя создать без изобретения ноды. Если при последующей загрузке нода с
таким ключом идентичности появится, факт закроется при ближайшем обходе; если нет — его
удалит джоба уборки. Собственного резолвера в прототипе нет.

**Пример: «документ А сослался на документ Б».** А загружается в пустую БД и говорит «эта
часть рассматривается в документе Б». Получаем факт «ссылка на имя, которого нет» и живой
факт документа А с его сущностями — вместо сноса слоя А. Позже приходит Б: если его
извлечение объявляет ноду с совпадающим ключом, ссылка материализуется; если Б называет себя
иначе и без алиаса в глоссарии — ссылку уберёт джоба. Второй исход корректен и заметен, а не
тихая потеря данных.

**Что сознательно НЕ делается на этом этапе.** Собственный резолвер отложенных ссылок,
фоновая очередь на повторные попытки, «умный» подбор релевантных нод домена для показа
модели. Для прототипа это лишнее, а объём корпуса мал; роль санитайра играет джоба уборки,
формат которой уже есть в проекте (ADR-014).

**Что должно быть сделано, когда резервы появятся** (зафиксировано заранее, чтобы решение
не принималось в момент, когда проект уже накопил таких ссылок):

- *джоба уборки неразрешённых ссылок* — по образцу orphan-cleanup: обход фактов, удаление
  тех, чья цель не появилась за N загрузок, и материализация тех, чья цель появилась;
- *срок жизни ссылки* — что делать со ссылкой, которая не разрешилась за N загрузок:
  помечать неразрешимой навсегда или отпускать;
- *резолвер по фоновой очереди* — повторные попытки при загрузке новых документов и при
  изменении глоссария; пример: А сослался на «документ Б» без ссылки на источник, Б пришёл
  через месяц под другим именем — очередь сопоставляет его по алиасу глоссария и закрывает
  ссылку;
- *показ существующих нод модели* — не всех, а релевантных чанку; пример: перед извлечением
  А показываем ноды домена, лексически близкие к чанку, чтобы модель могла сослаться на
  существующее, а не завела дубль;
- *объяснение пользователю* — отчёт о неразрешённых ссылках вместо молчаливого графа.
**Статус исполнения.** Форма объекта связи в инструкции (три обязательных поля, включая
kind) — сделано. Случай 3 (факт неразрешённой ссылки вместо отказа слоя) — следующий шаг,
не выполнен. Пока он не сделан, правило в инструкции остаётся прежним («оба конца — среди
обявленных здесь»): поощрять неразрешимые ссылки при строгой валидации значит увеличить
деградацию. Правило переворачивается на обратное ровно тогда, когда заработает случай 3.

**Уточнение после воспроизведения (2026-09-30).** Наблюдавшийся `model_error` оказался
вызван не межчанковыми связями, а расхождением соглашений об именах внутри одного ответа:
сущности объявлялись настоящими идентификаторами документа, а концы связей — по схеме из
примера в инструкции. Неразрешённые концы были следствием переименования, а не ссылок на
соседние фрагменты. Случай 3 в прототипе пока **не наблюдался** и не реализован; решение
принято про запись ссылки и джобу уборки, но повод для неё нужно сначала воспроизвести.
Разбор и цифры: `test_artifacts/llm-probe/README.md`. Оформление нового факта — ADR-038.

**Уточнение после сверки (2026-09-30).** Фраза «повод для неё нужно сначала воспроизвести»
снята: повод воспроизведён, переигрыванием записанных журналов воспроизведены все пути отказа
текущего кода, и результат сходится с `jobs.degraded`. Причина всех **атрибутируемых** деградаций —
неразрешённые концы, и ни одна другая. Четыре деградации в артефактах, и одна неатрибутируема:
журнал обмена того набора пуст. Разбор и цифры: `test_artifacts/llm-probe/README.md`.

**Механизм оказался не тот, что написано выше, и это исправление существующего утверждения
этой записи.** Не «концы переименованы», а **концы брались из поля `id`, которого валидация не
видит.** Промт на момент этих прогонов требовал использовать `id` как имя сущности, если он
уникален в домене, то есть **промт и валидация противоречили друг другу**, и модель послушалась
промта. Профиль с тех пор исправлен, и прогоны после этого дают 0 неразрешённых концов.

Отдельно, и профилем не адресовано: в expD концы — значения поля `category`, которое модель сама
же написала для этой сущности. Это «поле как узел», а не переименование. Прибор различает оба
механизма явно, а не по описанию: `unresolvable_matching_non_name_field` — это концы, совпавшие со
значением поля, которое именем не является, то есть «модель назвала не тем полем» стало
измеримым фактом.

**Проверяемое следствие, в честной формулировке.** Сказать «повторить условия `expA`» нельзя: одним
из условий был промт, требовавший использовать `id` как имя, а его уже нет, то есть условия нельзя
воспроизвести, не изменив их. Проверяемо другое и более слабое: **тот же документ, текущий профиль,
ожидается 0 неразрешённых концов.** Механизм `id` эта проверка не воспроизводит. Записана именно
она, потому что непроверяемое утверждение в ADR хуже отсутствующего: оно не падает.

**Контракт на поля, а не наблюдение о них.** Источники имени сущности — `tag_id`, `canonical`,
`canonical_name`, `name`. **`id` — идентификатор в пределах домена и никогда не является источником
имени.** Это решение: включение `id` создало бы второй канал именования и сделало бы разрешимость
зависящей от того, какое поле модель заполнила, то есть выдумка стала бы неотличима от имени. При
этом `id` — **источник** дефекта, а не его жертва: именно из него в expA пришли 12 выдуманных
концов. Правильный ремонт — промт плюс запись конца фактом, а не расширение списка имён.

Список полей и логика выбора имени вынесены в `orchestrator.py` (`ENTITY_NAME_FIELDS`,
`_entity_names_from_item`), и прибор, считающий разрешимость, импортирует их, а не пишет свои.
До этого прибор смотрел на большее число полей, чем валидация, и показывал «0 неразрешённых» там,
где их было 12; это четвёртый случай одного класса — прибор смотрит на один набор полей, код на
другой, и никто не сверял.

Контракт закреплён тестом
`prototype/tests/test_grounding_verdicts.py::test_id_is_not_a_name_source`, который проверяет
поведение `_validate_edges`, а не вид перечня. Оговорка: если `id` когда-нибудь станет допустимым
источником имени, меняются тест и этот контракт вместе; тест не отключается — иначе он перестанет
охранять утверждение и станет защитой от его исправления, то есть останется зелёным на лжи.

Отсюда **«частично исполнено» означает «по предмету покрыто, запись факта не написана»**, а не
«работает наполовину». Расхождение написаний (`DedupStage` / `DEDUP_STAGE`) этот ремонт не
закрывает и закрывать не должен — см. «Два разных вопроса».

**Пересечения, которые нельзя завести второй раз.** Этот ADR реализует часть решения
**ADR-032** (гранулярность сброса LLM-слоя, `Draft`, решение не принято): снос всего слоя на
неудачном ответе — это его предмет, и пункт 3 спецификации является его частичной реализацией.
Отдельного ADR под «не сносить слой» не заводим. Форма и хранение факта — предмет ADR-038;
обязательность `schema_version` при показе неразрешённых в отчёте джобы — там же.

### Требования, добавленные 2026-10-01 по итогам реализации пункта 3

Записаны требованиями, а не выводами из прогона: вывод от прогона устаревает вместе с прогоном,
а требование остаётся.

**1. Точность имени обязательна для цитаты.** Groundable и «ответ есть» — разные утверждения.
Если имя пришло не из текста, привязка цитаты разъезжается: цитата подтверждает не то, о чём
сущность. Проверка «оба конца среди объявленных» этого не видит — она про разрешимость, а не про
происхождение имени. **Требование к извлечению, а не к валидации:** имя обязано прийти из текста
документа, иначе цитата на него опираться не может.

**2. Границы пункта 3 — что он НЕ ловит.** Обязательно к записи рядом с самим пунктом, иначе
«ноль выдумок» будет прочитано как утверждение более сильное, чем оно есть:

- пункт 3 ловит **только необъявленные цели**. Объявленная не-инстансная цель — «glossary»,
  «requirements», имя, которого нет в тексте как отдельной сущности — проходит валидацию и
  остаётся в графе, потому что она объявлена;
- петли, хабы, взаимные пары и дубли он не увидит **никогда**: они считаются по уже
  разрешённым рёбрам, а он живёт только на неразрешённых.

Отсюда правило чтения отчёта: счётчики пункта 3 не доказывают чистоту графа, они доказывают
отсутствие висящих концов.

**3. Висячие связи бывают двух пород, и код их не различает.** Первую даёт порядок загрузки:
`README` из `learning/` — указатель на методички — даёт около 90% неразрешённых концов, и это
правильное поведение. Вторую даёт любой документ со списком внешних источников: библиография
даёт ссылки, которые висят **всегда**, пока их не уберёт джоба уборки, — они не появятся никогда,
потому что этих источников в проекте не будет. Различить их по коду нельзя: обе просто
неразрешённые концы. Различает их джоба уборки — проверкой домена, и потому до неё никакого
порога на неразрешённые концы быть не может.

**4. Владелец фактов — сейчас его нет, и это не «будущее».** Факты неразрешённых концов
копятся (`job_endpoint_missing_in_response`) и не удаляются. Ограничение записано в ADR-038:
удалять по признаку «не найдено в этом ответе» нельзя — это снесло бы ссылки на существующие
ноды. До появления проверки домена владельца нет, и джоба не пишется вовсе.

**5. Требование к структуре графа — открытое, без владельца.** Петли, хабы и взаимные пары
измерены (`job_resolvability`) и не являются гейтом: порог по входящей связности выбирался бы
после того, как числа увидели. Вопрос, который эта запись не закрывает: **принимаем
структурно неверный граф, финансируем ремонт или не строим слой.** Долг заведён (`BLG-A03`,
`BLG-03`), решение — нет, и оно не сводится к настройке порога.

## ADR-038: Факты — отдельными таблицами, схема версионируется в `meta`

**Статус:** Accepted (2026-09-30; решение владельца). Обязательно к исполнению вместе с
ADR-037 (неразрешённая ссылка — новый вид факта).

**Контекст.** Механизма миграций в проекте нет. Схема растёт вставками
`CREATE TABLE IF NOT EXISTS` прямо в коде инициализации
(`ingestion_service/registry.py`: `documents`, `jobs`, `job_stages`, `job_signals`,
`job_enrichment`, `job_stage_durations`, `job_orphan_cleanup`, `job_extraction_passport`).
Индексов на эти таблицы нет. Таблица `meta` (`store.py`) существует, но версия схемы в ней
не пишется.

**Следствия, из-за которых «просто добавим столбец» не работает.** `IF NOT EXISTS` создаёт
таблицу, но не добавляет столбец в существующую: любое `ALTER` при следующем старте на
старой БД не выполнится. Порядок применения изменений нигде не зафиксирован, поэтому
«применилось ли» нельзя узнать.

**Решение владельца.**

1. **Новый вид факта — новая таблица, а не столбец в существующей.** Тогда `IF NOT EXISTS`
   достаточен, миграция не нужна вовсе, и предыдущие данные не затрагиваются. Каждая такая
   таблица получает индекс минимум по `job_id`, а если факт ищется по чему-то ещё — по
   соответствующему ключу.
2. **Версия схемы пишется в `meta`.** На старте недостающие шаги выполняются по порядку.
   Это не фреймворк миграций, а достаточно, чтобы изменение было применимо повторно и
   проверяемо.
3. **Полноценный фреймворк миграций для прототипа не заводим.**

**Что сознательно не делается.** Нумерованные файлы миграций, откат (`down`), таблица
истории изменений. Появятся, когда появится причина — обычно это первая же необратимая
правка данных.

**Как это связано с ADR-037.** Неразрешённая ссылка оформляется таблицей
**`job_endpoint_missing_in_response`** — имя обязано отражать, что факт значит «не найдено среди
имён, объявленных в этом ответе», а не «не существует в домене». Различие не в пользу
безопасности: отсутствие ноды в домене вероятнее присутствия, и имя `job_unresolved_reference`
читается как доказательство отсутствия, чем факт не является. Проверка в коде отвечает только на
вопрос про объявленный ответ (ADR-037, «Что прототип может проверить на самом деле»), и таблица
не должна утверждать больше, чем проверяемо.

Состав: `job_id`, `source_url`, `chunk_id`, `endpoint_name`, `endpoint_key`, `relation_kind`,
`other_endpoint_name`. Индекс по `endpoint_key` обязателен: джоба уборки обходит факты по нему, а
не сканирует таблицу. Плюс отдельный индекс по `job_id`, чтобы видеть неразрешённое по джобе.

`endpoint_name` хранит имя **как его написала модель**, а `endpoint_key` — ключ идентичности.
Оба нужны: джоба сопоставляет конец с текстом по имени, и по одному ключу она не найдёт ничего,
потому что ключ уже потерял написание. Первичный ключ не содержит `endpoint_name`, поэтому два
одинаковых конца из разных мест документа схлопываются: факт о **неразрешённости имени** один,
а не два.

**Что происходит с самой строкой связи — решение, а не деталь реализации.** Спецификация говорила
«неразрешённый конец хранить как фактом», но при `4/10` связь сама по себе уже существует и куда-то
попадёт, поэтому судьба строки обязана быть решена до кода:

1. **Строка связи сохраняется с пометкой «конец не разрешён».** Иначе теряются `kind` и
   `confidence`, которые уже получены. Записать только факт — значит выбросить ровно то, ради чего
   извлечение и делалось: факт говорит «коня назвали `chunker parameters`», а `kind` говорит, что
   это `HAS_COMPONENT`. Потерянный `kind` не восстанавливается ничем.
2. **Рядом пишется факт с исходным именем** (`endpoint_name` как модель его назвала), а не с
   нормализованным ключом. Иначе джоба уборки увидит `chunker parameters` как ключ и не сможет ни
   сопоставить, ни удалить.
3. **Такая связь не участвует в обходе графа, пока не разрешена.** Обход по висящим концам
   упирается в отсутствующие ноды: либо исключаем их из обхода, либо обход возвращает путь, который
   нельзя развернуть. Исключение обязано быть явным, иначе висящий конец всплывёт как «путь без
   результата» и будет выглядеть как дефект обхода, а не как неразрешённая ссылка.

Три пункта связаны: (1) без (2) джоба не найдёт конец, (2) без (3) обход упирается, (3) без (1)
пропадает `kind`. Поэтому решение принимается целиком, а не по частям.

**Реализовано (2026-10-01, `921 passed`).** Все три пункта сделаны, и третий оказался не
очевидным местом: связь с неразрешённым концом не писалась в граф ещё и потому, что `COMMIT`
поднимал `ValueError` на неё («link references unknown context node»). То есть пункт 3 без
исправления `COMMIT` переносил потерю из `EXTRACT` в `COMMIT`, не устраняя её: документ
падал на поздней стадии, теряя всё, что было записано до неё. Теперь такие связи
исключаются из записи с логом — «связь не записана» и «связи не было» остаются разными
утверждениями.

**Форма ответа по-прежнему поднимает ошибку.** Не список, не объект, пустой конец — это дефект на
границе с моделью, а не утверждение о домене, и записать его фактом нельзя. Пункт 3 касался
разрешимости концов и не должен был расширяться на всё подряд: если бы и это перестало падать,
«слой не потерян» означало бы «мы не знаем, что модель вернула», а это разные утверждения.

**Кто удаляет факт — и почему это нельзя решить позже.** Сейчас не удаляет никто: джоба уборки
неразрешённых ссылок в ADR-037 числится в будущих работах. Ограничение, которое надо назвать
сейчас, а не при написании джобы: **удалять по признаку «не найдено в этом ответе» нельзя.**
Иначе джоба удалит ссылки на ноды, которые существуют, — то есть случай 2 из ADR-037, — и это
необратимая потеря данных. Прежде чем удалять, джоба обязана проверить домен; пока такой проверки
нет, джоба не пишется вовсе.

**`schema_version` идёт первым, если неразрешённые показываются в отчёте джобы.** Требование
«имена неразрешённых должны быть видны в отчёте джобы» (ADR-037) означает `ALTER` существующей
таблицы — по меньшей мере `job_enrichment`, где сейчас есть только `cause`, `lost_entities`,
`lost_edges`, `llm_records`, `llm_edges`. А `ALTER` — это ровно то, что п. 1 запрещает делать
через `IF NOT EXISTS`, и что п. 2 закрывает введением `schema_version`. Значит порядок
определён, а не выбирается: **сначала `schema_version` в `meta`, потом изменение
`job_enrichment`, и только потом — новая таблица.** Обойти это можно было бы, вынеся счётчик
неразрешённых в отдельную таблицу и собирая отчёт оттуда, но тогда отчёт перестаёт быть
согласованным с `job_enrichment`, а расхождение двух источников одного числа — это ровно тот
класс дефекта, который проект уже ловил.

**Проверка на прототипе.** Миграция не нужна там, где меняется только набор таблиц. Если
потребуется изменить существующую таблицу (например, добавить столбец в `job_enrichment`),
это уже обязательный повод завести `schema_version` по-настоящему, и такой случай должен
провалить гейт, а не тихо остаться незамеченным.

## ADR-039: счётчики разрешимости в отчёте джобы, без отдельной сущности

**Статус:** Accepted (2026-10-01; решение владельца). Спецификация: `docs/02` §1.4.
Код не написан: запись фиксирует решение и его границы, реализация — отдельная работа.

**Контекст.** Пункт 3 ADR-037 сделан: неразрешённый конец пишется фактом, связь сохраняется,
слой не теряется. Отсюда возник вопрос, который джоба ответить не может: **сколько неразрешённых
концов — это норма, а сколько дефект.**

Вопрос проявился на примере, который владелец привёл сам. Папка `learning/` — это указатель на
методички, и при загрузке `README.md` **первым в пустую базу** около 90% связей будут
неразрешёнными: список ссылается на документы, которых в базе ещё нет. Это не дефект
извлечения, это порядок загрузки, и система обязана отличать одно от другого. При этом
неразрешённые концы — обычное состояние частичной загрузки, а не сбой.

**Ключевое уточнение владельца, изменившее решение: «загрузка — это и есть ингест».** Для одного
документа эти слова означают одно и то же, отдельного понятия за ними нет. Моё первое решение —
объявить загрузку отдельной сущностью — выросло из требования *«в этой загрузке не участвовал»*,
а оно требует группы документов, которой в проекте нет и которая заводилась бы ради одного
счётчика.

**Решение владельца.**

1. **Отдельной сущности нет.** Счётчики разрешимости живут в отчёте джобы: числа — в
   `job_enrichment`, сами неразрешённые концы — в `job_endpoint_missing_in_response`. Агрегат по
   нескольким джобам — это запрос, а не таблица.
2. **Все числа пишутся всегда, без исключений и без порогов на месте.** Порог — решение
   читателя, у которого есть и корпус, и код.
3. **Доля без знаменателя не публикуется.** Отчёт обязан содержать число документов, чанков и
   связей, иначе доля не вычисляется, а проценты в неразрешённых концах на `README` и на
   `cosine-dedup` означают разное.
4. **Отдельного числа «вне загруженных» не будет** — по решению владельца. Если понадобится,
   это заводится как самостоятельная фича, а не устраивается заранее.

**`meta` нужна в базе джоб, а не в базе топологии.** Проверено 2026-10-01 при реализации: таблица
`meta` есть только в `topology_service/store.py`, где уже пишется `_META_REVISION`, — и это база
топологии. Джобы, `job_enrichment` и новые таблицы живут в другой базе
(`ingestion_service/registry.py`), и своей `meta` у неё не было. Версионировать надо схему джоб,
а `ALTER` предстоит именно там, поэтому `meta` заводится в `JobStore`.

**`schema_version` в этой работе не потребовался, и это не отступление.** ADR-038 требовал его
перед `ALTER`. Счётчики сознательно вынесены в **новую таблицу** `job_resolvability`, а не
добавлены столбцами в `job_enrichment`: `CREATE TABLE IF NOT EXISTS` не требует миграции, а
столбец потребовал бы `ALTER` на каждой базе, где пайплайн уже отработал. Требование ADR-038
остаётся в силе на случай, если кто-то когда-нибудь решит **изменить** существующую таблицу.

**Главное следствие — таблица не дублирует `job_enrichment`.** Объём слоя и факт его потери
остались там; здесь только то, чего там нет. Два источника одного числа разъедутся, а расхождение
двух источников — уже ловившийся в проекте класс дефекта.

**Распределение по полям хранится одним столбцом `by_field_json`.** Набор полей задаёт модель
ответа, а не схема: столбец на каждое возможное поле означал бы `ALTER` при каждом новом, то есть
ровно то, чего таблица избегает.

**`measured` отделён от нулевых счётчиков.** Он отвечает на вопрос «считал ли кто-нибудь», а не
«что насчитали». При `measured = 0` читатель обязан трактовать числа как `unknown`, а не как
«дефекта не было». Это то же требование, что прибор уже выполняет для отсутствующего документа,
и оно применено к продуктовому коду, а не только к измерению.

**Список ключей концов переехал в production-код (`ENDPOINT_KEYS`).** Прибор держал свою копию,
и это был второй источник соглашения об именах — после уже найденных трёх расхождений
(лишние поля имён, меньшие ключи концов, смешение измерения с предсказанием). Теперь `END_KEYS`
прибора есть ссылка на `ENDPOINT_KEYS`.

**Лестница разрешимости — три состояния, а не четыре.** Четвёртое («есть в корпусе, но не в этой
загрузке») не существует: корпуса как отдельного множества нет, есть только загруженное.

| состояние | что это | всегда ли допустимо |
|---|---|---|
| объявлен в этом ответе | разрешился | да |
| не объявлен, есть в загруженных документах | настоящая сущность, модель её не объявила | да |
| не объявлен, **нигде в загруженных** | **фабрикация или ещё не загружено** | см. ниже |

Третья строка объединяет два разных события, и это следствие решения владельца, а не упрощение.
«`README` из `learning`, загруженный первым» даст здесь те же 90%, что и выдумка. Различить их
без границы пакета нельзя.

**Значит пороговой цифры не остаётся.** То, что я назвал порогом, — обычное измеряемое число, за
которым следят. 90% на первом документе не «почти дефект», а прямое сообщение: база пуста.
После загрузки остальных документов число уходит вниз, и эта траектория и есть диагностика.
Порогов не вводится, и это честнее, чем порог, выбранный до данных.

**Почему не варнинг.** Варнинг срабатывает на неисправности. При 90% неразрешённых на `README`
он сработает на каждой загрузке и через неделю перестанет читаться. Это ровно то, что уже
произошло в проекте с `llm_layer_dropped`: счётчик считал «сработал сброс» вместо «исчезли
факты», и его пришлось разделить, потому что его уже не читали. Здесь то же, только наоборот:
неразрешённые концы — признак частичной загрузки; **сбой — это когда неразрешённых концов нет,
а связи между объявленными сущностями есть.**

**Отсутствие данных и отсутствие порядка вещей — разные результаты.** Если документы не
загружены, доля обязана быть `unknown`, а не `0`: пустая база — это первое, что произойдёт, и
`0` здесь был бы прямой ложью. То же требование, что прибор уже выполняет для отсутствующего
документа.

**Почему не порог «5%», который предлагался до этого решения.** Он был выбран до данных, то есть
по тому же принципу, который запрещён для хабов в ADR-037: «порог по входящим, выбранный после
того, как увидели 0.889 против 0.5 против 0.143». Порог отменён вовсе — потому что владелец
указал контрпример, а не потому, что порог неудобен.

**«Нигде» — это «нигде в загруженных документах».** Решение владельца, 2026-10-01. Вариант
«все документы домена» отпадает по той же причине: перечисления документов домена не
существует, есть только то, что загружено, — и оно пополняется. «Все на диске» отвергнуто по двум
причинам: на диске лежат артефакты и архив вне домена, и — практичнее — в домене `it`
художественная литература не нужна, её **не предлагают загружать**, то есть признак «в домене»
уже задан тем, что попадает в базу.

## ADR-040: золотой набор `it` — один файл, а судья строится прогоном

**Статус:** Accepted (2026-10-01; владелец подтвердил решение и способ проверки).
Следствие: `prototype/infra/eval/README-dataset.md`, `docs/test_plan.md` §6.0.

**Проблема.** Золотой набор `it` лежал в двух файлах: 50 вопросов в `questions.jsonl` и 24 в
`questions_graph.jsonl`. Второй файл появился потому, что в первом не было графовой части, и к
2026-10-01 эта причина перестала соответствовать данным. Требовалось решить, что делать с двумя
наборами, и отдельно — что считать «набором для человеческого судьи».

**Решение.**

1. **Канонический набор один.** `it/questions.jsonl`, 74 вопроса;
   `it/questions_graph.jsonl` удалён. `--extra-dataset` в раннере остаётся как общая
   возможность, для `it` не используется.
2. **Граница среза задаётся полем, а не файлом.** `golden_graph_evidence` проставлен явно у всех
   74 строк, включая `false`, чтобы «поля нет» и «поля `false»` не читались по-разному в одном
   файле.
3. **Набор для судьи — артефакт прогона, а не набор вопросов.** Разбор строится из вопроса,
   ответа модели, retrieved-чанков и `golden_facts`; до прогона его собрать нельзя.
4. **Критерий приёмки разделён по стоимости проверки.** «Ноль выдуманных имён» — агрегат;
   сверка имён ответа с корпусом и чанками находит **кандидатов**, но вердикт по каждому
   кандидату семантический и остаётся за человеком. «Каждое утверждение подтверждено цитатой
   или явно неподтверждено» — свойство вопроса, проверяется чтением по выборке. Слово
   «автоматически» здесь было бы неверно в обе стороны: и «человек не нужен», и «автоматика
   закрывает вопрос».

**Отвергнуто.**

| вариант | почему отвергнут |
|---|---|
| оставить два файла | граница файла не совпадала с маркером: из 24 строк `true` стоял только у 8; два файла уже дали неверное «9 из 66» вместо 8 из 74 |
| третий файл «50 + 15 для судьи» | третья копия текста вопросов; она разойдётся с двумя исходными, и неизвестно, по какой копии считался гейт |
| хранить графовый срез отдельным файлом | допустимо только генерируемым фильтром и без ручных правок; как место для данных — та же ошибка границы |

**Выборка для человека — 14 вопросов, правило зафиксировано заранее.** Все 8 с
`evidence_policy: graph_required` плюс 6 с `reasoning_type` из `contradiction`, `causal-risk`,
`evidence-boundary`, `conditional`. Поверх — всё, что разведочный прогон пометил слабой цитатой,
и базовая выборка из оставшихся 60 вопросов (из них 52 — `single-hop`), иначе регрессия в самом
массовом типе вопросов останется незамеченной. **Размер и состав базовой выборки фиксируются до
чтения ответов:** после чтения отбор превращается в «я посмотрел те, где понравилось». Это ровно
тот приём, который запрещён для хабов в ADR-037, — порог, выбранный после того, как увидели
результат.

**Набор не готов к финальному прогону.** `as_of` стоит на 2026-09-22 у 64 вопросов и на
2026-09-26 у 10, а документация правилась с 2026-09-27 по 2026-10-01 (ADR-035, ADR-037, промт
экстракции, профиль домена, критерий приёмки). У **71 вопроса из 74** хотя бы один `golden_source`
менялся позже `as_of`. Все пути существуют — расхождение не в файлах, а в содержимом
`golden_facts`. Ревью эталонов обязательно и должно идти после фиксации критерия, а не после
чтения ответов.

**Судья-LLM остаётся экспериментом.** `build_judge()` использует ту же модель, что и генератор,
поэтому измеряет связку «модель как судья» и не является источником истины.

## ADR-041: профиль грузит Analyzer один раз; концы связи переводятся по отдельности

**Статус:** Accepted (2026-10-02; решение владельца по обоим пунктам). Следствие: `docs/02` §1,
`docs/06` §2.

Запись сделана **после** кода, что нарушает spec-first из `D:\Otus\harness\.opencode\README.md`
(«amend the ADR before writing the fix»). Порядок исправлен здесь, а не оправдан: оба решения
приняты по итогам измерения, и измерение важнее формы. Причина правки кода до записи — не
уверенность в решении, а потребность в ответе «воспроизводится ли это вообще», и для этого нужен
был работающий код.

### Пункт 1. Ни одна связь от модели не попадала в граф

**Проблема.** `_validate_edges` признаёт конец разрешённым, сравнивая его с **именами**
(`_identity_key(значение) in known`). NORMALIZE (строка ~1191) переводит имена в идентификаторы по
`mapping: identity_key → entity_id`, но перевод стоял под `continue` на **всю связь**: увидев
непустой `from_id` **или** `to_id`, стадия пропускала оба конца. Модель законно отдаёт смешанную
форму (`from` именем + `to` именем + `to_id` идентификатором — промт это разрешает), и тогда
`edge["from"]` оставался сырым именем. COMMIT сравнивал его с множеством `tag:it:...` и поднимал
`ValueError` на весь документ.

Измерено на `docs/api_reference.md`, 7B, проекция выключена: 47 сущностей, 32 связи, 61 конец
из 64 EXTRACT считал разрешёнными — и документ всё равно падал на COMMIT. Замер, который снял
остаток с `tag:it:...`, до правки был в артефактах не виден: в отчёте стояло
`endpoints_resolved=61` при нуле записанных связей.

**Решение.**
1. NORMALIZE переводит **каждый конец независимо**. Связь не переводится целиком.
2. COMMIT делает последнюю попытку перевода по ключу, а конец, который не перевёлся, **записывает
   фактом и пропускает связь** — решение владельца от 2026-10-02, по духу ADR-037, случай 3.
   Раньше здесь был `raise`, и одна непереводимая связь убивала документ.
3. Сообщение об ошибке называет связь, оба конца, имена и число узлов в документе; путь
   «невалидный JSON» в EXTRACT прикладывает сырой ответ модели, как это уже делает соседний путь
   обрыва по `max_tokens`.
4. Пропуск считается и пишется в лог уровнем ERROR с именами концов. Молчание здесь стоило работы:
   пустой граф даёт `necessity = 0`, который читается как «граф не нужен».

**Отвергнуто.** Считать, что виновато сравнение «имя против идентификатора»: правка перевода
концов по отдельности вскрыла настоящую причину, а гипотеза «имя против id» дала ложное
уверение и прошла бы, если бы её не проверили.

**Почему это не видели 932 теста.** `test_commit_stage.py` не передаёт `links=` ни разу: его связи
детерминированные, а те дают ноль. `test_unresolved_endpoint_fact.py` доводит концы до EXTRACT и на
этом кончается. Ни один тест не коммитил связь, полученную от модели. Связь с именными концами,
собранная как её собирает модель, воспроизводит отказ за две секунды без стенда и без GPU.

**Результат после правки, 7B, один документ.** `lost_edges=0`, `degraded=0`, в графе
`REFERENCES` 13 и `REQUIRES_CONSTRAINT` 6 — 19 связей, которых не существовало ни разу.

### Пункт 2. Кто грузит профиль

**Проблема.** Профиль грузили три стадии — CHUNK, EXTRACT и COMMIT, — и у каждой был свой
`profile_fetcher`. `_load_profile` выходит по `ctx.profile_loaded`, то есть авторитетом становился
**кто позвал первым**. Связка в `app.py` была правильной (один `profile_loader.load` на все три),
и правильность держалась на ней, а не на коде: стадия без фетчера замораживала `profile={}`, и
LLM-экстракция молча уходила в детерминированный путь с `cause=None`. На этом споткнулся сам
новый тест, пока фетчер не начали подавать в одну точку.

**Решение.**
1. Профиль загружает **Analyzer один раз, до первой стадии**, и он замораживается на прогон.
   Стадии его только читают; `profile_fetcher` у стадий остаётся для одиночных юнит-тестов.
2. Отсутствие фетчера пишет WARNING с именем домена и источником. Пустой профиль — это «его не
   принесли», а не «профиля нет»: уход в детерминированный путь с `cause=None` не был описан ни
   в одной таблице причин.

**Что из этого следует для документации.** Правило «профиль грузится раз на джобу» было записано
в докстринг `profile_contract.py` и в имени теста, но **ни в одном живом документе**. Три места
загрузки не были объявлены нигде, а колонка «Зависимость от профиля» в `docs/02` §1 записывает,
что стадия *читает* из профиля, а не *где он берётся*; для `CommitStage` в ней о профиле нет
ни слова, хотя стадия его грузит. Правка внесена в `docs/02` §1 и в таблицу причин `docs/06` §2.

## ADR-042: проекция в прототипе — публикация inline в конце COMMIT

**Статус:** Accepted (2026-10-02; решение владельца). **ПРЕДПОСЫЛКА ПУНКТА 4 ОПРОВЕРГНУТА
измерением 2026-10-02 — см. «Поправку» ниже; решение по разделу «Что делать дальше» открыто.**
Следствие: `docs/06` §2.5, открытые вопросы ингест-аналитики (§3.16), ADR-043. Пункт 6 —
непроверенное допущение с планом проверки.

### Поправка 2026-10-02: два утверждения этого ADR неверны, решение требует пересмотра

Проверка в живом стенде опровергла два утверждения, на которых стоял пункт 4. Запись правится
до продолжения работы, а не после.

**Неверно 1: «inline-публикации нет, её надо написать».** Она **уже реализована** —
`CommitStage._record_projection_state` (`pipeline/orchestrator.py:1589`): считает `data_revision`
и `projection_revision`, пишет `projection_revision` в metadata чанков (backfill), делает
compare-and-set состояния, держит lease и `job_id = "inline-<job_id>"`. Замер состояния в
`projection_data/projection.db` это подтверждает: `job_id = inline-ded20a80-...`,
`processed_source_count = 1`, `last_error = inline_projection_pending`.

Ошибка была в способе проверки: я нашёл `status="ready"` только в `projection.py` и заключил
оттуда, что ингест публиковать не может. Публикация идёт из `orchestrator.py`, куда тот поиск
не заходил. Утверждение «единственное место» было построено на одном файле и не выдержало
проверки.

**Неверно 2: «причина `pending` — никто не публикует».** Причина в условии
`orchestrator.py:1600`:

```python
state_status = "ready" if active_source_count <= 1 else "pending"
```

При трёх активных источниках inline **не может** выставить `ready` никогда. Ни это условие,
ни `_record_projection_state` не встречаются ни в одном тесте и ни в одном документе — то есть
правило, держащее гейт закрытым, не закреплено ничем.

**Новый блокер, который важнее обоих.** Даже если снять условие `<= 1`, гейт всё равно не
откроется. `verify_projection` (`retrieval/adapters/neo4j.py:771-779`) требует, чтобы **все**
чанки домена несли ревизию состояния:

```cypher
MATCH (c:Chunk) WHERE c.domain = $domain
AND (c.projection_revision IS NULL OR c.projection_revision <> $projection_revision)
RETURN count(c) AS mismatches
```

Замер по домену `it` (21 чанк, три активных документа):

| источник | чанков | `projection_revision` |
|---|---|---|
| `docs/api_reference.md` | 10 | `2ada499c0abb` |
| `docs/prototype_requirements.md` | 9 | `aac3ec7e854e` |
| `docs/expert_reviews.md` | 2 | `ed9ce919a31d` |

Состояние называет `2ada499c0abb` — ревизию последнего загруженного документа. Значит
`verify_projection` увидит **11 расхождений** и вернёт `false`.

Причина разнобоя: каждая джоба проставляет `projection_revision` **только своим** чанкам, и
ревизия вычисляется от `data_revision` всего домена, который меняется с каждой загрузкой. То
есть ревизия каждого документа «устаревает» следующей загрузкой.

**Что из этого следует.** Приведение чанков домена к одной ревизии — операция **по всему
домену**, и её сегодня умеет ровно одна: офлайн-job, перебирающий источники. Это в точности то,
что пункт 5 объявил вне scope как «ремонт». Следовательно, объявление «ремонт не нужен» было
неверно: для домена из трёх документов ремонт — не украшение, а условие прохождения гейта.

Пункт 6 (счётчик, переживающий перезапись) и разведение терминов в пункте 1 остаются в силе:
терминологическая путаница и затирание следа подтвердились, а не опроверглись.

### Что делать дальше — решение открыто

Вариант требует выбора владельца, и это **не** «inline или read-back», как считали вчера:

- **А. Принять доменную перепростановку** как цену `ready`. Тогда офлайн-job обязателен, юниты
  обязательны, и вопрос «кто производит юниты» из открытых вопросов ингест-аналитики (§3.16)
  перестаёт быть отложенным — он становится блокером приёмки.
- **Б. Ослабить инвариант проверки:** «каждый источник помечен ревизией, действующей для него»,
  а не «в домене одна ревизия». Тогда проверке нужна ревизия на источник, а состояние —
  отображение `source_url → projection_revision`. Перепростановки не требуется, но меняется
  контракт гейта, и это решение, а не правка.
- **В.** Отложить `ready` целиком и закрыть прототип как vector-only с зафиксированным блокером.

Вариант А проверяется шагом E из пункта 7 (собрать юниты вручную, прогнать job, посмотреть
`ready` и `verify_projection`) — это по-прежнему единственный способ узнать, проходит ли
проверка после выравнивания ревизий. Шаг E **не отменяется**: он остаётся критерием для А.


### Пункт 1. Одно слово означало две вещи

Слово «проекция» в `CONCEPT.md` §32, `L1-04`, `docs/01`, `docs/03`, `docs/04` и
`openspec/changes/add-lightweight-context-graph/design.md:12` называло одновременно (а) сам
граф-shaped артефакт — generic-узлы и рёбра плюс `context_ids`/`tag_ids` в vector metadata, и
(б) квитанцию `ProjectionState` с отпечатками ревизий и результатом проверки. Гейту нужен (б),
job производит (б) после (а). Одно имя на два объекта — причина того, что разобраться в механике
было трудно: спрашивали «что такое проекция», а отвечать приходилось за оба сразу.

**Решение.** Разделить термины: **граф** — (а), **готовность графа** — (б). Слово «проекция»
в новых записях не используется; существующие цитаты выше остаются как есть, чтобы правка не
переписывала историю.

### Пункт 2. Почему граф не применялся ни разу

`status="ready"` выставляется **в одном месте** — `projection.py:1196`, внутри `run()` офлайн-job'а,
достижимого только из CLI `main()` (строка 1250). Ingest job не запускает: `app.py` лишь создаёт
store (`try_build_projection_state_store()`, строка 350).

Вход job'а — `ProjectionSourceProvider = Callable[[str, str], list[ProjectionUnit]]`
(`projection.py:620`), и реализация ровно одна: `JsonlProjectionSource` (строка 583) читает файл.
Экспортёра юнитов нет, а взять их негде: `job_enrichment` (`storage/registry.py:307-316`) хранит
только счётчики — `cause`, `lost_entities`, `lost_edges`, `llm_records`, `llm_edges`. Извлечённые
сущности и связи уходят прямо в Neo4j и в SQLite не остаются.

Итог наблюдаемый: `projection_status = "pending"`, граф не применён ни на одном вопросе,
`degraded_questions = 3`, `graph_contribution.mode = not_measured`.

### Пункт 3. Ложная готовность достижима

`total = len(units)` (`projection.py:1039`); при пустом списке юнитов цикл не выполняется,
`_validate_unit` не вызывается, и выполнение проваливается в
`ProjectionState(status="ready", input_source_count=0)` (строка 1196). Пустой units-файл при
существующем реестре даёт `ready` без единого источника и открывает эксперимент над пустым
графом. Класс тот же, что у §4 ADR-041: молчание выглядит как успех.

**Решение.** Контракт-позитив: **`ready` означает, что проверен хотя бы один источник**.
Guard обязателен в любом пути публикации, не только в CLI.

### Пункт 4. Публикация в прототипе — inline, без файла и без перебора корпуса

Перебор всего корпуса в designs оправдан ремонтом: чужой `config_fingerprint`, `stale`,
частичный сбой. Ремонт вне scope прототипа (пункт 5), поэтому и основание для перебора исчезает.
Остаётся ровно две операции: backfill `projection_revision` в vector store — без него не проходит
`verify_projection`, который вызывает гейт (`retrieval/pipeline.py:429`), — и публикация состояния.
Обе делаются из данных, которые ингест уже держит в памяти.

**Решение.**
1. В прототипе `trigger=auto`: backfill и compare-and-set в `ready` в конце COMMIT, из
   `ctx.entities` / `ctx.entity_edges` с `chunk_ids` и `source_ids`.
2. Триггер живёт в конце COMMIT, а не в начале загрузки и не в отдельной задаче: публикация
   **записывает уже сделанное** и не может провалить джобу. `L1-04` («граф не prerequisite для
   ingest») не нарушается — блокирующей зависимости не появляется.
3. Ручной режим — существующий офлайн-job без изменений; он остаётся путём ремонта.
4. Guard из пункта 3 обязателен в обоих режимах.

### Пункт 5. Восстановление после сбоя вне scope — и почему

`design.md` §5 обещает: «следующий запуск с тем же key безопасно продолжит/повторить незавершённые
source units». Механизмом объявлена идемпотентность — повтор всех юнитов безопасен, потому что MERGE
детерминирован. Но **повторять нечего**: юнитов нет ни в одном хранилище. Обещание §5 сегодня
неисполнимо не «потому что не сделано», а потому что отсутствует артефакт, который он перебирает.
Записано в `docs/06` §2.5 в форме «правило есть, задачи нет».

**Отвергнуто в прототипе:** read-back провайдер, читающий юниты из Neo4j. Он перебирает весь корпус,
чтобы восстановить то, что ингест уже записал, и всё равно не даёт rebuild — прочитать обратно
нельзя заменить отсутствующее. Решение обсуждалось и отклонено владельцем 2026-10-02; сам
провайдер и per-job сохранение enrichment вынесены в открытые вопросы ингест-аналитики (§3.16).

### Пункт 6. Границы видимости сбоя — решение владельца

Решение от 2026-10-02: **факт** неготовности виден в артефакте приёмки (`projection_status` на
каждый вопрос плюс `graph_degraded`, `manifest["projection_observed"]`); **причина** остаётся в
`last_error` и в логе и в отчёт не попадает. Перестановку проверок в гейте не делаем.

Известное ограничение, принятое вместе с этим: `stale` проверяется раньше статуса
(`pipeline.py:408` против `423`), поэтому при расхождении ревизий причина публикации маскируется
словами `stale`. Разбор причины ведётся по `last_error` и по логу.

**Счётчик неудачных публикаций обязателен и не обнуляется последующим успехом.** Без него
восстановление внутри батча затирает след: публикация, упавшая на 40-м документе и прошедшая на
41-м, перезаписывает состояние в `ready`, и «74 документа, один упал» становится неотличимо от
«все прошли». Отсутствие данных и отсутствие дефекта — разные результаты.

### Пункт 7. Непроверенное допущение и критерий проверки

**Ни разу не наблюдался `ready` в живом стенде.** Все прогоны давали `pending`, а значит ветка
`verify_projection` (`pipeline.py:429`) не исполнялась ни разу. Пункт 4 предполагает, что гейт
вообще удовлетворим: что `projection_revision` сойдётся и что vector store примет простановку.
Это допущение, а не деталь реализации.

**Критерий проверки, записанный до прогона.** Собрать юниты из Neo4j одноразовым скриптом,
запустить существующий CLI-job и проверить два наблюдения: состояние доходит до `ready`,
`verify_projection` проходит. Оба наблюдения получены — пункт 4 реализуется. Хотя бы одно не
получено — **ADR правится до кода**, потому что меняется предпосылка решения, а не его деталь.

## ADR-043: гейт выбора следующей части системы объявляется до результата

**Статус:** Accepted (2026-10-02; решение владельца). Заполняемые поля — после прототипа.

### Зачем гейт объявляется заранее

Выбор следующей части зависит от вердикта прототипа, а вердикт сейчас `not_measured`. Условия,
записанные после результата, подгоняются под этот результат: любое решение получает обоснование
задним числом. Поэтому условия записываются на холодную голову — как критерий измерения
записывается до прогона, только решение здесь, а не замер.

**Решение.**
1. Гейт объявляется сейчас и применяется после прототипа.
2. **Вход:** `Proposals/` (сейчас два файла: `graph_as_data_map_manifest.md`,
   `s3_integration_specification.md`) **и** реестры открытых вопросов — ингест, retrieval, eval,
   revision. Плюс вердикт с причинами: `run_eval.py` пишет `verdict` и `verdict_reasons` в отчёт.
   У `Proposals/` свой маршрут через `add-proposal-review-gate`, дублировать его не нужно, но
   вход гейта перечисляет оба источника.
3. **Критерии — таблицей по вердикту**, а не одним условием:

   | вердикт | что выбирается |
   |---|---|
   | `accepted` — вклад графа измерен и подтверждён | часть, углубляющая то, что дало эффект |
   | `rejected` — вклад не подтвердился | часть **вне графа**; опыт графа фиксируется как отрицательный результат |
   | `invalid` / `not_measured` | сначала блокер измерения; остальное не рассматривается |

   Ветка `rejected` включает обязательную фиксацию отрицательного результата, чтобы он не
   всплыл позже как «недооценённая идея».
4. **Выход:** один выбранный бандл `openspec/changes/<slug>/` либо явная запись «блокер не устранён,
   работа продолжается по ADR-042». Решение гейта — это артефакт, а не обсуждение.
5. Проекция **не является кандидатом гейта**: она производит его вход. Пока вердикта нет, гейт не
   созывается, а работа идёт по прототипу — сюда же входят ревью 74 эталонов и восстановление
   измерения.

**Открытым остаётся** (решение владельца применительно к моменту применения): заводится ли гейт
как OpenSpec-бандл — по `openspec/project.md:19-20` изменения начинаются с бандла — или иначе.
Словарь решений переиспользуется от `add-proposal-review-gate`: `accepted` / `partial` /
`deferred` / `rejected`. Записи решений хранятся каталогом `review-records/`, как в этом бандле.

**Следствие для документации.** Отдельной вехи под аналитику ингеста в
`audit/pm_audit_goals.md` §2 нет: M0–M6 — сервисы, ingestion, query, runtime-контракты, eval,
MCP/UI, масштабирование. Приоритетность открытых вопросов держится на реестре и его маркировке
(«ПРИОРИТЕТНЫЙ ВОПРОС» в заголовке), а не на вехе. Если веха под аналитику нужна, её надо
записать в §2 — незаписанное обязательство не выполняется, см. ADR-042 пункт 5 и `docs/06` §2.4.

## ADR-044: приоритет полей слитой ноды — первый из живых, владелец хранит источник и версию

**Статус:** Accepted (2026-10-02; решение владельца — вариант «1+3» из
`Ingest/analitic/manual_tags_and_ingest_open_questions.md` §3.12). Следствие: `docs/06` §2.7,
тест `prototype/tests/test_node_merge_rules.py`.

### Проблема

Одна нода приходит из нескольких документов — это штатный случай, а не конфликт
(§3.12). Идентичность ноды — `(domain, canonical_name)`, поэтому пересечение имён сливает ноды
намеренно. Между документами скалярные поля перезаписываются пришедшим последним: в
`_upsert_nodes` (`retrieval/adapters/neo4j.py:567`) идёт `SET n += $scalar_properties`, то есть
побеждает последний, и единственная защита — `origin = 'user'`.

Одновременно **внутри одного документа** `id`, `description`, `category` заполняются только при
отсутствии (`ingestion_service/pipeline/orchestrator.py:1303`), то есть побеждает первый. Один и
тот же `description` внутри файла берётся из первого извлечения, а между файлами — из последнего.
Следствие: содержимое общей ноды зависит от порядка загрузки корпуса, и один и тот же корпус,
обработанный в обратном порядке, даёт другие `description` при том же наборе документов.

Вариант 1 без поля-владельца отклонён владельцем отдельно: смена конфигурации не
переобрабатывает корпус (no-op, `orchestrator.py:1556-1562`), поэтому «первый победил» без
владельца означает, что описание устаревает внутри сессии навсегда.

### Что значит «решение принимает код»

Это **не** оценка формулировок и **не** очередь конфликтов. Ни человек, ни ИИ в выборе не
участвуют: система применяет объявленный полный порядок к кандидатам, и пришедший позже проигрывает,
если он не «новее». Сравнение чисел, без суждения о качестве текста.

Объявленный порядок для одного поля, у которого уже есть значение:

1. значения нет → пишем значение и его владельца;
2. `incoming_version > stored_version` → пишем;
3. `incoming_version == stored_version` → решает `source_url` лексикографически;
4. иначе оставляем существующее.

Поскольку порядок полный, результат **не зависит от порядка загрузки документов**.

### Решение

1. Владелец хранится на ноде как два поля на каждое перезаписываемое содержимое:
   `<field>_source_url` и `<field>_version`. Версия — та, что будет присвоена загрузке:
   `registry.current_version(domain, source_url) + 1` (`storage/registry.py:120-131`), под
   `source_lock`, поэтому гонки нет.
2. Покрываются `id`, `description`, `category` — ровно те поля, которые **уже** являются
   first-wins внутри документа. Правка снимает противоречие между уровнями, а не вводит новое
   правило.
3. Защита `origin = 'user'` сохраняется и имеет приоритет над новым правилом: машинная запись
   по-прежнему не трогает то, что завёл человек.
4. Число обращений к Neo4j не меняется: те же чтение и запись на ноду, владелец добавляется
   приписками в тот же запрос.

### Что здесь произвольно, и это надо называть прямо

Номера версий **внутри одного источника**, поэтому сравнение «документ A версии 2» с «документом
B версии 1» **не имеет смысла** — это ровно то неопределённое место, из-за которого вопрос и был
открытым. Первая редакция правила закрывала его сравнением `(version, source_url)`, то есть
сравнивала версии **между** источниками, а это ровно то, что объявлено бессмысленным.

### Поправка 2026-10-02: между источниками сравнивается приоритет источника, а не версия

**Основание — собственная, а не внешняя.** Решение ADR-044 уже фиксирует, что номера версий
привязаны к одному источнику и не сравнимы. Значит правило, которое ими пользуется, противоречит
основанию, и должно быть исправлено независимо от того, что говорят внешние источники. Правильный
порядок: **внутри источника — версия, между источниками — приоритет источника.**

Ответ внешней поисковой системы на вопрос об отраслевой практике (принесён владельцем,
`architecture_answers.md`, временный файл удалён) назвал ту же форму: приоритет источника
(`source authority`) решает между источниками, а внутренняя версия используется **только**
внутри своего источника. Это **непроверенное подтверждение**: ссылки в ответе были плейсхолдерами,
сеть в среде закрыта, первоисточник не открыт. Поэтому основанием правки служит наша же запись о
несравнимости версий, а совпадение формы с отраслевой практикой — аргумент сносный, не
определяющий.

Заодно ответ отвечает на вопрос, который мы тогда поставили в §3.12: общепринятого стандарта
стратегий нет, это решение владельца данных; в корпоративной практике рекомендуют приоритет
источника с откатом на «более свежее» при равном приоритете. То есть при равенстве приоритетов
сравнение всё-таки нужно — и оно остаётся, но объявляется как **второй** уровень, а не первый.

**Изменения правила.**

1. `<field>_source_url` и `<field>_version` остаются: они нужны для сравнения внутри источника.
2. Появляется приоритет источника. Он **конфигурируется** (`PROJECTION_SOURCE_PRIORITY`, JSON
   `{source_url: int}`), по умолчанию все источники равны. Произвольной константы в коде нет.
3. Порядок: владельца нет → пишем; **тот же источник** и версия новее → пишем; **разные
   источники** и приоритет выше → пишем; приоритеты равны → `source_url` лексикографически;
   иначе оставляем.

**Что это даёт.** Случай, который в первой редакции решался произвольно (два разных документа с
разными номерами версий), теперь определяется настраиваемым правилом, и репродуцируемость
сохраняется, потому что порядок полный. При пустой конфигурации поведение совпадает с прежним.

**Про терминологию.** Названные внешним ответом термины (`golden record`, `survivorship rules`,
`source of truth per attribute`) записаны в §3.12 как **подсказки для последующей проверки**, а не
как установленные факты: первоисточники не открыты. Название ошибки «одна глобальная метка вместо
локальной» в литературе не подтверждено, поэтому в §2.6 используется собственная формулировка.

### Что здесь осталось нерешённым

`canonical_name`, `name`, `origin`, `confidence` по-прежнему перезаписываются последним по
`_origin_rank` (`orchestrator.py:255-256`, `:1303`). То есть **асимметрия остаётся**: имя ноды по
прежнему зависит от порядка извлечения внутри документа, а содержимое — уже нет. Это отдельный
вопрос, и он не объявлен решённым.

### Следствие для теста

`test_node_merge_rules.py::test_last_writer_wins_for_equal_origin` закреплял старое поведение
текстом SQL и прямо называл его «единственным правилом, при котором содержимое общей ноды зависит
от порядка загрузки корпуса». Тест переписывается: проверять он будет новое условие, а его
докстринг сохранит запись о том, что было и почему изменилось.

### Ограничение не только наше, и оно не в рисках

Произвольность сравнения версий разных документов не выглядит особенностью прототипа: слияние
записей об одном предмете из нескольких источников, насколько я понимаю, требует правила
преобладания и в других областях, а само правило преобладания — самостоятельный вопрос, а не
побочный. **Это моя аналогия, а не установленный факт:** аналогия с каталогизацией возникает
первой, но на неё нельзя ссылаться как на правило, пока оно не проверено по источнику. Пока не
проверено — это подсказка, где искать, а не основание решения.

Записывать это в `docs/06` §2.7 не нужно: риск **закрыт** решением, произвольность — объявленное
ограничение решения, а не остаточный риск.

## ADR-045: «вклад графа не измерен» обязан называть причину в самом артефакте

**Статус:** Accepted (2026-10-02; решение владельца). Следствие: `infra/eval/run_eval.py`,
`prototype/tests/`.

### Отклонённое предложение: заменить `0.0` на `None`

Первая редакция этого ADR требовала в ветке `not_measured` писать `necessity = None` вместо `0.0`.
**Предложение отклонено: оно отменяет действующее решение, не прошедшее проверку.**

`graph_contribution` (`src/graphrag_proto/eval/metrics.py:130-147`) применяет конвенцию проекта
«ноль плюс флаг» (ADR-039, `job_resolvability.measured`): число остаётся вычислимым, а «измерено
ли» читается по отдельному признаку. Основание названо прямо: `None` в JSON-артефактах потребители
часто проглатывают молча, и тогда «не измерено» снова выглядит как ноль. То есть ровно тот молчащий
ноль, ради которого затевался ADR. Решение не опровергнуто, и отменять его на основании того, что
кто-то прочитал число вместо флага, — значит чинить симптом сменой конвенции.

Ветка `not_measured` в `_aggregate_graph_contribution` (`run_eval.py:1355-1365`) остаётся с
`necessity = 0.0` и `delta_recall = 0.0`.

### Что действительно не сделано

Флаг есть, но **не везде**. Отчёт предупреждает в двух случаях: `graph_axis_active = false`
(`run_eval.py:1677-1682`) и `degraded_questions > 0` (`:1683-1687`). Третий случай не покрыт:
`mode = "not_measured"` при `degraded_questions = 0`, то есть когда вклад не считался, потому что
в наборе нет графового среза. `docs/test_plan.md` §4 называет ровно этот вывод ложноотрицательным
(«не потому, что граф избыточен, а потому, что его нечего было искать»), а предупреждения в
отчёте для него нет: число `0.0` печатается в таблице без объяснения, `degraded_questions` равен
нулю и выглядит как «граф открылся, вопросов не пострадало».

### Решение

1. Агрегат получает `projection_statuses` — различные значения `projection_status`, собранные по
   вопросам. Причина перестаёт жить только в `qa_log.jsonl` и попадает в артефакт.
2. Отчёт предупреждает **при любом** `mode != "measured"`, называя число вырожденных вопросов и
   статусы проекции. Условие больше не зависит от того, обнулился ли счётчик.
3. Гард-тест: агрегат, у которого `mode` не `measured`, обязан нести хотя бы один
   `projection_status`. Формулировка положительная — «не измерено всегда с причиной», а не
   «причина не должна отсутствовать в этих трёх полях».

### Чего это не делает

Число остаётся нулём, и читатель, взявший только `necessity` из JSON, по-прежнему получит `0.0`.
Менять это можно только отменой ADR-039, а это отдельное решение с отдельным основанием. Наш прогон
не был молчащим: предупреждение о `degraded_questions` печаталось, и ошибка была в том, что читался
агрегат, а не предупреждение.

## ADR-046: готовность графа считается пораздельной — ревизия принадлежит своему источнику

**Статус:** Accepted (2026-10-02; решения владельца: вариант Б, ожидаемая ревизия хранится на
записи, миграции нет, содержательный `ready` отложен). Следствие: `docs/06` §2.6, §3.15,
`Ingest/analitic/…` §3.12 и §3.16; операторская кнопка вынесена в бандл
`add-operator-maintenance-controls`.

### Проблема, измеренная на стенде

`projection_revision` выводится из `data_revision` **всего домена** (ADR-026: `sha256` от набора
`(source_url, content_hash)`), а проставляется каждым ингестом **только своим** чанкам. Любая
следующая загрузка меняет доменную ревизию и делает ранее проставленные значения «не теми».

Замер домена `it`: 21 чанк, три активных документа, **три разных** ревизии — `2ada499c0abb` (10
чанков), `aac3ec7e854e` (9), `ed9ce919a31d` (2), тогда как состояние называет `2ada499c0abb`.
`verify_projection` (`retrieval/adapters/neo4j.py:771-779`) требует одну ревизию на весь домен, то
есть увидел бы 11 расхождений. Отдельно: `ready` недостижим из ингеста при нескольких источниках,
потому что условие `orchestrator.py:1600` требует `active_source_count <= 1`; ни это условие, ни
сама публикация состояния не закреплены тестом.

**Ключевое следствие, которое раньше осталось незамеченным:** ревизия, выведенная из отпечатка
**набора**, структурно не может ответить на вопрос «изменились ли данные этого источника» — только
«менялся ли состав целиком». То есть метка множества используется как метка элемента.

### Решение

1. **Ревизия принадлежит источнику.** Ожидаемая ревизия источника вычисляется из его
   `content_hash`, `config_fingerprint` и версии алгоритма — то есть **выводится**, а не хранится,
   и разойтись ей не с чем. Номер версии документа в вычислении не участвует.
2. **Ожидаемое значение лежит на `Source`-ноде.** `Source` получает `content_hash` и свою
   `projection_revision`. Нода пишется MERGE при каждой загрузке, то есть обновляется сама.
   Отклонённые альтернативы: перебор источников из реестра (по обращению на источник) и вынос
   ожидаемого значения в состояние — вторая добавляет дрейф между двумя хранилищами.
3. **Проверка — один запрос на домен:** для каждого `Chunk` его `Source`, и
   `chunk.projection_revision` должно совпадать с `source.projection_revision`. Ноль расхождений —
   готовность подтверждена. Это устраняет O(ребра) проверку, которой не хватало варианту А.
4. **Условие `active_source_count <= 1` снимается.** Готовность объявляется по завершении загрузки
   домена, а не по числу источников. Прямое следствие: состояние становится `ready` и публикуется
   последним коммитом батча — ровно тот случай, который система назвать не могла.
5. **`Source`-нода удаляется там же, где её чанки.** Места: перезагрузка документа
   (`orchestrator.py:1493-1495`) и удаление источника (`2315-2317`). Новый механизм не нужен.
6. **Пять направленных счётчиков**, а не равенство: `sources_active` (реестр), `source_nodes`
   (граф), `orphan_source_nodes` (ноды без активной строки реестра), `sources_without_graph`,
   `revision_mismatches`. Все — в состояние и в отчёт прогона. **Сравнивать счётчики нельзя:**
   до п. 5 расхождение гарантировано, после — временное, пока уборка не отработает.
7. **Гард-тест:** у каждого активного источника есть `Source`-нода с его `content_hash`, и ни один
   чанк не несёт ревизию, отличную от ревизии своего источника.

### Проверка риска, который сначала выглядел серьёзным

Предполагалось, что удаление `Source`-ноды сломает обход графа. **Риск не подтвердился:** ни один
запрос retrieval не матчит `Source`-ноды — обход идёт от чанков, найденных вектором
(`Chunk → MENTIONS → ContextNode`); единственный Cypher, который их трогает,
`list_chunk_ids_of_source` (`neo4j.py:161`), адресован по `node_id` и при отсутствии ноды
возвращает пустой список, что уже является правдой, поскольку её чанки удалены. Повторная загрузка
пересоздаёт ноду сама через MERGE.

### Побочное следствие для стоимости

Доменная ревизия сегодня считается на каждый документ (`data_revision_after`,
`storage/registry.py:211`) — скан всех активных документов домена, то есть O(N²) на загрузку
корпуса. Пораздельная ревизия O(1) на документ. **Замеров этих сканов нет**, поэтому «дешевле» —
это чтение кода, а не измерение.

### Чего не делаем и почему

**Содержательный `ready` отложен.** Он означал бы «прошёл юнит»: узлы на месте, каждое ребро
существует, у каждого `context_id` корректный provenance. Механика уже написана — `_verify_unit`
(`projection.py:792-847`), и job вызывает её после каждого юнита. Не хватает юнитов: ингест не
сохраняет enrichment per job, поэтому повторить и проверить нечего. Подробно и с оценкой работы —
`Ingest/analitic/manual_tags_and_ingest_open_questions.md` §3.16.

**Цена отказа, названная прямо:** пока содержательного `ready` нет, граница подтверждает **штам­пы,
а не содержимое графа**, и это должно быть сказано в отчёте, а не оставлено читателю.

## ADR-047: уборка не разделяет удалённые рёбра и узлы

**Статус:** Accepted (2026-10-02; найдено при реализации операторской кнопки). Правка кода — в
бандле `add-operator-maintenance-controls`.

**Проблема.** `delete_orphans` (`retrieval/adapters/neo4j.py:166-202`) считает рёбра и узлы
**отдельно** (`edge_count`, `node_count`), но возвращает их **суммой** — `return edge_count +
node_count`. А `run_orphan_cleanup` (`ingestion_service/retention_policy.py:134-143`) кладёт эту
сумму в `removed_relations`, а `planned_nodes` и `removed_nodes` проставляет константами `0`.

Итог: оператор видит в ответе «удалено N связей», где N включает удалённые узлы, и всегда видит
«удалено 0 узлов». Поле существует, называет узлы и всегда молчит.

**Почему это дефект, а не формальность.** Это ровно класс, который проект уже ловил: прибор
отдаёт значение, отличное от того, что делал код, и по имени поля это не читается. Ошибка не в
арифметике — она в том, что число **правдиво и подписано не тем**. Для приборной проверки это
работает (тест считает то же, что и предикат), для оператора — нет: он увидит «удалено 12 связей»
и решит, что связи удалены, хотя половина может быть узлами.

**Решение.**

1. `delete_orphans` возвращает раздельные счётчики, а не сумму.
2. `run_orphan_cleanup` кладёт их в соответствующие поля и пишет в реестр раздельно.
3. Гард-тест: если удалён хотя бы один узел, `removed_nodes` положителен. Иначе расхождение между
   подписью и значением вернётся молча.
4. До правки UI обязан **показывать оговорку**, а не делать вид, что поля разделены.

**Что сделано в этой правке.** UI показывает оговорку под результатом и не утверждает, что рёбра и
узлы разделены. Правка самих счётчиков вынесена в бандл: она трогает предикат удаления, где цена
ошибки — молчаливая потеря данных в графе, и требует отдельной проверки на реальном корпусе
(сценарий `docs/test_plan.md` §7.2).
