# Как гибридный RAG фильтрует изолированные острова контекста

Этот документ объясняет внутреннюю математику и алгоритмы, которые позволяют гибридным RAG-системам (Graph + Vector) эффективно собирать контекст из изолированных документов (островов), не перегружая контекстное окно большой языковой модели (LLM).

---

## 1. Анатомия Vector-First GraphRAG поиска

Когда вы описываете логику: *"Вектором находим чанки -> внутри чанков по мета-информации берем ноду -> смотрим соседние ноды"*, вы описываете паттерн **Vector-First GraphRAG** (или управляемый вектором локальный поиск).

### Пошаговая цепочка выполнения запроса:
1. **Пользовательский ввод:** Пользователь отправляет запрос (например: *«Соответствует ли структура наших таблиц в Postgres концепту безопасности?»*).
2. **Векторный зацеп:** Векторный поиск сканирует базу и находит наиболее релевантные куски текста. Допустим, он нашел Чанк №15 (из файла ADR по Postgres) и Чанк №3 (из Концепта безопасности). Они принадлежат к двум абсолютно разным, изолированным в графе "островам".
3. **Чтение метаданных:** Каждый чанк хранит в себе мета-информацию:
   ```json
   {
     "chunk_id": 15,
     "text": "Для хранения профилей пользователей используем PostgreSQL...",
     "associated_nodes": ["Node_PostgreSQL", "Node_User_Tables"]
   }
   ```
4. **Активация графа:** Система берет эти ID узлов (`Node_User_Tables` и `Node_Security_Rules`) и запрашивает их окружение в графовой БД в радиусе 1 шага (1-Hop). Граф разворачивает факты вокруг этих точек.

---

## 2. Проблема "Взрыва Контекста" на островах

Если под каждым островом (вокруг активированных нод) лежит по 10–20 чанков, суммарно мы получаем пул из 30–40 документов. Если отправить их в LLM «как есть», модель потеряет нить рассуждения (эффект *Lost in the Middle*) или исчерпает лимит токенов.

Чтобы этого не происходило, гибридный RAG применяет трехступенчатый алгоритмический фильтр, работающий как **хирургический скальпель**.

### Ступень 1: Первичная жесткая векторная отсечка (Similarity Threshold)
Векторный поиск находит острова не вслепую — он знает скор (косинусное сходство) каждого чанка. 
* Внутри Острова Безопасности из 10 чанков только 2 чанка напрямую говорят о шифровании данных пользователей (их скор равен `0.85`). Остальные 8 чанков описывают требования к паролям, VPN и сетевым доступам — их скор падает ниже `0.40`.
* Система применяет фильтр: `if similarity_score < 0.70: drop()`. Из 20 чанков на этом этапе мгновенно отсекается больше половины.

### Ступень 2: Топологическое пересечение сущностей (Entity Intersection Filter)
Система использует граф для того, чтобы отсеять чанки, которые семантически похожи, но уводят в сторону от конкретного вопроса.
1. Из текста запроса пользователя выделяются ключевые токены/сущности: `[PostgreSQL]`, `[Таблицы]`, `[Безопасность]`.
2. Система программно проверяет связи чанков внутри островов:
   * *Чанк №15* соединен в графе с узлом `[Таблицы]`. Количество совпадений с запросом = **1**.
   * *Чанк №19* (лежащий на том же острове Postgres) описывает стратегию бэкапов и соединен с узлом `[WAL-G]`. Количество совпадений с запросом = **0**.
3. Все чанки с нулевым совпадением по ключевым сущностям графа принудительно выбрасываются, даже если их векторный скор был неплохим.

### Ступень 3: Взаимное ранжирование (Reciprocal Rank Fusion — RRF)
Оставшиеся 4–5 кандидатов из обоих островов выстраиваются в финальный список на основе их позиций в выдаче обеих осей:

$$RRF\_Score(d) = rac{1}{60 + r_{vector}(d)} + rac{1}{60 + r_{graph}(d)}$$

Чанки, которые оказались одновременно важны и для векторного смысла, и для структуры графа, получают максимальный балл и поднимаются на самый верх.

## 3. Итоговый результат: Что уходит в LLM?

После работы всех трех ступеней фильтрации, от 20–30 исходных чанков двух изолированных островов остается жестко лимитированный топ (например, `Top-K = 3`):

1. **Чанк №15 (Остров Б):** Описание полей таблицы пользователей в Postgres (Векторный скор: 0.88, Граф-совпадение: Да).
2. **Чанк №3 (Остров А):** Правило концепта безопасности о шифровании персональных данных (Векторный скор: 0.85, Граф-совпадение: Да).
3. **Чанк №4 (Остров А):** Спецификация алгоритма AES-256 для баз данных (Векторный скор: 0.81, Граф-совпадение: Да).

Вместо каши из 20 страниц текста, LLM получает лаконичный контекст из **3 чанков (около 700 токенов)**. Она четко видит, какие поля заведены в базе данных, и какие требования к шифрованию предъявляет концепт безопасности. Модель выдает идеальный архитектурный аудит без галлюцинаций.
