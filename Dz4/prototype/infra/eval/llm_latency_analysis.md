# Анализ латентности LLM (M5 live, стек ohw-eval-s2)

> Неформальная замерочная заметка от 2026-09-19. Измерения — по логам llama-server
> в контейнере `ohw-eval-s2-llm-1` во время полного M5-прогона
> (`run_eval.py --mode hybrid`, датасет `it/questions.jsonl`, 50 вопросов) и пилотов
> baseline/hybrid (по 10 вопросов), гонявшихся в этом же контейнере ранее.

## Конфигурация стека

| Параметр | Значение |
|---|---|
| GPU | NVIDIA GeForce RTX 2070 Super 8 ГБ (Docker Desktop, WSL2) |
| Модель | Qwen2.5-Coder-7B-Instruct-abliterated-Q4_K_M.gguf |
| Запуск | `--n-gpu-layers 99` (полный offload), `--ctx-size 16384`, 4 слота, 8 потоков |
| Контекст ответа | ~7.5–8k токенов (RAG: vector + graph + chunk'и) |
| Eval-режим | hybrid, `EVAL_LLM_ADAPTER=openai` (реальный судья) |
| Стек сервисов | config / glossary / neo4j / embeddings / ingestion / llm / eval-runner |

## Методика измерения

1. Источник — `docker logs ohw-eval-s2-llm-1` (stdout llama-server).
2. Каждый вызов идентифицируется по строке
   `I slot launch_slot_: id X | task N | processing task` (старт) и
   `I slot release: id X | task N | stop processing: n_tokens = K` (финиш, число токенов).
   Wall-time вызова = разница префиксных таймстампов `минута.секунда.миллисекунды`.
3. Компьютерное (GPU) время каждого вызова — из `print_timing`:
   `prompt eval time = T ms / N tokens`, `eval time = T ms / N tokens`,
   `total time = ...`.
4. Классификация вызовов:
   - «большие» — суммарно >= 4000 токенов (`stop processing: n_tokens`);
   - «малые» — < 4000. Это разделение отделяет генерацию ответа/длиннопромптные
     вызовы от коротких судейских проверок.
5. Оценить, судья это или генерация, напрямую по логу нельзя (текст промптов в лог
   не пишется); разделение сделано по эвристикам (размер промпта, порядок вызовов).
6. Ограничения точности:
   - llama.cpp включает KV-кэш и переиспользует графы (`graphs reused`, растут до
   >20000 в конце) — per-task `total time` может занижать/перераспределять
   промпт-процессинг; wall-time по паре launch→release даёт верхнюю оценку.
   - Один контейнер llm обслуживал и пилоты, и M5 — часть вызовов в выборке — пилотные.
   - Префиксные таймстампы — «минута.секунда.мс», точность ~0.01 мин.

## Замеренные величины

### Пул вызовов за время жизни llm (пилоты + M5)

| Метрика | Значение |
|---|---|
| Всего вызовов с таймингом | 484 |
| Вызовов >= 4k токенов («большие») | 50 (всего ~10%) |
| из них >= 8k | 31 |
| из них 6–8k | 14 |
| из них 4–6k | 5 |
| Суммарное GPU-время «больших» (таймеры llama) | ~780 с |
| Суммарное GPU-время «малых» (таймеры llama) | ~280 с |

### Генерация одного ответа (7.5–8k контекст, 4 свежих вызова из M5)

| Вызов | Промпт | Генерация | Итого |
|---|---|---|---|
| task 23180 | 8062 ток, 9.2 с | 279 ток, 4.6 с | **13.9 с** |
| task 23733 | 7976 ток, 18.2 с | 381 ток, 7.4 с | **25.5 с** |
| task 24501 | 7883 ток, 9.8 с | 328 ток, 5.1 с | **14.9 с** |
| task 25034 | 7487 ток, 13.9 с | 143 ток, 4.7 с | **18.6 с** |

Установившийся режим (после прогрева): промпт-процессинг 8k токенов ≈ **0.44–0.87k ток/с
(9–18 с)**, генерация ≈ **50–65 ток/с**. Первый вызов в логе был заметно медленнее
(186 ток/с, 42 с на 8k) — прогрев KV-кэша/графа.

### Оценка прогресса M5

- Эвристика: «большие» вызовы с >= 4k токенов ≈ 1 генерация ответа + судейские вызовы
  с длинным промптом. На момент замера (≈52 мин прогона) ~24–26 из 50 вопросов;
  темп ≈ 2 мин/вопрос.
- Живых/завершённых «больших»: 44–50 (данные из двух проходов парсинга).

## Где основные потери

1. **Судья (LLM-judge оценка качества) — ~80–85% времени прогона.**
   - По числу вызовов: судья ≈ 90% (434 из 484 вызовов): разбиение ответа на факты,
     до 20 проверок groundedness, до 20 покрытий — каждый проверочный вызов повторно
     шлёт полный ответ в промпт (крупные 4–8k ток вызовы).
   - По времени: генерация ответа ≈ 15–25 с, but per-question eval ≈ 2 мин → остаток
     (1.5–1.75 мин) — судейские запросы.
   - В бою судьи НЕТ — это чисто eval-накладные.
2. **Длинный контекст.** Промпт 8k токенов = 9–18 с прогрева на каждый вызов огромного
   количества, и генерация при 8k контексте нелинейно дороже коротких.
   Реальный RAG (3–5 чанков по ~512 символов) → 2–3k токенов — в разы дешевле.
3. **Слабое железо.** RTX 2070 Super (2018 г., 8 ГБ) — mid-range; Q4 7B почти под завязку.
4. **Последовательный прогон eval** (вопросы по одному, 4 слота не используются).

## Что это означает для «боевого» применения (ответ пользователю)

Латентность одного ответа = ретрив (~1–3 с) + одна генерация с 8k контекстом (~15–25 с) =
**~20–30 с полного ответа** (первые токены со стримингом ~2–5 с). Для асинхронных и
потоковых сценариев это приемлемо.

Перенос на «нормальное» железо:
- 4090 / A100: промпт-процессинг и генерация ~3–6× быстрее → **5–10 с на ответ**.
- Короткий контекст (2–3k): промпт-прогрев ×3 дешевле + генерация заметно быстрее
  (внимание O(контекста)).
- Стриминг + кэш одинаковых вопросов снимают воспринимаемую задержку.

Вывод: узкое место не архитектура, а совокупность «дешёвое железо + полный контекст +
LLM-judge в eval». Ускорения добиваемся контекстом, GPU и отключением судьи для больших
прогонов (`EVAL_LLM_ADAPTER=fake`).

## Что добавить для точности в будущих прогонах

  (режим, время, метрики) для корректного расчёта точности и разложения времени
