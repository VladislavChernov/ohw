# Ревизия данных в query-контуре: аналитика и обоснование решений (Веха 4-хвост)

> **Контекст:** решение, отложенное на обсуждении свежести семантического кэша
> (2026-09-13). Проверяемый чеклист — `../../docs/prototype_requirements.md`
> §«Веха 4-хвост — Ревизия данных в query-контуре». Цель документа — объяснить
> «что это вообще такое» и дать обоснование вариантов по трём развилкам:
> гранулярность, источник ревизии, механизм доставки.

---

## 0. TL;DR

- **Проблема:** семантический кэш отдаёт ответы до `SEMANTIC_CACHE_TTL_S` (дефолт 3600 с),
  даже если данные в индексе только что изменились. Нет «отпечатка» того, какие данные
  (источники, переводы, издания) легли в основу ответа. В Dz4 — несколько источников
  на одну тему (две книги: EN + RU), и кэш не различает «по коллекции из 2 книг» vs
  «по коллекции из 3 книг».
- **Решение (суть вехи):** добавить **ревизию данных домена** в query-контур и включить её
  в **ключ кэша** (`query:sc:<rev>:<domain>`). Изменились данные → сменилась ревизия →
  запросы уходят в новый «слой» кэша (epoch), старый умирает по TTL. Дополнительно —
  ревизия становится **fingerprint'ом контекста ответа** для воспроизводимого Eval (ADR-015).
- **Рекомендации по развилкам:**
  1. Гранулярность — **по-доменная**; 2. Источник — **fingerprint активного сета**
  DocumentRegistry (и reused ADR-014 поля, без новой параллельной модели);
  3. Доставка — **`GET /revision` в ingestion + по-доменный `RevisionClient` в worker**.
- **Не меняется:** атомарность COMMIT (L2-04) и контракт pipeline. TTL ограничивает
  время жизни записи кэша, а revision определяет логическую эпоху данных; вместе они
  сокращают окно stale, но не заменяют проверку `done.revision` и manifest.

### Актуальная поправка к снимку

- `DocumentRegistry.data_revision(domain)` и endpoint `GET /api/v1/ingestion/revision`
  существуют; revision — fingerprint активного набора пар `(source_url, content_hash)`.
- Query worker получает revision через `RevisionClient`; отдельного фонового
  `DataRevisionPoller` с таким именем в текущем runtime нет.
- Semantic cache использует ключ `query:sc:<rev>:<domain>`; `revision=None`
  остаётся отдельным fallback-состоянием.
- Разные источники с одинаковым содержимым различаются, потому что в fingerprint
  входит `source_url`.

## 1. Что это такое вообще — объяснение «как студенту»

Представь настольную **справочную библиотеку** (это наша индексная БД: граф + векторы +
документы). В библиотеке не одна книга по теме, а **несколько**: например, по
«распределённым системам» — Kleppmann на английском и Tanenbaum на русском. Читатели
задают вопросы, и чтобы не перечитывать все книги каждый раз, библиотекарь
(query-контур) держит **карточку последнего хорошего ответа** (семантический кэш) — если
читатель спросил почти то же самое, ответ выдаётся сразу.

Теперь представь, что в библиотеку **привезли третью книгу** (ещё один автор/ещё один
язык). Старая карточка ответа всё ещё лежит — но она была собрана по *старой
коллекции* (две книги). Вопрос: сколько времени читатель может получать ответ,
основанный на неполной коллекции? Это и есть **свежесть данных (freshness)**.

В библиотеке не всё просто: книги могут быть разного года издания, переводы — от разных
переводчиков. Библиотекарю не важно *кто* автор — ему важно знать: **какие конкретно
книги сейчас стоят на полке** (active-источники). Если одна книга устарела и заменена на
другой перевод — это новое «поколение коллекции». Если прибавилась третья книга — тоже
новое поколение. Если ничего не изменилось — поколение то же.

У карточки есть два параметра старения:

1. **TTL (время)** — «карточка считается свежей 1 час, потом выбросить».
   Это неточно: если книгу обновили через секунду после кэширования, час старых ответов
   — слишком долго; если не обновляли вообще — час кэша выбросили зря.
2. **Ревизия (версия данных)** — «карточка помечена тем *поколением книг*, по которому
   её собрали». Если поколение изменилось — карточка устарела **немедленно**, и ответ
   пересобирается.

**Ревизия данных в query-контуре** = научить библиотеку понимать: «этот ответ собран по
данным поколения R». Тогда:

- кэш перестаёт полагаться только на время (TTL) и получает точный признак устаревания;
- у каждого ответа появляется **fingerprint** («по каким данным собран») — из него потом
  строится воспроизводимый Eval-срез (ADR-015): «метрики сняты на данных ревизии R».

Метафора из деплоя: это как **версия образа в контейнере**. Пока `latest` можно указывать
по-разному, но когда в запросе пишут конкретный `image:rev-42`, все получают одинаковую
неизменную сборку. Здесь мы хотим зафиксировать «rev-42» данных в контуре запроса, а не в
сборе.

## 2. Зачем это нужно: короткая теория

### 2.1. Инвалидация кэша — одна из «двух трудных задач»

Классика: *"There are only two hard things in Computer Science: cache invalidation and
naming things"* (Phil Karlton). Цитата живёт потому, что способы инвалидации имеют разные
гарантии и цену. Основные стратегии:

| Стратегия | Идея | Гарантия свежести | Цена |
|---|---|---|---|
| **TTL** (время жизни) | запись живёт N секунд | «не старее N секунд» | дешёвая, но грубая |
| **Эксплицитная инвалидация** | при записи данных удаляем/обновляем затронутые ключи | сильная, «как в индексе» | нужна карта «данное → ключи», дорогая |
| **Epoch / versioned keys** | в ключ входит версия данных; при bump — новый слой | «не старее ревизии R» | нужна доставка версии в читателя (наша веха) |

См. также: cache invalidation / cache replacement policies (Wikipedia), RFC 9111
(HTTP caching), дизайн-паттерны cache-aside, write-through.

### 2.2. Bounded staleness — «ограниченная усталость»

В распределённой семантике consistency моделей (Wikipedia: Consistency models) есть
промежуточный класс между «просто eventual» и «строго линейизуемым» — **bounded staleness**
(ограниченная устарелость): читатель гарантированно видит данные «не старше», чем
некоторое окно/версия.

Для нашей системы это выглядит так:

- ingestion пишет данные асинхронно (конвейер INGEST→COMMIT, ADR-018/021);
- query-контур читает индекс и кэш;
- без ревизии: свежесть ответа определяется моно-памятью TTL («может быть старым до часа»,
  инвариант L2-07 «свежесть ансвера = свежесть данных»).
- с ревизией: обещание становится явным — **«ответ не старше ревизии R»**, где R —
  состояние данных на момент сборки. Это и есть то, что мы должны зафиксировать в
  `../../docs/invariants.md` L2-07 (пункт вехи).

### 2.3. Fingerprint / content addressing — «отпечаток данных»

Fingerprint (отпечаток) — это короткий хэш содержимого. Вместо «ревизия 3» (счётчик)
мы говорим «sha256(список активных пар source_url + content_hash)». Свойства:

- **идемпотентность:** повторный INGEST того же контента (no-op, ADR-014) не меняет
  отпечаток → кэш не инвалидируется вхолостую;
- **честность:** отпечаток отражает *реальные данные*, а не «сколько раз кто-то нажал
  кнопку»;
- **переиспользование:** у каждой записи DocumentRegistry уже есть `source_url` и
  `content_hash` (ADR-014). Агрегат этих пар по домену — и есть «версия данных домена».

Аналогии из практики: IPFS/content-addressable storage, git (commit = дерево хэшей),
Merkle tree, checksums в пакетных менеджерах.

### 2.3.1. Много источников на одну тему — «разные издания одной книги»

Исходная концепция Dz4: **две книги на одну тему** (например, «распределённые
системы») — одна на английском, другая на русском, от разных авторов. Это
именно тот случай, который определяет, **почемуingerprint правильный выбор**, а
не монотонный счётчик.

**Как это лежит в данных (ADR-014):**

```
domain = "distributed_systems"

source_url = "book_en_kleppmann.pdf"
  content_hash = sha256(содержимое) = "abc123"
  version = 1, status = active

source_url = "book_ru_tanenbaum.pdf"
  content_hash = sha256(содержимое) = "def456"
  version = 1, status = active
```

Идентичность документа — `(domain, source_url)`. Две книги = два разных
`source_url` в одном домене. У каждого свой `content_hash` и своя
монотонная `version` (ADR-014: монотонная per source).

**Fingerprint домена (наша ревизия):**

```
rev(domain) = sha256(sorted([("book_en_kleppmann.pdf", "abc123"),
                              ("book_ru_tanenbaum.pdf", "def456")]))
             = sha256("book_en_kleppmann.pdf\\0abc123\\n"
                      "book_ru_tanenbaum.pdf\\0def456\\n")
             = "xyz789..."
```

**Что происходит при разных сценариях:**

| Сценарий | Что меняется в DocumentRegistry | Fingerprint |
|---|---|---|
| Добавлена третья книга (fr-перевод) | Новая запись `source_url="book_fr_xxx"`, content_hash="ghi789", active | `sha256(sorted((source_url, content_hash) для active-документов))` — **изменился** ✅ |
| Один из переводов устарел (superseded) | Старая запись → `status=superseded`, новая версия активна | **изменился** ✅ |
| Книгу удалили (soft delete) | `status=deleted` — выпадает из active-множества | **изменился** ✅ |
| Переиндексация того же контента (no-op) | Тот же `content_hash` → `(doc_id, version, False)` — ничего не меняется | **не изменился** ✅ |
| Одну книгу перевели заново (другой переводчик) | Старый active → superseded, новая active с новым `content_hash` | **изменился** ✅ |

**Почему счётчик тут сломается:** монотонный counter «+1 на каждый COMMIT»
не отражает, *какие* документы в домене. Если два одинаковых INGEST-а пройдут
для разных sources (оба成功 no-op для разных sources) — counter bump'нется
вхолостую, кэш сбросится без причины. Fingerprint — честный: если набор
active-документов не изменился, fingerprint тоже не изменился.

**Ключевой момент для Analogy:**

Вернёмся к библиотечной аналогии. Две книги на одну тему (Kleppmann EN +
Tanenbaum RU) = два разных **источника** в одном **домене**. «Поколение
библиотеки» = **какие конкретно книги** сейчас на полке (active). Если
прибавился третий перевод — поколение сменилось (rev изменился). Если
одну книгу заменили на переиздание — поколение тоже сменилось. Если ни
одной книги не добавили/не удалили — поколение то же.

Это не «ревизия каждой книги» (это per-source version), а **ревизия
коллекции** — «какие книги сейчас на полке в домене».

### 2.4. Polling vs события (pull vs push)

Доставка «версия изменилась» из писателя (ingestion) в читателя (query) имеет две
классические схемы:

- **Polling (pull):** читатель периодически спрашивает «а изменилось ли?» и сравнивает.
  Просто, доставляемо (retry), отказоустойчиво к перезапускам; цена — задержка (интервал)
  и лишние запросы.
- **Events (push):** писатель публикует событие, читатель подписан. Меньшая задержка, но
  нужен транспорт (Redis Streams / канал), обработка потери событий (компенсировать
  всё равно final-поллингом или чтением текущего состояния), а также бритва в inmemory-режиме.

Паттерн в проекте уже выбран: поллер топологии `_topology_rebuilder` в `worker.py`
сравнивает `client.revision(refresh=True)`. Ревизия данных — то же самое, другим источником.
Один механизм, одно «чувство согласованности» — это и есть «решение общее для всего
query-контура» (формулировка вехи).

### 2.5. Почему «именно сейчас», а не «в уже существующем TTL достаточно»

1. **Eval (M4).** Метрики AI = f(данные). Без зафиксированной ревизии знаний срез
   невоспроизводим: пересняли метрики после изменения данных — «почему упало?»
   Ответа нет. ADR-015 требует «фиксировать ревизию знаний в срезе».
2. **Коннекторы (M6, предусловие веха 4-хвост).** Потоковые источники делают окно
   «пока не истёк TTL» бизнес-критичным; изображение реального времени без версии данных
   невозможно.
3. **Конфигуратор профилей (M5).** Профиль меняет онтологию онлайн — нужен fingerprint
   контекста до/в паре с инвалидацией кэша.

## 4. Развилки и варианты

### Р1. Гранулярность ревизии: глобальная vs по-доменная

**Вопрос (текст вехи):** «Определить гранулярность ревизии: глобальная vs по-доменная —
решение общее для всего query-контура, не только для кэша».

**Что это означает.**
- *Глобальная*: одно число `rev` на всю платформу. Любой INGEST в домен `it`
  инвалидирует кэш и домена `legal`, и всех остальных.
- *По-доменная*: у каждого домена (`it`, `legal`, …) своё `rev<domain>`. Изменения в одном
  домене не трогают кэши других.

**Аргументы за по-доменную.**
1. **Существующая размерность.** Кэш уже *по-доменный* (ключ `query:sc:<domain>`),
   профили/онтология/словари — по-доменные, ingestion — по-доменный. Ломать симметрию
   было бы странно.
2. **Изоляция инвалидации.** Multi-domain нагрузка: переиндексация `it` не должна сжигать
   накопленный кэш `legal` (в противном случае TTL-кэш почти не работает на домене,
   который «недавно обновлялся где-то рядом»).
3. **Eval по-доменный.** Еval-датасеты живут в `prototype/infra/eval/{domain}/` — срез
   фиксирует ревизию знаний конкретного домена.
4. **Простота «общего решения»:** токен `rev<domain>` легко превращается в «глобальный»,
   если будущее потребует (частный случай), а наоборот — нет без переписывания ключей.

**Цена по-доменной:** ревизия должна считаться отдельно на домен (агрегат пар
`(source_url, content_hash)` активных документов домена — и есть она), поллер/эндпоинт
отдают ревизию по домену.

**Аргументы за глобальную:** проще (один счётчик), меньше логики. Но ценой бесполезности
кэша в multi-domain и — главное — противоречит принципу доменной изоляции L1-01
(«ядро не знает домен») и размерности остального контура.

**Рекомендация: по-доменная.** Она согласуется с «общее для всего query-контура»:
fingerprint ответа = f(домен) — для кэша и для Eval это одна и та же ось.

### Р2. Источник ревизии данных домена

**Вопрос: (а) fingerprint активного сета DocumentRegistry или (б) монотонный counter?**

**Вариант (а) — fingerprint активного сета.**
`rev(domain) = sha256` отсортированного списка пар `(source_url, content_hash)` активных документов.
- Активные = `status='active'`; superseded/deleted не входят.
- Идемпотентен: no-op INGEST (тот же `source_url` и `content_hash`) не меняет отпечатка → нет
  инвалидации вхолостую (соответствует ADR-014 no-op).
- Честен: реально отражает данные; delete/supersede убирают/меняют элемент → rev меняется.
- Переиспользование: поля `source_url`, `content_hash`, `status` уже есть (ADR-014) — «без новой
  параллельной модели ревизии» (точная формулировка вехи).

**Вариант (б) — монотонный counter на COMMIT.**
Новая таблица/счётчик, `rev += 1` при каждом реальном COMMIT/soft-delete домена.
- Проще вычислить (инкремент), но *не idempotent*: повторная переиндексация того же
  контента bump'ает rev, кэш сбрасывается вхолостую.
- Не является fingerprint-ом: «ревизия 7» ничего не говорит о данных; нельзя сравнить
  два окружения («одинаковые ли данные?» — сравнить rev нельзя, только хэши).

**Сравнение:**

| Критерий | (а) fingerprint set | (б) counter |
|---|---|---|
| Идемпотентность no-op | ✅ | ❌ |
| Отражает реальные данные | ✅ | ❌ (счётчик нажатий) |
| Переиспользует ADR-014 | ✅ | ❌ (новая модель/таблица) |
| Сложность вычисления | чуть больше (агрегат хэшей) | тривиально |
| Полезен для Eval (сравнение срезов) | ✅ (одинаковые данные = одинаковый отпечаток) | ⚠️ (rev переехала, метрики несопоставимы по смыслу) |

**Рекомендация: (а) — fingerprint активного сета** через существующие `source_url`
и `content_hash` (ADR-014). Канонично для source-aware identity и переиспользует модель
без новой параллельной.

### Р3. Механизм доставки ревизии в query-контур

**Вариант (а) — endpoint `GET` в ingestion + поллер в worker.**
- Ingestion: `GET /api/v1/ingestion/revision?domain=...` (X-API-Key, L5-01) →
  `{"revision": "<sha256>", "updated_at": ...}`.
- Query: поллер в `worker.main()` по аналогии с `_topology_rebuilder`
  (`TOPOLOGY_POLL_INTERVAL`), при изменении rev → актуализировать rev-зависимые лэйеры,
  кэш построен один раз и общий (ADR-025: старый слой `query:sc:<oldrev>:<domain>` умирает
  по TTL).
- `QueryPipeline` получает `rev(domain)` (из кэша/холдера) и прокидывает в
  `lookup(embedding, threshold, rev, domain)` / `store(...)`.

Преимущества: паттерн уже доказан в проекте (поллер топологии); retry/доставка бесплатны;
не требует новой инфраструктуры поверх Valkey; работает в inmemory-режиме.

Цена: задержка = интервал поллинга (около секунды-десятков секунд); лишний GET.

**Вариант (б) — Redis pub/sub при COMMIT.**
- Ingestion публикует в `query:revision:{domain}` (XADD/XREADGROUP как в ADR-023).
- Worker-подписчик при событии актуализирует rev.
Преимущества: меньшая задержка. Цена: второй транспорт для событий, обработка потерь событий
(подписчик перезапускался → пропустил bump → «почему кэш живёт?»), не работает в
inmemory-режиме, дублирует логику поллера для компенсации. Для нашей архитектуры
(TTL ограничивает время повторного использования записи) задержка не критична.

**Рекомендация: (а) — endpoint + поллер**, копируя работу `_topology_rebuilder`.
Один механизм согласованности на весь контур — «решение общее» для топологии и данных.
Если позже понадобится задержка-реактивность, поллер можно так же просто заменить на
подписчика, не меняя ни ABC кэша, ни контракт key.

## 5. Итоговое решение и его текущий статус

1. **Ingestion:** реализованы `DocumentRegistry.data_revision(domain)` и endpoint
   `GET /api/v1/ingestion/revision?domain=` (X-API-Key).
2. **Query:** используется `RevisionClient` с polling-интервалом; отдельного класса
   `DataRevisionPoller` в runtime нет. Revision передаётся в pipeline/cache.
3. **Кэш:** ключ Redis — `query:sc:<rev>:<domain>`; InMemory разделяет записи по
   `(rev, domain)`. Старые слои удаляются по TTL.
4. **Pipeline:** `done` содержит source-aware revision; semantic cache lookup/store
   учитывают epoch.
5. **Eval:** manifest/qa_log фиксируют source-aware revision; `fetch_revision` и
   проверка `done.revision` fail-closed на пустое/невалидное значение.
6. **Граница:** fingerprint пар `(source_url, content_hash)` различает источники с
   одинаковым содержимым, но не является полной идентичностью корпуса.

Контракты pipeline/API в основном сохранились; старые записи кэша умирают по TTL.
