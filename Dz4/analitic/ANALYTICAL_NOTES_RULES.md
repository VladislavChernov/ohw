# Правила для аналитических записок (sol_pro)

> Это руководство — внутренний стандарт оформления аналитических документов в `Dz4/`.
> Все новые аналитические записки должны следовать этим правилам.
>
> Материал, который не является проектной аналитикой (методички, внешние обзоры для
> самостоятельного чтения), в репозиторий не попадает вовсе.

## 0. Где лежит аналитика

> **Читать до написания.** Аналитика в проекте появилась раньше этих правил, поэтому папки
> не выглядят однородно, и легко положить записку не туда. Ниже — фактическая карта на
> 2026-09-27; она важнее интуиции «так принято в других проектах».

| Путь | Что туда кладётся | Что уже лежит |
|---|---|---|
| `Ingest/analitic/` | **всё про модуль ингеста**: конвейер, стадии, запись, provenance, ручные теги и связи, поведение экстракции | 6 записей, включая `manual_tags_and_ingest_open_questions.md` |
| `Retrieval/analitic/` | **всё про модуль запроса**: профиль со стороны retrieval, настройки расширения, что фактически применено, дрейф конфигурации | 1 запись: `retrieval_config_and_open_questions.md` |
| `analitic/eval/` | измерение качества: eval-датасеты, метрики, судья, gold set, ревизия корпуса перед прогоном | `dataset_and_docs_review.md`, `gold_set_proposals.md`, `judge_calibration_analysis.md` |
| `analitic/revision/` | ревизия данных и bounded staleness | `data_revision_analytics.md` |
| `analitic/` (корень) | **сквозная** аналитика, не относящаяся к одному модулю, и сами правила | `hardcoded_parameters_inventory.md`, `ANALYTICAL_NOTES_RULES.md` |

Правила размещения:

1. **Запись относится туда, чей модуль она разбирает, а не туда, где её писали.** Аналитика
   по extract-стадии ингеста — это `Ingest/analitic/`, даже если писалась подряд с кодом
   ретрива.
2. **Папка модуля пишется через имя модуля, а не через `analitic/<модуль>/`.** Для ингеста это
   `Ingest/analitic/`, для запроса — `Retrieval/analitic/` — так уже сделано и так указано
   здесь. Создавать `analitic/ingest/` нельзя: это не тот путь, и заметка окажется отдельно
   от остальной аналитики по ингесту.
3. **Сквозная аналитика** (инвентаризация параметров, обзор архитектур) идёт в корень
   `analitic/`. Если не можешь решить, модуль это или нет, — клади в корень и указывай в
   заголовке, какие модули затронуты.
4. **Папка `Ingest/analitic/` не является подпапкой `analitic/`.** Это разные деревья: правила
   лежат в `analitic/`, а аналитика по ингесту — в `Ingest/analitic/`. Отсюда и главная ошибка
   при размещении.
5. История расхождения: аналитические записки появлялись спонтанно и складывались в
   `Ingest/analitic/` с 2026-09-19; правила сформулированы позже (2026-09-22, компоновка
   уточнена 2026-09-26 коммитом `520f47d`, который вынес аналитику по качеству измерения из
   папки ингеста в `analitic/eval/`). Поэтому распределение выглядит несимметричным — это
   не ошибка, и «приводить к симметрии» не нужно.

## 1. Структура аналитической записки

Каждая записка должна содержать следующие разделы (в указанном порядке):

### 1.1 Шапка

```markdown
# [Название записки]

**Команда:** <автор или команда>  
**Дата:** YYYY-MM-DD  
**Статус:** Аналитика (фаза N) / Проектирование / Реализация / Review
**Язык:** русский (или английский, если указано)
```

- `Название записки` — информативное, отражает суть анализа
- `Команда:` - обязательное поле: автор или команда, которая делала разбор. Значение свободное и не привязано к модели или роли в проекте
- `Дата:` — дата создания или последнего обновления
- `Статус:` — текущий этап работы

### 1.2 Введение

Раздел **Введение** должен содержать:

1. **Контекст проблемы** — что анализируется, почему это важно
2. **Перечисление источников** — какие материалы прочитаны, какие папки/файлы исследованы
3. **Цель анализа** — конкретный вопрос, на который нужно ответить

### 1.3 Исследованные материалы

Раздел **Исследованные материалы** должен содержать список просмотренных файлов с краткой аннотацией:

- Название файла
- Тип документа
- Ключевая идея (1-2 предложения)
- Автор/дата (если известно)

### 1.4 Анализ текущего состояния

Раздел **Анализ текущего состояния** должен содержать:

- Описание проблем текущей реализации (проблемы, ограничения)
- Последствия этих проблем

Каждая проблема нумеруется и содержит ссылку на файл/строки кода.

### 1.5 Анализ предложений

Раздел **Анализ предложений** должен содержать оценку каждого исследованного предложения:

- Плюсы
- Минусы / риски
- Применимость к текущему проекту (Высокая / Средняя / Низкая / Откладывается)

### 1.6 Сравнительная таблица

Если исследовано более 2 предложений, должен быть раздел **Сравнительная таблица** в формате:

| Критерий | Предложение A | Предложение B | Предложение C |
|---|---|---|---|
| Критерий 1 | оценка | оценка | оценка |
| Критерий 2 | оценка | оценка | оценка |

Критерии для сравнения (пример):
- Решает ли конкретную проблему
- Не ломает ли концепцию/архитектуру
- Требует ли LLM
- Требует ли новые компоненты
- Применимо ли к текущей фазе (M1-M2 / M3+)

### 1.7 Рекомендации

Раздел **Рекомендации** должен содержать:

- Рекомендуемый путь для текущего этапа
- Аргументация `почему`
- Что нужно доработать в выбранном предложении перед реализацией
- Чек-лист для следующей фазы

### 1.8 Итог


Цитаты из прочитанных файлов должны быть в блоке `>`:

```markdown
> `Текст цитаты из предложения`
```

### 2.4 Таблицы

- Использовать стандартный Markdown-синтаксис
- Заголовки столбцов — информативные
- Избегать таблиц шире 6-7 столбцов

### 2.5 Списки

- Для нумерованных проблем/этапов — использовать `1. 2. 3.`
- Для не нумерованных — использовать `-`
- Глубина вложенности — не более 3 уровней

## 3. Правила содержания

### 3.1 Объективность

- Избегать оценочных суждений без обоснования
- Если говорим `это хорошо/плохо`, добавлять `потому что...`
- Указывать, что является утверждением автора, а что — фактом из материалов

### 3.2 Ссылки на источники

- Все утверждения, основанные на прочитанных материалах, должны иметь ссылку на файл
- Факты из кода — ссылки на файлы и строки
- Факты из предложений — ссылки на файлы предложений

### 3.3 Чёткие рекомендации

- Рекомендации должны быть конкретными, а не общими

### 3.4 Нестандартные ситуации

- Если материал не найден — указать это явно
- Если информация противоречивая — описать оба viewpoints
- Если предложение зависит от другого — указать зависимость

## 4. Чек-лист перед сохранением

- [ ] Заголовок информативен
- [ ] Указана команда, дата, статус
- [ ] Все исследованные файлы перечислены в разделе 2
- [ ] Каждая проблема содержит ссылку на код
- [ ] Каждое предложение оценено по плюсам/минусам/применимости
- [ ] Есть сравнительная таблица (если более 2 предложений)
- [ ] Рекомендации конкретные, а не общие
- [ ] Указаны следующие шаги (что делать дальше)
- [ ] Ссылки на связанные документы в Dz4 (ADR, openspec, code, docs)

## 5. Пример минимальной записки

Для быстрых анализов (1-2 файла, простой вопрос) можно использовать сокращённую версию:

```markdown
# [Название]

**Команда:** <автор или команда>  
**Дата:** YYYY-MM-DD  
**Статус:** Аналитика

## Контекст

[1-2 предложения]

## Прочитано

- `файл1.txt`: [ключевая идея]
- `файл2.md`: [ключевая идея]

## Проблема

[описание]

## Анализ

[оценка каждого предложения]

## Рекомендация

[конкретная рекомендация]

## Следующие шаги

1. [шаг 1]
2. [шаг 2]
```

Раздел **Итог** должен содержать:

- Таблицу `Что решено / Что не решено` по каждому предложению
- Что нужно сделать в следующей фазе

### 1.9 Приложения (опционально)

Раздел **Приложения** может содержать ссылки на файлы/папки, дополнительные материалы, связанные документы.

## 2. Стиль и оформление

### 2.1 Язык

- По умолчанию — русский
- Технические термины — на английском (с пояснением при первом упоминании)
- Ссылки на файлы — в формате `путь/к/файлу`
- Ссылки на строки кода — в формате `файл.py:строка-строка`

### 2.2 Оформление ссылок на код

```markdown
Файл: `orchestrator.py:151-165`
```

### 2.3 Оформление цитат из предложений
