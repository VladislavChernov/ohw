# Профиль как опора: настройки retrieval, их учёт и как это делают в больших системах

**Вопрос:** Как должна быть устроена настройка retrieval-половины профиля (глубина поиска,
состав расширения, boost, лимит контекста), чтобы ею можно было пользоваться и чтобы прогон
измерения мог сказать, какими настройками он измерен?
**Команда:** opencode (сессия 2026-09-27)
**Дата:** 2026-09-27
**Источник:** код `prototype/src/graphrag_proto/retrieval/`, `prototype/infra/eval/run_eval.py`,
`prototype/infra/compose.yaml`; `Ingest/analitic/manual_tags_and_ingest_open_questions.md` §3.11;
документация MLflow Tracking и Kubernetes ConfigMap
**Статус:** Аналитика

## 1. Введение

### 1.1 Контекст

Профиль домена — один YAML на две разные стороны системы. Его `extraction.*` читает ингест,
его `retrieval.*` и `context_assembly.*` — запрос. Ингестовая половина разобрана и закрыта
валидатором контракта (`prototype/src/graphrag_proto/ingestion_service/pipeline/profile_contract.py`,
коммит `fe8dcea`). Retrieval-половина не разобрана, и разбор 2026-09-27 показал, что
разница не в «есть проверка или нет», а в **цене ошибки**: ошибка в `extraction.*` необратима
(потерянный слой не восстановить, `content_hash` → no-op), ошибка в `retrieval.*` меняет ответ
пользователя, но данные целы.

Этот разбор отвечает на два вопроса, заданных отдельно:

1. как устроить настройки retrieval так, чтобы ими можно было пользоваться, и чтобы прогон
   фиксировал, чем он измерен;
2. как это делают в системах, которые эксплуатируют, — не по памяти, а по документации.

## 2. Анализ текущего состояния

### 2.1 Где стоит точка и что она решает

`QueryPipeline.run()` читает профиль один раз на запрос (`pipeline.py:227`) — не на прогон,
не на процесс. Дальше из него берутся: включён ли граф, лимит контекста, глубина и
направление расширения, виды рёбер, фан-аут, потолок узлов, boost и релевантность
источников. То есть **эта точка стоит на пути каждого ответа пользователя**, а не раз за
прогон, и ошибка в ней меняет ответ, а не артефакт.

### 2.2 Проблемы

1. **«Strict» проверяет одну строку.** `pipeline.py:76-78` проверяет
   `isinstance(profile, dict)` и всё. Имя обещает проверку содержимого — даёт проверку типа.
   Ошибка загрузки (файла нет) в eval падает громко, битое **значение** проходит молча.

2. **Одно поле, три разных поведения.**
   - `max_depth` / `max_fanout` / `max_graph_nodes` не число → `int()` → ValueError → широкий
     `except Exception` (`pipeline.py:447`) → `graph_degraded` → вопрос выпадает из измеренного
     среза. То есть **опечатка в одной строке профиля обнуляет вклад графа целиком** и
     обнуляет прогон по пути `degraded_questions`.
   - `graph_boost` не число → терпимая ветка на `pipeline.py:464-467` **недостижима**: то же
     поле вычисляется раньше, в теле trace-события (`pipeline.py:441`), а аргумент функции
     вычисляется до вызова, то есть даже при выключенном trace. Обработчик есть и не работает.
   - `retrieval` не mapping → `AttributeError` → 500 пользователю. В eval не достигается:
     `graph_search_enabled` (`pipeline.py:63-73`) читает env первым, а `graph_toggle`
     (`run_eval.py:897`) выставляет `RETRIEVAL_GRAPH_ENABLED` на весь прогон.

3. **Мёртвое чтение превращает «работает с дефолтом» в «деградировало».** Даже если починить
   (2), останется правильная, но незаметная деградация: `graph_boost` станет 0, и в артефакте
   будет «граф использован», хотя boost не применялся. `graph_degraded` этого не показывает.

4. **Артефакт не знает, каким конфигом измерен.** `run_manifest` пишет `code_commit`,
   `revision`, `timeouts` — профиля нет. `code_tree` приходит из env и по умолчанию `unknown`.
   `run_eval.py:1278` читает `graph_boost` **из trace-события**, то есть при выключенном trace
   это поле всегда `None`: запись о применённой настройке зависит от отладочного флага.

5. **Конфиг перечитывается на каждый запрос, кэша нет.** `../domain_profiles` — bind mount с
   хоста в шести сервисах; Config Service читает YAML на каждый HTTP-запрос
   (`config_service/app.py:81`); загрузчик кэша не имеет. Три секунды таймаута — внутри
   пользовательского запроса. Дрейф возможен только если человек правит файл на хосте
   (или делает `git pull`) во время прогона, но **следов у дрейфа нет никаких**.

6. **Вне eval ошибка загрузки не видна вообще.** `strict_profile=False` (дефолт
   `query_service/runtime.py:88`) → пустой профиль `{retrieval:{}, context_assembly:{}, ontology:{}}`
   → все параметры уходят в кодовые дефолты (`max_depth=2`, `max_fanout=8`,
   `max_graph_nodes=5`, `boost=0`). Граф при этом включён env'ом
   (`compose.yaml:366`, дефолт `true`), то есть система отвечает и выглядит рабочей.

### 2.3 Последствия

| Проблема | Что происходит | Кто узнаёт |
|---|---|---|
| 2.1 | битое значение не отличить от корректного | никто |
| 2.2 | опечатка обнуляет вклад графа | паспорт: `degraded_questions`, вердикт `invalid` |
| 2.3 | «граф есть, boost не применён» | **никто** |
| 2.4 | отчёт невоспроизводим по конфигу | **никто** |
| 2.5 | +3 с к запросу при недоступности Config Service | пользователь (по времени) |
| 2.6 | ответы на дефолтах выглядят как штатные | **никто** |

Асимметрия с ингестом: там провал виден в `ingest_report.json` и инвалидирует вердикт. Здесь
провал виден в единичном случае, когда попал в широкий `except`, и не виден вовсе, когда
конфиг просто не применился.

## 3. Как это делают в больших системах

Ниже — только то, что подтверждается документацией двух widely-used систем. Это не обзор
рынка и не «все так делают»; это две точки, где поведение описано явно.

### 3.1 Паттерн A: конфигурация — поле прогона, а не следствие версии кода

MLflow логирует параметры как отдельные сущности прогона рядом с версией кода и метриками
(`mlflow.log_param`), и связывает метрики с конкретными наборами данных для честного сравнения.

> MLflow Tracking is an API and UI for logging parameters, code versions, metrics, and
> output files when running your machine learning code

Почему это важно именно здесь: если параметр не записан, его нельзя восстановить из версии
кода, когда код менялся. У нас `code_commit` есть, а конфига нет — и это не «мелочь для
аккуратности», а недостающая третья нога: **код / данные / конфигурация**. Две ноги есть,
третьей нет, и отчёт неполон по построению.

### 3.2 Паттерн B: конфигурация закрепляется на старте либо имеет явную задержку

Kubernetes описывает четыре способа потребления ConfigMap и прямо говорит, что они
различаются способом моделирования данных, и что по-разному ведут себя при изменении:

> For the first three methods, the kubelet uses the data from the ConfigMap when it launches
> container(s) for a Pod. The fourth method means you have to write code to read a ConfigMap…

> ConfigMaps consumed as environment variables are not updated automatically and require a
> pod restart.

> When a ConfigMap currently consumed in a volume is updated, projected keys are eventually
> updated as well… the total delay from the moment when the ConfigMap is updated… can be as
> long as the kubelet sync period + cache propagation delay, where the cache propagation delay
> depends on the chosen cache type

То есть в системе, которой это не безразлично, есть ровно три осознанных варианта: закрепить
на старте (env, нужен рестарт), отдавать с **ограниченной** задержкой (файл + настраиваемая
стратегия кэша), или самому подписываться на изменения. Варианта «молча перечитывать на
каждый запрос без кэша, без версии и без следа» в этом списке нет — он не «другой вариант»,
а отсутствие выбора.

### 3.3 Паттерн C: неизменяемость как средство защиты

Kubernetes предлагает `immutable: true` у ConfigMap и объясняет, зачем:

> protects you from accidental (or unwanted) updates that could cause applications outages

Признание проблемы ровно нашей: «конфигурация не должна меняться под работающей нагрузкой,
и если это произошло — это авария, а не новая норма». У нас есть чему учиться: для
измерения профиль вообще должен быть неизменяем на время прогона.

### 3.4 Паттерн D: отдавать применённое, а не запрошенное

Ни одна из двух систем не «молчит о применённом», потому что показывает фактическое
состояние объекта (`kubectl get` отдаёт текущий объект целиком, включая defaulted-поля).
Общий принцип: потребителю отвечают **эффективной** конфигурацией, а не той, которую
попросили, — иначе «применилось с дефолтом» и «применилось как просили» неразличимы.

**Вывод по источникам:** три из четырёх паттернов сводятся к одному: **конфигурация должна
иметь идентичность, момент применения и право быть устаревшей — все три должны быть названы
в артефакте измерения.** У нас не названо ни одно из трёх.

## 4. Модель «опора», предложенная в разговоре

Отдельно от настроек, потому что это другой вопрос: пользователь мыслит профиль как **опору**
— шаблон с начальными данными, поверх которого он может руками проставить ноды и рёбра, и
почти то же — для правил извлечения.

Эта модель в проекте **уже реализована частично**, и стоит назвать её, а не изобретать:

| Слой | Что это | Где живёт | Кто пишет |
|---|---|---|---|
| извлечённый | сущности и связи, полученные из текста | граф | модель |
| **курируемый** | ручные теги, `tag_id` от человека | граф, `curated` | человек |
| правила | канонизация, синонимы, типы | профиль, `canonicalization` | человек |
| глоссарий | термины домена, сложные alias'ы | `glossary.*.yaml` | человек |

То есть «опора» — это уже существующий стек из трёх курируемых слоёв поверх машинного, и
единственное, чего не хватает, — **имени для этой конструкции и её границы**. Пункт 3
уровней доверия (`curated` / `proposed` / `rejected`) из открытых вопросов ингеста — это ровно
про неё, и она относится к обеим половинам профиля, а не только к ингесту.

Чего в этой модели нет и нужно решить: **приоритет слоёв нигде не записан**. «Рукой
проставленное» должно побеждать извлечённое — это уже верно для `tag_id` (B5, L1-05), но
записано как запрет модели назначать идентичность, а не как правило разрешения слоёв.

## 5. Оценка наброска «выставить в настройках → считать → положить в кэш»

Набросок правильный по направлению и неполный по трём пунктам.

| Шаг наброска | Оценка | Что добавить |
|---|---|---|
| «дать пользователю в настройках» | **высокая**, и он уже дан: `retrieval.*` в профиле | валидация на границе записи, а не на чтении (см. ниже) |
| «считать» | **высокая**, но считать надо не «сколько раз применилось», а **что фактически применено**: `config_fallbacks` (имена параметров, ушедших в дефолт) + применённые значения | без этого «считать» превращается в счётчик вызовов, который ничего не говорит |
| «скорее всего положить в кэш» | **средняя** | кэш без версии опаснее отсутствия кэша: он закрепляет конфиг молча. Нужен отпечаток, иначе кэш сделает дрейф невидимым, а не устранит |

Чего в наброске нет, а нужно:

1. **Валидация там, где пользователь пишет, а не там, где сервер читает.** Config Service
   уже имеет эндпоинт `POST /api/v1/config/domain/validate`. Плохой профиль должен
   отвергаться в момент сохранения, а не обнаруживаться через четыре часа прогона или
   через 500 пользователю. Для ингеста это обязательное требование (ADR-031 §2: optional
   enrichment не блокирует документ), для retrieval — просто здравый смысл.
2. **Идентичность конфигурации в артефакте** (паттерн A). Без неё отчёт неполон.
3. **Неизменяемость на время прогона** (паттерн C). Практически: отпечаток считается один
   раз на старте, и если он изменился — это повод пометить прогон, а не молча продолжить.

## 7. Рекомендации

**Рекомендуемый путь для текущего этапа: S3, начиная с мёртвого кода.**

> **Статус на 2026-09-27: S3 выполнен.** Решения владельца зафиксированы: конфигурация
> неизменяема в рамках сессии (сессия = прогон; в эксплуатации — пока работает клиент), и в
> артефакт вводятся все три величины: идентичность, момент применения, право на устаревание.
> Сделано: закрепление профиля на первом запросе сессии, отпечаток `profile_fingerprint` в
> ответе и в `run_manifest.config`, момент `profile_pinned_at`, право
> `profile_staleness = "immutable_for_session"`, детект дрейфа между режимами с инвалидацией
> вердикта, именованные fallback'ы `config_fallbacks` вместо деградации по конфигу,
> применённые значения `effective_retrieval`, контракт `retrieval.*` в
> `profile_contract.validate_retrieval_profile`. Раздел S4 (кэш поверх закрепления) отменён
> как отдельный пункт: закрепление на старте сессии его покрывает.
>
> Что осталось незакрытым и почему: **`config_fallbacks` не инвалидирует вердикт** — это
> продуктовое решение, отложенное вместе со строгостью вердикта (§8 п.1). И сам класс
> «написанный, но недостижимый обработчик» теперь закрыт тестом на достижимость, а не
> ревью: `tests/test_retrieval_config.py::test_boost_fallback_is_reachable_with_trace_off`
> падал бы при возврате второго чтения поля.

**Порядок реализации (зафиксированный).**

1. **Первым — починить мёртвое чтение `graph_boost` и убрать дублирующее чтение.** Это ошибка
   или легаси, а «лишнего кода быть не должно». Правка: читать параметр один раз, терпимо, до
   `try`, и использовать одну переменную и в trace, и в логике. Побочно чинится (2.4):
   применённый `graph_boost` должен попадать в `done`, а не только в trace.
2. **Затем — именованные fallback'ы вместо деградации по конфигу.** Опечатка в профиле не
   должна обнулять вклад графа: дефект конфига → дефолт по этому параметру + имя в
   `config_fallbacks`. Деградация остаётся для отказов рантайма (Neo4j недоступен), и это
   разные вещи: дефолт — это «работаем не так, как объявлено», деградация — «не смогли».
3. **Затем — отпечаток профиля в `done` и в `run_manifest`.** Даёт и «чем измерен», и
   наблюдаемость дрейфа одним механизмом.
4. **Затем — контракт `retrieval.*`** в том же `profile_contract.py`, по образцу ингеста:
   обязательное нечитаемо → ошибка, необязательное → предупреждение, ключ не читается →
   предупреждение. В strict-режиме (eval) ошибка поднимает, в обычном — только лог.
5. **S4 откладывается** до появления нагрузки: кэш без идентичности конфигурации ухудшает
   наблюдаемость, а не улучшает её.

**Почему в таком порядке.** Пункты 1-2 меняют наблюдаемость, без них всё остальное измеряет
неизвестно что: валидатор скажет «поле не число», а в артефакте по-прежнему будет «граф
использован». Пункт 3-4 — про полноту артефакта. Пункт 5 — про производительность, и он
дёшев только после того, как конфигурация обрела идентичность.

**Чек-лист перед реализацией:**

- [ ] Решить, где валидация обязательна: только на чтении или ещё и на записи через Config
      Service. Рекомендуется и там, и там; на записи — жёстко, на чтении — с дефолтами.
- [ ] Решить, попадает ли `config_fallbacks` в `degraded_questions` (то есть влияет ли на
      вердикт) или остаётся предупреждением без влияния на вердикт. Склонность: не
      инвалидировать — параметр применился с дефолтом, система ответила, а отчёт это
      показывает. Но это отдельное продуктовое решение, а не техническое.
- [ ] Определить, где живёт «опора» (курируемый слой) в документации: сейчас она описана
      в трёх разных местах и нигде как конструкция.

## 8. Открытые вопросы

1. **Строгость вердикта при именованных fallback'ах** — связан с п. 3.10 ингест-аналитики,
   решение отложено там же. Сейчас `config_fallbacks` не инвалидирует вердикт.
2. **Приоритет курируемых слоёв** — ручное против извлечённого. Для `tag_id` решено (B5,
   L1-05), для остальных полей и для правил извлечения — нет.
3. **Стратегия кэша профиля** — отложена до появления нагрузки; при появлении решать вместе
   с отпечатком, иначе кэш станет новым источником незаметности.
4. **Retrieval-контракт на стороне записи** (Config Service) — сейчас `validate_profile`
   проверяет только форму профиля и не проверяет `retrieval.*` вовсе.
5. **Открытые ключи профиля** — `retrieval.*` читаются кодом, но отсутствуют во всех трёх
   профилях, то есть применяются кодовые дефолты. Это тот же класс, что инертные ключи
   онтологии, и лечится тем же предупреждением.
