# Архитектурный манифест: Граф как Карта Данных (Data Map)
## Концепция оффлайн-обогащения и фонового майнинга знаний для гибридных RAG-систем

---

## 1. Введение и проблематика «Тяжелого» GraphRAG

Классический подход к **GraphRAG** предполагает активное использование графовой базы данных (например, Neo4j) непосредственно в рантайме поискового запроса пользователя. При таком подходе система выполняет параллельный или последовательный обход графа (Graph Traversal) в реальном времени, пытаясь извлечь сущности и связи, пересекающиеся с вектором пользовательского запроса.

В условиях реального продакшена (Scale) и миллионов документов этот подход неизбежно упирается в **инфраструктурный тупик**:
1. **Экспоненциальный взрыв контекста (Fan-out эффект):** Появление связей типа «многие ко многим» заставляет рантайм-запрос вытягивать из базы огромную, ветвящуюся паутину сущностей, которая забивает контекстное окно LLM мегабайтами лишнего текста.
2. **Проклятие распределенных транзакций (ACID):** При обновлении или удалении документов система вынуждена каскадно перестраивать связи и проверять базу на наличие «осиротевших» ребер, что требует сложнейших транзакционных контуров (вроде двухфазных коммитов — 2PC) и дико тормозит инжест.
3. **Разный характер нагрузки:** Векторный поиск — это прямолинейная потоковая математика (ANN), отлично ложащаяся на CPU/GPU и кеш. Графовый поиск — это хаотичные прыжки по указателям в оперативной памяти. Их рантайм-совмещение в критическом пути запроса резко увеличивает Latency.

## 2. Философия решения: Граф как Карта Данных (Data Map)

Вместо использования графа в качестве живой поисковой базы, мы переносим его роль исключительно в **оффлайн-контур (Ingest Stage & Background Background)**. Граф превращается из «базы знаний» в интеллектуальный **генератор метаданных фиксированной длины (Semantic Passport)** для векторного индекса.

Этот паттерн реализует два фундаментальных принципа:
* **Graph-driven Metadata Enrichment / Graph-to-Vector Projection** (Обогащение метаданных через граф на этапе инжеста).
* **Knowledge Graph Mining / Link Prediction** (Фоновый асинхронный майнинг скрытых связей).

### Архитектурное разделение обязанностей (Separation of Concerns)
* **Векторный бэкенд (например, Turbopuffer):** Быстрые ноги системы. Отвечает за *локальный контекст* (поиск точечного факта по семантическому сходству) и мгновенную фильтрацию по плоским тегам. Единственный источник истины в рантайме.
* **Графовый контур (Neo4j):** Оффлайн-мозг системы. Отвечает за *глобальный контекст*. Размечает координаты текстовых чанков на общей карте знаний, нормализует синонимы и вычисляет скрытые транзитивные зависимости. Полностью изолирован от поисковых запросов пользователя.

## 3. Паттерн 1: Проекция графа в метаданные (Graph-to-Vector Projection)

### Как устроен контур инжеста (Загрузка данных)
1. **Парсинг и чанкинг:** Исходный документ разбивается на базовые текстовые чанки (например, текстовое описание конкретного объекта — *"Дом №5 расположен на Улице Ленина"*).
2. **Экстракция и обращение к справочнику:** Текст анализируется (с помощью LLM или детерминированных правил). Сущности отправляются в оффлайн-песочницу Neo4j.
3. **Нормализация и канонизация:** Граф выполняет роль умного дедупликатора. Если LLM извлекла «Мск», «Москва» или «г. Москва», граф сопоставляет их со своим внутренним жестким глоссарием и склеивает в один канонический узел.
4. **Вычисление транзитивных связей (Скачок вверх):** На основе базового доменного справочника граф автоматически достраивает цепочку вложенности. Если в чанке упомянут только *Дом №5*, граф выполняет мгновенный обход дерева вверх: `(Дом №5) -> [INSIDE] -> (Улица Ленина) -> [INSIDE] -> (Район Хамовники) -> [INSIDE] -> (Москва)`.
5. **Сборка Семантического Паспорта:** Из графа выгружается плоский массив тегов строго ограниченной длины (например, **не более 5 ключевых тегов** на чанк), отражающий разные измерения контекста:
   ```json
   {
     "chunk_id": "doc_ch_1024",
     "text": "Дом №5. Капитальный ремонт фасада запланирован на 2027 год.",
     "metadata": {
       "hierarchy_tags": ["Москва", "Хамовники", "Улица_Ленина", "Жилой_Фонд", "Модернизация"]
     }
   }
   ```
6. **Запись в Векторную БД:** Этот плоский паспорт намертво зашивается в метаданные вектора.

### Как устроен контур поиска (Runtime Retrieval)
В рантайме Neo4j **не вызывается вообще**. Запрос пользователя («Когда ремонт в Хамовниках на Ленина?») улетает в векторную базу данных, которая выполняет ультрабыстрый **Pre-filtering** по тегам метаданных. 

Система извлекает чанк, внутри которого *уже* лежат теги `Хамовники` и `Москва`, гарантируя **идеальный граундинг (Grounding)** и защиту LLM от галлюцинаций. При этом Latency поиска составляет считанные миллисекунды.

## 4. Паттерн 2: Фоновый майнинг скрытых связей (Knowledge Graph Mining)

Поскольку граф избавлен от рантайм-нагрузки, мы можем запустить отдельный асинхронный процесс (воркер/cron-джобу) для глубокого анализа структуры данных. Его цель — находить неочевидные, распределенные по разным документам взаимосвязи, которые невозможно обнаружить классическим векторным поиском.

### Алгоритм поиска транзитивных мостов
Представим два текстовых чанка в разных концах базы данных:
* **Чанк А:** Обсуждает *Объект 1* (теги: `["Строительство", "Компания_Альфа"]`).
* **Чанк Б:** Обсуждает *Объект 2* (теги: `["Судебный_Иск", "Личность_Петров"]`).

Прямого текстового или векторного сходства между ними нет. Но оффлайн-анализатор запускает в Neo4j алгоритмы поиска путей (Pathfinding) или предсказания связей (Link Prediction) и обнаруживает скрытую цепочку:
`[Компания_Альфа] -> (Дочерняя фирма) -> [Инвестиционный Фонд X] -> (Мажоритарный владелец) -> [Личность_Петров]`.

### Замыкание контура обогащения (Incremental Re-indexing)
1. Обнаружив этот транзитивный мост, фоновый процесс генерирует новый синтетический ассоциативный тег — например, `#риск_аффилированности_петров`.
2. Система выполняет точечное обновление метаданных (**No-op для эмбеддингов, меняются только теги**) в векторной базе для Чанка А и Чанка Б.
3. **Результат:** Когда на следующий день пользователь вводит запрос про *Компания_Альфа*, векторная база благодаря общему скрытому тегу мгновенно поднимает в топ выдачи Чанк Б про *Личность_Петров*. 

Фоновая математика графа превратилась в моментальный плоский фильтр в рантайме.

## 5. Сравнение подходов (Сводная матрица)

| Критерий оценки | Классический Тяжелый GraphRAG (В рантайме) | Легкий Граф как Карта Данных (Оффлайн-проекция) |
| :--- | :--- | :--- |
| **Latency поискового запроса** | Высокий (зависит от глубины обхода сети в Neo4j) | Сверхнизкий (прямой поиск в Векторной БД) |
| **Нагрузка на RAM сервера графов** | Критическая (граф должен быть полностью в памяти) | Минимальная (только во время загрузки и ночью) |
| **Сложность мутаций / удаления** | Высокая (требует каскадных проверок и ACID транзакций) | Нулевая для рантайма (векторный индекс — изолированная проекция) |
| **Качество Граундинга (Grounding)**| Отличное | Отличное (LLM получает те же контекстные теги) |
| **Поиск скрытых связей** | Поверхностный (ограничен таймаутом запроса пользователя) | Глубокий (полноценный ночной майнинг по всей базе) |
| **Инвалидация данных** | Мгновенная (изменили узел — изменился рантайм-ответ) | Требует фонового обновления тегов вектора (Re-indexing) |

---

## 6. Заключение и выводы для прототипа

Концепция **«Граф как Карта Данных»** устраняет главное противоречие гибридных поисковых систем: необходимость выбирать между скоростью плоских индексов и семантической силой графовых взаимосвязей. 

Ограничивая выход графа компактным паспортом из нескольких тегов и перенося всю графовую аналитику в оффлайн/инжест контур, мы получаем масштабируемую, дешевую в обслуживании архитектуру. Граф выполняет сложнейшую роль картографа и аналитика, в то время как векторный бэкенд обеспечивает молниеносный и точный Retrieval.
