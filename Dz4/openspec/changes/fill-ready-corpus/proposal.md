# Proposal: набор `ready` наполняется отдельным контуром ингеста

## Что делаем

Пишем контур, который наполняет набор `ready`, и наполняем его. До этого набор был
именем без содержимого: том `ohw-runtime_ready_neo4j` весил 4 КБ, нод не было, и отличить
его от `empty` по данным было нечем.

## Почему это отдельная работа, а не «просто прогнать загрузку»

Том создаёт compose, но заполнить его нечем: `compose.runtime.yaml` ингеста не содержит
(ADR-058), и инструмента, который пишет в этот том, не существовало. Написали
`compose.ingest.yaml` — оверлей поверх runtime, добавляющий ровно один сервис.

## Три молчаливых отказа

Все три дали результат, похожий на успех: джобы завершались `succeeded`, ошибок в логах
не было. Ни один не был виден без целенаправленной проверки. Это тот класс, что в
правилах проекта назван «молчание хуже отказа».

### 1. Кандидаты монтировались не оттуда

В оверлее было `../pre-ingest`. Каталог `infra/` находится на уровень ниже корня
репозитория, поэтому docker **создал пустую папку `prototype/pre-ingest`** и смонтировал
её. Контейнер видел 0 кандидатов, ингест уходил в vector-only (ADR-053).

Вид сверху: 703 `Chunk`, 0 `ContextNode`, 0 связей. Все 32 джобы — `succeeded`.

### 2. Не хватало `EXTRACT_LLM`

На eval-стенде переменная задана (`compose.eval-minimal.yaml`:148), в новом оверлее —
нет. Профиль при этом разрешает LLM (`llm_enabled: true`), и отказ выглядел как
«выключено конфигурацией».

Вид: те же 703 `Chunk`, ноль нод графа, в каждой джобе
`enrichment_degraded: EXTRACT_LLM не объявлен`.

### 3. `start_period` меньше времени старта

`start_period: 5s` при фактическом старте 36 секунд. Контейнер объявлялся `unhealthy` и
сам же становился `healthy`. Здоровый контейнер в статусе `unhealthy` хуже отсутствия
проверки: на такой статус начинают опираться как на отказ.

### Почему второй отказ не нашли сразу

Первый искался по логу ингеста, второй — нет: в нём не было ни слова про переменную.
Понадобился обход API по всем джобам. После второго отказа контракт переменных сверен
**целиком** с eval-стендом, а не по одному ключу, и так нашлись `LLM_EXCHANGE_LOG*` — с
ними LLM виден в логе сразу.

Вывод, который стоит проверить отдельно: новый compose-файл копируется не из головы, а
должен сверяться с рабочим. Третий пункт ниже — как именно.

## Что получилось

| величина | значение |
|---|---|
| документов `succeeded` | 17 |
| джоб `failed` | 0 |
| `ContextNode` | 717 |
| `Chunk` | 432 |
| связей | 1731 |
| запросов к LLM | > 0, журнал обмена подтверждает |

## Границы применимости

- **17 из 30 документов**, загрузка остановлена по решению владельца. Значит набор `ready`
  заполнен частично, и **полнота извлечения по корпусу не измерена**.
- **6 из 17 джоб с деградацией** — причина не разобрана. Это 35%, и наполненность графа
  нельзя читать как «извлечение работает».
- Один прогон, одна модель, один корпус. Числа выше — наблюдение этого прогона, а не
  характеристика системы.

## Что осталось открытым

- Нужен ли остальной корпус (13 документов) или достаточно этих семнадцати.
- Разобрать ли 6 деградировавших джоб и что они означают для качества графа.
- Нужен ли пребор корпуса перед загрузкой, чтобы не начинать с чистого листа.
- Где живёт прибор загрузки: `infra/checks/fill_ready.py` создан, но как он попадает в
  контейнер (копируется вручную, монтируется или ставится образом) — не решено.
- Нужен ли предварительный осмотр корпуса перед загрузкой, чтобы не начинать с чистого
  листа и не тратить час на заведомо плохую загрузку.
- Как новый compose-файл должен сверяться с рабочим, чтобы три пропуска не повторились.

## Чего это изменение не делает

- Не отмечает задачи выполненными: по договорённости галочка ставится после решения
  владельца, а не после того, что код написан.
- Не закрывает `ready` как готовый набор: он заполнен частично и с деградацией.
- Не переносит ингест в runtime — разделение остаётся как в ADR-058.
