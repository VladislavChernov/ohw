# Proposal: Набор `ready` наполняется отдельным контуром ингеста

## Почему

Том `ready` был именем без содержимого: `ohw-runtime_ready_neo4j` весил 4 КБ, нод не
было, и отличить его от `empty` по данным было нечем. Том создаёт compose, но заполнить
его нечем: `compose.runtime.yaml` ингеста не содержит (ADR-058), и инструмента, который
пишет в этот том, не существовало.

Наполнение упиралось в три отказа подряд, и все три дали результат, неотличимый от
успеха: джобы завершались `succeeded`, ошибок в логах не было.

1. **Кандидаты монтировались не оттуда.** В оверлее было `../pre-ingest`; каталог `infra/`
   на уровень ниже корня, поэтому docker **создал пустую папку** и смонтировал её.
   Контейнер видел 0 кандидатов, ингест ушёл в vector-only (ADR-053): 703 `Chunk`,
   0 `ContextNode`, 0 связей.
2. **Не хватало `EXTRACT_LLM`.** На eval-стенде переменная задана, в новом оверлее — нет.
   Тот же вид и то же сообщение в каждой джобе.
3. **`start_period` меньше времени старта.** 5 с при фактическом старте 36 с: контейнер
   объявлялся `unhealthy` и сам же становился `healthy`.

Первый отказ виден в логе ингеста и в данных Neo4j. Второй — **не виден нигде**: в логе
нет ни слова про переменную, понадобился обход API по всем джобам. После него контракт
сверен целиком с eval-стендом, а не по одному ключу, и так нашлись `LLM_EXCHANGE_LOG*`,
без которых отказ модели виден только обходом.

Вывод, который стоит закрыть отдельной задачей: новый compose-файл не копируется по
памяти, а сверяется с рабочим.

## Что делаем

- Пишем `compose.ingest.yaml` — оверлей поверх runtime, добавляющий ровно один сервис.
- Наполняем набор `ready` до 17 документов: на полный корпус уходит больше часа.
- Пишем прибор `fill_ready.py`: ждёт конца сам, идемпотентен, проверяет три условия
  независимо.

## Спека

Новое требование: **набор данных не должен называться готовым, пока он пуст, а
заполнение набора обязано быть проверяемым.** Подробности — в
`specs/fill-ready-corpus/spec.md`.

Не входит в спеку: разделение ingestion и query (ADR-058), выбор набора томов (`VOL`),
извлечение и качество графа.

## Проверка

```powershell
# 1. Набор заполнен и это видно по данным
docker exec ohw-runtime-neo4j cypher-shell -u neo4j -p ... `
  --format plain "MATCH (n) RETURN labels(n)[0] AS label, count(*) AS c ORDER BY c DESC;"
# ожидание: ContextNode > 0 И связи > 0. Одного Chunk недостаточно.

# 2. Прибор ждёт конца сам и не дублирует корпус
docker exec ohw-runtime-ingestion /app/.venv/bin/python /tmp/f.py --limit 17
# повторный запуск: "уже загружено: 17, к загрузке: 0"

# 3. Прибор падает на ложном успехе
#    снять монтирование кандидатов -> прибор видит ContextNode = 0 и ждёт
#    снять EXTRACT_LLM -> то же
```

**Результат на сейчас:** 17 документов, 717 `ContextNode`, 1731 связь, 0 `failed`.

**Границы:** 17 из 30 документов — загрузка остановлена по решению владельца, полнота
извлечения по корпусу не измерена. **6 из 17 джоб с деградацией** (35%), причина не
разобрана, поэтому наполненность графа нельзя читать как «извлечение работает».
