# Delta Spec: configurator-ui

## ADDED Requirements

### Requirement: Отложенный сервис помечен явно

Сервис, объявленный в compose, но не реализованный, обязан сопровождаться указанием
причины: нет образа, нет `build`-контекста, нет entrypoint. Объявление без такой пометки
хуже отсутствия объявления — видно, что сервис есть, и он не работает.

#### Scenario: Чтение объявления без истории git

- **WHEN** инженер читает `compose.yaml` и встречает `configurator-ui`
- **THEN** в комментарии сказано: сервис нужен, не реализован, веха M5, и приведён документ,
  фиксирующий назначение

#### Scenario: Название «призрак» без проверки истории

- **WHEN** сервис объявлен, но образа нет
- **THEN** вывод «сервис не существует» делается только после проверки истории git и
  документации; в текущем репозитории такая проверка показала бы, что объявление есть
  с вехи M0 и задокументировано в `docs/04`

### Requirement: Момент готовности определён до реализации

UI конфигуратора нужен, когда выполняются оба условия:

1. требование `docs/02_pipeline_and_normalizer.md`:456 стало проверяемым — то есть
   появилась хотя бы одна настройка, обязательная к смене **без перезагрузки контейнера**;
2. такой настройки нельзя безопасно менять через REST руками: вызов затрагивает живой
   стенд и требует подтверждения и видимости того, что применено, а не запрошено.

Пока нет ни одной настройки такого рода, UI незачем. Это отсутствие работы, а не
«красиво».

#### Scenario: Настройки, меняемой без перезагрузки, ещё нет

- **WHEN** параметры правятся файлами `infra_topology.yaml` и `namespaces.yaml`
- **THEN** критерий готовности не выполнен, UI не реализуется, и это записано как
  решение, а не как молчание

#### Scenario: Момент решения не выводится из даты

- **WHEN** веха M5 ещё не разбиралась и её состав не зафиксирован
- **THEN** дата готовности UI не назначается; решение переносится на момент разбора вехи

### Requirement: Прибор не путает отложенное с дефектом

Сервис без `build`-контекста и без образа может быть объявлен намеренно. Прибор
выводит его отдельным разделом при каждом прогоне — не ошибкой монтирования, но и не
молча, чтобы отложенная работа не сгнила незамеченной.

#### Scenario: Прогон прибора при объявленном, но несобираемом сервисе

- **WHEN** `check_mounts.ps1` встречает сервис из пространства `ohw/*` без build-контекста
- **THEN** сервис попадает в раздел «DECLARED BUT NOT RUNNABLE», монтирование для него не
  требуется, и прибор завершается кодом 0

### Requirement: Набор подключений к LLM отложен и в прототип не входит

**Это требование о будущем, а не о прототипе.** Заголовок содержит слово «Requirement»
потому, что требования в этом файле и есть, но ни одна строка ниже не описывает работу
внутри прототипа.

В финальной версии системы подключение к языковой модели задаётся набором, а не одним
именем: провайдер, адрес, модель, таймаут, параметры генерации. Переключение между
подключениями — горячая настройка, и именно поэтому конфигуратор существует.

Сейчас это не реализовано, и решение владельца от 2026-10-15 — **отложить набор
адаптеров на более поздние стадии**. Для прототипа достаточно того, что есть: реализация
одна на слот, а смена реализации выполняется через runtime config без правки ядра
(`prototype_requirements.md`, L1-02/L1-03).

Фактическое состояние зафиксировано в каталоге адаптеров (`ADAPTER_CATALOG`):

| слот | варианты | настоящих реализаций |
|---|---|---|
| `graph_store` | `neo4j`, `inmemory` | 2 |
| `vector_store` | `neo4j`, `inmemory` | 2 |
| `embeddings` | `deterministic`, `bge_m3_service` | 1, второе — заглушка |
| `reranker` | `noop`, `bge_reranker` | 1, второе — заглушка |
| `llm` | `openai`, `fake` | 1, второе — заглушка |

Отдельного адаптера под Ollama, vLLM или LM Studio нет, и в коде нет ни одного упоминания
такого класса; работа идёт через OpenAI-совместимый `/v1` (`OpenAICompatibleAdapter`),
поэтому любой сервер с таким API подключается без правки ядра.

#### Scenario: Подключение выбирается в конфиге

- **WHEN** меняется `adapters.llm`, `base_url` или `model` в runtime config
- **THEN** ядро не меняется, а протокол остаётся OpenAI-совместимым `/v1/chat/completions`

#### Scenario: Набора подключений в прототипе ещё нет

- **WHEN** читается конфигуратор и его спецификация
- **THEN** сказано, что набор подключений к LLM входит в финальный вариант, отложен на
  более поздние стадии, и это одна из причин появления UI, а не его исходная задача

#### Scenario: Границы не размываются

- **WHEN** набор подключений переносится на поздние стадии
- **THEN** смена реализации через runtime config остаётся требованием и сейчас
  выполняется, а отложено именно расширение набора, а не сама смена
