# Proposal: Гейт готовности объявляет наполненность, а не исполняемость

## Почему

Критерий готовности прототипа (`docs/prototype_requirements.md` §8) состоит из пяти
пунктов. Ни один из них не проверяет, что **процесс загрузки создаёт граф**.

Пункт 1 требует, чтобы «один вызов Ingestion API проходил обязательные
document/chunk/embed/vector-commit этапы». Это требование исполняемости, а не
наполненности: перечисленные этапы не включают `Extract`, и пайплайн, который честно
записал векторы и не построил ни одной `ContextNode`, этот пункт выполняет.

Разрыв стал виден из-за стадии pre-ingest. ADR-053 принят 2026-10-05 (коммит `7da0fa6`),
за 26 дней после появления UI загрузки (`64d1c82`, 2026-09-09). UI был написан, когда
стадии не существовало, и с тех пор не менялся: кнопки запуска `pre_ingest` нет, сам
`ingestion-api` стадию не вызывает (в `ingestion_service` нет ни одного вызова
`pre_ingest`), а `demo_ui/client.py:114` отправляет документ содержимым в JSON и ждёт ответа.

Что происходит при загрузке документа из UI сегодня:

| шаг | место | что делает |
|---|---|---|
| файл прочитан | `demo_ui/app.py:119` | `upload.getvalue().decode("utf-8")` |
| отправлен | `demo_ui/client.py:114` | `POST /api/v1/ingestion/documents` с `{source_url, domain, doc_type, content}` |
| ищется список | `orchestrator.py:1151` | `load_candidates(candidates_dir_from_env(), <имя файла>, текст)` |
| списка нет | `orchestrator.py:1156-1162` | `candidates_absent = True`, WARNING в лог, `return` — графа не будет |

Джоба при этом завершается **`succeeded`**. Тот же класс, что уже описан в
`openspec/changes/fill-ready-corpus/specs/fill-ready-corpus/spec.md`: «джоба succeeded, а
графа нет» — это ложный успех. Сейчас спека закрывает его для прибора загрузки, но не для
пользовательского пути через UI.

**Вопрос владельца, зафиксированный дословно:** процесс, создающий только вектор, — это
проблема процесса. Значит исправлять надо не UI, а конвейер: чтобы путь «документ → граф»
работал сам, без ручной предварительной подготовки папки с кандидатами.

Следствие для §8: пункт 4 требует метрики не ниже baseline, но не говорит, на каком срезе
измерено. Открытая находка (`docs/defense_notes_simplifications.md:503`): золотой набор
назван контрольным, у 71 из 74 вопросов `golden_source` менялся позже `as_of` самого
вопроса. Метрика, посчитанная на таком наборе, не является основанием объявлять готовность.

## Что делаем

- **Требование к процессу загрузки:** путь «документ → граф» обязан работать сам. Отсутствие
  кандидатов перестаёт быть штатным режимом `vector_only` для пользовательского пути и
  становится признаком ненастроенного конвейера. Решение владельца: режим `vector_only`
  остаётся, но путь, который до него приводит, обязан быть пройден.
- **Гейт наполнения в §8:** в базе есть `ContextNode` и связи, ноль `failed`. Ноль нод не
  «прохождение этапов», а исполняемость с пустым результатом.
- **Гейт полного золотого набора в §8:** метрики считаются на всех 74 вопросах, а не на срезе
  `golden_graph_evidence`. Срез остаётся отдельным вопросом — вклад графа, — и не заменяет
  готовность.
- **Сверка кандидатов как часть гейта:** список кандидатов свеж по `sha256` для каждого
  загруженного документа.

## Спека

Новое требование: **готовность объявляется по факту наполнения, а не по факту
исполняемости.** Требования и сценарии — в `specs/demo-readiness-gates/spec.md`.

Не входит: изменение самого механизма pre-ingest, разделение ингеста и извлечения
(ADR-058), состав томов наборов `empty`/`ready` (ADR-058), наполнение набора `ready`
(`fill-ready-corpus`).

## Проверка

```powershell
# 1. Загрузка документа из UI даёт граф, а не только вектор
#    (docker exec в ingestion-api, затем проверка в Neo4j)
docker exec ohw-runtime-ingestion /app/.venv/bin/python -c "..."
docker exec ohw-runtime-neo4j cypher-shell -u neo4j -p $env:NEO4J_PASSWORD --format plain \
  "MATCH (n:ContextNode) RETURN count(*) AS nodes;"
# ожидание: nodes > 0 для только что загруженного документа.
# nodes = 0 при статусе succeeded - дефект конвейера, а не пустая база.

# 2. Гейт наполнения
#    ожидание: ContextNode > 0 И связи > 0 И failed = 0.
#    Отдельно проверяется знаменатель: документов > 0.

# 3. Кандидаты свежи
python prototype\infra\checks\verify_candidates.py
# ожидание: ВЕРДИКТ: согласовано. Пустая папка - код 2, а не «согласовано».

# 4. Метрики на полном наборе
docker compose -p ohw-eval-minimal -f prototype/infra/compose.eval-minimal.yaml \
  run --rm --no-deps eval-runner python /app/infra/eval/run_eval.py \
  --domain it --mode both --corpus /repo/docs --source-prefix docs \
  --dataset /app/infra/eval/it/questions.jsonl --out "/reports/gate-$run"
# ожидание: corpus_documents_count > 0, golden_coverage выше усечённого,
# questions_total = 74. Срез graph_required не считается полным набором.
```

**Границы применимости.** Сейчас готовность не объявляется, поэтому все пункты §8
описывают требования к будущему объявлению, а не результат сегодняшнего прогона. Числа
прошлых прогонов (17 документов, 6 деградировавших джоб из 17) относятся к набору `ready`
и критерию §8 не удовлетворяют.

## Открытые вопросы

- [ ] Форма запуска `pre_ingest` в конвейере: отдельный вызов стадии перед приёмом документа
      или встраивание стадии в `ingestion-api`. Встраивание меняет картину ресурсов
      (NER-модель без GPU и без сети внутри сервиса, который тянет LLM на GPU).
- [ ] Что считать полным набором, пока у 71 из 74 вопросов `golden_source` устарел:
      переписать вопросы, зафиксировать `as_of`, или объявлять готовность по срезу с явным
      признаком `not_measured` на остальных. Решение владельца.
- [ ] Относятся ли гейты к §8 `prototype_requirements.md` или к отдельному документу
      готовности. Правка §8 затрагивает документ, который система ест как корпус.
