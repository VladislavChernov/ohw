## Что поправилось в методике по ходу разведки

- `MENTIONS` в шаблоне пути даёт **фиктивный мост через Chunk** (в цепочке появлялся `NULL`) —
  цепочки среза строим без `MENTIONS`.
- `ORDER BY depth DESC LIMIT 200` вернул 200 почти одинаковых строк глубины 6 — выборку надо
  брать по хабу, а не по глубине.
- Число путей растёт как 4→1,5М, 5→12,4М, 6→115М: граф плотен по путям, и решает не глубина, а
  бюджет узлов.
- `startNode(path)` в Cypher принимает **связь**, а не путь (ошибка была в первом прогоне);
  правильно — `head(nodes(path))`.

## Первая сверка рёбер с текстом (2026-10-15)

Проверены два реальных ребра (у рёбер свои `source_ids`, запрос — `edge-sources.cypher`):

**1. `adr-012` —REQUIRES_CONSTRAINT→ `vector-only baseline graph adapter`**, источник —
`adapters_specification.md`. В тексте: стр. 236 «В vector-only baseline graph adapter не
требуется…», стр. 242 «Контрактные тесты обязательны для каждой реализации обоих интерфейсов
(ADR-012)». **Обе сущности есть, тема общая, но заявленный вид связи текстом не подтверждается:**
нигде не сказано, что ADR-012 *требует* `vector-only baseline graph adapter`; более того, стр. 236
утверждает обратное про необходимость адаптера. Вид ребра — артефакт извлечения.

**2. `api` —REFERENCES→ `get /config/adapters`**, источник — `adapters_guide.md`. В тексте
эндпоинт дан как `curl http://localhost:8001/api/v1/config/adapters` (стр. 97), а форма
`GET /config/adapters` живёт в другом документе (`04_services_config.md:44`). Сущности сосуществуют,
связь «ссылается» — правдоподобна, но и она не выведена из конкретной фразы.

**Вывод, меняющий методику среза:**
- опираться на **вид** извлечённого ребра нельзя — он не читается в тексте;
- опора переносится на **совместное появление** двух сущностей в документе плюс **факт**,
  который вопрос спрашивает и который проверяется по тексту независимо от графа;
- поэтому вопрос должен быть такой, что его ответ — фраза/раздел документа, а роль графа —
  **доставить документ**, который вектор по формулировке не достал.

Отсюда требование к отбору цепочек: брать их через **мостовой узел** (`source_ids` из 2+
документов): `adr-012` (adapters_guide + adapters_specification), `topology orchestrator`
(00 + 04), `llm` (6 доков), `api`/`neo4j` (5), `reranker`/`entry_points` (4). Список мостов —
в выводе запроса 4 (`inspection-output.txt`).

## Диагностика: почему у шести доков нет узлов (2026-10-15)

Замер `candidates_probe.py` (вывод — `candidates-probe-output.txt`): правила кандидатов дают на
vector-only доках **не меньше**, чем на контрольных.

| документ | кандидатов по правилам |
|---|---|
| `05_adr_log.md` (vector-only) | **1142** |
| `defense_notes_simplifications.md` (vector-only) | 369 |
| `06_operations_and_risks.md` (vector-only) | 368 |
| `02_pipeline_and_normalizer.md` (vector-only) | 213 |
| `01_ontology_and_domain_profile.md` (vector-only) | 97 |
| `connectors_guide.md` (vector-only) | 87 |
| _04_services_config.md (узлы есть)_ | 216 |
| _api_reference.md (узлы есть)_ | 120 |
| _adapters_specification.md (узлы есть)_ | 135 |

**Значит отсутствие узлов — не от нехватки кандидатов.**

**Это не зависшие джобы — зависшие другие.** Три состояния набора, и все три видны в замерах:

| состояние | сколько | признак |
|---|---|---|
| граф есть | 11 | чанки + `ContextNode` |
| vector-only | 6 | чанки есть, узлов ноль |
| застряли | 2 | `demo_runbook.md`, `demo_user_guide.md` — ни чанков, ни узлов |

У застрявших нет **ничего** (их нет среди 17 документов с чанками), потому что джоба не дошла до
COMMIT. У vector-only чанки записаны, значит джобы завершились `succeeded` — просто без узлов.

**Причина документирована в самом коде.** Комментарий у продюсинга кандидатов в
`orchestrator._extract_llm`: «до правки список лежал в папке и требовал ручного запуска стадии, а
отсутствие файла означало тихий уход в vector-only со статусом `succeeded`». ADR-053
(2026-10-14) перенёс продюсинг кандидатов внутрь пайплайна; набор `ready` собран до этой правки,
поэтому для этих шести шаг кандидатов не выполнялся. Кандидаты в их тексте есть (таблица выше) —
то есть при принудительной перезагрузке сегодня узлы бы появились.

**Практический вывод для среза:** принудительная перезагрузка этих шести документов сейчас дала
бы узлы — кандидаты для выбора модели есть. То есть «обогащение» этими документами возможно, и
цена у него — извлечение (минуты на документ), а не «нет из чего извлекать».

### А что отдаёт запрос по такому документу

Замер `mentions.cypher` (вывод `inspection-output-mentions.txt`): у **всех 289 чанков** шести
vector-only документов **ноль `MENTIONS`** — у их чанков нет ни одного `context_id`/`tag_id`.

Следствия, и они двусторонние:

- запрос, чьи чанки пришли из vector-only документа, отвечает **только из векторных чанков**:
  графовая ось не добавляет ни одного имени;
- ось при этом не молчит: семян нет, поэтому в трассе и `qa_log` стоит именованная причина
  `no_context_ids` и `graph_degraded=true`, а не тихий успех;
- и главное: **граф не может достать vector-only документ в принципе** — ни один узел не несёт
  его `source_ids`, поэтому он не появится и как источник с `axis=graph`. Для любого вопроса,
  чей `golden_source` — один из этих шести, `necessity` равен нулю по построению, чем бы граф
  ни занимался.

Отсюда правило отбора вопросов среза: **`golden_source` не должен быть vector-only документом**,
иначе вопрос заведомо не различает оси и портит замер.

**Новая находка о качестве извлечения (не про срез, но важная).** По полям джобы:
`llm_names_total=92`, из них **`llm_names_off_list=43`** — 47 % имён модель выдала ВНЕ списка

18 из 92 имён присутствуют в своём чанке дословно. То есть ограничение имён списком (ADR-053)

среза он значит, что имена в графе могут быть изобретёнными, и опора на «цель ответа — имя
сущности» требует выборочной ручной проверки.

**И идентичность сработала как описано:** произведено 81 узел, чистое приращение 57 — значит
24 узла слились с уже существующими из других документов. Это и есть междокументный механизм:
общая сущность даёт общий узел.

## Про двухпроходный ингест (что решено и что в коде)

**Решено** (ADR-056, принято): «двухпроходная схема (ноды отдельным вызовом, связи по
подтверждённому набору) и seed принимаются **обе**. Смысл двух проходов — дать модели опору,
чтобы она не зацикливалась: ей нечего перечислять, когда пары не запрошены». Причина —
измеренная поломка на одном ответе: 35 имён, 120 пар, из них `NormalizeStage → X` 108 раз,
87 % дублей, все пары одного вида, JSON не закрыт.

То есть второй проход — **про связи по подтверждённому набору узлов**, а не про междокументность.

**В коде на 2026-10-15 — один вызов на чанк** (`orchestrator._extract_llm:1208`): в одном ответе
модель отдаёт и сущности, и связи; связи валидируются против сущностей **этого же ответа**
(`_validate_edges`), неудалённые концы считаются. Значит двухпроходная схема **принята, но не
реализована** — решение и код расходятся.

**Междокументные связи проходом не делаются и по построению не могут:** «обе вершины любой связи
должны быть извлечены в одном ответе модели, то есть исходно связь всегда внутри одного
документа. Междокументность обеспечивается общим узлом, а не самой связью»
(`data_model.md` §2.1). Одинаковая сущность из двух документов — один узел, и его `source_ids`
накапливают provenance обоих. Именно это, а не ребро, даёт оси документ, который вектор по
тексту запроса не ранжирует (`docs/03_retriever.md:47`).

Следствие для среза: цепочки, на которые можно опираться, — это совместное появление сущностей и
мостовые узлы; ждать «второго прохода за междокументными связями» не следует.
