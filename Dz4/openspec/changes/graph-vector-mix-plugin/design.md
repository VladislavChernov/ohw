# Design: мост `chunk_ids` → текст и взвешенное RRF

## 1. Где именно смешиваются оси

По `QueryPipeline.run`, по порядку:

| строка | что происходит | кто главный |
|---|---|---|
| `pipeline.py:~780` | семена обхода берутся из `context_ids`/`tag_ids` **векторных** чанков | вектор решает, куда идти графу |
| `pipeline.py:~789` | `expand(...)` — обход; строки несут `source_ids`, `chunk_ids`, `path`, `depth`, `kind`, `confidence` | граф |
| `pipeline.py:887` | `rerank(query, body_chunks)` — **реранкер видит только векторные чанки** | вектор |
| следом | boost поднимает оценки векторных чанков, чей документ достигнут | граф влияет на вектор |
| `pipeline.py:~867` → `build_sources` | **смешение в один список и сортировка с приоритетом оси** | место слияния |
| `pipeline.py:903` | `assemble(skeleton_rows, body_chunks)` → промпт | отдача в LLM |

Смешивания как оценки нет нигде: реранкер стоит **до** слияния и про граф не знает вообще.

## 2. Почему RRF, а не сумма оценок

Выбор сделан по внешним источникам, а не по вкусу. Основные:

- **Cormack, Clarke & Büttcher, SIGIR 2009** — сам RRF, формула `Σ 1/(k + r(d))` и `k = 60`.
  https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf
- **Bruch, Gai & Ingber, TOIS 2023** — разбор слияний. Два нужных нам вывода: (1) при
  выпуклой комбинации выбор нормировки почти не важен (любая ограниченная линейная карта
  ранг-эквивалентна, сдвигается только вес `α`); (2) **RRF отбрасывает величину оценок** и
  чувствителен к своим параметрам.
  https://dl.acm.org/doi/full/10.1145/3596512
- **Почему нельзя складывать оценки:** Vespa прямо описывает провал — оценки BM25 не нормированы
  и «перебивают» оценку близости. https://docs.vespa.ai/en/learn/tutorials/hybrid-search.html
  То же у Pinecone (https://docs.pinecone.io/guides/search/hybrid-search) и Weaviate
  (https://docs.weaviate.io/weaviate/concepts/search/hybrid-search).

**Наш случай попадает ровно в то, что RRF чинит:** у графового кандидата нет оценки,
сравнимой с косинусом. Отсутствие калибровки для RRF — не недостаток, а условие его работы.
Обратная сторона честно записывается: RRF выбрасывает величины оценок, поэтому «насколько сильно
похож этот документ» в слиянии не участвует — только порядок.

## 3. Мост: кандидат, а не решение

**Мост не реализуется сейчас** (решение владельца 2026-10-16: способ слияния обсуждается
отдельно). Здесь только то, что нужно для этого разговора: мост технически дешёв, но он не
обязателен, поэтому обсуждать его как данность нельзя.

Дешёв он потому, что инфраструктура уже есть: текст чанка лежит в том же Neo4j
(`Chunk.text`, `ingestion_service/pipeline/orchestrator.py:2451`), а обход уже отдаёт
`chunk_ids` (`_PROVENANCE_KEYS` в `retrieval/adapters/neo4j.py:44`). Выборка текстов по этим
идентификаторам — одна пакетная выборка, без новой подсистемы.

Но мост меняет **смысл** графовой оси, а не только её счёт:

- **без моста** ось может только переупорядочивать найденное вектором, и тогда документ,
  которого вектор не нашёл, она не принесёт в принципе — `necessity` становится вырожденной;
- **с мостом** ось приносит читаемые кандидаты, и `necessity` снова измерима.

Зрелые системы идут вторым путём: MS GraphRAG local search извлекает «релевантные фрагменты
текста из исходных документов, связанные с найденными сущностями»
(https://microsoft.github.io/graphrag/query/local_search/); LightRAG собирает «сущности,
отношения и соответствующие фрагменты текста» (https://arxiv.org/html/2410.05779); Neo4j
`VectorCypherRetriever` возвращает тексты исходных чанков вместе со связями
(https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html); RAPTOR требует
текста у каждого узга-кандидата, потому что «суммарарий и есть единица эмбеддинга»
(https://arxiv.org/html/2401.18059).

Это аргумент **за** мост, а не решение его делать.

## 4. Контракт плагина

Точка расширения: после обхода, до `ContextAssembly`.

```
вход:  query, vector_chunks, expansion_rows (с provenance)
выход: один упорядоченный список чанков + provenance каждого
```

Правила, которые следуют из проверки, а не из вкуса:

- **Плагин не может выбросить provenance.** Из неё читаются `necessity`, `blind_golden`,
  `linked_golden` и метрики осей. Плагин, который её теряет, делает замер недостоверным.
- **Плагин не может вернуть чанк без текста.** Такой чанк нельзя ни отдать модели, ни честно
  оценить — это ровно тот дефект, который мы чиним.
- **Неизвестное имя реализации — ошибка, а не откат на вектор.** Молчаливый откат читается как
  «проверено, графа нет». `PluginLoadError` уже даёт это для чанкера
  (`plugin_registry.py`), тот же загрузчик используется здесь, а не вторая система плагинов.
- **Входные и выходные данные снимаются как применяемые, а не как запрошенные** — тем же
  правилом, что `effective_retrieval` и `config_fallbacks`.

## 5. Параметры

| параметр | по умолчанию | чем обоснован |
|---|---|---|
| `k` (RRF) | 60 | значение из оригинальной работы; все крупные системы используют 60 (Elastic, Vespa, LangChain, Pinecone) |
| `w_v` | 1.0 | вектор — базовая ось |
| `w_g` | 1.0 | **не подбирается на одном прогоне.** `α`/`w` в литературе подбирают на размеченной выборке; у нас её нет. При `w_g = 0` слияние вырождается в чистый вектор — это и есть измеримая базовая точка |

`k`, `w_v`, `w_g` пишутся в артефакт: значение, применённое к прогону, должно быть видно, а не
восстанавливаться из кода.

## 6. Почему не LLM-судья и не кросс-энкодер сейчас

- **LLM-судья над сырыми оценками даёт массу ничьих.** G-RAG: LLM с zero-shot «не справляется
  с ранжированием», причина — «слишком много ничьих в оценках релевантности».
  https://arxiv.org/abs/2405.18414
- **Кросс-энкодер требует модели**, которой в проекте нет, и стоит ~100–200 мс на запрос
  сверх первого этапа.

Это не запрет на будущее, а порядок: сначала дешёвое слияние, потом платный оценщик, если
слияние покажет, что порядок вообще влияет.

## 7. Границы прибора

`skeleton_count` / `body_count` / `dropped` уже считаются в `ContextResult` (`context.py`), но
живут только в runtime-трейсе. Они становятся полями ответа и артефакта. На кэш-попадании
значение — `None`, **не `0`**: кэш отдаёт чужой ответ, и «сборка не выполнялась» — это
отсутствие данных, а не нулевой расход.

## 8. Риски

- **RRF на коротких списках.** Слияние по двум спискам из 3 элементов почти ничего не даёт —
  документ должен попасть в оба. Если векторная ось короткая, эффект слияния измерим, но мал,
  и это надо написать в результат, а не выдать за успех.
- **Обход может принести много `chunk_ids`.** Мост увеличит число кандидатов; бюджет контекста
  ограничен, и лишнее вытеснит текст. Поэтому число кандидатов, пришедших от графа, пишется в
  артефакт.
- **Наш `vector_search` в Neo4j считает косинус в Python по всем чанкам** (`neo4j.py:902`).
  Значит выборка по `chunk_ids` дешевле полного поиска, но общий объём растёт — это видно по
  времени, и время остаётся в артефакте.
