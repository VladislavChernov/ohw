# Proposal: A-2 — честный контракт атомарности COMMIT (capability `consistency` + компенсация + ADR)

> Бандл закрытия замечания **A-2** (`review_team.md:40-42`, средняя приоритетность):
> инвариант L2-04 «атомарность COMMIT» заявлен, но CommitStage открывает **две
> независимые транзакции** (graph tx и vector tx, `orchestrator.py::CommitStage._write`),
> между которыми есть окно частичного коммита.

## Почему

1. `CommitStage._write` (строка 345) пишет через
   `with graph_store.transaction() as graph_tx, vector_store.transaction() as vector_tx:`
   — это две последовательные транзакции (на Neo4j — два отдельных
   `session.begin_transaction()`, `neo4j.py:147`/`:288`). Если вторая падает или падает
   процесс между ними, граф и вектор расходятся: чанк есть на одной оси и нет на другой.
2. Инвариант L2-04 (`docs/invariants.md:32`) и §1.2 прототип-требований
   («Ошибка на этапе COMMIT → граф без частичных записей») обещают то, что код не
   выполняет ни для одной пары провайдеров.
3. Вендор-независимость ядра (L1-02/L1-03, ADR-012/013) запрещает «свести всё к одной
   Cypher-транзакции» в общем виде: у разнородных СУБД нет общего транзакционного
   коордиента, и честный ответ — не притворяться атомарным, а декларировать
   capability провайдера и поведение ядра по нему.

## Что делаем

- **Capability-контракт провайдеров**: у `GraphStoreProvider`/`VectorStoreProvider`
  появляется capability `consistency: "atomic" | "best_effort"` (дефолт `best_effort`).
  - `atomic` — пара осей обслуживается **одним движком/транзакционным координатором**
    (например общий инстанс Neo4j): есть путь записи обеих осей в **одной транзакции движка**.
  - `best_effort` — разнородные пары (Neo4j + не-графовая векторная БД и т.п.):
    последовательный commit + **фаза компенсации** при сбое второй оси.
- **`CommitStage`**: выбор стратегии по capability пары; atomic-путь — одна транзакция
  движка; best_effort — commit по очереди, при сбое второй оси откат первой через
  DocumentRegistry (компенсация существующими операциями удаления, idempotent повтор
  той же джобы даёт консистентный результат).
- **Честность метаданных**: флаг учитывается в топологии (`infra_topology.yaml`) и в
  SSOT `namespaces.yaml` (namespace `adapters`) по тем же правилам каталога, что и
  существующие слоты; ядро не хардкодит Cypher и ничего не знает о конкретной СУБД.
- **ADR-024** (черновик) в `docs/05_adr_log.md` + аннотация L2-04: «атомарность
  гарантирована только внутри одного движка; разнородные пары — best-effort + компенсация»;
  §2.6 `docs/adapters_specification.md` уточняется.
- **Пометка идеи «БД как плагины»** (по решению на обсуждении A-2): тезис выносится
  в `design.md` как тема для отдельной проработки — провайдеры БД как entry-point-плагины
  с capability-метаданными (механизм плагинов уже есть: чанкинг, `docs/chunkers_guide.md`,
  `docs/adapters_guide.md`). В рамках этого бандла — только фиксация идеи, не реализация.

## Спека

- `specs/architecture-atomic-commit/spec.md` — «Delta Spec»: контракт capability
  `consistency`, правила выбора стратегии в CommitStage, фаза компенсации, правки L2-04
  и §2.6 (по-честному §1.2 прототип-требований).

## Что НЕ входит

- Двухфазный коммит / распределённые транзакции (нет общего коордиента; это осознанно
  не вводится — фиксируется в ADR-024).
- Реализация «БД как плагины» (entry-point-регистрация провайдеров БД) — только пометка
  идеи для последующего решения.
- Семантический кэш (бандл 3/3 `add-semantic-cache`) и прочие тяжёлые пункты ревью.
- Правка push-контракта `POST /documents` (ADR-018) и стадий пайплайна (ADR-021).

## Проверка

1. `uv run pytest -q` зелёно; `uv run ruff check .`, `uv run mypy src` — чисто.
2. Unit: пара InMemory+InMemory (atomic-провайдеры) — одна транзакция движка;
   пара InMemory+фейк-Neo4j (best_effort) — сбой второй оси → вызвана компенсация,
   первая ось откачена; повтор джобы — консистентный результат.
3. Live на стеке (профиль по умолчанию, inmemory-индекс): ingestion проходит,
   повторная загрузка того же контента — no-op (идемпотентность L2-06 сохраняется).
