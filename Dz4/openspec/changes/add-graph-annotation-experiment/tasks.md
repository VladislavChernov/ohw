# Задачи: эталонная разметка графа и измерение согласия с LLM

> Стадия: новый экспериментальный контур. Начинается с решения по способу разметки — без него
> объём работ не определён (см. открытые вопросы в `proposal.md`).

## 1. Решение по методу разметки (блокирует п. 3)

- [ ] 1.1. Выбрать метод: ручной, LLM-ассистированный с ревизией, или разметка только
      документов из `graph_required` вопросов. Решение фиксируется здесь отдельной строкой с
      обоснованием и оценкой трудоёмкости.
- [ ] 1.2. Определить, что считается узлом эталона: типизированные `Requirement`/`Concept`/
      `Contract` из `ontology.node_types` или плоская схема (`canonical_name` + связи).
      Предпочтение — плоская: она не наследует отменённую типизацию и ближе к тому, что
      фактически извлекает LLM.
- [ ] 1.3. Проверить, что `ontology.node_types[].type` не попадает в формат эталона, иначе
      бандл `tidy-domain-profile-keys` и этот будут противоречить друг другу.

## 2. Формат и загрузка

- [ ] 2.1. `prototype/infra/eval/it/graph_annotation.jsonl`: схема `{source_url, tags, links,
      annotator, annotated_at, notes}`; `tags` — объекты с `canonical_name` и опциональными
      `aliases`/`description`, `links` — объекты с `from`/`to` (канонические имена) и `kind`.
- [ ] 2.2. Валидация при загрузке: неизвестные поля, `from`/`to` не из `tags` того же документа,
      `source_url` вне корпуса — ошибка, а не тихий пропуск.
- [ ] 2.3. `run_eval.py`: параметр `--graph-source none|gold|llm` (дефолт `llm`, чтобы поведение
      не менялось неявно).
- [ ] 2.4. Передача аннотации в ingest только в руке `target`; в `baseline` теги и связи не
      подаются — иначе ручная разметка станет утечкой в сравнение.
- [ ] 2.5. Проверка детерминизма: два прогона `gold` на одном корпусе дают одинаковый состав
      графа и одинаковый `manifest.json` по `corpus_documents` и ревизиям.

## 3. Измерение

- [ ] 3.1. Согласие по узлам: precision/recall/F1 по каноническим именам после `_identity_key`.
- [ ] 3.2. Согласие по рёбрам: по тройке (нода, вид, нода), с приведением вида к верхнему
      регистру и фолбэком `RELATED`.
- [ ] 3.3. Отчёт отдельным артефактом прогона, вне lift-отчёта и вне вердикта паспорта.
- [ ] 3.4. В манифест прогона писать источник графа явно, чтобы агрегаты `gold` и `llm` нельзя
      было смешать: разные `graph_source` — разные строки отчёта.

## 4. Тесты

- [ ] 4.1. Юнит-тесты разбора `graph_annotation.jsonl`: валидный файл, неизвестное поле,
      висячий `from`/`to`, `source_url` вне корпуса.
- [ ] 4.2. Тест, что в baseline-руке аннотация не передаётся в ingest.
- [ ] 4.3. Тест на детерминизм: две сборки графа из одной аннотации совпадают.
- [ ] 4.4. Тест на метрики согласия: искусственный случай, где рёбра совпадают, а узлы — нет.

## 5. Проверка

- [ ] 5.1. `pytest`, `ruff check src tests`, `mypy src` в dev-контейнере с host
      `RUN_CODE_COMMIT`. До зелёного гейта коммит не делается.
- [ ] 5.2. Стенд: `gold`-прогон на полном корпусе укладывается в минуты, а не в часы, и даёт
      непустой `graph_paths` — иначе ручная разметка не образует междокументных путей и
      `necessity` останется нулевым.
- [ ] 5.3. Стенд: `llm`-прогон по-прежнему работает и даёт сопоставимый `recall_graph`.

## Открытые вопросы

- Метод разметки (п. 1.1) — блокирует объём работ.
- Объём: все 33 документа или только те, что цитируются в `graph_required` вопросах.
- Третий arm «ручная разметка, отредактированная LLM» — отвечает на вопрос «помогает ли LLM,
  если человек проверяет», но это ещё одно сравнение.
- Нужен ли отдельный процесс подтверждения аннотации человеком, чтобы эталон считался эталоном.
