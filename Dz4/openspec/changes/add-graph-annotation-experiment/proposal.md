# Proposal: эталонная разметка графа как arm эксперимента

## Почему

Сегодня единственный способ построить граф в eval-контуре — LLM-экстракция: `EXTRACT_LLM=true`
и `_extract_llm` на каждый чанк. Измеренная цена этого решения:

- одна экстракция — ~3.3 тыс. токенов JSON, ~95 с при 56 ток/с;
- ~211 чанков на корпусе `docs/` (33 документа) → **5.6 часа только на ingest**;
- экстракция не детерминирована: два одинаковых чанка дают разные сущности, поэтому прогон
  невоспроизводим, а состав графа — не измеряемая величина;
- с `EXTRACT_LLM=false` между `ContextNode` **не создаётся ни одной связи** (`_extract_deterministic`
  делает только ноды из слов длиннее 5 букв), то есть графовая ось теряет единственное, ради
  чего измеряется.

При этом механизм ручной разметки **уже реализован и не используется**: `POST
/api/v1/ingestion/documents` принимает `tags` и `links` (`app.py:166-167`, валидация типов на
271-274), `orchestrator.py:1091-1115` превращает их в сущности и связи с `origin="user"`, и на
строке 1312 они идут в ту же запись, что и LLM-сущности. Слияние с уже накопленным графом тоже
работает: тег без `tag_id`, но с `canonical_name` переиспользует существующий узел, если кандидат
ровно один (иначе создаёт новый — инвариант `L2-02`), а `upsert_edges` не даёт ручной связи
перетереть модельной.

То есть ручная разметка — это **аналог golden set для графа**, и она позволяет ответить на
вопрос, который сейчас не поставлен: не «помогает ли граф», а «насколько разметка LLM совпадает
с эталонной разметкой и какой из двух графов полезнее для поиска».

## Что делаем

1. **Формат эталона.** Новая датасетная таблица `prototype/infra/eval/it/graph_annotation.jsonl`:
   одна запись на документ корпуса — `{source_url, tags: [...], links: [...], annotator,
   annotated_at, notes}`. Формат совпадает с тем, что уже принимает Ingestion API, поэтому
   раннер не переводит данные, а передаёт их как есть.

2. **Параметр источника графа.** В `run_eval.py` появляется `--graph-source`:
   - `none` — только vector, граф не строится вовсе (для проверки, что параметр не хуже);
   - `gold` — граф из `graph_annotation.jsonl`, LLM-экстракция выключена, ingest детерминирован
     и быстрый;
   - `llm` — текущее поведение, экстракция из профиля.

   `gold` и `llm` дают полный набор комбинаций, нужных для вывода о вкладе графа: пара
   vector-only против vector+graph для обоих источников графа.

3. **Новая измеряемая величина: согласие LLM с эталоном.** Отдельный отчёт, не влияющий на
   lift: по узлам — precision/recall/F1 по каноническим именам; по рёбрам — по паре
   (нода, вид, нода). Это отдельная метрика качества экстракции, а не качества поиска, и она
   не смешивается с `necessity`/`delta_recall`.

4. **Проверка честности эталона.** Эталон не должен выводиться из текста вопроса. Проверяется
   тем, что аннотация составляется по документу, а вопросы — по эталонным фактам, и никакой
   вопрос не содержит имён узлов из того же документа в том же виде. Формально: ни одна
   `golden_graph_evidence`-разметка не должна совпадать с `query` символ в символ.

5. **Как размечать — открытый вопрос, фиксируется как таковой.** Рассматриваются: ручная
   разметка человеком; LLM-ассистированная разметка с последующей ревизией; разметка только
   тех документов, на которые ссылаются `graph_required` вопросы (то есть сокращение объёма).
   Выбор не входит в этот бандл и требует отдельного решения: от него зависит, можно ли
   считать эталон эталоном.

6. **Побочное следствие.** Прогон `gold` снимает вопрос времени экстракции: 33 документа
   без LLM-экстракции проходят за минуты, и появляется возможность получить первый честный
   результат по вкладу графа на этой неделе, а не через несколько дней.

## Спека

- **`--graph-source=gold` обязан давать тот же результат на том же корпусе при повторе.**
  Это проверяемое требование, а не пожелание: иначе эталон непригоден.
- **Вклад графа измеряется отдельно для каждого источника графа**; смешивать `gold` и `llm` в
  один агрегат нельзя, иначе получится «граф из двух разных графов».
- **Согласие LLM с эталоном — отдельная метрика**, не входящая в lift-отчёт и не влияющая на
  вердикт паности.
- **Эталонные связи не должны попадать в baseline-руку.** Иначе ручная разметка станется
  утечкой в сравнение, а сравнение перестаёт быть честным.
- Инвариант `L2-02` (неоднозначные варианты не объединяются молча) сохраняется: неоднозначная
  аннотация создаёт отдельный узел, а не выбирает один из кандидатов.

## Проверка

1. `pytest`, `ruff check src tests`, `mypy src` в dev-контейнере с host `RUN_CODE_COMMIT`.
2. Юнит-тесты `run_eval.py`: разбор `graph_annotation.jsonl` (валидация схемы, неизвестные поля,
   ссылки на несуществующий `source_url` — ошибка, а не тихий пропуск).
3. Интеграционно на стенде: два прогона `--graph-source=gold` на одном корпусе дают
   одинаковый `manifest.json` по составу графа и одинаковые источники.
4. `gold` против `llm`: отчёт согласия заполнен и различает два случая — узлы найдены,
  связи расходятся.
5. Проверка отсутствия утечки: в baseline-руке `gold` теги и связи не подаются в ingest.

## Открытые вопросы

- **Как размечать** — главный открытый вопрос; от ответа зависит трудоёмкость и честность.
- Нужен ли эталон для всех 33 документов или достаточно тех, что цитируются в `graph_required`
  вопросах. Второй вариант дешевле, но смещает выборку.
- Что считать узлом эталона: понятие, требование, контракт — то есть использовать ли
  `ontology.node_types` как схему аннотации, или держать аннотацию плоской (только
  `canonical_name` + связи). Плоская схема ближе к тому, что реально извлекает LLM, и не
  наследует отменённую типизацию.
- Нужен ли отдельный arm «ручная разметка, отредактированная LLM» — это уже третье
  сравнение, и оно отвечает на вопрос «помогает ли LLM, если человек проверяет».
