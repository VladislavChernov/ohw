# Proposal: Подключение внешних источников данных (source connectors)

> **Планирование, без реализации.** Бандл фиксирует НАПРАВЛЕНИЕ: как к существующему
> проекту подключать внешние системы как источники данных (Jira, Test Management Systems,
> корпоративные вики/Confluence и т.п.) без переписывания ядра. Коннекторы в этом бандле
> НЕ пишутся — оформляется контракт, карта задач и гайд `docs/connectors_guide.md`.
> Реализация — отдельным бандлом, по мере необходимости.

## Почему

Ingestion API (:8002) принимает источники **push**-моделью: клиент сам шлёт содержимое
(`content`) с метаданными `source_url`/`domain`/`doc_type` (`docs/api_reference.md` §5,
ADR-018). Поддерживаются txt/md/pdf через реестр `DocumentReader` (`registry.py::factory`,
ADR-021). Внешние системы (GitLab, Confluence/Wiki, Jira) зафиксированы на границе
системы как входной поток (C4 v6, `docs/history/v6/c4_level1_system_context.txt`), но
**pull-коннекторов нет и не спланировано**: чтобы загрузить данные из Jira/TestRail/вики,
сейчас нужно вручную выгрузить контент и передать его в API.

Требуется: (1) спланировать этот слой, (2) описать в доках, **как создавать коннекторы**,
(3) гарантировать, что будущий коннектор встраивается в существующий проект без
изменения пайплайна.

## Что делаем

- **`docs/connectors_guide.md`** — отдельный гайд «Как создать коннектор внешнего
  источника»:
  - разбор существующих точек расширения: JSON push через `POST /documents`
    (работает уже сейчас, ядро не трогается);
  - путь «коннектор → материал → /documents» (materialize-first): фетчер тянет данные
    по API внешней системы, пишет локальный файл (в `runtime/uploads`), дальше работает
    реестр ридеров — пайплайн и реестр не меняются;
  - целевой контракт `SourceProvider`/`Fetcher` (`fetch(source_url, domain, creds) -> bytes`),
    кормящий существующие `DocumentReader`; регистрация через реестр `doc_type`
    (PDF-паттерн);
  - примеры для Jira / TestRail / Confluence: выбор `doc_type`, метаданные, идемпотентность
    (ADR-014, content_hash), безопасность кредов;
  - тестирование коннектора контрактными проверками.
- **OpenSpec-бандл `add-source-connectors`** — план-бандл: proposal/tasks/design/spec
  фиксируют границы (что делаем / что НЕ делаем) и декомпозицию реализации на будущее.
- **`docs/prototype_requirements.md`** — новая веха «Внешние источники (коннекторы)»
  в статусе «запланирована»; `docs/history.md` — пометка о планируемом бандле;
  `docs/adapters_guide.md` — кросс-ссылка на гайд коннекторов.

## Спека

- `specs/add-source-connectors/spec.md` — «Delta Spec» планируемого поведения:
  контракт `SourceProvider`, регистрация коннекторов в реестре `doc_type`,
  не-регрессия существующего push-пути и пайплайна INGEST→COMMIT.

## Что НЕ входит (границы этого бандла)

- Никакого кода коннекторов (Jira/TestRail/Confluence и пр.) — реализация отдельным
  бандлом по потребности.
- Новая веха НЕ блокирует M3 (adapters/hot-reload), M4 (eval), M5 (MCP/UI).
- Не вводим глобального «поглощения» транспорта в `DocumentReader`:
  фетчинг (транспорт) и чтение (формат) остаются раздельными ответственностями.

   ADR-018, ADR-021).
2. В `prototype_requirements.md` появилась веха «Внешние источники» в статусе
   «запланирована»; статус-таблица вех обновлена.
3. Код не менялся: `uv run pytest -q`, `ruff`, `mypy` — зелёные (регрессии нет).
4. Бандл-задачи в `tasks.md` всё `[ ]` (отложены) — реализация отдельным бандлом.
