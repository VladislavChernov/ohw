## Зафиксированный пробел

1. **Источники не разделены по осям.** `done.sources` строится из векторных чанков
   (`pipeline.py:185` `build_sources(body_chunks)`), графовый скелет
   (`skeleton_rows`, `pipeline.py:163`) в `sources` **не попадает вообще** (ED10-04).
   Значит retrieval-метрики (ADR-015) принципиально не видят графовые доказательства,
   а «вклад графа» сейчас не измерим даже теоретически (EV09-02).
2. **Набор вопросов не пригоден для ответа про граф.** Main it-набор — плоский формат
   ADR-015 (одна строка `golden_facts`, нет `reasoning_type`, групп evidence, rubric);
   нет multi-hop вопросов, которые требуют именно графовых путей (ED10-02). Формат,
   который ревью назвал «первым полноценным IT-набором», реализован только в маленьком
   пилоте `pilots/docs-review/` (10 вопросов, development-выборка).
3. **Dанные теряются.** Раннер не сохраняет пары «вопрос → ответ»: в артефактах нет
   текста ответа, per-вопросных источников и таймингов — нельзя посчитать точность
   и провести ручной/постпроцессный разбор. `README-minimal.md:56` прямо фиксирует
   «per-question ответы не сохраняются».
4. **LLM-judge — узкое место.** На текущем железе judge ≈ 80–85% времени eval-прогона
   (~2–3 ч на M5). Судья мешает быстрому итеративному циклу «переработка набора →
   парный прогон → разбор пар», поэтому нужен штатный fast-loop без судьи.

## Что делаем

- **Типизированный граф (предусловие)**: сейчас загрузка пишет однородные `Entity`
  без рёбер (`orchestrator.py:442,470-472`), а Cypher требует `Requirement|Concept|Contract`
  (`retrievers.py:82-90`) — соседи не матчатся, графовая ось вырождена (ED10-04
  подтверждён разбором логов M5: `label does not exist`). EXTRACT переносит онтологию
  (LLM-путь по `extraction.prompt_template` под флагом, детерминированный fallback
  для fake-режима); профиль загружается один раз на джобу и передаётся через
  `PipelineContext.profile`, а извлечённые связи — через `PipelineContext.entity_edges`.
  COMMIT пишет тип как метку, рёбра по `edge_types` и связь `Chunk-[:MENTIONS]-> Entity`.
  Плюс **schema-провижининг**: `GraphStoreProvider.ensure_schema(node_types)` —
   constraints уникальности по паре `(domain, canonical_name)` для всех трёх доменных типов текущего
  `it`-профиля; вызов
  выполняется перед первым COMMIT домена и должен быть идемпотентным при повторных
  вызовах. Это заменяет неисполненное обещание автоматического DDL при активации
  профиля: Config Service не имеет доступа к Neo4j.
- **Парный дизайн эксперимента**: каждый вопрос прогоняется дважды на одной revision —
  `RETRIEVAL_GRAPH_ENABLED=false` (vector-only) и `=true` (гибрид). Вклад графа
  оценивается на срезе вопросов с разметкой `golden_graph_evidence`: где графовые
  доказательства необходимы и отличны от векторных.
- **Разделение источников по осям**: `sources` получают признак `axis` (graph|vector),
  графовый скелет включается в `done.sources` (закрывает ED10-04). Новые метрики
  `graph_contribution` — recall по осям и «необходимость графа».
- **Переработка it-набора (50) в формат v2**: атомарные `golden_facts`,
  `reasoning_type`, `answerability`, `as_of`, `evidence_sections`, `evidence_policy`,
  `rubric` (по образцу `pilots/docs-review/questions.jsonl`); отдельный поднабор
  `it/questions_graph.jsonl` — multi-hop и графо-специфичные вопросы с признаком
  `golden_graph_evidence`. `library`/`cinema` остаются smoke-наборами
  (реальные доменные корпуса — вне прототипа по ревью №10).
- **DoD по ингесту (Вариант А, внутри этого бандла)**: единый `_identity_key`
  (`canonical_name` для всех трёх типов онтологии; тип — метка узла, не часть
  node_id), вырез эхо-текста из свойств узла (текст хранится один раз — в
  чанке/векторной оси), жёсткая связка сущности с `chunk_id`. Без этих пунктов
  типизированный граф получает разнобой ключей, дубли текста и несводимые оси —
  эксперимент мерил бы шум.
- **Судья: ревизия набора и калибровка**: 50 контрольных вопросов настраиваются
  **до** переразметки в v2 (фонящие переписать/удалить; набор — не gold set,
  статус фиксируется в датасете), версия промпта-судьи записывается в
  `run_manifest.json`, разовая калибровка (согласие с ручной оценкой выборки
  пар) — до финального прогона.
- **Послойные артефакты прогона**: прогон оставляет проверяемый след в четырёх слоях —
  `run_manifest.json` (условия: что сравнивалось), `<out>/qa_log.jsonl` (пары «вопрос–ответ»,
  append, переживает прерывание: id, mode, graph_enabled, query, retrieved+axis, golden,
  answer, timings, метрики), `lift_report.json/.md` (агрегат и вердикт) и опциональная
  диагностическая трасса `<out>/trace.jsonl` (`--trace`: ход данных внутри одного вопроса).
  Слои 1–3 обязательны **в любом режиме**, включая judge-less (иначе fast-loop не оставляет
  следа — инвариант «оценка не зависит от железа судьи»).
- **Режим без судьи**: `--no-judge` (генерация есть, LLM-judge нет) и `--retrieval-only`
  (без генерации и judge; LLM ingestion требуется только при `--corpus` с `EXTRACT_LLM=true`).
  Полный прогон с судьёй — опциональный, одиночный, на финальном этапе (оба режима, как договорено).
- **Жизненный цикл проекций:** текущий эксперимент использует синхронный COMMIT, source-aware
  revision и отдельные graph/vector-адаптеры; полноценные outbox, dual-generation и миграция
  проекций отложены на **M6-Growth / pre-connectors**. До этого этапа профиль/ontology
  считаются неизменными для уже загруженного корпуса: повтор того же `content_hash` — no-op,
  автоматический reindex после смены профиля не реализован.

## Зафиксированные контрактные решения

До реализации оркестратора принимаются следующие решения:

- **Идентичность:** `_identity_key(canonical_name)` возвращает нормализованный ключ
  (`NFKC`, `ё → е`, `casefold`, сжатие пробелов). `node_id` доменной сущности имеет
  вид `ent:{domain}:{identity_key}` и не содержит тип. Тип остаётся меткой; совпадение
  canonical-имени у разных типов объединяет метки одного узла. Это решение применяется
  к `it`-профилю; `library`/`cinema` сохраняют собственные `unique_key` до отдельной
  миграции. `source_ids` в Entity — список канонических `source_url`, а `chunk_ids` —
  список стабильных идентификаторов чанков; это разные уровни адресации.
- **Профиль и API:** профиль загружается один раз на джобу; `PipelineContext`
  содержит `profile` и `entity_edges`. `ChunkStage`, `ExtractStage` и `CommitStage`
  используют один снимок профиля, а не загружают его независимо. Production wiring
  `Executor`/`build_analyzer` обязан передавать LLM и загрузчик профиля так, чтобы
  `create_app()` собирался без `TypeError`.
- **LLM и fallback:** `EXTRACT_LLM=true` включает почанковый вызов по
  `extraction.prompt_template`; выключенный флаг и fake/in-memory режим используют
  deterministic fallback с меткой `Entity`. Явно включённый LLM-путь не переходит
  на fallback молча при ошибке профиля или LLM.
- **Связи:** доменные связи принимаются только из `ontology.edge_types`, их endpoints
  нормализуются и проверяются после NORMALIZE/DEDUP. Платформенная связь —
  `Chunk-[:MENTIONS]-> Entity`; текст чанка в свойствах Entity не дублируется.
- **Идентификаторы и изоляция домена:** `chunk_id` включает `domain`, чтобы одинаковый
  URL в разных доменах не приводил к коллизии Chunk/vector; graph/vector retrieval
  фильтрует активный домен, а результат Neo4j vector search нормализует metadata
  до `{chunk_id, text, source_url, domain, index}`. Entity↔chunk связывается через
  `chunk_ids` и `MENTIONS`.
