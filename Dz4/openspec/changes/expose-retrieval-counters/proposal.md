# Proposal: Счётчики retrieval объявляют то, что измерено

## Почему

Два счётчика в ответе на запрос показывали не то, что происходило.

**Глубина обхода.** `max_depth_effective` — это результат `_expand_depth`, то есть
`min(max(depth, 1), MAX_EXPANSION_DEPTH)`: чистый зажим числа в диапазон. Подпись
«Глубина: запрошено 3, применено 3» на пустой базе утверждала, что глубина применена,
хотя обход не выполнялся вовсе. Настоящее измерение существовало — `depths` по строкам
обхода, — но доходило только в трейс, а трейс уходил наружу под условием `if trace:`,
а sink вызывающим не передавался.

**Расход токенов.** `last_usage` читался только в нестриминговом ответе
(`_extract_content`), а пайплайн и UI работают через `generate(..., stream=True)`. В потоке
счётчик приезжает отдельным чанком с пустым `choices`, а `_extract_delta` такой чанк
возвращает как `("", None)` — то есть молча пропускает. Итог: `usage: null` при
полностью состоявшемся ответе.

Оба молчали. Это тот класс, что в правилах проекта назван «молчание хуже отказа»: отказ
виден по логу, молчание выглядит как «измерено».

## Что делаем

1. Разводим три величины: `max_depth_requested`, `max_depth_allowed`,
   `hops_traversed`. Существующее имя `max_depth_effective` сохраняем — приборы и отчёты
   могли его читать.
2. В UI слово «применено» заменяется на «разрешено» и добавляется «пройдено».
3. Запрашиваем `stream_options.include_usage` при `stream=True` и принимаем `usage` из
   чанка **до** разбора дельты.
4. В подпись ответа добавляется расход токенов: `prompt`, `completion`, `total`.
5. Каждый счётчик защищён сторожем, проверенным откатом.

Проверка на сервере, а не чтением кода: без флага 7 чанков и `usage: null`, с флагом
8 чанков и точные числа.

## Спека

Новое требование: **объявленный счётчик обязан отличать разрешённое от выполненного, а
счётчик, который не измеряет, обязан молчать или показывать ноль измеренного — но не
выдавать разрешённое за выполненное.** Требования и сценарии — в
`specs/expose-retrieval-counters/spec.md`.

## Проверка

```powershell
# 1. Глубина: три величины, а не две
docker exec ohw-runtime-query-api python -c "...stream... "
# ожидание: allowed = 3, hops = 0 на пустой базе

# 2. Расход токенов доезжает
# в ответе есть usage; completion_tokens совпадает с eval time в логе llama.cpp

# 3. Сторож ловит откат
# hops_traversed = 0 вместо max(depths) -> assert 0 == 1
# usage не принимается из потока      -> assert None == {...}
```

Замер на живом стенде: `prompt 84, completion 118, total 202`; лог llama.cpp показывает
`eval time / 118 tokens` — генерация совпадает до единицы.

**Границы:** измерения сделаны на одном запросе и одном пустом наборе. Полнота по корпусу
не измерялась.
