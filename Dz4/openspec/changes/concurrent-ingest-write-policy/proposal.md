## Зафиксированный пробел

**Концепция регламентирует:**
- **атомарность пары осей** в пределах одного движка (L2-04, ADR-024) — это про *одну джобу*;
- **идемпотентность повторной загрузки** того же `source_url` (L2-06, ADR-014) — про *повтор одной и той же джобы*;
- **поочерёдность GPU-фаз** (L4-01 → ограничение среды, ADR-027) — про *эмбеддинг/LLM на одной видеокарте*.

**Чего нет нигде:** правило поведения при **конкурентной записи нескольких разных джоб
в общие узлы графа** (нормированные `Entity`, разделяемые между документами корпуса).
Инварианты и ADR покрывают композицию «одна джоба», но не пересечение «N джоб × N сущностей».

**Реализация** честно исполняет контракт: `CommitStage` открывает транзакцию движка и пишет
поштучным `MERGE (n {node_id: $node_id})` (`neo4j.py:227`, `_upsert_nodes`/`_upsert_edges`).
Две такие транзакции по одним узлам в разном порядке захвата замков → классический deadlock
движка. Дальнейшая классификация: `DeadlockDetected` входит в класс **transient-ошибок**
Neo4j, которые вендор официально предписывает ретраить — успех при повторе почти гарантирован.
В коде пути retry **нет** (поиск по `retry|TransientError|DeadlockDetected` даёт только
backoff воркера Redis-очереди query-контура, не в прошлом записи).

**Вывод:** это пробел на стыке «концепция → контракт → реализация». Точка входа найдена
на уровне реализации, но узел фиксируется в концепции: политика конкурентной записи
COMMIT не декларирована. L4-01/ADR-027 к нему отношения не имеют (другая ось — VRAM).

## Принципы концепции, которыми руководствуемся

| Принцип | Где зафиксирован | Как применяем |
|---|---|---|
| Ядро не знает реализаций и вендоров | L1-02, ADR-012 | Sorted-порядок — контрактный (по полям плана `node_id`), transient-retry — через свойство хранилищ, без импорта `neo4j` в ядро |
| Отказоустойчивость записывающего контура — честная декларация, а не «починим потом» | ADR-024 (capability-паттерн) | Новый контракт `commit_retry`/`transient_aware` на провайдерах — по образцу `consistency_capability` |
| Детерминизм критичных шагов Python-кодом | L1-05 | Детерминированный порядок узлов/рёбер перед записью |
| Масштабирование через очередь, а не через число потоков | `docs/06` §4 (`ingestion: Синхронно → Redis/RabbitMQ → Kafka`) | Правило формулируется для N воркеров очереди (S3) |
| Идемпотентность повторов | L2-06, ADR-014 | Ретрай безопасен: повтор MERGE — no-op по контенту |

## Варианты решения

### A. Retry transient-ошибок COMMIT (рекомендуется, «честный» вариант)
Обернуть транзакционную запись (`_write_atomic` / `_write_best_effort` / soft-delete) в retry с
backoff+jitter, ловищий **transient**-класс ошибок движка. Neo4j ретраить — официальная
рекомендация; deadlock почти никогда не повторяется при повторе.
- Ядро не знает вендора: провайдеры декларируют способность `transient_aware() -> bool`
  (Neo4j — да, InMemory — нет) и/или экспонируют `is_transient(exc)`; retry-loop в
  `CommitStage` использует декларации (паттерн ADR-024).
- Скаляр: `N_RETRY_COMMIT` (дефолт 3), backoff `0.2 * 2^i + jitter`, среды не блокирует.
- Сохраняет параллелизм (`INGEST_MAX_CONCURRENT>1` остаётся валидным).

### B. Детерминированный порядок записи (рекомендуется как дополнение к A)
Сортировать `nodes` по `node_id`, `edges` — по `(from_id, to_id, type)` перед записью:
все транзакции захватывают замки в одном порядке → взаимное ожидание невозможно.
- Контрактный lexicographic sort на полях плана — без знания о внутренностях движка (L1-02).
- Полностью не исключает deadlock в общем случае (эджи и вложенные операции тоже берут
  замки), поэтому A остаётся обязательным; B ещё и повышает дедупликацию паттернов записи.

### C. `INGEST_MAX_CONCURRENT=1` (текущий обход для eval — не решение)
Сериализация джоб убирает конфликт, но отменяет параллельную индексацию и не регламентирует
конкурентность на стадии роста («очередь ingestion», `docs/06` §4). Годится как временный
обходной путь, фиксируется в прототипной доке как ограничение среды.

### D. Отдельный писатель-очередь (single-writer commit)
Все записи через одно owned-место. Максимально надёжно, но добавляет компонент (общая
очередь коммита) — избыточно, пока конкурентность = потоки одного процесса; становится
уместным на S3 (несколько воркеров), где писатель = часть очереди.

**Рекомендация:** A + B — правильное продуктовое решение (ложится на принципы L1-02/L1-05/
ADR-024); C — обход для текущего прогона M5; D — пересмотреть на стадии «Рост».

## Стадии внедрения

| Стадия | Содержание | Когда | Что становится |
|---|---|---|---|
| **S1** | `INGEST_MAX_CONCURRENT=1` в eval-compose; фиксация дефекта в `docs/06` §5/matrx рисков | сейчас (блокирует полный прогон M5) | временное ограничение среды |
| **S2** | Вариант B (ordering) + вариант A (retry transient) + контракт на провайдерах + тесты | M5-хвост (ближайший бандл) | снимает ложку deadlock, возвращает `INGEST_MAX_CONCURRENT=2` (дефолт) |
| **S3** | Переход ingestion на очередь (Redis/RabbitMQ → Kafka, `docs/06` §4); N воркеров очереди пишут по правилам S2; при необходимости — single-writer путь | стадия «Рост» | конкурентность регламентирована для N воркеров |

S2 фиксируется отдельным инвариантом (см. спека) и ADR-028.

## Что делаем (в рамках этого бандла)

- **Фиксация пробела** в концепции: этот proposal + правки `docs/invariants.md` (новый
  инвариант конкурентной записи) + `docs/06` §5 (запись риска/deadlock, сегодня как S1-ограничение).
- **Контракт retry**: `transient_aware()`/`is_transient()` на `GraphStoreProvider`/
  `VectorStoreProvider` (паттерн ADR-024); реализация Neo4j (обёртка драйвера) и InMemory (None);
  `is_transient` учитывает цепочку `__cause__` (UC12-02).
- **CommitStage**: retry-loop вокруг атомарной записи и best-effort пары; компенсация
  выполняется только после исчерпания retry (не на первом transient) (UC12-02);
  `N_RETRY_COMMIT` — число повторов, всего попыток N+1, env валидируется fail-fast
  (UC12-03); причина ошибки сохраняется через все обёртки.
- **Согласованность soft-delete** (UC12-06): компенсация реестра
  `rollback_soft_delete` при окончательном отказе удаления в хранилищах.
- **Упорядочение записи**: сортировка `nodes`/`edges` по контрактным ключам в `_write`.
- **Еval-доки**: `compose.eval.yaml`: `INGEST_MAX_CONCURRENT=1` (S1) помечается как временное;
  после S2 возврат к 2.
- **ADR-028** (черновик): политика конкурентной записи COMMIT.
- **Тесты**: retry на transient (фейк-стоres бросают transient N раз, потом успех), порядок
  записи (последовательность вызовов отсортированная), инвариант no-op повтора.

## Что НЕ входит

- Переписать боевой путь на single-writer (S3, отложено).
- Изменение контракта `POST /documents` и стадий пайплайна (ADR-018/ADR-021).
- Распределённые транзакции/2PC (запрещено ADR-024).
- Дефекты eval-раннера из ревью №12: UC12-01 (режим `both` в run_eval.py),
  UC12-04 (строгая готовность корпуса), UC12-10 (дедлайн retrieval-futures) —
  отдельный бандл по раннеру; UC12-10 требует собственного proposal.

## Проверка

1. `uv run pytest -q` зелёно; `uv run ruff check .`, `uv run mypy src` — чисто.
2. Unit: фейк-pair бросает `TransientError` → retry + успех; не-transient — failed без retry;

3. Live на стеке (inmemory-индекс): ingestion проходит, повторная загрузка — no-op (L2-06).
4. Neo4j-стек (вариант M5): полный прогон с `INGEST_MAX_CONCURRENT=2` без deadlock (после S2).
