# Delta Spec: политика конкурентной записи COMMIT

## Scope

Планирование и реализация декларации «как конкурентные ingestion-джобы пишут в общий граф»
(найдено: полный eval M5, `Neo.TransientError.Transaction.DeadlockDetected`). Пробел концепции
фиксируется, контракт и код закрываются в порядке стадий S1→S3.

## 1. Контракт провайдера: transient-retry (паттерн ADR-024)

`src/graphrag_proto/retrieval/adapters/base.py`:

```python
class GraphStoreProvider(ABC):
    def transient_aware(self) -> bool: ...       # дефолт False
    def is_transient(self, exc: BaseException) -> bool: ...   # вызывается только при transient_aware()

class VectorStoreProvider(ABC):
    def transient_aware(self) -> bool: ...       # дефолт False
    def is_transient(self, exc: BaseException) -> bool: ...
```

- `transient_aware()==True` — бросает transient-ошибки (сеть/deadlock), повторы имеют смысл.
- `is_transient(exc)` — вендор-специфичная классификация; ядро не импортирует драйвер (L1-02).
- Neo4j-адаптеры: `transient_aware()==True`, `is_transient = isinstance(exc, neo4j.exceptions.TransientError)`
  + `neo4j.exceptions.ServiceUnavailable` (класс transient по драйверу). URL/сеть — transient.

## 2. CommitStage: retry-loop + порядок

> Ревизия 2026-09-17 по ревью №12 (UC12-02, UC12-03, UC12-06, UC12-07): уточнены
> семантика `N_RETRY_COMMIT`, момент компенсации, сохранение причины ошибки и
> согласованность soft-delete. Формулировка инварианта смягчена (см. §3).

- `_write_atomic`, `_write_best_effort`, тело `soft_delete_source` оборачиваются в
  `_with_commit_retry(stores, fn)`:
  - `N_RETRY_COMMIT` — число **повторов** после первой (исходной) попытки; дефолт 3,
    всего попыток `N_RETRY_COMMIT + 1`. `N_RETRY_COMMIT=0` — ровно одна попытка, без
    повторов. Env-параметры (`N_RETRY_COMMIT`, `RETRY_BASE_S`, `RETRY_JITTER_S`)
    валидируются при старте: отрицательные и нечисловые значения — ошибка конфигурации
    (fail-fast), не молчаливый дефолт;
  - backoff `0.2 * 2^i + U(0, 0.1)` между повторами;
  - transient только если **какой-либо** store пары декларирует
    `transient_aware() and is_transient(exc)`; иначе — сразу raise (failed);
  - **компенсация best_effort выполняется ПОСЛЕ исчерпания повторов, не на первом
    transient** (UC12-02): путь «первая ось ок → transient сбой второй оси» обязан
    пройти весь retry второй оси; компенсация — только при окончательном отказе;
  - причина ошибки сохраняется на границе адаптера и обёрток (UC12-02): все
    `raise ... from exc` — цепочка `__cause__` intact; `is_transient(exc)` провайдера
    проверяет и сам `exc`, и его `__cause__` (транспарентная развёртка цепочки),
    чтобы обёртка `CommitStageError` не ломала классификацию. Это дополнение к
    переносу момента компенсации, а не замена.
- `CommitStage._write`: перед вызовом хранилищ —
  `nodes.sort(key=node_id)`, `edges.sort(key=(from_id, to_id, type))` (детерминированный
  порядок замков, L1-05; поля контрактные — без знания вендора).
- `_upsert_nodes`/`_upsert_edges` (neo4j.py) дополнительно сортируют входящий список
  (контрактная гарантия порядка для любых вызовов).

## 2а. Согласованность soft-delete (UC12-06)

Текущий порядок «`registry.soft_delete` → удаление в хранилищах (под retry)» оставляет
рассинхрон: при окончательном отказе хранилищ реестр уже помечен deleted, данные остались.

Контракт ревизии:
- `registry.soft_delete` остаётся гейтом идемпотентности (L2-06) и выполняется первым;
- при **окончательном** отказе удаления в хранилищах (исчерпан retry / non-transient)
  реестр возвращается в исходное состояние компенсирующим действием
  `registry.rollback_soft_delete(domain, source_url)` (новый метод реестра), после чего
  джоба failed; повторная джоба снова проходит полный путь;
- повторный вызов `soft_delete_source` после частичного удаления безопасен: удаление
  чанков идемпотентно (L2-06), `list_chunk_ids_of_source` вернёт остаток.

Альтернатива «реестр после хранилищ» отклонена: ломает гейт идемпотентности и допускает
двойную обработку при повторе джобы.

## 3. Инварианты и ADR

- Новый инвариант (L3-06, черновик; формулировка по UC12-07 — без заявления
  «deadlock невозможен»): план записи COMMIT детерминирован по порядку (контрактные
  ключи сортировки); transient-ошибки движка ретраятся до `N_RETRY_COMMIT` перед
  fail/компенсацией; не-transient — фаил без повторов. Детерминированный порядок
  **снижает вероятность** deadlock-циклов на общих сущностях, но не исключает их
  полностью (другие операции и блокировки движка) — отсюда обязательный retry.
- ADR-028 (черновик): политика конкурентной записи; границы (без 2PC, без single-writer
  на S2); семантика `N_RETRY_COMMIT` = число повторов; согласованность soft-delete по §2а.
- `docs/06` §5: риск «Neo4j deadlock при INGEST_MAX_CONCURRENT>1» + пометка S1-обхода.

## 4. Стадии

- **S1 (текущая блокировка прогона):** `INGEST_MAX_CONCURRENT=1` в `compose.eval.yaml`;
  фиксация риска в `docs/06` §5. Временное ограничение среды (паттерн ADR-027).
- **S2 (M5-хвост):** контракт transient + retry-loop + сортировка + тесты; возврат дефолта
  `INGEST_MAX_CONCURRENT=2`; дока + инвариант + ADR-028.
- **S3 (стадия «Рост», `docs/06` §4):** ingestion на очереди (Redis/RabbitMQ→Kafka), N воркеров
  пишут по правилам S2; single-writer — при необходимости. Инварианты не меняются.

## 5. Не входит

- 2PC (ADR-024), изменение `POST /documents` (ADR-018), pipeline-стадий (ADR-021),
  реализация single-writer/s3.
- Дефекты eval-раннера из ревью №12: UC12-01 (режим `both`), UC12-04 (строгая
  готовность корпуса), UC12-10 (дедлайн retrieval-futures) — отдельный бандл
  по раннеру; UC12-10 требует собственного proposal (нетривиальное изменение
  контракта дедлайнов).

## Проверка приемлемости

- `pytest`-юниты: фейк-transient store (N повторов → успех; не-transient → failed сразу;
  порядок вызовов отсортирован по контрактным ключам); transient второй оси → успех
  **без преждевременной компенсации** (UC12-02); исчерпание повторов → финальная
  компенсация; причина ошибки (`__cause__`) доступна классификатору после обёртки;
  `N_RETRY_COMMIT=0/1/3`, отрицательные и нечисловые значения → fail-fast;
  компенсация `rollback_soft_delete` при окончательном отказе удаления (UC12-06).
- `ruff`/`mypy` чисто.
- Live-стек: полный прогон M5 с `INGEST_MAX_CONCURRENT=2` (после S2) без deadlock;
  повторная загрузка — no-op (L2-06).
