# Design: Ревизия данных в query-контуре (Веха 4-хвост, L2-07)

## Контекст

ADR-026 (Accepted) зафиксировал три решения: по-доменная гранулярность; источник —
fingerprint активного сета DocumentRegistry (`sha256(sorted(content_hash))`); доставка —
`GET /api/v1/ingestion/revision?domain=` + поллер в worker. Ниже — конкретные
строительные блоки прототипа и границы гарантии.

## Архитектура

```
Ingestion (DocumentRegistry.upsert/soft_delete)
   └─ data_revision(domain) = sha256(sorted active content_hash)
   └─ GET /api/v1/ingestion/revision?domain=   (X-API-Key)

Query Worker (loop)
   └─ RevisionClient  (per-domain кэш + интервал REVISION_POLL_INTERVAL_S)
        └─ process_one(task): rev = revisions.revision(task.domain)
             └─ QueryPipeline.run(query, domain, emit, revision=rev)
                  └─ SemanticCache.lookup/store(..., revision=rev)
                       Redis: query:sc:<rev>:<domain> | query:sc:<domain>
```

## Ключевые решения (в развитие ADR-026)

1. **Поллер «по потребности», без статического списка доменов.**
   `process_one` вызывает `revisions.revision(task.domain)`; `RevisionClient`
   обновляет ревизию домена не чаще интервала (пер-доменный `last_poll`).
   Задержка bump ≤ интервал — совпадает с ADR-026 «задержка = интервал поллинга».
   Статический список доменов (опция ADR-026) не требуется: домены приходят из
   задач запросов.

2. **Эпоха по умолчанию = без ревизии.**
   Домен до первой успешной доставки ревизии (включая недоступный ingestion) работает
   на ключе `query:sc:<domain>` — буквально M3-поведение, обратная совместимость и
   честный fail-open. После bump запросы переходят на `query:sc:<rev>:<domain>`,
   старые эпохи выпадают из поиска и дочищаются TTL.

3. **`None`-ревизия не маскируется от оператора:**
   `done.revision` присутствует всегда (str | None) — Eval-срез фиксирует «по каким
   данным собран» даже когда ревизия ещё/уже неизвестна.

4. **Счётчики кэша живут там же, где записи:**
   meta-ключ повторяет эпоху записи (`query:sc:<rev>:<domain>:meta`) — `stats()`
   агрегирует по всем эпохам, `clear()` сметает и старые эпохи (SCAN `query:sc:*`).

5. **InMemory — тот же контракт:**
   бакет ключуется `(domain, revision)`. Старые эпохи не хлазурятся принудительно
   (доживают до TTL) — продлитое допущение, как в Redis.

6. **Ошибки поллера не молчат (паттерн S6/`topology_poll_errors_total`):**
   `RevisionClient` считает `revision_poll_errors_total`; значение попадает в
   снапшот метрик воркера — «тихая глотка» сбоев ingestion исключена.

7. **Видимость свежести для оператора (ревью-07, вывод 3):**
   снапшот метрик несёт известные текущие ревизии доменов
   (`{domain: revisions.revision(domain)}`) — ответ на «какая ревизия данных
   сейчас в query-контуре» без захода внутрь контейнера.

## Риски и границы (фиксируются)

- **Bounded staleness:** «свежесть ответа = свежесть данных» гарантируется только при
  совпадении `done.revision` и текущей `rev<domain>`; окно рассогласования ≤ интервал
  поллинга + время обработки запроса. Прямая инвалидация «как в индексе» не
  реализуется (ADR-025).
- Ревизия по-доменная; глобального fingerprint-а нет — изоляция доменов (L1-01).
- `data_revision` строится на `content_hash` активных документов — soft-delete
  источника меняет ревизию (честно: срез данных изменился).
- Лишний HTTP на первый запрос домена в окне поллинга — незначимо для прототипа
  (интервал кэширует; один воркер).
