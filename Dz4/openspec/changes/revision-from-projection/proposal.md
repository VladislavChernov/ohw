# Proposal: ревизия в query-контуре читается из опубликованной проекции

## Почему

ADR-026 п.3 сделал доставку ревизии в query-контур через
`GET /api/v1/ingestion/revision` и поллер в воркере. Для вопроса «по каким данным собран
ответ» это не та сторона: ревизия реестра меняется в момент приёма документа, а видимыми
данные становятся в момент публикации проекции. Между этими моментами запрос заполнил бы кэш
под новым epoch старыми данными, и запись жила бы до следующей смены — гонка «epoch раньше
публикации».

Обычный порядок в системах с read-model обратный: версия, по которой ключуется кэш,
принадлежит тому, что читает запрос, и меняется в одной публикации с ним. У нас это уже так
устроено для готовности: `retrieval/pipeline.py:810-870` читает `projection_state`, а прибор
считает `projection_revision` независимым сигналом и прямо называет `done["revision"]` эхом
аргумента (`infra/eval/run_eval.py:1107-1118`).

Файл состояния уже смонтирован в контейнер (`compose.runtime.yaml`, том `projection`).
Значит новая зависимость не вводится — снимается HTTP-зависимость от ингеста.

Решение владельца (2026-10-19): вариант 2 — читать ревизию из `projection.db`; считать, что
БД актуальна; ответ при неизвестной ревизии отдавать из кэша.

## Что делаем

- воркер берёт `data_revision` из `projection_state` (через `ProjectionStateStore`, уже
  используемый пайплайном) вместо `RevisionClient`;
- значение передаётся в `pipeline.run(..., revision=...)` как раньше — кэш и fingerprint
  среза не меняют форму;
- ревизия неизвестна (строки проекции нет): `revision = null`, `revision_source =
  unavailable`, ответ формируется и **отдаётся из кэша** (решение владельца), epoch —
  именованная константа, отличная от любого `sha256`;
- `done` ответа несёт `revision` и `revision_source`; в отчёте прибора источник уже есть
  (`run_eval.py:1478-1480`), манифест берёт ревизию из ответа так же, как раньше;
- `RevisionClient` и поллер снимаются; `revision_poll_errors_total` заменяется счётчиком
  **чтения проекции** (ошибка открытия/чтения — счётчик, отсутствие строки — `unavailable`),
  а не остаётся нулём;
- `GET /api/v1/ingestion/revision` **остаётся**: им пользуются клиенты ингеста и прибор
  (`run_eval.py:1083-1104`). Меняется только источник в query-контуре.

## Спека

`specs/revision-from-projection/spec.md`: источник ревизии, семантика `null`/`unavailable`,
epoch кэша при неизвестной ревизии, метрика чтения, что остаётся неизменным (HTTP-эндпоинт,
смысл `data_revision` по ADR-046 п.8, готовность графа не зависит от доменной ревизии).

**Переопределяет** разделы «RevisionClient (query-воркер)» и «Метрики снапшота воркера»
спеки `openspec/changes/data-revision-query-context/specs/.../spec.md:48-66`. Форма кэша
(`query:sc:<rev>:<domain>`) не меняется.

## Проверка

- `pytest prototype/tests` — включая новые гарды:
  - строка проекции есть → `revision` равен `projection_state.data_revision`, `revision_source
    = reported`;
  - строки нет → `revision = null`, `revision_source = unavailable`, ответ не падает и
    отдаётся из кэша;
  - значение не превращается в `""` или `0`.
- `run_eval --mode both --no-judge` на наборе `ready`: в манифесте `revision` совпадает с
  `projection_revision`-эпохой, `revision_source = reported`; на `empty` — `null` /
  `unavailable` и граф выключен по `projection_status=missing`, а не по `revision_unknown`.
- `gate.sh full` перед коммитом.
