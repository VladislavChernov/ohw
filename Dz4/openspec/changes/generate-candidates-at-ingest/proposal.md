# Proposal: Кандидаты не хранятся, а производятся при загрузке

## Почему

Сейчас список кандидатов — файл на диске: `pre-ingest/<документ>_candidates.json`,
привязанный к `sha256` исходного текста, и `load_candidates` (`candidates.py:93`) читает его
при загрузке. ADR-053 закрепил это как отдельную операцию: «кандидатов производит отдельная
операция — отдельный контейнер и отдельный скрипт запуска, а не стадия ingestion-пайплайна»
(п. 4), а `pre-ingest/` объявлена «папкой ПРОИЗВОДНЫХ файлов» (Дополнение 3).

**Проверка мотивации «не жрать место на диске»: она не подтверждается измерением.**
Вся папка `pre-ingest/` — **30 файлов, 127 065 байт, 0.12 МБ**. Крупнейший файл
`05_adr_log.md_candidates.json` — 24 892 байта. Экономия места здесь не ощущается ни на
каком объёме корпуса: кандидаты — это имена, а не текст.

Значит настоящая причина другая, и её надо назвать прямо, иначе изменение будет защищаться
неверным доводом.

**Настоящая причина — артефакт как второе состояние.** Хранимый список обязан быть
синхронизирован с документом, и синхронизация обеспечивается вручную: отдельный запуск
`run_pre_ingest.ps1` перед загрузкой. Три отказа подряд дали результат, неотличимый от
успеха (`openspec/changes/fill-ready-corpus/proposal.md`):

1. кандидаты монтировались не оттуда — docker создал пустую папку, 703 `Chunk`, 0 `ContextNode`;
2. не хватало `EXTRACT_LLM` — те же джобы, тот же вид;
3. `start_period` меньше времени старта.

Из них первый и есть следствие хранения: **контейнер видел 0 кандидатов, и это нигде не было
видно до загрузки.** При хранении на диске отсутствие артефакта — законное состояние папки,
и система обязана его трактовать как «режим `vector_only`», а не как поломку. Отсюда и
`candidates.py:109`: документ без списка грузится только в вектор, и джоба завершается
`succeeded`.

**Если кандидаты производятся при загрузке, сверка хешей становится ненужной по построению.**
Список получается из того же текста, который идёт в разбор, поэтому он не может оказаться от
другой версии документа — нечего сверять. Исчезают: папка `pre-ingest/`, переменная
`CANDIDATES_DIR`, ошибки `CandidateListStaleError` и `CandidateListConfigError`, а также
режим `vector_only` как путь, в который можно попасть случайно.

Замечу отдельно: `CandidateListStaleError` сейчас ловит подмену — «работа по чужому списку
даёт правдоподобный, но неверный граф». При переносе в пайплайн подмена становится
невозможна конструктивно, и этот класс исчезает вместе с ошибкой, а не с проверкой.

## Форма, заданная владельцем (2026-10-14)

Предыдущая редакция этого proposal предлагала вычислять кандидатов прямо в пайплайне.
**Форма уточнена владельцем и отличается:**

- **Документ существует ровно в двух местах:** там, откуда его взяли для загрузки, и внутри
  базы. Третьего места хранения не будет — ни папки с корпусом, ни архива.
- **`pre-ingest/` — временное место.** Туда кладётся порезанный документ с кандидатами на
  время загрузки.
- **После успешной загрузки `<документ>_candidates.json` удаляется.** Удаляется ровно один
  файл: отдельного «списка нод документа» не существует и не заводится.
- **Сейчас это делается вручную**, и это не работающая схема, а её отсутствие.

Оговорка «после успешной» существенна: при отказе файл остаётся, иначе нечего предъявить
для разбора причины.

## Стадия очистки пре-ингеста: её нет ни в коде, ни в планах

Проверено перед тем, как записать:

| где искали | результат |
|---|---|
| код `prototype/src` | единственный `unlink` — `app.py:581`, оборванный файл загрузки при обрыве стрима; удаления кандидатов нет |
| `prototype/infra/scripts`, `checks` | нет |
| `openspec/changes/*` | нет упоминаний очистки кандидатов ни в одном change |

Значит стадия очистки не реализована и не запланирована. `pre-ingest/` растёт бесконечно, и
это не замечается только потому, что 30 файлов занимают 0.12 МБ. Признак совпадает с
запрещённым в проекте: пустой рапорт при ненулевом результате здесь невозможен, потому что
результата нет.

### Порядок, который требуется

Проверка «документ уже загружен» обязана быть **первой операцией всего конвейера — до
запуска стадии pre-ingest**, а не внутри пайплайна.

Сейчас порядок обратный, и холостой прогон на неизменившемся документе — это факт
прототипной стадии, а не дефект, который чинится в пайплайне:

```
run_pre_ingest.ps1   ← NER отработал, <документ>_candidates.json создан
POST /documents      → INGEST → try_noop → return
                       файл создан и не прочитан никем
```

Внутри пайплайна отсечка и так первая: `Analyzer.run` (`orchestrator.py:2857`) зовёт
`try_noop` сразу после стадии `INGEST` — первой — и выходит до `CHUNK`. Полезная работа не
теряется, теряется работа стадии pre-ingest и остаётся файл.

**Записано как ограничение прототипной стадии:** pre-ingest на неизменившемся документе
отрабатывает вхолостую. Это принято и не является поводом переделывать пайплайн; устраняется
переносом проверки до стадии.

### Что нужно, чтобы проверка шла до стадии

Реестр `documents` живёт в томе ingestion-api, а у стадии pre-ingest отключена сеть
(`compose.preingest.yaml:46`). Отсюда два пути, и оба имеют цену:

| путь | что требуется | цена |
|---|---|---|
| pre-ingest сам считает `content_hash` и спрашивает реестр | импорт `compute_content_hash` | **импорт уже проверен и работает**: `document.py` тянет только `hashlib`/`json`/`re` и импортируется в образе пре-ингеста. Нужен доступ к реестру или эндпоинт |
| эндпоинт «есть ли такой документ» в ingestion-api | новый контракт API | ломает «пре-ingest работает без сети» |

**Обязательное условие при любом пути:** считать надо `compute_content_hash`, а не `sha256_of`.
Это разные величины — `content_hash` строится из нормализованного канона
(`normalize_text` + JSON с `sort_keys`), `sha256_of` — из сырого текста. Возьми не тот — и
no-op перестанет отсекать на границе, молча и внешне безобидно.

## Что делаем

Форма зафиксирована решением владельца от 2026-10-14 (ADR-053, «Форма производства и место
хранения»); ниже она, а не более ранняя редакция этого документа.

- Кандидаты вычисляются пайплайном перед `EXTRACT` и **после** проверки no-op, из того же
  текста, что уходит в разбор.
- Файл документа и файл его кандидатов лежат в одном каталоге загрузки. `CANDIDATES_DIR` и
  монтирование папки с хоста уходят: кандидаты не пересекают границу контейнеров, и пустая
  папка снаружи больше не может привести к тихой потере.
- Убираются вместе: файл кандидатов **и файл загрузки** — по одним правилам, после успеха и
  при no-op; при отказе остаются. Отказ уборки не меняет статус джобы и объявляется.
- Папка `pre-ingest/` и её **30 файлов из-под git** удаляются.
- `verify_candidates.py` удаляется: входа у него больше нет. Взамен — гард «кандидаты
  получены для текущей версии документа» и гард «каталог не копит».
- Внешний запуск стадии перестаёт быть шагом конвейера и остаётся режим посмотра.
- ADR-053: п. 1, п. 4 и Дополнение 3 отменены. Запись остаётся в силе в части обоснования —
  **почему модель не зовут без списка** (ADR-052, 137 из 274 имён выдуманы), и п. 2–3.

**Сверка `sha256` остаётся** — как защита от подмены файла, а не от рассинхронизации. Пока
файл можно положить руками, равенство обязано проверяться. Снимать её можно только отдельным
решением: заведомо истинная проверка ничего не сторожит — тот же класс, что ADR-049,
Дополнение 4.

## Стоимость, измеренная до решения

Проверялось прямо на образе, потому что возражение «natasha не нужен ingestion-пайплайну»
было записано в `Dockerfile.preingest:2`:

| вопрос | факт | источник |
|---|---|---|
| natasha в основных зависимостях | **да**, `pyproject.toml:22`, в `[project.dependencies]` | не только dev-группа |
| основной образ ставит `--no-dev` | **да**, `Dockerfile:14` | пересобранный `ingestion-api` содержал бы natasha |
| **natasha в текущем образе `ingestion-service`** | **нет**, `ModuleNotFoundError` | образ собран 2026-09-16, natasha добавлена 2026-10-05 (`7da0fa6`) |
| размер модели slovnet+navec | ~40 МБ, CPU | `pyproject.toml:21` |
| наличие `torch` | natasha **тянет torch**, но при `uv sync --no-dev` в образ не ставится | комментарий `pyproject.toml:20` |

**Образ пересобран 2026-10-14:** `natasha` в нём есть вместе с моделью (`natasha OK, модель в
пакете: True`). Прежний образ от 2026-09-16 — тот же класс «образ выглядит рабочим, а код
другой», что описан в §7 этого же ADR-журнала.

**Что не измерено:** сколько стоит NER на CPU при каждой перезагрузке документа. Оценки нет
ни одной. Поля `stage_durations_ms` и `total_duration_ms` в ответе джобы уже отдаются, так
что замер снимается существующими средствами — на живом стенде.

## Проверка

```powershell
# 1. Кандидаты не хранятся
Test-Path .\pre-ingest  # ожидание: False — папки нет вовсе

# 2. Загрузка документа создаёт граф без подготовки
#    загрузить один документ через UI, затем проверить:
docker exec ohw-runtime-neo4j cypher-shell -u neo4j -p $env:NEO4J_PASSWORD --format plain \
  "MATCH (n:ContextNode) RETURN count(*) AS nodes;"
# ожидание: nodes > 0. Раньше здесь был 0 при статусе succeeded.

# 3. Повторная загрузка даёт тот же результат
#    кандидаты детерминированы: тот же текст - тот же список
#    проверка: два прогона на одном документе дают одинаковый отчёт о разборе

# 4. Гейт
pytest, ruff, mypy
```

**Границы применимости.** Замеров стоимости NER на CPU при перезагрузке нет. Измеренного
сокращения места на диске нет — 0.12 МБ. Если решение будет защищаться экономией места,
это защита неверным доводом: правильная причина — снятие ручной синхронизации и класса
тихих отказов.
