## Измерено на стенде 2026-10-14

| сценарий | результат |
|---|---|
| загрузка без запуска стадии | succeeded, 6 `ContextNode`, `uploads/` пуст |
| список получен пайплайном | `natasha+CANDIDATE_PATTERNS`, файл рядом с документом |
| `CANDIDATES_KEEP=1` | оба файла остались, джоба написала `CANDIDATES_KEEP` в отчёт |
| возврат к `CANDIDATES_KEEP=0` | третий документ убран |
| no-op | сигнал `ingest_noop`, 785 мс против 7093 мс |
| `/documents/status` | отвечает, хэш считает сервис |

**Цена NER в памяти — 100,2 МиБ** поверх загруженного сервиса ингеста.

Замер в том же образе и тем же интерпретатором, что и приложение (`/app/.venv`), модуль
сервиса импортирован целиком, затем вызвана ровно та функция, что зовёт пайплайн:

| шаг | RSS | прибавка |
|---|---|---|
| пустой python | 10,3 МиБ | — |
| + весь сервис ингеста (`ingestion_service.app`) | 47,0 МиБ | +37,7 |
| + NER `slovnet` поверх сервиса | 147,3 МиБ | **+100,2** |

Живой контейнер вырос с 56,78 до 249,9 МиБ (+193 МиБ) и **удержал** память после job:
модель кэшируется в процессе и не выгружается. Разница с изолированными 147 МиБ — работа
живого процесса (драйверы Neo4j и эмбеддингов, состояние джобы, данные документа), не NER.

Значение 2,04 ГБ из Docker Desktop — **сумма по всем контейнерам стенда**, а не ингест.
Сопоставлять его с 249,9 МиБ нельзя: это разные величины, в сумму входят веса LLM,
модель эмбеддингов и куча JVM Neo4j. Атрибуция по сервисам требует поднятого полного стенда
и не проводилась.

**Время NER не измерено и измеряться не будет** (решение владельца, 2026-10-14): NER и вызов
модели лежат в одной стадии `EXTRACT`, разделить их по `stage_durations_ms` нечем. Вопрос,
который стоял изначально, снят в пользу измерения памяти.
