> Стадия: корректирующий бандл. Спека и документы правятся до кода, иначе получится
> расхождение в третий раз — два предыдущих закрывались уже после коммита кода.

## 1. Документация и контракты

- [ ] 1.1. `docs/04_services_config.md` §5.0-5.2: зафиксировать, что семь read-time ключей
      retrieval имеют домом Config Service, а значения в Domain Profile — дефолты домена;
      перечислить ключи, которые остаются нечитымими, и почему.
- [ ] 1.2. `docs/01_ontology_and_domain_profile.md`: отметить `retrieval.cypher_template` как
      неисполняемый (подстановка `{node_labels}` из `ontology.node_types` не вызывается) —
      чтобы правка YAML не создавала ложного ощущения управляемости.
- [ ] 1.3. `docs/03_retriever.md` §1: указать фактический приоритет параметров обхода
      Config Service > Domain Profile > дефолт кода.
- [ ] 1.4. `docs/invariants.md`: не добавлять новый инвариант, а дополнить L1-03/L1-04
      указанием, что переключение retrieval-параметров на горячую разрешено и идёт через
      Config Service, а не через профиль.

## 2. Засев Config Service

- [ ] 2.1. Идемпотентный засев `runtime_config` из `namespaces.yaml` при старте: значение
      пишется только если ключа ещё нет, чтобы не затирать правки оператора.
- [ ] 2.2. Тест на повторный старт: после `PUT` через API значения не перетираются засевом.
- [ ] 2.3. Тест на засев: свежая БД после старта содержит `retrieval.max_graph_nodes`.

## 3. Оверлей в query-контуре

- [ ] 3.1. `RuntimeRetrievalOverlay` в `graphrag_proto/retrieval/`: чтение
      `namespace: retrieval` из Config Service, отбор только семи читаемых конвейером ключей
      (`graph_boost`, `expansion_direction`, `expansion_kinds`, `max_depth`, `max_fanout`,
      `max_graph_nodes`, `graph_source_relevance`).
- [ ] 3.2. Слияние: ключ из Config Service перекрывает профиль; отсутствие ключа оставляет
      профиль; отсутствие в обоих оставляет дефолт кода.
- [ ] 3.3. Отказоустойчивость: таймаут, недоступность, невалидный тип или невалидный
      `expansion_kinds` (не список) не ломают запрос — используются значения профиля,
      факт фиксируется в логе и в метрике, а не проглатывается.
- [ ] 3.4. `QueryPipeline` принимает оверлей и подмешивает его в `retrieval` в обеих точках,
      где конвейер читает параметры обхода, плюс `graph_source_relevance` в источниках.
- [ ] 3.5. `graph_search_enabled` не перекрывается оверлеем: тумблер остаётся env > профиль
      (решение о его домене принимается отдельно, оно не следует из правила 5.0 автоматически,
      потому что тумблер определяет режим измерения).
- [ ] 3.6. Политика обновления: оверлей перечитывается при пересборке пайплайна; периодический
      опрос — вне бандла, зафиксировано как открытая задача.

## Открытые вопросы

- Домен `retrieval.graph_search_enabled` (и `retrieval.cosine_threshold`): по правилу §5.0 это
  чтение, то есть Config Service. Но тумблер одновременно определяет режим измерения eval, и
  вынос его в runtime-конфиг делает результаты прогона зависимыми от состояния сервиса. Решение
  не принято; в этом бандле тумблер не трогается (3.5).
- `PROJECTION_CONFIG_FINGERPRINT` включает ли конфиг проекции? После появления оверлея одинаковые
  конфигурации проекции могут иметь разное поведение обхода; нужно решить, входит ли
  `graph_boost`/`max_depth` в fingerprint проекции. В этом бандле не меняется.
