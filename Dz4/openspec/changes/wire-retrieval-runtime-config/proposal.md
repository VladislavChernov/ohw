# Proposal: подключить Config Service к read-time параметрам retrieval

## Почему

Read-time параметры retrieval живут не там, где должны. `docs/04_services_config.md` §5.0
устанавливает правило разделения: **Config Service — поведение на чтение** (меняется на hot,
ответ меняется, хранилище не трогается), **Domain Profile — поведение на запись** (версионируется
вместе с корпусом, требует re-ingest). По этому правилу `graph_boost`, `expansion_direction`,
`expansion_kinds`, `max_depth`, `max_fanout`, `max_graph_nodes` и `graph_source_relevance`
должны жить в Config Service.

Фактически они читаются из `retrieval` секции Domain Profile (`pipeline.py`), то есть смена
гранитного бюджета обхода или отключение boost формально требует re-ingest и версии корпуса.
При этом в `namespaces.yaml` объявлен `namespace: retrieval`, и из кода его читает **только**
`domain.active_profile` — остальное не подключено (`docs/04` §5.2).

Следствия, которые уже видны:

1. Документация вынуждена описывать несостоявшееся разделение. В `docs/04` §5.2 написано, что
   «для параметров чтения домом должен стать Config Service — подключение namespaces к
   `QueryPipeline` не сделано», то есть расхождение зафиксировано, но не закрыто.
2. `ConfigStore.set` при старте не вызывается, поэтому `namespaces.yaml` даже не засевается в
   `runtime_config`: читать из БД нечего, пока оператор не запишет значение через API. Значит
   проводка требует и засева.
3. Оператор не может снять boost или ограничить обход на горячую.

Отдельно: `it.yaml` в `retrieval` содержит `cypher_template` и ссылается на `{node_labels}`,
которые подставляются из `ontology.node_types` — то есть на мёртвый код. Правкой профиля это
не лечится, а раздел `ontology` при выбранном решении просто выпадает из контура чтения.

## Что делаем

1. **Узкий оверлей, а не весь namespace.** В `QueryPipeline` добавляется источник
   `RuntimeRetrievalOverlay`, который подмешивает в `retrieval` только те ключи, которые конвейер
   действительно читает. Ключи вроде `retrieval.cosine_threshold` и
   `retrieval.similar_to_expansion` остаются нечитымими: иначе проводка молча включила бы
   фильтрацию, которой сегодня нет.
2. **Приоритет Config Service > Domain Profile.** Ключ берётся из Config Service, если он там
   присутствует; иначе остаётся значение профиля; иначе кодовый дефолт. Это обратимо: удаление
   ключа возвращает поведение профиля без перезапуска.
3. **Засев `namespaces.yaml` в `runtime_config` при старте** Config Service, идемпотентный:
   запись только если значения ещё нет, чтобы не затирать правки оператора.
4. **Отказоустойчивость — в сторону профиля.** Недоступность Config Service, таймаут или
   невалидный тип не ломают запрос: запрос уходит в vector-only с текущим поведением, а факт
   неудачи виден в метриках и логе, а не молча.
5. **Без горячей перезагрузки в этой итерации.** Оверлей перечитывается при пересборке пайплайна
   (тот же цикл, что и смена топологии). Периодический опрос — отдельная задача бандла, потому
   что он требует согласования с `topology_service` и своей метрики.
6. `docs/04_services_config.md` §5.2 и §5.0, `docs/invariants.md` (раздел про покрытие
   read-time ключей) и `docs/03_retriever.md` §1 приводятся к фактическому состоянию после
   реализации; `docs/01_ontology_and_domain_profile.md` фиксирует, что `retrieval.cypher_template`
   не исполняется.

## Спека

Затрагивается контракт read-time конфигурации. Требования, которые меняются по существу:

- **`domain.active_profile` остаётся единственным ключом `namespace: domain`, читаемым сейчас.**
  Расширяется перечень читаемых namespace'ов до `retrieval`, но только для семи перечисленных
  ключей. Ключ `retrieval.graph_boost` и равенство нулю: при `0.0` блок boost пропускается
  целиком, и это остаётся штатным поведением, а не дефектом.
- **Правило разделения не ослабляется.** Домен этих семи ключей — Config Service. В профиле
  они остаются как дефолты домена и как документация, но не являются источником истины;
  приоритет у Config Service. Это прямо следует `docs/04` §5.0, а не отменяет его.
- **Поведение при отсутствии Config Service не меняется.** Запрос работает как сейчас, то есть
  на значениях профиля. Это требование обратной совместимости, а не деталь реализации.
- **Не меняется:** `retrieval.cosine_threshold`, `retrieval.similar_to_expansion`,
  `retrieval.context_size`, `retrieval.max_vector_chunks`, `retrieval.reranker_enabled` — они
  не читаются и в этой итерации не читаются.

Не входит в бандл: `cypher_template` из профиля, `ontology.node_types`/`edge_types`/`unique_key`
(мёртвые ключи, `docs/01` §1.1), реализация порогов дедупликации (`L3-02a`).

## Проверка

1. `uv run pytest -q -p no:cacheprovider tests/`, `uv run ruff check src tests`,
   `uv run mypy src` в dev-контейнере с host `RUN_CODE_COMMIT`.
2. Регрессии в `tests/test_retrieval_pipeline.py`:
   - ключ из Config Service перекрывает значение профиля;
   - отсутствие ключа оставляет значение профиля;
   - недоступность Config Service не ломает запрос и даёт прежний результат;
   - невалидный тип значения (например, `max_depth: "abc"`) не ломает запрос.
3. Интеграционная проверка на стенде: `PUT /api/v1/config/retrieval {"graph_boost": 0.5}`
   меняет `graph_boost` в трассировке ответа; удаление ключа возвращает значение профиля;
   `GET /health` Config Service показывает засеянные значения.
4. Отдельный ручной контроль: `retrieval.cosine_threshold`, засеянный в Config Service, **не**
   влияет на retrieval — иначе оверлей шире своей задачи.
