# Архитектура ингеста для мультидоменной графовой БД (Legal, IT, HR)

Проектирование процесса загрузки и обработки данных (Ingestion Pipeline) для мультидоменной графовой базы данных требует создания гибкого конвейера. Главная задача — извлекать специфичные для каждого домена сущности, связывая их через сквозные узлы в единую корпоративную сеть.

---

## 1. Архитектура конвейера ингеста (3 этапа)

Процесс устроен как последовательный трехэтапный пайплайн обработки сырых данных:

```
[ Сырые данные ] (Письма, PDF, Логи, Jira, 1С)
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ ЭТАП 1. Приемник и Очистка (Ingestion & Normalization) │
│ • Хранение: S3 / MinIO / Kafka / Airflow               │
│ • Парсинг: Извлечение текста (OCR для сканов), дат     │
└────────────────────────────────────────────────────────┘
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ ЭТАП 2. Мультидоменный AI-семантический слой (LLM/NER) │
│ • Маршрутизация: Определение домена (HR / IT / Legal)  │
│ • Экстракция: Извлечение узлов и связей по паспорту    │
└────────────────────────────────────────────────────────┘
       │
       ▼
┌────────────────────────────────────────────────────────┐
│ ЭТАП 3. Графовый маппинг и Склеивание (Entity Resolution)│
│ • Логика: Проверка дубликатов по ID и эмбеддингам      │
│ • Запись: Транзакции MERGE в графовую БД (Neo4j)       │
└────────────────────────────────────────────────────────┘
```

---

## 2. Детальный разбор этапов конвейера

### Этап 1: Приемник данных и нормализация
Входящий поток состоит из разнородных источников:
* **Legal (Юристы):** Сканы договоров (PDF), претензии, исковые заявления, расшифровки встреч (TXT/DOCX).
* **IT (Служба поддержки):** Тикеты из Jira/Service Desk, системные логи, отчеты об инцидентах.
* **HR (Кадры):** Резюме кандидатов, приказы о приеме/увольнении, карточки сотрудников из 1С/BambooHR.

**Функция этапа:** Скрипт принимает документ, сохраняет оригинал в S3-хранилище, извлекает метаданные (источник, дата загрузки, автор) и конвертирует контент в чистый текст (используя OCR-библиотеки вроде Tesseract или специализированные парсеры документов).

### Этап 2: AI-семантический слой и Доменные паспорта
Для обработки текста используется LLM-оркестратор (например, на базе LangChain/LlamaIndex):
1. **Маршрутизатор (Router):** Анализирует текст и классифицирует его тип (например, "Трудовой договор" -> HR/Legal, "Отчет о сбое сервера почты" -> IT).
2. **Экстракция по Паспорту Домена (Domain NER):** Чтобы ИИ извлекал данные строго по схеме, ему передаются жесткие паспорта сущностей (Structured Outputs через JSON Schema):
   * **Паспорт [HR]:** Искать сущности `[Сотрудник]`, `[Должность]`, `[Департамент]`, `[Навык]`, `[Приказ]`.
   * **Паспорт [IT]:** Искать сущности `[Сервер]`, `[Микросервис]`, `[Инцидент]`, `[База данных]`, `[Уязвимость]`.
   * **Паспорт [Legal]:** Искать сущности `[Судебное дело]`, `[Контрагент]`, `[Договор]`, `[Пункт соглашения]`, `[Закон]`.

*Результат этапа:* Стандартизированный JSON, содержащий массивы найденных узлов (`nodes`) и направленных ребер (`edges`).

### Этап 3: Графовый маппинг и Разрешение сущностей (Entity Resolution)
Прямая запись без проверок превратит граф в несвязный набор дубликатов. Этап склеивания решает эту проблему:
1. **Жесткие детерминированные ключи:** Сотрудники склеиваются по Email, СНИЛС или корпоративному ID. Компании — по ИНН/БИК.
2. **Вероятностное семантическое склеивание (Векторный поиск):** Текстовые названия (например, компания «Ромашка» и ООО «ТД Ромашка») переводятся в векторные эмбеддинги. Если косинусное сходство выше порогового (например, 0.92), система предлагает объединить узлы или связывает их отношением `[:SAME_AS]`.

## 3. Схема сквозного пересечения доменов в графе

Смысл мультидоменной базы заключается в сквозных узлах, которые объединяют изолированные департаменты в общую сеть. Главными сквозными хабами выступают узлы `(:Person)` (Сотрудник/Участник) и `(:Organization)` (Контрагент/Клиент).

```
   [ IT ДОМЕН ]                       [ СКВОЗНОЙ УЗЕЛ ]                  [ LEGAL ДОМЕН ]
 
(Сервер: Exchange)                           ┌───────────────┐                  (Договор: №44-ФЗ)
         │                                   │               │                          │
    [:CRASHED_BY]                            │               │                    [:SIGNED_BY]
         ▼                                   ▼               ▼                          ▼
 (Инцидент: #991) ───[:ASSIGNED_TO]───> (Сотрудник: Иван) <───[:RESPONSIBLE]─── (Дело: Суд по утечке)
                                             ▲
                                             │
                                       [:EMPLOYED_BY]
                                             │
                                     (Департамент: IT)
                                      [ HR ДОМЕН ]
```

### Практическая ценность сквозных связей:
* **Расследование инцидентов:** При падении сервиса (IT) можно мгновенно увидеть, какой разработчик за него отвечал (HR), и какие юридические обязательства/штрафы по SLA прописаны в договоре с клиентом (Legal), если сервис лежит дольше часа.
* **Безопасность (Offboarding):** При увольнении сотрудника (HR) система строит граф его доступов к критической инфраструктуре (IT) и выводит список контролируемых им судебных дел или активных договоров (Legal), которые необходимо переназначить.

## 4. Как автоматизировать прототип через Cline

1. **Генерация схемы:** Написать Python-скрипт с использованием Pydantic-моделей для задания строгой структуры JSON, которую ИИ должен возвращать после анализа документов.
2. **Настройка промптов:** Написать системный промпт, обучающий модель преобразовывать текст в Cypher-запросы (коллекции инструкций `MERGE`).
3. **Пайплайн записи:** Использовать официальный драйвер `neo4j` для выполнения пакетных транзакций в графовую СУБД.
