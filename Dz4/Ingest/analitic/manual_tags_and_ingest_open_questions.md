## 1. Введение

### 1.1 Контекст

Повод — подготовка к первому полному eval-прогону. Стенд встал, но ingest не укладывается в
разумное время: LLM-экстракция вызывается на каждый чанк и генерирует тысячи токенов JSON.

**Стоимость одной экстракции НЕ установлена.** Первая оценка («95 с на чанк, ≈5.6 ч на корпус»)
оказалась неверной и снята: она делила общее число токенов задачи на скорость генерации, хотя
`n_tokens` в логе llama.cpp — это промпт **плюс** генерация. В том же логе присутствуют две
записи, дающие несопоставимые величины:

| Наблюдение | Значение | Комментарий |
|---|---|---|
| `stop processing: n_tokens = 5314` | 5314 — всего | prompt + gen, не чистая генерация |
| `release: ... 7650 prompt + 102 gen = 7752` | 102 токена генерации | при `total` 7.2 с |
| `print_timing` по задаче 2687 | `n_gen` 658 → 2729 за ~36 с | ~57 ток/с генерации |

То есть по одним этим строкам стоимость чанка не выводится: разброс от 7 с до десятков секунд
наблюдается в пределах одного прогона. Число «5.6 часа» не имеет артефакта и **не должно
использоваться для планирования** до прямого замера. Прямой замер: `--limit-docs 3` без
`--retrieval-only`, с сохранением `llm.log` и `--trace`.

Прочая измеренная на прогоне 2026-09-26 фактура (контур `ohw-eval-s2`, RTX 2070 SUPER, 8 ГБ
VRAM):

| Величина | Значение | Как получено |
|---|---|---|
| записано за ~12 мин | 1 Source, 4 Chunk, **307 ContextNode** | опрос Neo4j |
| корпус | 33 `.md`, 0.5 МБ | измерено |
| RAM/VRAM на старте | 12.22 ГБ из 15.91 ГБ; 5729 МБ из 8192 МБ | `resources.json` |

> **Оговорка о методе.** Число чанков тоже не измерено: чанкер `sliding_window(512, 64)` на
> 0.5 МБ кириллицы даёт ориентировочно 100–210 чанков, то есть разброс вдвое. Любая оценка
> полного времени ingest до прямого замера — гипотеза.

307 ContextNode на 4 чанка — это ~77 сущностей на чанк. Это не только дорого, это ещё и
качество: граф наполняется длинным хвостом, который разбавляет всё, что мы собираемся измерять.

### 1.2 Источники

## 3. Анализ текущего состояния

### 3.1 Ручной ввод — это реализовано, а не план

`POST /api/v1/ingestion/documents` принимает `tags` и `links` и валидирует их типы:

```text
app.py:166  tags: list[dict[str, Any]] | None = None,
app.py:167  links: list[dict[str, Any]] | None = None,
app.py:274  if not isinstance(tags, list) or not isinstance(links, list) or not isinstance(metadata, dict):
```

Дальше ручные теги становятся полноценными сущностями, а ручные связи — рёбрами с
`origin="user"`, и на запись идут **вместе** с извлечёнными моделью:

```text
orchestrator.py:1106        record.setdefault("origin", "user")
orchestrator.py:1114        relation.setdefault("origin", "user")
orchestrator.py:1312        entities = [*ctx.entities, *ctx.tags]
```

То есть существование ручной разметки не блокирует LLM и наоборот: это два источника одной
структуры.

### 3.2 Слияние с накопленным графом — тоже реализовано

Сценарий «шаблон + база» работает на двух уровнях.

**Уровень 1 — разрешение идентичности при загрузке.** Если тег приходит без `tag_id`, но с
`canonical_name`, код ищет его среди уже известных алиасов:

```text
orchestrator.py:1096        if not tag_id and canonical:
orchestrator.py:1097            candidates = alias_ids.get(_identity_key(canonical), set())
orchestrator.py:1098            tag_id = next(iter(candidates)) if len(candidates) == 1 else _context_node_id(domain, tag)
```

Ровно один кандидат — переиспользуется существующий узел; несколько — создаётся новый узел, а не
выбирается один из вариантов. Это и есть инвариант `L2-02`, и он здесь соблюдён.

**Уровень 2 — слияние при записи.** `upsert_edges` не перезаписывает ребро, а объединяет
свойства, причём ручная связь не перетирается модельной:

```text
inmemory.py:143-149         preserve_manual = existing.origin == "user" and incoming.origin != "user"
inmemory.py:150-151         source_ids/aliases: union через dict.fromkeys
```

При перезагрузке корпуса связи не удаляются, а теряют provenance документа:

```text
inmemory.py:118-136         source_ids и chunk_ids вычитаются для инцидентных узлов и рёбер
```

Это же означает ограничение: связь, извлечённая прежней версией документа и не восстановленная
новой, остаётся в графе уже без provenance этого документа. Для измерения вклада графа это
значимо — такую связь видно в обходе, но её источник атрибутировать нечем.

### 3.3 Роль LLM в ингесте — ровно одна

Весь оркестратор вызывает `llm.generate` **один раз**:

```text
orchestrator.py:474        raw = "".join(llm.generate(prompt, system=str(template["system"]), stream=False))
```

Это `ExtractStage`. Normalize, Dedup, Contract, Validate, Commit LLM не касаются. Модель отвечает
на один вопрос: «что в этом куске текста упомянуто и как связано».

Ворота включения — env `EXTRACT_LLM` плюс профильный `extraction.llm_enabled`:

```text
orchestrator.py:52          return os.environ.get("EXTRACT_LLM", "").strip().lower() in {"1","true","yes","on"}
orchestrator.py:425-447     четыре ветки отката к детерминированной экстракции
```

Детерминированная ветка — ключевой факт для нашего замера:

```text
orchestrator.py:428        self._extract_deterministic(ctx)
```

Она создаёт `ContextNode` из каждого слова длиннее пяти букв и **не создаёт ни одной связи между
контекстными узлами**. Значит при `EXTRACT_LLM=false` графовая ось теряет единственное, ради чего
измеряется: идти по нему некуда.

### 3.4 Ответ LLM не может быть обрезан без последствий

```text
orchestrator.py:117-121    json.JSONDecodeError -> TypeError("EXTRACT LLM вернул невалидный JSON")
```

Толерантного разбора и повтора с укороченным промптом нет. Значит снижение `LLM_MAX_TOKENS` ниже
того, что нужно модели, превращает «долго» в «сломано»: джоба упадёт на обрезанном JSON.
Рабочий рычаг — ограничить число сущностей в промпте, чтобы модель укладывалась в предел сама.

### 3.5 Найденная опасность: модель может подменить идентичность

`tag_id` принимается в объекте сущности от LLM, а идентификатор узла строится так:

```text
orchestrator.py:269-275    raw = entity.get("tag_id") or entity.get("node_id")
                           ... return f"tag:{domain}:{_identity_key(canonical)}"   # если raw пуст
```

То есть непустой `tag_id` от модели становится идентификатором узла дословно. Галлюцинированный
`tag_id` не приведёт к ошибке — он молча создаст **отдельную ноду** вместо слияния по canonical
key. Для измерения это тихая порча графа. В ответе LLM `tag_id` быть не должно; для ручных тегов
он остаётся, потому что там его задаёт человек.

### 3.6 Eval-раннер ручную разметку не передаёт

```text
run_eval.py:283-288        body = {source_url, domain, doc_type, content}
```

Ни `tags`, ни `links` в тело запроса не входят. Поэтому сейчас у раннера ровно один способ
получить граф — LLM-экстракция. Механизм в API есть, но из eval-контура недоступен.

### 3.7 Деградация экстракции не видна нигде

`ExtractStage` при ошибке не пробрасывает исключение, а деградирует:

```text
orchestrator.py:442-447    except Exception: ctx.entities = []; ctx.entity_edges = []
                            ctx.enrichment_degraded = True; self._extract_deterministic(ctx)
```

Флаг `enrichment_degraded` выставляется на объекте контекста и больше **нигде не читается**:
проверено рекурсивным поиском по `prototype/src` — три вхождения, все в `orchestrator.py`
(объявление и две установки). Он не попадает ни в ответ джобы, ни в отчёт прогона:

```text
run_eval.py:378-391        documents.append({source_url, relpath, bytes, job_id, status,
                                              last_stage, noop, error, wall_time_s, seconds_per_kb})
```

`enrichment_degraded` в этом списке нет. Следствие: чанк, который тихо потерял LLM-экстракцию,
не виден ни в одном артефакте — прогон выглядит здоровым, а граф собран частично. Для измерения
это хуже явной ошибки, потому что частичный граф неотличим от полного, а `graph_required`-срез
начинает измерять пустоту. Именно этим эффектом объясняется, почему ось молча ничего не давала
после починки обхода.

Отдельно: это означает, что «повтор при невалидном ответе» — не первая проблема. Первая —
видимость. Пока деградация не попадает в артефакты, повтор нельзя даже измерить: неизвестно,
сколько раз он понадобился бы.

### 3.8 Повтор при невалидном ответе LLM — не наблюдавшийся отказ

Ни одного фактического случая «LLM ответил невалидно» на прогонах не зафиксировано: вскрывшиеся
проблемы — время и калибровка дедлайна, а не разбор ответа. Повтор проектировался бы вслепую.

Если отказ всё же наблюдается, измеренные свойства стенда задают ограничения:

- `LLM_TEMPERATURE: "0"` на eval-стенде, поэтому повтор с **идентичным** промптом
  детерминирован и воспроизведёт ту же битую выдачу. Повтор имеет смысл только если промпт
  меняется — например, в следующую попытку добавляется текст ошибки валидации;
- обрезанный по `max_tokens` JSON повтором того же промпта не лечится вовсе;
- `relationships: []` — валидный ответ («связей в тексте нет»), повторять его нельзя;
- бюджет попыток по правилу `docs/04_services_config.md` §5.0 относится к поведению записи,
  значит его дом — профиль (`extraction.max_attempts`), а не env и не Config Service.

Порядок слоёв по стоимости: толерантный разбор (срезать markdown-fence и прозу, взять внешний
сбалансированный объект) → повтор с исправляющей подсказкой в пределах бюджета → явная деградация
с пометкой «граф непригоден для измерения», а не «готов, но пуст».

### 3.9 Слоты ingest и дедлайн раннера

Ingestion API держит два слота и отвечает `429`, раннер это обрабатывает корректно — повторяет
до исчерпания бюджета слота:

```text
run_eval.py (ingest_corpus)  while True: ... "429" -> ждём слот до slot_timeout_s,
                              общий потолок фазы — submit_budget_s
```

Падение первого прогона было не ошибкой логики: истёк общий дедлайн 300 с на слот, потому что
документ с LLM-экстракцией занимает минуты. Калибровка не соответствовала сценарию.
**Закрыто 2026-09-27 (B3):** дедлайн разделён на окно слота, окно недоступности стенда, окно
неподвижной джобы, жёсткий кап пачки и отдельный бюджет фазы подачи; условия взаимоисключающие,
поэтому соотношение констант ничего не решает. Фактические пороги пишутся в
`run_manifest.timeouts`.

### 3.10 Строгость вердикта при потере LLM-слоя — ОТКРЫТО

Смещение из-за пропавших фактов одностороннее: их нельзя ни найти, ни вспомнить, поэтому
`recall_graph`, `necessity`, `delta_recall` и `coverage` занижены гарантированно и на
неизвестную величину. С 2026-09-27 прогон с потерей слоя получает `verdict = "invalid"`
(`run_eval.build_ingest_quality` → `metrics.build_lift_report`), причина названа в
`verdict_reasons`, проверяются обе стороны пары.

**Сейчас для прототипа это приемлемо, и вопрос сохранён как открытый, а не решённый молча.**

Варианты, которые ещё не выбраны:

1. **Как сейчас.** Любая потеря → `invalid`. Консервативно и согласуется с уже действующим
   правилом для `degraded_questions`. Цена: на корпусе в 200 документов один нестабильный
   документ обнуляет прогон.
2. **Порог по числу записей**, а не по числу документов. Пять потерянных записей и пять тысяч
   на одном и том же корпусе — разные события, а «потерян один документ» их не различает.
   Возражение: порог — настраиваемое значение, и его подберут под желаемый результат. Тот же
   класс, что «бюджет под корпус», который убрали в B3.
3. **Severity вместо булева флага:** всегда `invalid`, но в причине уже есть и документы, и
   записи, и сторона пары — то есть фактически сделано, и остаётся решить, достаточно ли
   этого для автоматики или нужен отдельный порог.

Не решён также смежный вопрос: **деградация без потери слоя** (`cause=profile_unavailable` или
`profile_invalid`) вердикт **не** инвалидирует — терять нечего, векторная ось цела. Для оси
графа это спорно: факты-то всё равно не извлечены, и недооценка такая же. Решение отложено
вместе с этим пунктом.

### 3.11 Валидация профиля на стороне потребителя — сделано частично, вопрос открыт

Разбор контракта профиля (2026-09-27) показал: `config_service.domain.validate_profile`
проверяет только форму профиля (секции-маппинги, `node_types` — список, структура
глоссария) и вызывается **только** на пути Config Service. Ingest грузит профиль из
локального YAML в обход Config Service и не проверяет ничего, кроме «это mapping».

Поэтому контракт экстракции (`extraction.llm_enabled`, `extraction.prompt_template`) добавлен
на стороне потребителя: `ingestion_service/pipeline/profile_contract.py`, вызов в
`_load_profile` (единственная общая точка трёх стадий, срабатывает раз на джобу).
Уровни: **обязательное отсутствует — ошибка** (ERROR в лог один раз на набор проблем плюс
`cause=profile_invalid` в счётчиках), **необязательное отсутствует или ключ не читается —
предупреждение** (WARNING один раз, в счётчики не идёт). Исклюшение бросать нельзя:
ADR-031 §2 требует, чтобы optional enrichment не блокировал сохранение документа.

**Открытым остаётся:**

1. **Тихая деградация vs намерение.** `llm_enabled: false` при неполном шаблоне и
   «`llm_enabled` не задан + шаблон неполный» — это разные вещи, но обе приводят к
   детерминированному пути. Сейчас первое не ошибка (домен выключен намеренно, шаблон
   хранится про запас), второе — ошибка. Граница проведена по признаку «выражено ли
   намерение», и это решение владельца, а не вывод из кода.
2. **Retrieval грузит профиль второй, независимой точкой** (`retrieval/pipeline.py`). Разбор
   вынесен в `Retrieval/analitic/retrieval_config_and_open_questions.md`, потому что это
   другой модуль, и цена ошибки другая: потеря слоя ингеста необратима, а ошибка настроек
   запроса меняет ответ, но данные целы. **Поправка формулировки (2026-09-27):** раньше здесь
   было написано, что при `strict_profile=False` пустой профиль получается «молча» — это
   верно только частично. Граф при этом НЕ выключается: `graph_search_enabled` читает
   `RETRIEVAL_GRAPH_ENABLED` первым, а env в compose задан (`compose.yaml:366`, дефолт
   `true`). Что происходит на самом деле — тихий откат всех параметров расширения на кодовые
   дефолты при полностью рабочем графе, и без единого флага. Это хуже выключенного графа:
   выключенный граф хотя бы виден в `projection_status`.
3. **`extraction.temperature` и `extraction.max_tokens` в профилях не читаются ingest** —
   в профиле лежит `0.1`/`4096`, в запрос уходит `0.3`/`2048` из env и дефолтов сборки
   адаптера. Профиль обещает влияние, которого нет. Стоит ли чинить чтением из профиля или
   удалять ключи — открытый вопрос бандла `tidy-domain-profile-keys` (задача 4.1).
4. **Инертные ключи онтологии** (`unique_key`, `properties`, `edge_types`,
   `chunk_entity_edge`): объявлены в профиле как контракт, не применяются. `unique_key`
   читается только в `ensure_schema`, который ingest не вызывает никогда. Сейчас
   предупреждаются валидатором; удалять из профилей или применять — решение.

### 3.12 Приоритет слоёв при записи ноды — ПРИОРИТЕТНЫЙ ВОПРОС

Разбор 2026-09-27. Слияние происходит **в момент записи** (`_upsert_nodes`,
`retrieval/adapters/neo4j.py`), а не в пайплайне: `DedupStage` (стадия 6) видит только записи
одного документа. Одна нода может быть в метаданных многих документов — это штатный случай,
а не конфликт. Полная таблица правил и что из неё закреплено тестом — `docs/02`
§4.1–4.2.

**Как в прототипе сейчас:**

| группа полей | правило |
|---|---|
| provenance (`sources`, `source_ids`, `chunk_ids`) | объединение |
| `origin = 'user'` | не перезаписывается машинной записью |
| вложенный `properties` при `user` | сохраняется |
| остальные скалярные | **последний записавший** |

Внутри одного документа действуют две **противоположные** политики: `canonical`,
`canonical_name`, `name`, `origin`, `confidence` — последняя запись при `_origin_rank >=
current_rank`; `id`, `description`, `category` — заполняются, только если ещё не заполнены
(первый). То есть в одном файле имя ноды приходит из последнего извлечения, а `description` —
из первого, и повторная загрузка того же хэша это не исправляет (no-op).

**Что объявлено как решение.** Для прототипа принято правило «побеждает более новая ревизия
документа». Проверено по коду: оно выполняется уже по построению — ревизия получает бóльший
`version` (`latest_active` сортирует по `version DESC`) и записывается позже. Корпусной
`data_revision` для этого непригоден: это `sha256` от `(source_url, content_hash)` (ADR-026),
отпечаток без порядка. В документации правило зафиксировано как решение, но **реализовывать
нечего** — менять поведение не требуется, и «сделать» его было бы изменением ради изменения.

**Что на самом деле не определено — междодокументный случай.** Два разных документа дают
одну ноду, а версии у них независимы, поэтому «более новая ревизия документа» их не
различает. Сейчас побеждает последний обработанный, и **содержимое ноды зависит от порядка
загрузки корпуса**: тот же корпус, обработанный в обратном порядке, даст другие `description`
при том же наборе документов.

Варианты для проработки (ни один не выбран):

1. **Порядок не влияет.** Побеждает первый, а не последний. Дёшево, но тогда более новая и
   более точная формулировка никогда не заменит худшую.
2. **Детерминированный порядок, не зависящий от загрузки** (например, по `source_url`).
   Результат воспроизводим, но «лучше» не значит «новее» — качество страдает.
3. **Поле хранит владельца** (`source_url` + `version` последней записи) и перезаписывается
   по сравнению. Воспроизводимо и отдаёт новизну; требует нового поля на ноде и сравнения в
   запросе — оценка «средняя», не «дорого».
4. **Очередь конфликтов** (§3.14): значение не выбирается молча, а попадает пользователю.
   Совместимо с любым из 1–3 и снимает вопрос «кто прав» с системы.

**Побочная находка, которая делает вопрос срочнее.** Смена конфигурации не переобрабатывает
корпус: принудительной пересборки нет ни в раннере, ни в API (`docs/02` §1.3), а неизменённые
документы становятся no-op. То есть «починил промпт и перепрогнал тот же корпус» не работает,
и каждый следующий замер извлечения требует перезагрузки корпуса заново. Пока это так, номер
ревизии ноды влияет на то, какой результат вообще можно получить.

### 3.13 Принято в прототипе как есть — практика плохая, подлежит переработке

Сводка трёх пунктов, которые **приняты осознанно** и требуют переработки до промышленного
ингеста. Решение владельца от 2026-09-27: прототип и первые замеры важнее чистоты правил;
менять поведение без продуктового решения значит закрепить случайность. Ни один пункт не
является целевым поведением. В документации зафиксировано с той же оговоркой — `docs/02`
§4.1 (область действия) и §4.2 (таблица «почему плохо»).

| # | что принято | почему это плохо | что нужно переработать | приоритет |
|---|---|---|---|---|
| 1 | междодокументный приоритет скалярных — **последний обработанный** | содержимое общей ноды зависит от порядка загрузки корпуса; тот же корпус в обратном порядке даст другие `description` | выбрать правило: порядок не влияет / детерминированный порядок / нода хранит владельца / очередь конфликтов (разбор в §3.12) | высокий |
| 2 | `description` перезаписывается при ревизии документа | ревизия старого документа затирает описание, данное более новым; `provenance` хранит список источников, а не «кто написал это поле», поэтому прежний владелец теряется; повторная загрузка того же хэша — no-op, то есть исправить значение, не изменив файл, невозможно | хранить владельца поля (`source_url` + `version`) либо отдавать конфликт пользователю (§3.13) | средний |
| 3 | `origin = 'system'` не защищён при записи | один и тот же узел трактуется двумя разными правилами: внутри документа `system` (ранг 2) переживает `ai` (ранг 1), при записи защищён только `user` | свести `_origin_rank` и условие в Cypher к одному правилу; пока исход может быть и правильным, что делает расхождение неочевидным при разборе | средний |

**Пункт 3 подробно, потому что он наименее очевиден.** `origin: "system"` ставит
детерминированный fallback, то есть им наполняются домены с `llm_enabled: false` (`cinema`,
`library`) — синтетические слова ≥5 символов с `tag_id` вида `tag:<domain>:<слово>`. Путь
до расхождения проходит через отключение no-op ручными тегами (`docs/02` §1.2): пользователь
ставит тег → смена `llm_enabled` на `true` перестаёт быть no-op'ом → та же методичка
пересобирается и пишет `origin = "ai"` → `system`-нода перезаписывается, её `origin`
становится `ai`. Без ручных тегов путь закрыт. Расхождение закреплено тестом
`tests/test_node_merge_rules.py::test_system_node_is_not_protected_at_write_time`, и тест
фиксирует **фактическое** поведение: менять его нужно вместе с решением, а не правкой
теста.

**Что из этого следует для замеров.** Все три пункта влияют на интерпретируемость графа, и
ни один не влияет на то, переживут ли данные. Пока они в силе, сравнение двух прогонов,
различающихся составом корпуса, рискует сравнивать не разницу систем, а разницу порядка
загрузки. Отдельно: смена конфигурации не переобрабатывает корпус (`docs/02` §1.3), поэтому
«починил промпт и перепрогнал тот же корпус» не работает, и каждый новый замер извлечения
требует перезагрузки корпуса.

### 3.14 Конфликты при записи — уходят пользователю или теряются

Ручные аннотации отключают no-op намеренно (`docs/02` §1.2): пользователь, расставивший теги,
явно просит полную обработку. Оговорка: **конфликты при записи уходят ему на рассмотрение**.

Механизма в проекте нет. Сегодня есть только два молчаливых guard'а: нода `origin = 'user'`
не перезаписывается машинной записью, и счётчик `model_tag_ids_ignored` (к конфликтам значений
отношения не имеет). Поэтому оговорка записана как ожидание, и это обещание, которое пока не
выполняется.

### 3.14.1 Что нашли в практике: конфликт как запись, а не как исключение

Источник: **dbt, «Add data tests to your DAG»**, <https://docs.getdbt.com/docs/build/data-tests>
(прочитан 2026-09-27). Это документация по data tests, а не по слиянию записей, поэтому
переносится **структура решения**, а не буквальный механизм: dbt ничего не решает про значения,
он их показывает. Ровно это нам и нужно от «отдать конфликт пользователю».

| в dbt | как устроено | что из этого следует для нас |
|---|---|---|
| проверка возвращает записи, а не бросает | singular test — это SQL, возвращающий непрошедшие строки; generic test — параметризованный вид того же; «если запрос вернул ноль непрошедших строк, проверка проходит» | конфликт значений должен порождать **запись**, а не исключение: из-за конфликта на общей ноде пайплайн падать не должен, документ сохраняется |
| результаты сохраняются в отдельную таблицу | `--store-failures` / `store_failures`: «dbt сначала сохранит результаты в таблицу, а затем посчитает по ней число непрошедших»; схема по умолчанию `dbt_test__audit`; «allows you to query and examine failing records much more quickly» | очередь конфликтов — **отдельная таблица**, а не поле в тексте сообщения: текст нельзя запросить, а очередь можно |
| громкость решает владелец | `severity`, плюс `error_if` / `warn_if` с порогом | «ошибка это или предупреждение» — конфигурация проверки, а не решение кода; для нас это отвечает на вопрос, должен ли конфликт инвалидировать вердикт |
| непрошедшая запись несёт контекст | встроенные тесты возвращают только значение; «чтобы добавить контекст к каждой строке, напишите свой тест, который захватит и `customer_id`» | наша запись конфликта обязана содержать **поле, оба значения, оба источника и версии** — иначе её нечем разбирать, и очередь превращается в шум |
| результаты заменяют предыдущие для того же теста | «A test's results will always replace previous failures for the same test» | очередь без дублей: одна запись на пару (нода, поле), а не по записи на каждую попытку. Иначе повторный прогон забивает очередь тысячами одинаковых строк |
| проверки идут и в разработке, и в production | «Whenever you are writing new code… and whenever you run your transformations in production» | проверка конфликтов должна быть частью обычного прогона, а не отдельной процедурой «проверить конфликты перед релизом» |

**Что это даёт и чего не даёт.** Даёт форму: поверх расчёта, отдельно от его результата,
сохраняется очередь; громкость настраивается; решение принимает человек. Не даёт ответа на
§3.12 — «чьё значение победит». dbt этого вопроса не решает by design, и это же делает очередь
совместимой со всеми четырьмя вариантами из §3.12: она не спорит с правилом приоритета, а
убирает молчание. Практически это значит, что можно сначала поставить очередь (дёшево, данные
начинают копиться), а правило приоритета выбрать позже, уже посмотрев, что там реально
конфликтует. Для прототипа это, вероятно, самый выгодный порядок: сейчас мы не знаем частоты
конфликтов, а очередь её измеряет.

**Что не нашлось и почему — важно не перепутать с «такой практики нет».** Не найдена вторая
половина вопроса: «ручная правка как сигнал на переобработку». Две попытки: страница Salesforce
про duplicate rules вернула пустое содержимое, документация dbt про snapshots переехала и по
старому адресу отдаёт 404.

Причина глубже этих двух кодов: **в этой сессии поиск был недоступен** — поисковый провайдер
отдавал 403 на каждый запрос, и оставался только прямой запрос по URL, то есть по тем
адресам, которые я могу назвать заранее. Пространство поиска было «что я могу вспомнить»,
а не «вся документация мира». Поэтому корректный вывод — **«не найдено при ограниченной
возможности искать»**, а не «механизма не существует»: отсутствие находки ничего не
доказывает, пока искать было нечем.

Чтобы закрыть пункт, нужен работающий поиск (например, по «manual override invalidates
derived data», «curated layer re-derivation») либо разговор с тем, кто это внедрял. Пока
остаётся аналог внутри проекта — курируемый слой и «merge proposal» вместо автоматического
слияния (`docs/glossary.md`); это наше решение, а не заимствованная практика, и выдавать
одно за другое нельзя.

### 3.15 Устаревшие рёбра: решение принято, код написан будет в офлайновой джобе

**Поправка от 2026-09-28 (третья корректирующая запись ADR-014).** Прежняя запись здесь
требовала «не удалять при re-ingest и фильтровать на чтении». Это было отменено: требование
уточнено — прототипу нужна **только актуальная информация**, поэтому осиротевшие рёбра
удаляются. Ниже итог, а не прежний список долгов.

**Действующее правило:** ребро удаляется, когда не осталось ни одного поддерживающего
`chunk_id`; ребро, поддержанное другим активным документом, обязано выжить. Стирание
ссылки на умерший чанк при ingest уже происходит, признак вычислим.

**Что из прежнего списка закрыто и почему:**

1. **Гипотеза раздувания — снята.** Рёбра не накапливаются, измерять нечего. Взамен нужен
   счётчик удалённого в `job_signals`, иначе результат уборки нечем подтвердить.
2. **Дыра в каскадном удалении персональных данных — закрыта по построению.** Раньше
   материал старой версии был недостижим для удаления (`soft_delete` берёт только
   `latest_active`, а `source_url` у выживших рёбер уже снят). Теперь его не остаётся.
3. **Мусорные сущности без активных источников — закрываются тем же правилом.**
4. **Признак происхождения, который мы искали как отдельное решение, не понадобился.**
   Проблема была в необходимости достать выживший материал; при удалении выжившего
   материала нет.
5. **Многоисточниковые связи — не проблема, а правило.** Именно они требовали формулировки
   «нет ни одного поддерживающего», а не «нет одного источника».

**Правила реализации приняты до кода (2026-09-28), `docs/02` §4.5 и ADR-014 п. 16–19:**

1. **Канонический признак жизни — непустой `chunk_ids`, не `source_ids`.** Расходятся, когда
   связь поддержана источником, чьи чанки не записались. Выбран `chunk_ids`, потому что чанк
   — то, что физически удаляется. Следствие: непустой `source_ids` при пустом `chunk_ids`
   считается мёртвым.
2. **Порядок: сначала связи, потом узлы, одним проходом.** Узлы — здесь же, иначе остаётся
   долг по мусорным сущностям. Обратный порядок ломает и счёт: удалённый узел уносит связь,
   которую мы посчитали удалённой, не удаляя её.
3. **Подсчёт обязателен до удаления.** Цена ошибки предиката — молчаливая потеря данных в
   графе; ни одна транзакция её не откатит, потому что команда исполнилась честно.
4. **Дискриминатор `chunk_ids IS NOT NULL` обязателен.** Без него снесёт `CONTAINS` и
   `MENTIONS`, у которых этого свойства нет вовсе, и ошибка проявится как «сломался поиск».
5. **Факт уборки требовался писать в той же транзакции, что и удаление.** Иначе сбой между
   коммитом и записью счётчика даёт правдоподобный ноль, читаемый как «удалять нечего».
   **Проверено 2026-09-28: в коде этого нет** — удаление коммитится в Neo4j отдельными
   коммитами, факт пишется в SQLite третьим, то есть ни общей транзакции, ни общей базы.
   Правило удаления не меняется, не реализована только доставка факта; см. ADR-014,
   четвёртая корректирующая запись (пп. 20–23), и `operations_requirements.md` §6
   (transactional outbox, отложен на M6-Growth).

**Что осталось открытым:**

1. **Проверка предиката на реальном корпусе — описана как E2E, ждёт прогона.** Предикат на
   пустом графе тривиален, поэтому зелёный тест на синтетике доказывает только, что код
   написан верно, и не доказывает, что предикат верен: это единственный способ узнать, что мы
   удаляем мусор, а не живые связи. Сценарий из двух посевов одного документа, утверждения
   T1–T8 и правило чтения результата описаны в `docs/test_plan.md` §7.2. Ключевая проверка —
   **многоисточниковая связь**: она обязана выжить, и её удаление означает пересмотр правила.
   Отдельно там же зафиксировано, что тест **не** ловит обрыв уборки между удалением и
   записью счётчика, — это отдельный сценарий. Синтетика: `tests/test_ingestion_api.py` (8)
   и `tests/test_retention_policy.py` (15).
2. **Переключатель как конфигурация — не реализован** (`docs/02` §4.4, `docs/06` §2.4). Шов
   объявлен, хранилище выбрано (Config Service, клиентом будет конфигуратор), кода нет.
3. **Онлайн не удаляет — и это не баг.** Удаление необратимо, путь записи компенсируем
   (ADR-028), откатить удалённое без повторной экстракции нельзя. Проверять надо не онлайн, а
   офлайновую джобу.
4. **Подсчёт и удаление развязаны по времени.** Между проходами может прийти другой ingest и
   изменить граф, после чего удалится не то, что посчитано. Решение: подсчёт повторяется
   непосредственно перед удалением; уборка фоновая, транзакцию ingest'а не держит.

**Поправка к предыдущим записям.** Ранее здесь и в `NEXT_SESSION_INSTRUCTIONS` значилось,
что безопасно удалять старые версии, потому что «источник истины — git». Это верно только
для нашего корпуса. Формулировка «сносить безопасно» снята как обобщение: у системы нет
права считать, что внешний VCS существует (`docs/02` §4.3, ADR-014, третья корректирующая
запись). При действующей политике вопрос снимается практически: старой версии в системе
нет, и каскадить нечего.

## 4. Анализ предложений

### 4.1 Ограничить стоимость экстракции

**Плюсы:** не требует кода, кроме правки промпта; сокращает прогон с часов до десятков минут;
плотность графа становится управляемой, а 77 сущностей на чанк уходят.

**Минусы:** меняет то, что мы измеряем, — состав графа становится параметром эксперимента и
должен попасть в манифест; детерминизма не добавляет, два прогона дадут разные графы.

**Применимость:** высокая, но только вместе с п. 4.3.

### 4.2 Эталонная разметка вместо LLM-экстракции

**Плюсы:** граф строится детерминированно, прогон воспроизводим и быстрый; появляется
измеряемая величина «насколько LLM совпадает с эталоном»; вклад графа меряется на заведомо
хорошем графе, а не на том, что выдала модель.

**Минусы:** требует разметки корпуса; смещает вопрос — вместо «помогает ли граф» получается
«помогает ли заранее известный граф»; для домашки это другой эксперимент, а не тот, что заявлен.

**Применимость:** высокая, но объём работ зависит от ответа по п. 6.1.

### 4.3 Поднять `max_wait_s` и починить wrapper

**Плюсы:** устраняет падение на `429`; объективно необходимо при любом LLM-сценарии.
`run_eval_run.ps1` вообще нерабочий — склеивает аргументы раннера в один, и `python` отвечает
`unknown option`.

**Минусы:** не помогает с длительностью; маскирует проблему, если слоты действительно зависли.

**Применимость:** высокая, делается независимо и в первую очередь.

### 4.4 LLM, обогащающий пользовательские теги

**Плюсы:** аддитивный режим — человек задаёт каркас, модель дополняет; измеряемо: считается,
сколько сущностей модель добавила к ручным.

**Минусы:** сейчас не реализовано — в промпт уходят только шаблон и текст чанка
(`orchestrator.py:469-472`), пользовательские теги модель не видит; объединение происходит
после, по каноническому ключу, то есть без осведомлённости модели. Требует отдельной правки
промпта и нового измерения.

**Применимость:** средняя, делается после 4.2, иначе не на чем проверять.

## 6. Рекомендации

1. **Сначала п. 4.3.** Поднять `max_wait_s` до значащей величины и починить wrapper: без этого
   прогон падает независимо от остальных решений.
2. **Затем п. 4.2 как основной путь.** Эталонный источник графа снимает и вопрос времени, и
   вопрос детерминизма, и даёт новую измеряемую величину. Ожидание: прогон `gold` на полном
   корпусе укладывается в минуты.
3. **П. 4.1 применять только к ветке `llm`**, если она вообще понадобится, и записывать предел
   в манифест как параметр эксперимента.
4. **П. 4.4 отложить** до появления эталона: пока не на чем измерять, что модель добавляет.
5. **П. 3.5 закрыть независимо и немедленно** — запретить `tag_id` в ответе LLM. Это тихая
   порча графа, а не вопрос удобства.
6. **Видимость деградации (п. 3.7) — до первого прогона, а не после.** Пока `enrichment_degraded`
   не попадает в артефакты, частичный граф неотличим от полного, и любой измеренный результат
   нельзя интерпретировать. Объём правки мал: пробросить флаг и текст ошибки в запись джобы и в
   `ingest_report.json`.
7. **Повтор (п. 3.8) не проектировать вслепую** — ни одного наблюдавшегося отказа на
   невалидный ответ нет. Сначала видимость, потом решение по бандлу, и только если отказ
   будет предъявлен.

## 7. Итог

### Что решено

| Вопрос | Решение | Раздел |
|---|---|---|
| Ручной ввод тегов и связей — план или факт | **факт**, работает в коде; в eval-контур не пробрасывается | 3.1, 3.6 |
| Как происходит слияние с базой | по `canonical_name` через алиасы (один кандидат → общий узел, несколько → новый узел), при записи — union `source_ids` и приоритет ручной связи | 3.2 |
| Какая роль у LLM в ингесте | одна стадия из девяти; без него между `ContextNode` нет рёбер | 3.3 |
| Можно ли обрезать ответ LLM | нет: обрезанный JSON валит джобу | 3.4 |
| Где молча портится граф | `tag_id` от LLM становится id узла | 3.5 |
| Видна ли деградация экстракции | **нет**: `enrichment_degraded` не выходит из оркестратора, частичный граф неотличим от полного | 3.7 |
| Наблюдался ли отказ «невалидный ответ LLM» | нет; проектировать повтор вслепую не на чем | 3.8 |
| Почему прогон упал | истёк дедлайн ожидания слотов, а не ошибка логики | 3.9 |

### Что не решено

| Открытый вопрос | Почему это важно |
|---|---|
| **Как размечать эталон** | руками, LLM с ревизией или только по документам из `graph_required` вопросов — от этого зависит объём работ |
| Объём разметки: 33 документа или только цитируемые в `graph_required` | второе дешевле, но смещает выборку и ослабляет сопоставимость |
| Плоская схема узла или типизированная (`Requirement`/`Concept`/`Contract`) | типизированная наследует отменённую модель; плоская ближе к тому, что реально извлекает LLM |
| Нужен ли третий arm «ручная разметка, отредактированная LLM» | отвечает на вопрос «помогает ли LLM, если человек проверяет», но это ещё одно сравнение |
| Нужен ли процесс подтверждения аннотации человеком | без подтверждения «эталон» — это вторая разметка, а не независимая |
| Какое значение `max_wait_s` считать правильным | сейчас 300 с не подходит ни к одному LLM-сценарию; правильное значение зависит от решения по разметке |
| **Нужен ли повтор при невалидном ответе LLM** | сначала видимость деградации; сам повтор писать только при предъявленном отказе, и с изменением промпта, а не идентичного |
| **Должен ли деградировавший документ считаться `ready` для проекции** | если считается — `graph_required`-срез снова измеряет пустоту; «непригоден» и «готов, но пуст» должны различаться |
