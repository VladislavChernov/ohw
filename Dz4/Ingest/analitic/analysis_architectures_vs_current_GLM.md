## 2. Карта архитектур (из `hybrid_rag_architectures.md`)

| # | Подход | Ингест | Рантайм | LLM на ингесте | Ключевое свойство |
|---|---|---|---|---|---|
| 1 | **Классический GraphRAG** (multi-hop, строгая онтология) | Дорогой (LLM-экстракция сущностей и связей) | Глубокий обход графа | Да | Скрытые связи, транзитивность; минусы: рост контекста, риск пустых скелетов |
| 2 | **«Облако тегов + Столицы»** (квазиплоский) | Копеечный, детерминированный | Тот же Cypher, компактный скелет | **Нет** | Плоские теги по двойным меткам, рёбра Chunk→Tag, минимум рёбер между тегами |
| 3 | **Иерархический (Microsoft Leiden)** | Астрономически дорогой | Global-запросы через резюме сообществ | Да, массово | Единственный отвечает на «главные темы всего корпуса»; пересчёт кластеров при обновлении |
| 4 | **HippoRAG** (ассоциативный) | Средний (PPR-матрица) | Personalized PageRank вместо Cypher | Нет на обходе | Multi-hop без LLM, сверхбыстрый; тяжёлый математический движок |
| 5 | **Продвинутый векторный** (Dense + Sparse BGE-M3 + rerank) | Самый дешёвый | Векторный поиск + reranker | Нет | Без графовой БД вообще; слеп к макроструктуре |
| 6 | **Contextual Retrieval** (Anthropic) | LLM на каждый чанк (дёшево) | Обычный векторный | Да | Контекстный префикс приклеивается к чанку; буст точности без графов |
| 7 | **Agentic RAG** | Обычный | LLM-цикл, Tool Calling (ReAct) | Да, на рантайме | Адаптивный добор данных; минусы: latency, расход токенов |

## 3. Языковые стеки (из `rag_language_stacks.md`)

| Вариант | Суть | Плюсы | Минусы | Совместимость с продвинутыми подходами |
|---|---|---|---|---|
| **А: Pure Python (текущий Dz4)** | Монолит: ingest, чанкинг, клиенты БД, ретрив | Единая AI-экосистема, лучшие парсеры, минимум стыков | GIL при параллельном ретриве, память, таймауты | Идеален для Agentic RAG (LangGraph/CrewAI); Contextual Retrieval — нативно |
| **Б: Pure Go** | Рантайм и ретрив на Go, ML через CGO/ONNX или API | Максимальная скорость параллельного ретрива, лёгкие контейнеры | Нет нативного PyTorch/HF, бедные парсеры, ручной Tool Calling | Подход №2 («облако тегов») на Go идеален; Agentic RAG — сложно |
| **В: Go/TS бэкенд + Python AI-сервис** | Системная логика на Go/TS, тяжёлый ML (bge-m3, reranker) — в FastAPI/gRPC-сервисе | SoC, асинхронный бэкенд без GIL, GPU-масштабирование Python-сервиса | Сетевой оверхед, два контейнера | Contextual Retrieval и Agentic RAG распределяются естественно |

## 4. Сравнение: текущая реализация Dz4 vs карта архитектур

| Аспект | Сейчас в Dz4 (M1-M2) | Позиция на карте |
|---|---|---|
| Ингест | `ExtractStage` — слова ≥5 букв, без связей; метки `Source/Entity/Chunk`; рёбра только `Source-CONTAINS-Chunk` | **Вырожденный №2 без тегов**: «облако» (Entity) есть, но не привязано ни к чанкам, ни к онтологии |
| Рантайм графовой оси | Cypher `MATCH (n) WHERE any(t IN $terms ...) OPTIONAL MATCH (n)-[r]-(m) WHERE m:{node_labels}` | Написан под **№1** (multi-hop), но топология графа не даёт материала → OPTIONAL MATCH пуст, скелет вырожден |
| Векторная ось | `DeterministicEmbedder` (SHA-256 хэш, 8-dim); bge-m3 (1024-dim, RU/EN) заготовлен в M3 | Заготовка под **№5** (Dense); нет Sparse-компоненты, реального эмбеддера и реранкера сейчас |
| Склейка осей | ContextAssembly: скелет первым (не вытесняется), тело вторым по reranker-score, лимит 4096 токенов | Слой совместим со всеми подходами №1/№2/№5 — менять не требуется |
| Реранкер | Не реализован (план M3) | Нужен для №5 и №6 |
| Стек | Pure Python монолит, `ThreadPoolExecutor` | **Вариант А** — соответствует стадии PoC |

### Ключевое наблюдение

Проект находится в «слепой зоне»: **рантайм написан под классический GraphRAG (№1), а ингест не производит даже материала для «облака тегов» (№2)**. Отсюда предупреждения M5 (`label does not exist`, пустой скелет).

## 5. Оценка траектории: предложение `ingest_refactoring_solution.txt`

Предложение «Облако тегов + Столицы» — это **сознательный спуск с №1 на №2**:

| Шаг | Что меняется | Эффект на карте |
|---|---|---|
| Двойные метки (`Tag` + `Concept`/`Requirement`/`Contract`) | Cypher `m:{node_labels}` находит узлы без изменения рантайма | Топология становится совместимой с №2 |
| `chunk_id` в сущности + ребро `Chunk-TAGGED_WITH->Tag` | Закрывает разрыв «сущность ↔ чанк» | №2 полностью материализован |
| `Source-HAS_TAG->Tag` | Столица агрегирует темы документа | Компактный скелет в промпте |
| Детерминированный ингест без LLM | Копеечная стоимость | Ключевой плюс №2 из таблицы |

При этом путь наверх остаётся открытым:

- **№1 (LLM-извлечение связей)** — за M4+ под флагом `EXTRACT_LLM=true` (задача 1.1 из `eval-graph-contribution-experiment/design.md`)
- **№6 (Contextual Retrieval)** — дешёвая надстройка поверх чанкера, когда в ингесте появится LLM: один вызов на чанк, скелет графа не трогается
- **№5 (Sparse в bge-m3)** — bge-m3 уже выбран (ADR-003) как dense-модель; её sparse-компонента даёт лексический поиск без графовой БД, полезно как fallback-ось

Не рекомендуются сейчас: **№3** (Leiden — стоимость индексации неоправданна для прототипа), **№4** (HippoRAG — отдельный математический движок, конфликт с существующим Cypher-рантаймом), **№7** (Agentic RAG — непредсказуемый latency, противоречит фиксированному контракту `done.sources`/кэшированию).

## 6. Рекомендации

### 6.1 Для текущего Dz4 (M1-M2 → M3)

**Рекомендуемый путь:** реализовать предложение `ingest_refactoring_solution.txt` (архитектура №2), сохранив существующий Cypher-рантайм и ContextAssembly без изменений.

**Почему:**
1. Прямо закрывает проблемы M5 (пустой скелет, предупреждения о несуществующих метках)
2. Не требует LLM и GPU — детерминированный ингест работает на текущем стеке
3. Cypher-шаблон и `render_skeleton` совместимы без доработок
4. Оставляет траекторию к №1/№6 открытой (двойные метки и `TAGGED_WITH` не мешают будущим связям между тегами)

**Что доработать перед реализацией (чек-лист):**
1. Валидация: `ent['chunk_id']` из `ExtractStage` должен гарантированно совпадать с `ctx.chunks_meta` того же пайплайна (иначе висячие рёбра `TAGGED_WITH`)
2. Дедупликация `Tag`-узлов при нескольких чанках с одной сущностью (узел один, рёбер — по числу чанков)
3. `ensure_schema()` — уникальность по `unique_key` для Tag-узлов (задачи 1.5/1.6 `eval-graph-contribution-experiment`)
4. Решить, создаётся ли `chunk_id` в `Chunker`-стадии или переносится (влияет на место, где ExtractStage его получает)

### 6.2 По стеку

- **Сейчас (PoC/M3):** остаться на Варианте А (Pure Python) — Agentic-перспективы и bge-m3 в Python нативны, GIL на текущих объёмах не узкое место
- **Production (если состоится):** миграция по паттерну Варианта В — рантайм/чанкинг/сборка контекста на Go/TS, ML (bge-m3 Dense+Sparse, reranker) — отдельный Python-сервис; текущий `embeddings_service` уже является прообразом такого изолированного ML-сервиса

## 7. Итог

| Подход | Что решает для Dz4 | Что НЕ решает |
|---|---|---|
| №2 «Облако тегов» (через рефакторинг ингеста) | Пустой скелет M5, связь сущность↔чанк, соответствие онтологии, без LLM-зависимости | Глубокие транзитивные вопросы (3-4 хопа) — путь к №1 |
| №6 Contextual Retrieval | Точность векторной оси без графа | Требует LLM в ингесте; не даёт структурного скелета |
| №5 Dense+Sparse | Лексическая точность (Sparse), дешёвый fallback | Не даёт макроструктуры между документами |
| Вариант В (стек) | Production-масштаб, SoC | Сетевой оверхед; для M1-M3 избыточен |

**Следующие шаги:**
1. Утвердить рефакторинг ингеста по №2 как M3-задачу (в связке с задачами 1.1–1.2 `eval-graph-contribution-experiment`)
2. Проработать валидацию `chunk_id` и дедупликацию Tag-узлов на уровне design-документа бандла
3. Запланировать Sparse-компоненту bge-m3 и реранкер как часть M3-векторной оси
4. Вернуться к оценке №6 (Contextual Retrieval) после появления LLM-контура в ингесте
