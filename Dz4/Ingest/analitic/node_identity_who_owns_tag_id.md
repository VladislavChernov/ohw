# Кто владеет идентичностью узла: разбор `tag_id` из ответа LLM

**Команда:** Свободный Космический Заяц
**Дата:** 2026-09-27
**Статус:** Аналитика
**Язык:** русский

## 1. Введение

### 1.1 Контекст

Повод — подготовка к первому полному eval-прогону. Задача 3.4 бандля
`tidy-domain-profile-keys` («запретить `tag_id` в ответе LLM») не выполнена: предыдущая
попытка потребовала переписать ожидания в шести тестах, регулярка по тесту сломала ещё
семь, правка была откачена целиком.

Вопрос в том, почему правка не прошла. Ответ оказался не в сложности: **инвариант `L1-05`
уже решает вопрос, и код его нарушает**. То есть находка дефектная, и лечится правкой;
ложной была не постановка задачи, а цитата, которой её обосновали.

### 1.2 Источники

Прочитаны код, профили доменов, документы и бандль. Все утверждения о коде снабжены
ссылками `файл:строка`; цитаты инвариантов приведены дословно.

### 1.3 Цель

1. Установить, кто фактически владеет идентичностью контекстного узла и требует ли
   документ или код.
2. Ответить на четыре вопроса, поставленных в разборе предыдущей сессии, в том числе
   проверить утверждение «документация L2-01 говорит, что идентичность задаёт canonical key».
3. Дать рекомендацию с оценкой цены и сформулировать инвариант, а не «золотой набор».
4. Разобрать, откуда взялась ошибка формулировки — иначе она повторится в следующей
   находке.

## 3. Анализ текущего состояния

### 3.1 Факт: модель фактически именует узлы

Файл: `prototype/src/graphrag_proto/ingestion_service/pipeline/orchestrator.py:269-275`

```python
def _context_node_id(domain: str, entity: dict[str, Any]) -> str:
    raw = entity.get("tag_id") or entity.get("node_id")
    if isinstance(raw, str) and raw:
        prefix = f"tag:{domain}:"
        return raw if raw.startswith(prefix) else f"{prefix}{raw}"
    canonical = str(entity.get("canonical_name") or entity.get("canonical") or entity.get("name") or "")
    return f"tag:{domain}:{_identity_key(canonical)}"
```

Непустой `tag_id`/`node_id` **закорачивает** вычисление от `canonical`: канонический
ключ не вычисляется вовсе. Дальше этот идентификатор становится `node_id` при записи
в граф (1139, 1143) и ключом дедупликации (675).

Поле `tag_id` попадает в запись сущности дословно, без фильтра:

Файл: `orchestrator.py:239`

```python
for key in ("id", "description", "category", "tag_id", "confidence"):
```

### 3.2 Факт: платформа канонический ключ умеет и считает его сама

Тот же файл, строки 91-94 и 274-275: `_identity_key` (NFKC + ё→е + casefold + сжатие
пробелов) — это и есть канонический ключ из контракта. То есть «postобработка на нашей
стороне» не гипотеза: она существует, вызывается в NORMALIZE и доступна.

Более того, для LLM-сущностей канонический ключ **glossary-осведомлён**:

Файл: `orchestrator.py:595-605`

```python
canonical = str(entity.get("canonical") or entity.get("canonical_name") or name)
if self._glossary_url:
    canonical = self._resolve(name or canonical, ctx.domain)
normalized_name = _identity_key(canonical)
entity["canonical"] = normalized_name
...
entity_id = _context_node_id(ctx.domain, entity)
```

`_resolve` (644-664) ходит в glossary-service и заменяет синоним на каноническую форму;
`glossary_url` пробрасывается из `app.py:114`. Идентификатор от модели глоссари не
касается — по построению.

### 3.3 Факт: модель `tag_id` не просят, но доверяют

Файл: `prototype/domain_profiles/domain_profile.it.yaml:65-68`

```
- Элементы трёх списков — ОБЪЕКТЫ, не строки. Обязательное поле — canonical_name
  (каноническая форма имени сущности); необязательные: name (человекочитаемая форма),
  id (идентификатор из текста, только если он там присутствует), aliases (синонимы),
  description (Concept), category (Contract).
```

`tag_id` в промпте не значится. `id` — значится, но в идентичность не попадает:
`_context_node_id` читает только `tag_id` и `node_id`. То есть поле, которому доверяют,
не запрашивают, — это не «модель обязана дать идентификатор», а «платформа доверяет
полю, которого не просила».

### 3.4 Расхождение: три источника против друг друга

| Артефакт | Что утверждает об идентичности | Дата |
|---|---|---|
| `docs/invariants.md:29` (L2-01) | узел имеет стабильный `tag_id` в пределах домена; `canonical_name` — **не** глобальный constraint | инвариант |
| `docs/01_ontology_and_domain_profile.md:36`, `docs/prototype_requirements.md:345` | то же: разрешение идёт через `tag_id`/aliases | инвариант |
| `prototype/domain_profiles/domain_profile.it.yaml:17-20, 86` | идентичность — `canonical_name`; `id` — бизнес-свойство, ключом склейки **не** является | «Вариант А, Стадия 7» |
| `prototype/tests/test_typed_graph.py:335-365` | разные `tag_id` при одном `canonical_name` ⇒ **разные узлы** | ADR-031 (2026-09-25) |
| код `orchestrator.py:269-275` | решает модель, если прислала `tag_id` | — |

**Здесь важно исправить утверждение предыдущей сессии.** Записка формулировала вопрос как
«документация (L2-01) говорит, что идентичность задаёт canonical key». Это неверно: L2-01
утверждает обратное — идентичность держит `tag_id`, а `canonical_name` быть глобальным
constraint не должен. Требование «canonical key» приходит из профиля домена, а не из
инварианта. Отсюда практическое следствие: запрет `tag_id` **не приводит код в соответствие
с инвариантом L2-01, а ломает его** — инвариант прямо требует стабильного `tag_id` в
пределах домена, и `tag:{domain}:{_identity_key(canonical_name)}` этому требованию
соответствует лишь настолько, насколько канонический ключ стабилен.

### 3.5 Расхождение структурное, а не опечатка

Файл: `prototype/domain_profiles/domain_profile.it.yaml:23-30`

```yaml
node_types:
  - type: "Requirement"
    unique_key: "canonical_name"
    properties: ["canonical_name", "name", "id", "source_ids", "chunk_ids", "extractor_version", "variants"]
```

Профиль декларирует `unique_key`, но механизм его применения — `UNIQUE`-constraint
в `retrieval/adapters/neo4j.py:161-181` — из ingest-path выведен (ADR-031,
`docs/05_adr_log.md:963-965`, закреплено тестом `test_eval_dataset.py:204-214`).
`tag_id` в белом списке `properties` вообще отсутствует.

Значит заявленного enforcement у `canonical_name` нет: единственное место, где
идентичность реально вычисляется, — Python. И он отдаёт приоритет модели. Профиль
и код расходятся не из-за забытой строки, а потому что профиль описывает правило,
которое никто не применяет.

### 3.5a Почему `UNIQUE` отключён, и почему constraint тут не защита

Отдельный вопрос от «кто отдаёт приоритет модели»: было ли отключение `UNIQUE` ошибкой,
раз идентичность вычисляется только в Python. Ответ — нет, и это видно из двух цитат.

**Первая — намерение.** `docs/05_adr_log.md:967-969` (ADR-031, Контекст):

> Цель проекта — измерить вклад лёгкой графовой связности, а не внедрить тяжёлую
> академическую ontology или Neo4j schema ownership.

`docs/05_adr_log.md:978-979` (ADR-031, п. 4 решения):

> `_validate_ontology`, `ensure_schema`, typed labels, edge whitelist и runtime Neo4j
> constraints **удаляются из ingest path**. `Source`/`Chunk` остаются technical anchors.

То есть отказ от constraint — часть цели: constraint это и есть schema ownership.

**Вторая — механизм, который constraint бы сломал.** `docs/05_adr_log.md:976-977`
(ADR-031, п. 3):

> `tag_id` стабилен в пределах domain; multilingual aliases разрешаются через optional
> glossary/AI, **неоднозначные кандидаты не объединняются молча**.

И `docs/invariants.md:44` (L3-02):

> Дедупликация объединяет сущности по точному совпадению нормализованного canonical key;
> неоднозначные варианты **не объединяются молча**. Ключ узла выводится из canonical name,
> поэтому одна сущность из разных документов домена — один узел

`UNIQUE(domain, canonical_name)` умеет ровно два: **слить** или **отвергнуть**. «Слить» —
прямое нарушение второй клаузы L3-02. «Отвергнуть» — тоже: инвариант требует различать
неоднозначные варианты, а отказ от_constraints превращает их в потерю документа. Плюс
отвергнутая вставка ломает документированную возможность, закреплённую тестом
`test_same_canonical_with_distinct_tag_ids_remains_distinct`: два узла с одинаковым
`canonical_name` и разными `tag_id` **обязаны** остаться разными.

**Про «держится только на Python» — неточно, и это стоит поправить.** Приоритет
«курируемое над предложенным» на реальном хранилище выполняет **база**, а не Python:

- `retrieval/adapters/neo4j.py:491-500` и `:544-553` — `preserve_manual` и
  `SET n += CASE WHEN n.origin = 'user' AND $incoming_origin <> 'user' …`;
- Python-версия того же правила есть в `retrieval/adapters/inmemory.py:78-92` и `:144-154`
  (in-memory — тестовая подмена реального движка) и в DEDUP внутри документа через
  `_origin_rank` (`orchestrator.py:194`, `:720-721`: `ai` 1 < `system` 2 < `user` 3).

Чего на уровне БД нет — не приоритет, а **гарантия непоявления дубля**. Но и она после
этой правки не востребована: два разных `node_id` с одним `canonical_name` из LLM
невозможны, потому что идентичность считается из `canonical_name` (L3-02, вторая часть
той же строки). Остаточные «два разных id на один canonical» — это ровно случай
`origin=user` плюс `origin=ai`, который по L2-01 **обязан** остаться раздельным.

**Настоящая дыра рядом — не constraint, а наблюдаемость.** «Не объединяются молча»
соблюдалось: `ambiguous_aliases` в `NormalizeStage` подавляет алиасы для неоднозначных
ключей. Но это локальный сет, и после подавления он **выбрасывается** — ни счётчика, ни
лога. То есть «не молча» относится к слиянию, а не к наблюдаемости: нельзя отличить
документ без неоднозначности от документа, где их были десятки и алиасы пропали молча.
Constraint этого не дал бы в любом случае: он умеет только слить или отвергнуть.

Поэтому правка добавляет `ctx.ambiguous_aliases` и одну строку лога — минимальную
наблюдаемость, которой L3-02 не имел, и которая делает инвариант проверяемым.

### 3.6 Цена расхождения, которую никто не измерил

Галлюцинированный `tag_id` молча создаёт дубликат-ноду вместо слияния. Дальше:

- DEDUP (675) считает ключом `tag_id` — разные `tag_id` не сливаются;
- `_validate_edges` (528-548) разрешает концы связей по `tag_id` в том числе, поэтому
  связи выживают вместе с дублями;
- retrieval идёт по `tag_id`: `inmemory.py:239-241`, `neo4j.py:250`
  (`coalesce(node_id, tag_id)`) — то есть дубль виден и в выдаче.

Величина этого вклада в метрики **не измерена ни одним прогоном**: валидного полного
eval не было. Поэтому цена сейчас нулевая в терминах сравнения с прошлым, и это
единственный аргумент за «менять сейчас, а не после первого прогона».

Обратная сторона: заявленный плюс запрета («исчезает режим, где галлюцинированный id молча
создаёт дубликат») не измерен ничем, кроме рассуждения. Сколько именно дубликатов даёт
модель на реальном корпусе — неизвестно. Правка закрывает это: счётчик
`model_tag_ids_ignored` даст частоту на первом прогоне, и спор станет измерением.

### 3.7 Что именно ломается в коде при запрете

Проверено, а не предположено. Правка `_context_node_id` (запрет `tag_id`/`node_id` из
ответа модели) меняет идентичность всех LLM-сущностей, и вот где это видно:

| Место | Что сломается | Характер |
|---|---|---|
| `test_typed_graph.py:485-492` | узлы `tag:it:requirement` / `tag:it:indexing` при `canonical_name` «требование»/«индексирование» станут `tag:it:требование` / `tag:it:индексирование` | переписать ожидания |
| `test_typed_graph.py:756-790` | `test_llm_accepts_dynamic_context_payload_with_optional_legacy_hints` прямо проверяет, что `tag_id` из LLM доезжает до узла | тест проверяет обратное запрету — переписать или снять |
| `test_typed_graph.py:726-753` | payload с `tag_id` используется как вход; ассертится только `description`, но идентичность узла поедет | проверить |
| `test_typed_graph.py:335-365` | `test_same_canonical_with_distinct_tag_ids_remains_distinct` — **сам закрепляет** нынешнее поведение | требует решения, а не правки ожидания |
| `orchestrator.py:609-610` | `ambiguous_aliases` считает расхождение явного `tag_id` и канонического ключа ошибкой модели | после запрета ветка недостижима — либо удалить, либо оставить для user-origin |
| `_validate_edges` (528-548) | `tag_id` в списке ключей разрешения концов связей | после запрета избыточен для LLM, нужен для ручных тегов |

Итого «шесть тестов» из записки — это нижняя оценка: по факту затрагивается и
документация (L2-01), и профиль (`unique_key`/`properties`), и сам тест, фиксирующий
противоположное намерение. Правка поэтому и не прошла в прошлый раз: объём работ был
оценён как «поправить ожидания», а он в три раза шире.

**Граница запрета.** Запрет должен действовать на путь «ответ модели», а не на поле
`tag_id` вообще. Иначе ломаются пути, где `tag_id` — законное пользовательское решение:
`test_lightweight_context_graph.py:164-209` задаёт сущности напрямую в `ctx.entities`
(не через LLM) и проверяет, что COMMIT сохраняет `tag:it:quicksort`;
`test_commit_stage.py:227` — ручной тег `tag:it:manual`. Практически это означает: резать
в `_entity_record` (239), а не в `_context_node_id` (269-275), иначе один и тот же запрет
убьёт и человеческий ввод.

### 3.8 Откуда взялись проблемы: разбор процесса, а не кода

Правка не прошла не потому, что была трудна. Цепочка была такой:

1. **Доктрина выведена из имён функций.** `_identity_key` и `_context_node_id` прочитаны,
   `docs/invariants.md` — нет. Из названий сделан вывод «идентичность задаёт canonical
   key», который тут же приписан инварианту. Первая ошибка — не в правке, а в основании:
   утверждение о документе, взятое не из документа.
2. **Ошибка записана в бандл как задача.** Ложное основание легло в `proposal.md`
   обоснованием, а оттуда — в `tasks.md` чекбоксом. Это самая исполняемая форма ошибки:
   чекбокс читается как готовое решение, и следующая сессия выполнила бы его, не проверяя.
   Ошибка пережила сессию потому, что была закоммичена.
3. **Категория назначена по умолчанию.** Таксономия ADR-015 (тогда — три категории) не
   имела ячейки для «расхождения без решения», и находка ушла в «дефект → чиним».
4. **Правка начата раньше, чем прочитано основание.** Способ выбран regex по
   1544-строчному тесту — приём, который в проекте уже однажды сломал семь тестов.
   Вывод «сработала страховка, а не рассудок» верен: тесты упали и правка была откачена.
   То есть гейт поймал ошибку исполнения, но не ошибку формулировки — и это разные вещи.
5. **Ничего не требовало прочитать инвариант.** Задача ссылалась на код и не ссылалась на
   документ, который при этом противоречил коду. Не было шага «назови артефакт, который
   требует поведения, и процитируй его».

**Что из этого следует практически.** Три из пяти пунктов — про формулировку, а не про код,
и все три лечатся одним: находка обязана называть источник требования поимённо и цитатой.
Пока цитаты нет, категория («дефект», «выбор», «точка роста») назначается наугад, и гейт
единственной общей защитой не является.

**И та же ошибка повторилась в обратную сторону.** При разборе 2026-09-27 сначала было
уверенно записано, что запрет «сломает L2-01» — тоже без чтения инварианта, только в
другую сторону. L2-01 требует существования и стабильности `tag_id`, а не его
происхождения, поэтому запрет его не ломает. Совпадение форм не случайно: обе ошибки —
утверждения о документе, выведенные из кода. Правило «цитата берётся из документа»
добавлено в `docs/05_adr_log.md` ADR-034 (corrective note 2026-09-27; перенесено из
`CONCEPT.md` 2026-09-28) и в п. 6 рекомендаций.

## 4. Анализ предложений

### Предложение A. Оставить как есть, зафиксировать намерение

Ничего не менять в коде; в профиле и инварианте явно сказать, что `tag_id` из ответа
модели — сознательно доверенное поле, идентичность узла задаёт модель.

- **Плюсы:** нулевая цена, ноль изменений в тестах, поведение совпадает с
  `test_same_canonical_with_distinct_tag_ids_remains_distinct` и с духом ADR-031
  (лёгкий граф, минимум схемы).
- **Минусы:** дубликат-ноды от галлюцинаций остаются и в графе, и в выдаче; профиль
  продолжает объявлять `unique_key: canonical_name`, который не применяется, — то есть
  расхождение 3.5 сохраняется и получает статус «нарочно», что неправда: расхождение
  появилось не как решение.
- **Применимость:** Низкая. Закрепляет невыбранную сторону конфликта.

### Предложение B. Запретить `tag_id`/`node_id` из ответа LLM (пункт 3.4 бандля)

Канонический ключ считает только платформа; для ручных тегов (`origin=user`) `tag_id`
остаётся разрешённым.

- **Плюсы:** идентичность становится функцией `canonical_name` + `_identity_key` +
  glossary, то есть воспроизводимой и не зависящей от настроения модели; исчезает
  режим молчаливых дублей; правило из профиля начинает соответствовать коду.
- **Минусы:** меняет идентичность всех LLM-сущностей (граф, который никогда не был
  измерен, обесценивается — цена реально нулевая, но это нужно проговорить); требует
  синхронной правки L2-01 и профиля, иначе доказанное противоречие станет
  доказанным несоответствием; требует явного решения по
  `test_same_canonical_with_distinct_tag_ids_remains_distinct`; длина идентификатора
  становится неограниченной по содержимому (имя сущности произвольной длины уходит в
  `node_id`).
- **Применимость:** Высокая, но **не раньше** решения по разделу 5.1.

### Предложение C. Игнорировать `tag_id`, но принимать как алиас

`tag_id` не определяет идентичность, но сохраняется в `aliases`/`variants`, чтобы
ручные теги и старые ссылки продолжали резолвиться.

- **Плюсы:** снимает риск «потерять связь с уже загруженными документами» при смене
  правила; даёт мягкий переход.
- **Минусы:** если алиас остаётся в `alias_ids` (1090), неоднозначность возвращается —
  ровно та, что даёт `ambiguous_aliases` (610-622). То есть предложение не устраняет
  источник проблемы, а прячет его; плюс требует отдельного кода и миграционных
  соображений.
- **Применимость:** Средняя, только как переходная мера после B.

### Предложение D. Отдельный префикс для модельных идентификаторов

`tag_id` из LLM принимается, но с префиксом `ai:` и наравне с каноническим, то есть
сущность получает два идентификатора.

- **Плюсы:** ничего не ломает, provenance различима.
- **Минусы:** два идентификатора на одну сущность означают, что вопрос «что является
  ключом» вообще не закрыт; стоимость в графе и в индексах удваивается, а логика
  `coalesce(node_id, tag_id)` в `neo4j.py:250` становится двусмысленной.
- **Применимость:** Откладывается.

## 5. Ответы на четыре вопроса

### 5.1 Кто владеет идентичностью узла

Ответ дан инвариантом, и получен он чтением, а не рассуждением.

Файл: `docs/invariants.md:22`

> L1-05 | Детерминированность критичных шагов (tag identity, dedup policy, context assembly,
> bounded expansion, вытеснение) обеспечивается Python-кодом; LLM допускается только на
> optional enrichment и пограничных предложениях

Значит находка — **дефект**, а не нерешённый продуктовый выбор, и лечится правкой, а не
ADR. Основания два, независимых:

- `L1-05` — `tag identity` детерминируется Python-кодом;
- `L3-02` — «**ключ узла выводится из canonical name**, поэтому одна сущность из разных
  документов домена — один узел».

Второе основание важнее: оно не только запрещает модели задавать идентичность, но и
предписывает, откуда ключ берётся. То есть профиль (`unique_key: "canonical_name"`) не
противоречил инварианту — он его повторял, а код был единственным, кто от него отступил.

**Что при этом говорит L2-01** (`docs/invariants.md:29`):

> Context node имеет стабильный `tag_id` в пределах домена, `canonical_name`/aliases и
> provenance; `canonical_name` не является глобальным constraint

Инвариант требует **существования и стабильности** `tag_id`, а не его происхождения.
Вычисленный `tag:{domain}:{_identity_key(canonical_name)}` стабилен, доменный и
glossary-осведомлённый, то есть L2-01 выполняется. Запрет его не ломает — он устраняет
нарушение L1-05.

Итог: **идентичность LLM-сущности задаёт платформа**; `tag_id` из ответа модели в неё не
входит; идентичность ручного тега задаёт человек (следует и из L2-01, и из
`proposal.md`, менять не нужно).

### 5.2 Цена в метриках

Нулевая: валидного полного прогона не было, сравнивать не с чем. Реальная цена — объём
синхронной правки (код + 6 тестов, раздел 3.7), а не потеря сопоставимости.

### 5.3 Кто пишет `tag_id` вообще

Три источника, и это важно, потому что запрет бьёт только по одному:

| Источник | Где | Запрет затронет |
|---|---|---|
| Модель | `orchestrator.py:239` — дословный приём | да |
| Детерминированный экстрактор | `orchestrator.py:564` — `f"tag:{ctx.domain}:{word}"` | нет: значение совпадает с каноническим |
| NORMALIZE | `orchestrator.py:606` — `entity["tag_id"] = entity_id` | нет: платформа пишет сама |
| Ручной тег | `orchestrator.py:1094-1102` (`origin=user`) | нет, и не должен |

Ответ на исходный вопрос: **постобработка на нашей стороне есть и уже владеет
каноническим ключом**, причём glossary-осведомлённым. Доверять модели поле, которое не
запрашивалось, при наличии собственного вычисления не требуется.

### 5.4 Как проверять

Золотой набор идентичностей не нужен и был бы дороже самой задачи: он отвечал бы на вопрос
«правильно ли модель выбирает `canonical_name`», а это отдельная тема качества извлечения.

Достаточно инварианта: **в payload ответа модели подставлены `tag_id` и `node_id` — после
нормализации идентичность узла обязана совпасть с
`tag:{domain}:{_identity_key(canonical_name)}`**. Это юнит-тест на существующей инфраструктуре
`FakeLLM`, без корпуса и без стенда.

Существующий тест `test_same_canonical_with_distinct_tag_ids_remains_distinct` правке не
противоречит: он кладёт сущности в `ctx.entities` напрямую, то есть это путь ручного тега.
Достаточно было дописать в докстринг происхождение — что и сделано, иначе старый и новый
тесты выглядели бы как противоречащие друг другу.

## 6. Рекомендации

1. **Правка выполнена в этом же изменении, а не отложена.** Находка дефектная (нарушение
   L1-05, раздел 5.1), цена нулевая, объём понятен. Задача 3.4 бандля
   `tidy-domain-profile-keys` **возобновлена**: обоснование исправлено, рамка «требует ADR»
   снята как неверная.
2. **Точка реза — белый список полей ответа модели** (`_entity_record`), а не
   `_context_node_id`. Иначе запрет убьёт ручной ввод: `tag_id` человека — сознательное
   решение, и `test_commit_preserves_dynamic_tag_ids_and_links` с ним существует.
3. **Проигнорированные `tag_id` считать и логировать.** Именно этот счётчик заменяет
   недоказанное утверждение раздела 3.6: он даст частоту на первом реальном прогоне и
   превращает спор о модели в измерение. Одна строка на документ, не на сущность.
4. **Адресация связей — последствие, и оно ломающее, причём грубее, чем кажется.** В
   строгом режиме `_validate_edges` отвергает конец связи, адресованный модельным `tag_id`,
   и это правильно (L1-05). Но **продовый путь другой**: `app.py` собирает
   `ExtractStage(..., optional_failure=True)`, а `ExtractStage._degrade_after_extraction_failure`
   делает `ctx.entities = []; ctx.entity_edges = []` и уходит в детерминированный fallback.
   То есть на проде адресация модельным `tag_id` не «отклоняет одно ребро», а
   **уничтожает весь LLM-слой документа**, и документ остаётся `succeeded`. Это четвёртый,
   неназванный вариант гранулярности рядом с «отбросить / карантин / автослияние».
   **Это не однозначное «плохое», и вывод не должен предопределяться.** Размен такой:
   сброс слоя — худший по сохранности, но лучший по простоте и предсказуемости: никогда
   не бывает полу-состояния, всегда либо полный AI-слой, либо детерминированный fallback,
   и второе честно помечено `enrichment_degraded` (B1 сделало его видимым). Карантин
   сохранил бы больше, но требует ревью-пути и своей инфраструктуры. Решение законное с
   ценой обоих концов, поэтому оно и не сделано сразу.
   **Цена, которая делает его прототипным:** потеря **необратима**. Повторная загрузка
   того же `content_hash` — no-op (`CommitStage.try_noop`), то есть простая перезагрузка
   файла не перезапустит экстракцию. Одна транзиентная ошибка LLM навсегда оставляет
   документ без AI-слоя. Зафиксировано как риск №7 в `docs/06_operations_and_risks.md` и
   пометкой в коде на месте сброса.
   Границы `except Exception` **больше нет** (2026-09-27, коммит `5b25363`): ловится ровно
   `ExtractionConfigError` и `ExtractionModelError`, дефект нашего кода падает, а не
   попадает в `enrichment_degraded_documents`. Причина пишется именем, размер потери —
   числами, и потеря инвалидирует вердикт прогона.
   Оба поведения закреплены тестами, чтобы факт не разъехался с решением:
   `test_context_edges_reject_model_invented_tag_id_addressing` (строгий режим) и
   `test_optional_failure_wipes_whole_ai_layer_not_one_edge` (продовый).
   **Гранулярность сброса вынесена в ADR-032** (единственный открытый вопрос): она не
   следствие 3.4 и решается независимо от него. Различение причин ADR-032 не ожидало, а
   закрыл.
5. **Промпты.** `domain_profile.it.yaml` уже требовал адресовать `from`/`to` только по
   `canonical_name`, поэтому запрет не расходился с живым промптом; 2026-09-27 туда добавлен
   явный запрет `tag_id` и его аналогов (`entity_id`, `uid`, `key`).
   **Поправка к ранней формулировке этого раздела (2026-09-27).** Раньше здесь было
   написано, что у `cinema`/`library` нет `user`-шаблона, а `_extraction_template` его
   требует, «поэтому LLM-экстракция для этих доменов невозможна». Вывод неверен: у обоих
   профилей стоит явный `llm_enabled: false`, и `_profile_llm_enabled` замыкается на нём
   раньше, чем дойдёт до чтения шаблона. Негодного шаблона там нет — экстракция выключена
   решением домена. Форма ошибки та же, что разобрана в `CONCEPT.md`: утверждение о коде,
   выведенное не из кода. Практическое следствие нулевое — домены с `llm_enabled: false`
   не деградируют и в счётчики потерь не попадают.
5. **Профиль приводить в соответствие отдельно.** `unique_key: "canonical_name"` и
   whitelist `properties` без `tag_id` сейчас читаются как контракт, но не применяются
   (ADR-031). После этой правки они хотя бы совпадают по смыслу с кодом; «снимать
   неприменяемое» — задача бандла, не эта правки.
6. **Не трогать `ambiguous_aliases` (609-610) в этом изменении.** После запрета ветка
   недостижима от LLM, но она же покрывает user-origin. Уборка — отдельная задача, и
   делать её одновременно с изменением идентичности значит менять два поведения за раз.
7. **Ошибку формулирования не повторять — в обе стороны.** Ложной была и фраза «L2-01
   говорит, что идентичность задаёт canonical key» (нет, не говорит), и зеркальная
   «запрет сломает L2-01» (тоже нет: L2-01 требует существования и стабильности
   `tag_id`, а не происхождения). Обе выведены без чтения `docs/invariants.md`. Отсюда
   правило в ADR-015 (corrective note 2026-09-27): утверждение о документе берётся из
   документа, и находка обязана называть артефакт цитатой.

## 7. Итог

### Что решено

| Вопрос | Ответ |
|---|---|
| Кто владеет идентичностью по инварианту | Платформа: L1-05 называет `tag identity` детерминированным Python-шагом, L3-02 — «ключ узла выводится из canonical name» |
| Кто владеет фактически | Модель, если прислала `tag_id`; иначе платформа |
| Нарушает ли текущий код инвариант | Да, L1-05 и L3-02 |
| Ломает ли запрет L2-01 | Нет: L2-01 требует существования и стабильности `tag_id`, не происхождения |
| Почему `UNIQUE` отключён | ADR-031 §4 + Контекст: цель — не брать schema ownership; §3 и L3-02 требуют не сливать неоднозначное молча, а constraint умеет только слить или отвергнуть |
| Держится ли «курируемое над предложенным» только на Python | Нет: на Neo4j приоритет выполняет база (`neo4j.py:491-500, 544-553`); Python-версия — только в in-memory адаптере и в DEDUP внутри документа |
| Просят ли модель `tag_id` | Нет (`domain_profile.it.yaml:53-80`) |
| Кто пишет `tag_id` | Модель, детерминированный экстрактор, NORMALIZE, ручной тег |
| Есть ли своя канонизация | Да, `_identity_key` + glossary `_resolve`, и она лучше модельной |
| Цена запрета в метриках | Нулевая (валидного прогона не было) |
| Что ломается в коде | 6 тестов; инварианты не ломаются |
| Как проверить | Инвариант на подставленном `tag_id`, без золотого набора |

### Что не решено

1. **`unique_key`/`properties` в профиле остаются неприменяемым обещанием** (ADR-031) —
   задача бандла, не этой правки.
2. **Частота модельных `tag_id` и неоднозначностей не измерена** — счётчики добавлены,
   числа появятся на первом прогоне.
3. **Ветка `ambiguous_aliases` (627-628) после запрета недостижима от LLM** — уборка
   отдельной задачей, в этой правке не трогалась намеренно.
4. **`cinema`/`library` не имеют `user`-шаблона** — `_extraction_template` его требует, то
   есть LLM-экстракция для этих доменов невозможна. Найдено попутно, не чинится здесь.

### Что делать в следующей фазе

1. Прогнать гейт и закоммитить: запрет `tag_id` из ответа LLM отдельным изменением.
2. Первым `--retrieval-only` прогоном прочитать `model_tag_ids_ignored` из логов.
3. Взять из бандла уборку `unique_key`/`properties` — теперь, когда код им соответствует.
