# Архитектурные концепции гибридных RAG-систем

В данном документе представлен высокоуровневый анализ фундаментальных подходов к построению систем извлечения контекста (RAG), объединяющих семантические (векторные) и структурные (графовые) данные.

## Сводный анализ архитектур

| Архитектурный подход | Суть механики | Главные преимущества (Pros) | Ключевые недостатки (Cons) |
| :--- | :--- | :--- | :--- |
| **1. Классический GraphRAG (Multi-hop / Строгая Онтология)** | Тяжелые цепочки отношений: `(Chunk)->(Entity)-[REL]->(Entity)->(Chunk)`. Рантайм делает глубокий обход связей (graph traversal). | • Идеально для сложных логических цепочек.<br>• Строгий контроль типов данных домена.<br>• Находит неочевидные скрытые связи. | • Экспоненциальный рост контекста (`multi-hop`).<br>• Дорогая LLM-экстракция на ингесте.<br>• Риск пустых скелетов при ошибках топологии. |
| **2. Квазиплоское «Облако тегов» + Столицы** | Источники — это «Столицы». К чанкам на ингесте детерминированно привязываются плоские теги из онтологии по двойным меткам. Рёбер между тегами минимум. | • Копеечный детерминированный ингест.<br>• **Не требует изменения Cypher-рантайма**.<br>• Компактный скелет в промпте. | • Слабо справляется с глубокими транзитивными вопросами (обход через 3-4 сущности). |
| **3. Иерархический GraphRAG (Microsoft Leiden Pattern)** | Алгоритм **Leiden** (кластеризация) разбивает граф на иерархические сообщества. Для каждого сообщества LLM заранее пишет текстовое резюме (Summary). | • Единственный подход, идеально отвечающий на глобальные запросы типа: *«Каковы главные проблемы в коде?»* | • Астрономическая стоимость первичного индексирования.<br>• Обновление одного документа требует пересчета кластеров. |
| **4. Ассоциативный GraphRAG (HippoRAG)** | Моделирует работу гиппокампа мозга. Вместо Cypher использует алгоритм **Personalized PageRank (PPR)**, динамически подсвечивая подграфы. | • Фантастическое multi-hop рассуждение **без вызовов LLM** на этапе обхода графа.<br>• Сверхбыстрый ретрив. | • Требует тяжелых математических движков поверх графа.<br>• Сложно контролировать текстовый вывод скелета. |
| **5. Продвинутый Векторный гибрид (Dense + Sparse + Rerank)** | Векторный поиск (Dense), усиленный лексическим поиском (Sparse, как в **BGE-M3**) + кросс-энкодер реранкер на выходе. Без графовой БД. | • Не требует графовой БД вообще.<br>• Точно бьет по точным терминам (Sparse) и синонимам (Dense).<br>• Самый дешевый ингест. | • Абсолютная «слепота» к макроструктуре данных и внешним зависимостям между документами. |
| **6. Contextual Retrieval (Контекстуальный ретрив от Anthropic)** | На ингесте перед векторизацией чанка к его тексту с помощью дешевой LLM приклеивается 1-2 предложения контекста всего исходного документа. | • Полностью решает проблему потери контекста при примитивном чанкинге.<br>• Драматический буст точности векторного поиска без использования графов. | • Увеличение стоимости ингеста (требуется LLM на каждый чанк).<br>• Увеличивает размер индексной базы и токенов в промпте. |
| **7. Agentic RAG (Агентский поиск)** | Поиск выносится внутрь цикла размышлений LLM (Agent Loop). Модель сама решает через Tool Calling, какие базы (вектор, граф) и с какими запросами вызывать. | • Максимальная гибкость и автономность.<br>• Способность делать адаптивный добор данных, если первого ретрива не хватило для ответа. | • Высокий и непредсказуемый Latency (задержка ответа).<br>• Огромный расход токенов из-за многошаговых циклов рассуждения (Reasoning). |

## Детальное описание современных подходов

### Contextual Retrieval (Контекстуальный ретрив от Anthropic)
Этот подход нивелирует главный минус примитивного чанкинга. Вместо того чтобы отдавать на эмбеддинг изолированный кусок текста вроде *"Вызовите метод `execute()`"*, система на этапе ингеста делает быстрый запрос к LLM, передавая весь документ целиком. Модель генерирует контекстный префикс (например: *"Этот чанк относится к подразделу пула потоков в архитектурном описании бэкенда. Он описывает запуск пайплайна."*). Этот префикс жестко приклеивается к тексту чанка. Векторный эмбеддер (Dense и Sparse в BGE-M3) видит всю картину целиком, благодаря чему точность поиска взлетает без усложнения структуры графа.

### Agentic RAG (Агентский поиск)
Переход от жесткого линейного конвейера ("запрос -> ретрив -> ответ") к динамическому. Логика на Go или Python описывает функции-инструменты (например, `search_vectors(query)`, `query_graph(cypher)`), а LLM в цикле размышлений (например, ReAct-паттерн) сама выступает диспетчером. Если пользователь задает сложный вопрос, агент может сначала вызвать векторный поиск, проанализировать результаты, понять, что ему не хватает контекста по конкретному контракту, сгенерировать точечный Cypher-запрос к графу и только после этого собрать финальный ответ.
