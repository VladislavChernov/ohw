# Архитектурный анализ технологических стеков реализации RAG

При проектировании ядра гибридной RAG-системы выбор языка программирования определяет производительность параллельного поиска (рантайм) и стабильность обработки данных (ингест). Ниже приведено сравнение трех паттернов реализации с учетом современных подходов (Contextual Retrieval и Agentic RAG).

## Сводное сравнение технологических стеков

| Вариант реализации | Суть подхода | Главные преимущества (Pros) | Ключевые недостатки (Cons) | Влияние на продвинутые подходы |
| :--- | :--- | :--- | :--- | :--- |
| **Вариант А: Pure Python (Текущий монолит)** | Весь пайплайн (Ingest, Чанкинг, Клиенты БД, Эмбеддинги, Ретрив) написан в едином монолите на Python с использованием `ThreadPoolExecutor` или `asyncio`. | • Единая экосистема для AI-моделей и логики.<br>• Лучшие библиотеки для грязного парсинга данных.<br>• Минимальное количество сетевых стыков. | • Блокировки GIL при параллельном ретриве.<br>• Высокое потребление памяти.<br>• Проблемы с таймаутами при обработке больших контекстов. | • **Идеально для Agentic RAG**: вся агентская экосистема (LangGraph, CrewAI) написана на Python.<br>• Легко реализовать **Contextual Retrieval** за счет нативных клиентов Anthropic/OpenAI. |
| **Вариант Б: Pure Go (Полный отказ от Python)** | Пайплайн и параллельный ретрив пишутся на Go. Работа с BGE-M3 и Reranker идет через CGO-биндинги (например, ONNX Runtime) или внешние API. | • Максимальная скорость параллельного ретрива (Goroutines).<br>• Ультра-легкие Docker-контейнеры (15-20 МБ).<br>• Строгая типизация и высокая надежность рантайма. | • Сложная поддержка ML-моделей (нет нативного PyTorch/HuggingFace).<br>• Бедная экосистема готовых парсеров документов (PDF/Docx). | • **Сложно для Agentic RAG**: агентские фреймворки на Go развиты слабо, логику Tool Calling придется писать вручную.<br>• **Contextual Retrieval** реализуется стандартными HTTP-клиентами без проблем. |
| **Вариант В: Смешанный (Go/TS Бэкенд + Python AI Service)** | **Рекомендуемый паттерн**. Системная логика, параллельные запросы к БД, чанкинг и сборка контекста — на Go/TS. Тяжелый ML (BGE-M3 Dense/Sparse, Reranker) изолирован в FastAPI/gRPC сервисе на Python. | • Идеальное распределение обязанностей (SoC).<br>• Асинхронный бэкенд не зависит от GIL.<br>• Python-сервис легко масштабировать на GPU.<br>• Защита от Idle Timeout. | • Появляется сетевой оверхед (gRPC/HTTP) между бэкендом и AI-сервисом.<br>• Необходимо поддерживать два разных Docker-контейнера. | • **Contextual Retrieval**: Go управляет конвейером и чанками, а Python-сервис берет на себя вызовы локальных моделей или API.<br>• **Agentic RAG**: Высокоуровневый агентский цикл может крутиться на Go (управление стейт-машиной), дергая Python для рассуждений. |

## Детальный разбор вариантов

### Вариант А: Монолит на Python
Подходит для стадии PoC. При переходе к **Agentic RAG** Python является стандартом, так как управление инструментами (Tool Calling) и сложными графами рассуждений реализуется проще всего. Однако параллельный ретрив (одновременный поход в вектор и граф) начинает упираться в производительность потоков при росте конкурентных запросов от пользователей.

### Вариант Б: Компиляция в чистый Go
Обеспечивает колоссальную скорость. Если ваша цель — построить **Квазиплоское облако тегов + Столицы (Подход №2)**, Go идеален: горутины моментально стянут данные из Neo4j и векторного индекса. Но если вы захотите уйти в **Agentic RAG**, отсутствие зрелых библиотек для LLM-агентов на Go заставит вас писать тонны низкоуровневого кода для парсинга ответов модели.

### Вариант В: Архитектура изолированного AI-сервиса (Микросервис)
Оптимальный выбор для Production-ready систем. Бэкенд (Go или TypeScript) берет на себя тяжелую параллельную работу по одновременному вызову Neo4j и Векторной базы, гарантируя минимальный Latency для пользователя. При реализации **Contextual Retrieval** Go-бэкенд асинхронно нарезает документ, а параллельные вызовы для генерации контекста и эмбеддингов распределяет на Python-сервис, балансируя нагрузку на GPU.
