# Ингест и хранение: как делают «большие дяди» и что это значит для Dz4

**Команда:** GLM
**Дата:** 2026-09-21
**Статус:** Аналитика (независимый обзор, вне внутренней аналитики проекта)
**Язык:** русский

## 1. Введение

**Контекст.** Ингест в Dz4 находится в зачаточном состоянии (детерминированная заглушка ExtractStage, синхронный пайплайн, полный текст чанков внутри узлов графа). Цель — понять, как эти проблемы решают зрелые open-source и промышленные системы, и что из этого применимо при ограничении по RAM.

**Исследованные материалы (внешние):**

- LightRAG (HKUDS) — архитектура хранения и ингест-пайплайн (DeepWiki, июль 2026)
- Contextual Retrieval vs Late Chunking — контролируемый бенчмарк (ConTEB, arXiv:2505.24782, май 2025; обзор Particula Tech, август 2026)
- Общая практика production RAG 2025-2026

**Цель анализа:** выработать собственную рекомендацию по ингесту и хранению, отвлекаясь от внутренней аналитики, с учётом RAM-ограничения проекта.

## 2. Три канона «больших дядей»

### 2.1 LightRAG — эталон архитектуры хранения

Ключевое решение LightRAG — **четыре раздельных хранилища** вместо двух осей:

| Хранилище | Что держит | Почему отдельно |
|---|---|---|
| **KV Storage** | Исходные документы, кэш LLM-ответов, маппинги | Не нужна семантика — fast get/upsert по ключу |
| **Vector Storage** | Эмбеддинги чанков **+ сущностей + связей** (рёбра тоже векторизуются) | Поиск по similarity на всех уровнях |
| **Graph Storage** | Узлы-сущности и рёбра-связи | **Только топология, без текста** |
| **Doc Status Storage** | Жизненный цикл: PENDING → PROCESSING → PROCESSED | Ретраи, идемпотентность, инкремент |

Контраст с Dz4: в Dz4 узел `Chunk` в графовой оси несёт **полный текст** чанка. LightRAG держит в графе только сущности/связи; текст — в KV, вектор — в vector store. Граф худой и дешёвый по памяти.

Ещё три решения LightRAG:

1. **Инкрементальный ингест с очередью и статусами.** Документ ставится в очередь (`enqueue`), статус пишется в Doc Status Storage, пайплайн обрабатывает, отмечает PROCESSED. Падение на середине → документ остаётся PROCESSING → ретрай с места ошибки. Повторный ингест → дифф, а не дубликаты.
2. **Merge-слой после экстракции.** Сущности/связи извлекаются по чанкам независимо, затем отдельная стадия **сливает** дубликаты: сущность из 20 чанков = один узел с накопленным описанием и source_ids. Рёбра дедуплицируются по паре (src, dst, rel_type) с накоплением весов.
3. **Gleaning.** После первой экстракции LLM спрашивают «что пропустил?» — вторая попытка добора. Дорого (x2 к ингесту), полнота +15-30%.

### 2.2 Anthropic — Contextual Retrieval и цены альтернативы

Бенчмарк 2025 (ConTEB, arXiv:2505.24782):

| Техника | Качество (nDCG@10) | Стоимость индексации | Когда выбирать |
|---|---|---|---|
| Contextual Retrieval (LLM-префикс на чанк) | **72.4** | 1890 мс/док (**120x**) | Статичный корпус, качество критично |
| Late Chunking (mean pooling на весь док) | 61.0 | 15.8 мс/док | Длинные документы (>500 токенов) |
| Ничего (плоские чанки) | базовая | базовая | Короткие документы (<500 токенов) |

Важные детали:

- Late Chunking на коротких документах **вредит**: MSMarco 0.630 → 0.503 nDCG@5 (-20% относительных)
- Перейти на Late Chunking можно только на Apache-2.0 long-context энкодерах (nomic-embed-text-v1, gte-modernbert-base); Jina-модели — cc-by-nc (нельзя коммерчески)
- Кэширование контекстных префиксов Contextual Retrieval дёшево на реиндекс, но замораживает контекст под старую версию модели/чанкера

Вывод индустрии: для часто меняющегося корпуса Contextual Retrieval слишком дорог (120x на реиндекс); выбор определяется **медианной длиной документов корпуса**.

### 2.3 Канон В: инкрементальность как первоклассное свойство

Все зрелые системы (LightRAG, Microsoft GraphRAG, Khoj) сходятся в одном: **ингест — фоновый процесс с очередью, а не синхронный пайплайн в HTTP-запросе**. Re-ingest того же документа → дифф: пересчитываются только изменившиеся чанки, граф смержится, векторный индекс получит апсерты.

## 3. Моя рекомендация для Dz4 (при RAM-ограничении)

### 3.1 Хранение: «худой граф» без смены движка

Раздельная схема (упрощение четырёх хранилищ LightRAG до трёх):

```
┌─────────────────┬──────────────────┬─────────────────┐
│  GraphStore     │  VectorStore     │  DocStore (KV)  │
│  ТОЛЬКО сущности│  чанки+эмбеддинги│  исходный текст │
│  и связи        │  + метаданные    │  + статусы инг. │
│  БЕЗ текста     │                  │                 │
└─────────────────┴──────────────────┴─────────────────┘
```

Эффекты:

- **RAM графа падает на порядок**: узел `Chunk` превращается в лёгкий указатель `{chunk_id, source_id, domain}`, текст убирается
- Текст и так живёт в векторном хранилище — дублировать в графе незачем
- Рёбра `TAGGED_WITH` **не требуют текста** — только `chunk_id`. Это снимает противоречие между «облаком тегов» (нужны чанки в графе для рёбер) и turbopuffer (текст наружу): храним узел-указатель, текст — в векторе
- Миграция в turbopuffer/Qdrant в будущем не блокируется: граф уже худой

### 3.2 Ингест: три отсутствующие стадии

**Стадия 1 — Doc Status + идемпотентность.** Таблица статусов (`doc_id, status, error, retries, updated_at`). Падение COMMIT → ретрай; повторный ингест → дифф. Дешёвое изменение, превращает ингест из «скрипта» в систему.

**Стадия 2 — Merge-слой после ExtractStage:**
- *Интра-документ:* сущность из 10 чанков → один узел + список `chunk_ids` (даёт 10 рёбер `TAGGED_WITH`)
- *Интер-документ при COMMIT:* тег `OAuth` уже в графе → апсерт с накоплением `source_ids`, а не дубль

Поддержка уже есть: `unique_key` в профиле + `ensure_schema()` с UNIQUE-constraint делают мерж декларативным.

**Стадия 3 — очередь (не спринт №1).** Сейчас ингест синхронный. Архитектурно оставить место под `enqueue_document(doc)` → фоновый воркер.

### 3.3 Экстракция: не спешить с LLM

Детерминированный ингест («облако тегов») + хороший чанкинг + Dense/Sparse bge-m3 — базовая линия для eval. LLM-экстракция оправдана, когда:
- eval покажет, что скелета из тегов не хватает
- появится отдельный LLM-контур (не resident, гейтинг ADR-022/027)

Gleaning — не сейчас (x2 к стоимости ингеста).

### 3.4 Чанкинг: качество бесплатно

1. Проверить **медианную длину документов**: если <500 токенов — Late Chunking и Contextual Retrieval оба не нужны, вкладываться в Dense+Sparse + реранкер
2. Sparse от bge-m3 — бесплатно (одна модель на два поиска, ADR-003)
3. Лёгкий реранкер (`bge-reranker-base`, ~1 GB) — самый дешёвый буст точности на рантайме, не на ингесте

## 4. Приоритеты для Dz4 (RAM-оптимизированный порядок)

| Приоритет | Что | RAM | Зачем |
|---|---|---|---|
| **1** | Худой граф: убрать `text` из `Chunk`-узлов, оставить `chunk_id`-указатели | **-90% RAM графа** | Решает хранение дёшево, без смены движка |
| **2** | Doc Status Storage + идемпотентный COMMIT | ~0 | Ингест из «скрипта» → система; дифф-реингест |
| **3** | Merge-слой: интра-док + интер-док, UNIQUE-constraint из `unique_key` | ~0 | Дублей нет, `TAGGED_WITH` строится корректно |
| **4** | Теги из онтологии («облако тегов») — детерминированно | ~0 | Рабочий скелет без LLM |
| **5** | Активация bge-m3 (Dense + Sparse), замер медианной длины доков | +4 GB (запланировано) | Качество вектора; Sparse бесплатно |
| **6** | Лёгкий реранкер (`bge-reranker-base`) | +1 GB | Дешёвый буст на рантайме |
| **7** | LLM-экстракция (M4+), флаг `EXTRACT_LLM` | по запросу | Только по данным eval |
| **8** | Очередь ингеста, gleaning, Leiden/HippoRAG/Agentic | по обстоятельствам | Не в горизонте прототипа |

## 5. Итог

**Ключевая мысль, которой нет во внутренней аналитике проекта:** главный RAM-оверхход сейчас — не в эмбеддере и не в ретриве, а в **хранении полного текста чанков внутри узлов графа**. Убирание текста из графа (узел-указатель по `chunk_id`) одновременно:

1. Решает проблему хранения (RAM графа падает на порядок)
2. Не блокирует ни «облако тегов» (рёбрам `TAGGED_WITH` текст не нужен), ни будущую миграцию в turbopuffer/Qdrant (граф уже худой)
3. Делает граф дешёвым при росте корпуса

**Принятые решения по альтернативам:**

| Альтернатива | Решение | Причина |
|---|---|---|
| Облако тегов (№2) | **Делаем** (приоритет 4) | Минимальный RAM, рабочий скелет, без LLM |
| Худой граф (LightRAG-паттерн) | **Делаем** (приоритет 1, раньше всего) | Решает хранение, совместим со всем остальным |
| Doc Status / идемпотентность | **Делаем** (приоритет 2) | Дёшево, превращает ингест в систему |
| Merge-слой | **Делаем** (приоритет 3) | Дёшево, корректные рёбра и дедупликация |
| Contextual Retrieval (№6) | Отложить | 120x на реиндекс; решать по медиане длины доков |
| Late Chunking | Отложить | Работает только на >500 токенов, нужен другой энкодер |
| LLM-экстракция (№1) | M4+, флаг `EXTRACT_LLM` | Только после базовой линии и eval |
| HippoRAG / Leiden / Agentic | Вне горизонта | RAM/latency не оправданы для прототипа |

**Что нужно подтвердить замерами:**

- Медианная длина документов корпуса (от неё зависит выбор чанкинг-стратегии)
- Объём графа с текстом vs без текста (для обоснования приоритета 1)
