# Сценарий: Юрист и работа с делами

> **Статус:** черновик  
> **Дата:** 2026-09-19  
> **Автор:** по запросу пользователя

---

## 1. Контекст

Базой пользуется юрист. У него есть текущие дела, переговоры, документация. Он начинает работу над новым делом — идут созвоны, обновляются данные для старых дел (расшифровки встреч, новые документы).

**Цель сценария:** понять, как заводить метки для разных типов активности:
- новые дела
- встречи/переговоры
- документы
- обновления старых дел

**Домен:** юридическая практика (аналог `it`, `cinema`, `library` — но пока без domain profile).

---

## 2. Персонажи и их роли

### Юрист (основной пользователь)
- Ведёт несколько дел параллельно
- Проводит созвоны и встречи по делам
- Загружает документы в систему
- Обновляет информацию по старым делам
- Ищет информацию по делам и встречам

### Система (как её ожидают использовать)
- Хранит дела, встречи, документы
- Позволяет связывать сущности между собой
- Поддерживает поиск по контексту
- Позволяет обновлять данные без потери истории

## 3. Сценарии использования

### 3.1. Начало нового дела

**Ситуация:** Юрист берёт новый кейс.

**Что происходит:**
1. Создаётся метка-дело (например, "Дело №2026-007: АГАЙС-2026")
2. В ней фиксируются:
   - номер дела
   - тип (уголовное/гражданское/административное/хозяйственное)
   - статус (открытие/активность/архив/закрытие)
   - ответственный юрист
   - дата открытия
   - клиент (если есть)
   - краткое описание

**Вопрос для обсуждения:** Должна ли метка-дело быть "родителем" для всех связанных встреч и документов?

---

### 3.2. Проведение созвона / встречи

**Ситуация:** В ходе дела проходит созвон с клиентом, встреча с противной стороной, переговоры.

**Что происходит:**
1. Фиксируется встреча с параметрами:
   - дата и время
   - тип (совещание/переговоры/консультация/встреча)
   - участники (кто присутствовал: юрист, клиент, представитель другой стороны)
   - темы обсуждения
   - результат/резолюция
   - связанное дело (привязка к метке-делу)
2. Встреча может порождать документы (протокол, меморандум, соглашение)

**Вопрос для обсуждения:** Как связывать встречу с делом — через явную ссылку или автоматически по контексту?

---

### 3.3. Загрузка документов

**Ситуация:** Юрист загружает документы в систему — договоры, доказательства, ответы, материалы.

**Что происходит:**
1. Документ загружается с метаданными:
   - название/тип документа
   - дата создания/вхождения
   - автор/источник
   - связанное дело
   - связанная встреча (если документ создан по результатам)
2. Документ может быть прикреплён к встрече или делу

**Вопрос для обсуждения:** Если документ обновляется (новая редакция) — что происходит с метками? Новая версия? История изменений?

---



### 3.4. Обновление старых дел

**Ситуация:** По старому делу появляются новые факты — новые доказательства, результаты переговоров, новые документы.

**Что происходит:**
1. Юрист открывает старое дело (метка уже существует)
2. Добавляет новую информацию:
   - новая встреча (дата, участники, тема)
   - новый документ (прикреплён к старому делу)
   - обновление статуса дела (если изменилось)
3. Старое дело теперь содержит новый контент, но история предыдущих данных сохраняется

**Вопрос для обсуждения:** Как понимать, что "дело обновилось"? Нужна ли метка версии? Или достаточно даты последнего обновления?

---

### 3.5. Архивация дела

**Ситуация:** Дело завершено, его нужно отправить в архив.

**Что происходит:**
1. Статус дела меняется на "архив" или "закрыто"
2. Архивное дело больше не активно, но:
   - доступно для поиска
   - можно посмотреть всю историю (встречи, документы)
   - можно сослаться на него из новых дел
3. В архиве дело может быть исключено из показа "активных дел"

**Вопрос для обсуждения:** Архивное дело — это новая метка или изменение старой?

---

### 3.6. Поиск и навигация

**Ситуация:** Юрист ищет информацию — по делам, по встречам, по документам.

**Что может быть нужно:**
1. Найти все дела, где участвовал определённый клиент
2. Найти все встречи по определённому делу
3. Найти все документы, привязанные к встрече
4. Найти дела, которые обновлялись за последние N дней
5. Найти все дела определённого типа (например, все уголовные)

## 4. Предложения по заведению меток

> Это раздел "предложения" — варианты того, как можно реализовать заведение и обновление меток на основе сценариев выше.

### Вариант A: Ручное заведение через UI/форму

Для каждого нового объекта (дело, встреча, документ) юрист заполняет форму:

```
[Добавить новую метку]
├── Тип метки: [Дело | Встреча | Документ | Задача]
├── Название: _____
├── Описание: _____ (опционально)
├── Связанные объекты:
│   └── Ссылка на другое дело / встречу / документ
└── Сохранить
```

**Плюсы:**
- Не нужно знать YAML или структуру данных
- Визуальная привязка между объектами

**Минусы:**
- Нужно разрабатывать UI
- При большом количестве объектов — перебор форм

---

### Вариант B: CLI-скрипты для типовых операций

Команды для стандартных действий:

```bash
# Создать новое дело
ohw create-case \
  --name "Дело №2026-007" \
  --type criminal \
  --status active \
  --lawyer "ivan@lawfirm.com"

# Добавить встречу по делу
ohw add-event \
  --case "Дело №2026-007" \
  --type negotiation \
  --date 2026-12-31 \
  --participants "client@example.com, lawyer@example.com" \
  --description "Переговоры по договору"

# Загрузить документ
ohw add-document \
  --case "Дело №2026-007" \
  --file contract.pdf \
  --title "Договор аренды" \
  --date 2026-12-30

# Обновить старое дело (добавить документ и встречу)
ohw update-case \
  --id "Дело №2026-001" \
  --add-document evidence_new.pdf \
  --add-meeting "2027-01-15: переговоры с прокуратурой"
```

**Плюсы:**
- Быстро, автоматизируемо
- Валидация через CLI-аргументы
- История команд — документация действий

**Минусы:**
- Нужно знать CLI-аргументы
- Требует разработки скриптов

---

### Вариант C: Автоматическая типизация по контексту

Система сама определяет тип метки по сигналам:
- Загрузка файла `Дело_№2026-007_Договор.pdf` → автоматически создаёт метку "Дело №2026-007" (если ещё нет) и привязывает документ
- Добавление встречи (видео/аудио/текст) → определяет тип (переговоры/совещание) по содержимому

**Плюсы:**
- Минимум ручной формализации
- Юрист просто загружает файлы и проводит встречи — система сама связывает

**Минусы:**
- Сложная логика для точной типизации
- Риск некорректной типизации (автоматика может ошибиться)

---

### Вариант D: Мета-метки (категории-пакеты)

Ввести категории с предустановленными полями:

```
категория "Дело" {
  поля: номер, тип (уголовное/гражданское/адм), статус, ответственный, клиент, дата_открытия
}
категория "Встреча" {
  поля: дата, тип (совещание/переговоры/консультация), участники, тема, результат, связанное_дело
}
категория "Документ" {
  поля: название, тип, дата, автор, связанное_дело, связанная_встреча
}
```

При создании юрист выбирает категорию — поля подставляются автоматически.

**Плюсы:**
- Единая структура категорий
- Гибкость — можно добавлять свои поля в категорию
- Юрист не видит YAML

**Минусы:**
- Требует разработки механизма категорий

## 6. Вопросы для обсуждения

1. **Как связывать сущности:** явные ссылки (ссылка на дело из встречи) или иерархия (дело → встречи → документы)?
2. **Версионирование:** нужно ли хранить версии документов/меток? Или достаточно даты последнего обновления?
3. **Поиск:** какие запросы будут наиболее частыми? (по клиенту, по статусу, по дате, по типу)
4. **Архивация:** как отличать архивные дела от активных? Нужна отдельная метка или просто статус?
5. **Частичные обновления:** как обрабатывать ситуацию, когда обновляется только часть информации?
6. **Общие встречи:** может ли одна встреча относиться к нескольким делам?

### 5.1. Несколько дел параллельно

Юрист ведёт 5-10 дел одновременно. Нужно:
- Быстро переключаться между делами
- Видеть обзор всех дел (активные, архивные)
- Не путать документы и встречи разных дел

**Сложность:** Как организовать навигацию без путаницы? Нужна панель "мои дела" или фильтрация по меткам?

---

### 5.2. Обновление документации после созвона

Состоялся созвон — это повлияло на документацию:

**Что может измениться:**
- Некоторые пункты уходят (условия не приняты)
- Некоторые пункты добавляются (новые согласованные условия)
- Часть формулировок меняется на новые

**Что в результате:**
1. Старая документация остаётся как "версия N"
2. Новая версия — "версия N+1"
3. Различия видны (diff или журнал изменений)

**Вопрос для обсуждения:** Нужно ли хранить версии документов? Или можно обновлять на месте? Если хранить — как связывать версии с встречей, на которой всё решили?

---

### 5.3. Встреча влияет на несколько дел

Один созвон затрагивает несколько дел сразу (например, обсуждение общих условий для двух кейсов).

**Что происходит:**
- Встреча создаётся один раз
- Но она привязывается к нескольким делам
- Документы могут быть общими для нескольких дел

**Вопрос для обсуждения:** Может ли встреча быть "общей" для нескольких дел? Или нужно создавать отдельную встречу для каждого дела?

---

### 5.4. Частичное обновление метки

Метка "Дело №2026-001" существует давно. По нему появилась новая информация:
- Статус изменился (активное → на рассмотрении)
- Добавился новый документ
- Изменился ответственный юрист (переведён другой юрист)

**Вопрос:** Обновляется ли вся метка целиком или только отдельные поля?

**Варианты:**
- Обновление отдельных полей (исправление статуса, добавление документа)
- Всё обновляется вместе с датой модификации
- Версионирование — каждая правка создаёт новую версию метки

---


- **UI/CLI для типовых операций** (создание дела, добавление встречи, загрузка документа)
- **Мета-метки для структуры** (категории с полями)
- **Автоматическая привязка** (если документ назван по шаблону "Дело_№XXX", система сама привязывает к делу)
- **Ручная правка для сложных случаев** (когда автоматика не справилась)

## 6. Вопросы для обсуждения

1. **Как связывать сущности:** явные ссылки (ссылка на дело из встречи) или иерархия (дело → встречи → документы)?
2. **Версионирование:** нужно ли хранить версии документов/меток? Или достаточно даты последнего обновления?
3. **Поиск:** какие запросы будут наиболее частыми? (по клиенту, по статусу, по дате, по типу)
4. **Архивация:** как отличать архивные дела от активных? Нужна отдельная метка или просто статус?
5. **Частичные обновления:** как обрабатывать ситуацию, когда обновляется только часть информации?
6. **Общие встречи:** может ли одна встреча относиться к нескольким делам?
