# Эксперимент: форма связи и соглашение об именах

Серия из трёх прогонов одного и того же документа (`docs/plans/cosine-dedup.md`,
2762 символа) на разогретой модели, без пересборки образа. Все прогоны — одна серия,
сравнивать их между собой можно только так: образ один и тот же, менялся только текст
метода в `domain_profiles/domain_profile.it.yaml`.

## Критерии приёмки

| # | критерий | почему он |
|---|---|---|
| C1 | документ не деградирует: `cause=None`, `degraded 0/1` | иначе теряется LLM-слой документа (риск №7, `docs/06`) |
| C2 | у каждой связи есть объявленный `kind` | иначе загрузчик подставляет `RELATED` по умолчанию и вид связи теряется |
| C3 | каждый конец связи совпадает с объявленным `canonical_name` | иначе `_validate_edges` поднимает `ExtractionModelError` |

Честная оговорка: критерии были сформулированы после первого провального прогона, а не
заранее. Это ошибка метода, а не результат; в следующей серии критерии пишутся первым
пунктом.

## Гипотеза

`model_error` вызывается не межчанковыми связями, а **расхождением соглашений об именах
внутри одного ответа**: сущности объявляются настоящими идентификаторами документа
(`DEDUP_AUTO`), а концы связей пишутся по другой схеме (`REQ-1: порог точного совпадения`).

## Условия прогона

- образ `ingestion-api` — старый: закоммиченный в `08490ca` генератор формы объекта
  связи в него **не входит**, промт = старый рендерер + текст профиля;
- модель не дообучалась, поэтому выдуманный формат имен в примере она копирует дословно;
- `domain_profiles` смонтирован в контейнер как `:ro`, правки профиля видны без пересборки.

## Результаты

| прогон | что в профиле | сущностей | связей | без `kind` | неразрешённых концов | prompt | completion | итог |
|---|---|---|---|---|---|---|---|---|
| `expA-req-n-example-failed` | пример с `REQ-2: хранение контекста в памяти` | 8 | 6 | 0 | **12** | 2072 | 608 | **model_error** |
| `expB-rule-only` | правило «не переименовывай», без примера | 11 | 9 | **9** | 0 | 2030 | 573 | успех |
| `expC-rule-plus-example` | правило + пример с нейтральными именами | 9 | 6 | **0** | **0** | 2093 | **481** | **успех** |

Базовая линия для сравнения — `llm-probe-full-20260930-174640` (старый профиль):
успех, 17 сущностей / 7 связей, prompt 1871, completion 900.

## Выводы

Ингредиенты работают **раздельно**, и это видно по тому, что каждый вариант чинит ровно
одну вещь:

- **правило «не переименовывай»** чинит концы: неразрешённых концов 12 → 0 (`expB`, `expC`);
- **пример** держит `kind`: без примера `kind` пропадает у всех 9 связей (`expB`), с
  нейтральным примером — у всех 6 на месте (`expC`);
- **выдуманная схема имён в примере** ломает всё сразу: модель копирует `REQ-N:` и
  получает неразрешимое (`expA`, 12 неразрешённых концов).

Победил `expC`. Он же самый дешёвый по completion.

## Что опровергнуто

- **Гипотеза «`model_error` из-за связей между чанками» не подтверждается** ни на одном
  документе: концы расходились с объявленными именами внутри одного ответа, а не ссылались
  на соседние фрагменты.
- **Гипотеза «концы переименованы» тоже неверна** — см. «Механизм отказа». ADR-037 пришлось
  исправить в части механизма; решение (факт вместо отказа) осталось в силе.

## Механизм отказа: концы брались из поля `id`

Выяснено 2026-09-30 переигрыванием записанных журналов через настоящий код
(`prototype/infra/eval/replay_extract_failure.py`). Один этот прогон снял неверную формулировку
из ADR-037.

**Предполагалось:** модель переименовала концы, то есть взяла имена из ответа и переписала их.

**На самом деле:** концы взяты из поля `id`, которого валидация не видит.
`_entity_record` кладёт в запись `canonical` (из `canonical_name`/`canonical`/`name`) и `name`,
а `_validate_edges` собирает известные имена из `tag_id`, `canonical`, `canonical_name`, `name` —
**без `id`**.

В `expA` это видно буквально:

| где | что лежит |
|---|---|
| `canonical_name` | настоящие идентификаторы: `DEDUP_AUTO`, `DEDUP_AUTO_THRESHOLD`, … |
| `id` | выдуманные `REQ-1..3` / `CON-1..4` |
| `relationships[].from/to` | значения `id` |

Все 6 связей идут по `id`, ни один конец не разрешается, джоба деградирует.

**Промт это требовал.** На момент прогона в тексте метода стояло: «если `id` — идентификатор,
уникальный в пределах домена, использовать именно его как имя сущности». То есть промт и валидация
противоречили друг другу, и модель послушалась промта. Профиль с тех пор исправлен — `id` теперь
объявлен идентификатором, прочитанным из текста, — и прогоны после правки дают 0 неразрешённых
концов.

**Третий механизм, профилем не адресован.** В `expD` концы — значения поля `category`, которое
модель сама же написала для этой сущности: `retrieval.graph_search_enabled` →
`"graph search enabled"`. Это не переименование и не поле-идентификатор, а «поле как узел».

**Знаменатель — концы, а не связи, и на этом уже удваивались доли.** У каждой связи два конца, и в
expA все 6 связей потеряли оба, поэтому «12 из 12 концов» читалось как «12 из 5 связей», а expD —
как «4 из 5» вместо `4/10`. Доли, посчитанные по числу связей, завышены примерно вдвое. Прибор
теперь отдаёт `ends_total` рядом с `ends_unresolvable`, и отношение считается только к нему.

Итог по всем наборам (`ends_unresolvable / ends_total`):

| набор | концы | откуда |
|---|---|---|
| `expA-req-n-example-failed` | 12/12 | `id` (7 имён) |
| `expB-rule-only` | 0/18 | — |
| `expC-rule-plus-example` | 0/12 | — |
| `expD-rule-plus-example-big-doc` | 4/10 | `category` (4) |
| `llm-probe-20260930-165440` | 0/0 | журнал пуст, не измерено |
| `llm-probe-20260930-170953` | 0/14 | — |
| `llm-probe-20260930-172056` | 2/42 | `id` (1, запись 4) |
| `llm-probe-full-20260930-174640` | 0/14 | — |

**Распределение по полям, а не одно число.** `unresolvable_by_field` отвечает на вопрос, на который
одного счётчика попаданий нет: уклон в одно поле или разнобой. Здесь виден уклон в одно поле в
каждом случае — `id` в expA, `category` в expD, — и это разные дефекты с разными владельцами.
Уклон в `category` — кандидат на промт («`category` — это описание, не имя»); разнобой по разным
полям был бы дефектом формы ответа, и лечился бы он не промтом. Поля с нулём не выводятся, иначе
«уклон в поле» и «поле не смотрели» стали бы неразличимы.

**Как это проверять дальше.** Формулировка «повторение условий `expA` не деградирует» была бы
непроверяемой: одно из условий `expA` — тот самый промт, требовавший использовать `id` как имя,
а его уже нет, то есть условия нельзя воспроизвести, не изменив их. Проверяемо иное: **тот же
документ, текущий профиль, ожидается 0 неразрешённых концов.** Это слабее — механизм `id` этим
не проверяется — но это единственная честная формулировка, и в ADR она записана именно так.

Прибор `prototype/infra/eval/score_extraction_grounding.py` пересчитывает всё это офлайн по тем
же журналам. Счётчик `unresolvable_matching_non_name_field` показывает, что конец совпал со
значением поля, которое именем **не является** (`id`, `category`, `description`): «модель назвала
не тем полем» после этого измеримый факт, а не загадка, которую пришлось раскрывать вручную.
expA — `id`, expD — `category`.

**Про поля, по которым прибор считает имена.** Раньше прибор писал свой список полей, отличный от
списка валидации, и из-за этого показывал «0 неразрешённых» там, где их было 12. Теперь список
один: `ENTITY_NAME_FIELDS` в `orchestrator.py`, и прибор импортирует его вместе с той же логикой
выбора имени, что и `_entity_record`. Это четвёртый случай одного класса — прибор смотрит на один
набор полей, код на другой, и никто не сверял; лечится тем, что источник один, а не правкой
списка.

## Ограничения

- `n = 1` документ на вариант для серии A/B/C/D. Этого хватает, чтобы отбросить вариант,
  и не хватает, чтобы зафиксировать правило как рабочее.
- `expC` не проверен на большом документе (`docs/01_ontology_and_domain_profile.md`).
- Не проверено поведение промта после пересборки `ingestion-api`: тогда в промте окажутся
  одновременно текст профиля и сгенерированный блок формы связи.
- **`165440` неатрибутируема:** журнал обмена пуст, джоба деградировала, причину по этому набору
  восстановить нельзя. Она помечена в своём вердикте как `attributable: false`, а не выпала из
  числа наборов молча.

## Состав

В каждом каталоге: `exchange_fresh.json` (журнал обмена, режим `full`), `jobs.json`,
`summary.json` (метрики пробника), `grounding_verdict.json` (вердикты прибора: grounded-оценка
имён, разрешимость концов, петли/хабы/взаимные пары). Текст профиля, действовавший в прогоне,
приведён в колонке «что в профиле» таблицы результатов.

Вердикты пересчитываются офлайн, без стенда и без LLM:

```
docker exec ohw-dz4-dev sh -c 'cd /repo/prototype && uv run --no-sync python infra/eval/score_extraction_grounding.py'
```

`--check` ничего не пишет и сверяет пересчёт с тем, что лежит на диске, по значениям, а не
побайтово: форма JSON меняется вместе с прибором, и побайтовое сравнение тарило бы шумом.

Запуск требует `PYTHONPATH` на рабочее дерево, иначе прибор импортирует пакет из образа, а не из
исходников, и считает по другой версии кода:

```
docker exec ohw-dz4-dev sh -c 'cd /repo/prototype && PYTHONPATH=/repo/prototype/src uv run --no-sync python infra/eval/score_extraction_grounding.py'
```

**`UNKNOWN` — не ступень лестницы, а отдельный вердикт.** Счётчик, который не может измерить,
возвращает `UNKNOWN`, а не `0`: отсутствие данных и отсутствие дефекта — разные результаты. Раньше
при отсутствующем документе имена попадали в `UNGROUNDED`, то есть прибор обвинял модель в выдумке
на данных, которых у него не было. Это тот же класс, что и неатрибутируемый `165440`.
