# Demo: GraphRAG по документам проекта

Это демонстрационный стенд системы, которая отвечает на вопросы по документам репозитория.
Она ищет текст двумя осями: **векторной** (похожие фрагменты) и **графовой** (связанные
сущности и документы), а затем отдаёт ответ языковой модели вместе с источниками.

Стенд нужен, чтобы увидеть три вещи своими глазами:

- какой ответ получается на вопрос по документации;
- какие документы и чанки в него попали;
- что именно добавил граф сверх обычного векторного поиска.

Ничего из внешних сервисов не требуется: всё работает локально в Docker. На Linux, macOS и
Windows команды разные только из-за оболочки: `demo.sh` и `demo.ps1` содержат одну логику,
расхождение между ними ловит `prototype/tests/test_demo_scripts_parity.py`.

## Если вы здесь впервые

Есть три пути. Выберите один, не смешивайте их.

| что хотите | что запускать | сколько ждать |
|---|---|---|
| быстро посмотреть готовый граф и задать вопрос | `restore --set ready`, затем `up --set ready` | минуты |
| посмотреть на пустую систему | `up --set empty` | минуты |
| самому загрузить документ и увидеть, как растёт граф | `ingest ... up`, `load`, затем `demo ... up` | десятки минут и больше |

**Все команды ниже выполняются из каталога `Dz4`** — того, где лежит папка `Demo/`, а не из
корня репозитория и не из `prototype/`.

## Быстрый старт на готовом наборе

Нужен только Docker Desktop (на Linux — работающий `dockerd`). Python, Node и что-либо ещё
на хосте не нужны.

### Windows

```powershell
cd D:\Otus\ohw\Dz4
powershell -File Demo\demo.ps1 restore -Set ready
powershell -File Demo\demo.ps1 up -Set ready
```

### Linux и macOS

```sh
cd /path/to/ohw/Dz4
./Demo/demo.sh restore --set ready
./Demo/demo.sh up --set ready
```

Откройте **http://localhost:8503**. На боковой панели введите ключ API `demo-key-2026`, если
он не подставился сам. Дальше обязательно переключите домен на `it` (по умолчанию может
стоять `cinema`), задайте вопрос и нажмите «Спросить».

Первый ответ может идти **минуты**: в стенде работает настоящая модель 7B. На процессоре —
в несколько раз дольше. Это нормально, стенд не завис.

Проверить, что поднято и сколько узлов в базе:

```powershell
powershell -File Demo\demo.ps1 status -Set ready
```

```sh
./Demo/demo.sh status --set ready
```

Остановить:

```powershell
powershell -File Demo\demo.ps1 down -Set ready
```

```sh
./Demo/demo.sh down --set ready
```

### Почему сначала `restore`, а потом `up`

Тома Docker не лежат в git. На чистой машине набора `ready` просто нет, и `up --set ready`
создаст **пустой** том с этим именем. `restore` разворачивает архив из `Demo/fixtures/` в
тома; после этого `up` поднимает стенд уже с данными. Если набор уже развёрнут, повторять
`restore` не нужно.

`restore` затирает содержимое томов и на существующих спрашивает подтверждение.

## Что видно в UI

После ответа UI показывает:

- **Ответ** и время генерации;
- **глубину и лимит обхода** — что запрошено, что разрешено и сколько хопов реально
  пройдено;
- **«Вклад графа»** — сколько чанков граф добавил сверх векторной оси, сколько из них
  материализовано и сколько доехало в контекст, который получила модель;
- **источники** — документы с осью (`вектор` или `граф`) и меткой `graph_knowledge`.

### Как читать «Вклад графа»

Единица здесь — **чанк**, а не документ. Это важно: документная метрика `necessity` при
одном размеченном документе равна нулю по построению и не отвечает на вопрос «помог ли
граф». Поэтому UI показывает чанковый критерий, тот же, что описан в ADR-072:

- `graph-only` — чанки, которые граф добавил сверх векторной оси;
- **материализовано** — текст чанка был собран в контекст;
- **доехало в контекст** — текст реально вошёл в промпт модели, а не просто был найден.

Три состояния не смешиваются:

| что видно | что это значит |
|---|---|
| «Граф выключен» | ось не запускалась; это не нулевой вклад |
| «Граф не добавил ни одного чанка» | граф отработал, результат измерен и равен нулю |
| «Вклад графа не измерен» | ответ пришёл из кэша или в ответе нет нужных полей; это не ноль |

На наборе `ready` в вопросе G1 граф приносит graph-only чанки из `docs/05_adr_log.md`;
часть из них доезжает в контекст. Отдельная строка «Из 05_adr_log.md» показывает это
числом. На других вопросах и на другом наборе картина может быть иной — читайте числа,
а не переносите этот пример на всё.

Метки источников:

- `граф дал текст` (`contributed`) — чанк этого документа вошёл в контекст;
- `граф дошёл, текст не взят` (`reachable_unused`) — связь до документа есть, но его текст
  не попал в ответ;
- `граф не знает источник` (`blind`) — документа не было в графе;
- `не измерено` (`unknown`) — метки нет; это не `blind` и не `contributed`.

## Полный стенд и своя загрузка документа

Загрузка вынесена из основного стенда в отдельные скрипты (ADR-065). Так стенд запросов не
тащит ingestion-api, когда он не нужен.

Порядок для пустой базы:

```sh
./Demo/ingest.sh up --set empty
./Demo/ingest.sh load --path ./docs/00_hi_level_architecture.md --domain it
```

На Windows:

```powershell
powershell -File Demo\ingest.ps1 up -Set empty
powershell -File Demo\ingest.ps1 load -Path .\docs\00_hi_level_architecture.md -Domain it
```

`ingest.ps1` считает на видеокарте, `ingest-cpu.ps1` — на процессоре. На Linux и macOS
вариант один, процессорный: `ingest.sh`.

`load` принимает файл или папку. В папке берутся `*.md` и `*.txt` по алфавиту. Скрипт
спрашивает у сервиса, не загружен ли документ в текущем виде, ждёт конца джобы и
**проверяет, что граф вырос**. Последнее обязательно: джоба может завершиться `succeeded`
при пустом графе — это vector-only загрузка, и она не должна выглядеть как успех.

Загрузка идёт долго: измерено около **33 секунд на чанк** (`measured-load-time.md`), у
большого документа — часы. Для показа используйте готовый набор, а не загрузку с нуля.

После загрузки:

```sh
./Demo/ingest.sh down --set empty     # остановить стенд с ingestion-api
./Demo/demo.sh up --set empty         # поднять стенд запросов без ingestion-api
```

Данные остаются в томе `empty`: `down` не удаляет наполнение. UI снова на
http://localhost:8503.

### Можно ли загрузить документ прямо в UI

Да, если поднят `ingestion-api` (`ingest.sh up` / `ingest.ps1 up`): на вкладке «Документы»
появится форма загрузки. Но проверку «граф действительно вырос» делает только `load`.
Если джоба из UI завершилась `succeeded`, а графа нет, это vector-only результат, а не
доказательство работы графа. Для демонстрации надёжнее путь через `load`.

## Почему часть связей размечена вручную

**Об этом нужно знать при чтении любых измерений по этому стенду.**

Часть связей между сущностями разных документов внесена вручную, а не получена ингестом.
Причина — состояние проекта: надёжного ингеста кросс-документных связей в текущие планы
**не входит**. Цель работы — понять механизм графовой надстройки, а не полировать запись
данных. Собственный ингест даёт связи только внутри одного документа (замер 2026-10-17:
**0 из 759** связей имеют концы в разных документах), и на таком графе ретриверу нечего
предъявлять — нечем проверить, умеет ли он работать с такими связями.

Что из этого следует, и что не следует:

- Ручная разметка **не доказывает**, что система сама производит такие связи. Это измерение
  инструмента на данных, которые человек подготовил сам.
- Если ингест когда-нибудь научится делать такие связи, результат должен с ними совпасть —
  но это отдельная проверка, а не следствие текущего стенда.
- Связи, внесённые вручную, помечены признаком `origin: "user"`, и машинная запись их не
  перезаписывает. Это видно в самих данных, а не только в этом тексте.

Что ещё нужно решить, прежде чем такая разметка станет измерением: сколько связей и каких
типов (три разметки результата не дают) и как отличать их от извлечённых без догадок.
Записано в `docs/05_adr_log.md`, раздел «Идеи, ждущие решения».

## Наборы и фикстуры

| набор | что это |
|---|---|
| `empty` | пустая система. Тома создаются заново, в базе ноль узлов. |
| `ready` | набор с документами: на снимке 2026-10-18 — 1014 `ContextNode`, 515 `Chunk`, 2829 связей. Точные числа после `export` смотрите в `status`. |

Набора `ready` в репозитории нет — это тома Docker, а git хранит только файлы. Он
разворачивается из архивов в `Demo/fixtures/`:

| файл | что внутри | куда попадает |
|---|---|---|
| `ready-neo4j.tar.gz` (≈22,7 МБ) | граф, тексты чанков и **векторы** | том `ohw-runtime_ready_neo4j` |
| `ready-ingestion.tar.gz` (≈0,12 МБ) | реестр источников | том `ohw-runtime_ready_ingestion` |
| `ready-projection.tar.gz` (≈0,03 МБ) | состояние проекции | том `ohw-runtime_ready_projection` |

Векторы лежат внутри Neo4j, в свойстве `embedding` у узлов `Chunk`, поэтому отдельного
векторного хранилища нет: поиск по векторам работает сразу после `restore`. Реестр
источников обязателен — без него сервис не знает, что документы уже загружены, и повторная
загрузка создала бы вторую копию вместо no-op.

**Сами файлы документов** — это `docs/*.md` в репозитории, оттуда они и грузились. Копия,
попавшая в том при загрузке, удаляется сразу после успеха и намеренно не хранится.

Том `query` в архив не входит: в нём только журнал задач запросов, он пуст, и compose
создаст его при первом же вопросе.

Архив — снимок на дату. Он соответствует перечисленным документам на момент сборки. После
правки `docs/` он устаревает: обновляется командой `export`. Последняя ingestion-джоба в этом
снимке — 2026-10-18; правки `docs/` после этой даты в него не входят. Если вопрос требует
текста, добавленного в документацию позже, снимок может его не содержать — это ограничение
данных, а не поиска.

## Видеокарта или процессор

Разница ровно в одном — где считает языковая модель. На Windows есть оба варианта, на Linux
и macOS — только процессорный.

| | на видеокарте NVIDIA | на процессоре |
|---|---|---|
| Windows | `demo.ps1` | `demo-cpu.ps1` |
| Linux, macOS | — | `demo.sh` |
| нужно | видеокарта NVIDIA | ничего, кроме Docker |
| скорость ответа | минуты | десятки минут |

```powershell
powershell -File Demo\demo.ps1 up -Set ready          # Windows, видеокарта
powershell -File Demo\demo-cpu.ps1 up -Set ready      # Windows, процессор
```

```sh
./Demo/demo.sh up --set ready                          # Linux, macOS
```

На Linux и macOS скрипта для видеокарты нет: кто хочет считать на GPU, собирает команду
compose сам (ADR-065, пересмотр 2026-10-19).

Модель на видеокарте занимает примерно 5,35 ГБ VRAM, поэтому помещается в карту от 8 ГБ.
Число слоёв, отданных видеокарте, задаётся `LLM_NGPU_LAYERS`, по умолчанию **99** — вся
модель целиком. Значение нужно снижать только на карте меньше 8 ГБ.

Вариант на процессоре задаёт `LLM_NGPU_LAYERS=0` сам: без видеокарты значение 99
бессмысленно, и полагаться на то, что llama.cpp сам перейдёт на CPU, нельзя — молчаливое
решение за ресурс выглядело бы как «тормозит», а не как «считает не там».

**Почему нельзя просто переключить:** бронь устройства объявляется самим compose, и была
объявлена безусловно — на машине без драйвера NVIDIA Docker не может её удовлетворить, и
стенд не поднимется вообще. Перекрыть бронь сверху нельзя: проверено, что ни `devices: []`,
ни `devices: null` её не снимают. Поэтому бронь убрана из базового файла и вынесена в
`compose.runtime-gpu.yaml`, который подкладывают только GPU-скрипты.

Имя переменной `LLM_NGPU_LAYERS` единое для всех стендов — так оно было в eval, и оттуда
взято.

## Учётные данные

| что | значение |
|---|---|
| Neo4j, логин | `neo4j` |
| Neo4j, пароль | `local-stand-not-a-secret` |
| Ключ API, заголовок | `X-API-Key: demo-key-2026` |

Ключ вводится прямо в UI (поле `X-API-Key` на боковой панели). В Neo4j Browser
(http://localhost:7474) вход теми же данными.

Пароль базы **не меняется**: том создан один раз, Neo4j применяет `NEO4J_AUTH` только при
первом старте, и смена пароля означала бы пересоздание тома вместе со всем наполнением.
Значение задано в обоих скриптах и нигде больше.

## Если что-то не поднялось

- **Первый запуск на чистой машине иногда падает.** `embeddings-service` стартует дольше,
  чем отведённый ему healthcheck, и `docker compose --wait` успевает сдаться. Повторный
  запуск проходит, потому что сервисы уже подняты. Запустите ту же команду ещё раз.
- **Порт занят.** Стенд поднимается на фиксированных портах; если что-то уже слушает 8503
  или 8000, сначала освободите его.
- **Пустой том с именем `ready`.** Если запустить `up --set ready` без `restore`, compose
  создаст пустой том под этим именем, и база будет пустой при названии «с данными».
  Скрипт об этом предупредит.
- **Ответ идёт долго.** Это модель 7B, а не зависание. На процессоре ждать нужно дольше.
- **В UI нет вкладки загрузки.** ingestion-api не поднят; это штатно для `demo.sh` /
  `demo.ps1`. Загрузка живёт в `ingest.sh` / `ingest.ps1` (ADR-065).

## Что лежит в этой папке

Полный список. Документ, добавленный в `Demo/`, обязан появиться здесь: папка наполнялась
документами по мере надобности, и без списка они копились незамеченными.

**Важно для корпуса:** `Demo/` **не входит** в ингестируемые документы. Корпус — это каталог
`docs/` (проверяется `prototype/tests/test_ingest_corpus_exclusion.py`, сейчас 28 файлов).
Поэтому документ здесь не меняет то, что система ест, и не сдвигает retrieval посреди
ревью. Документ о приёмке нельзя класть в `docs/` именно по этой причине.

```text
POST /api/v1/glossary/validate                       8003
```

Пример. Поле называется `query`, не `question`:

```sh
curl -s http://localhost:8000/query \
  -H 'X-API-Key: demo-key-2026' \
  -H 'Content-Type: application/json' \
  -d '{"query": "из чего состоит пайплайн?"}'
```

Ответ приходит не сразу и не в этом ответе: `/query` возвращает только `task_id`, а сам
текст идёт потоком. Статусы задачи: `queued` → `running` → `succeeded`.

```sh
curl -N http://localhost:8000/query/tasks/<task_id>/stream \
  -H 'X-API-Key: demo-key-2026'
```

В потоке идут события: `status` со стадиями (`embedding` → `vector` → `rerank` → `llm`),
затем `token` с кусками ответа и `done` с источниками, `effective_retrieval` и `context`.

## Полезное

```sh
./Demo/demo.sh up --set empty                 # пустая система с нуля
./Demo/demo.sh export --set ready             # пересобрать архив после правки документов
./Demo/demo.sh restore --set ready            # развернуть архив заново
```

`export` останавливает Neo4j на время выгрузки и поднимает обратно. Если набор не запущен,
архив собирается из тома на диске.

## Что на этом наборе меряли

- [eval-questions.md](./eval-questions.md) — **список вопросов-кандидатов** для замера на

  по двум документам; (D) «не из доки» — пробы на выдумывание, правильный ответ «в контексте
  этого нет»; (E) **повторный вопрос** — время ответа и попадание в семантический кэш. В
  файле — что меряет каждая группа, как читать `necessity = 0`, команда прогона
