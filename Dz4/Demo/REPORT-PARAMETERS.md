# Отчёт о прогоне: параметры, метрики и что они значат

Справочник по тому, что попадает в артефакт прогона. Назначение — чтобы посторонний человек
прочитал `lift_report.json` и `qa_log.jsonl` и **не приписал отчёту того, чего в нём нет**.

Две незыблемые договорённости, из которых выведены все определения ниже:

1. **Ноль и «не измерено» — разные результаты.** Неизмеренная величина пишется `null`, а не
   `0.0`. Молчаливый ноль — это зафиксированный в проекте класс отказов.
2. **Знаменатель называется рядом с числом.** Доля без знаменателя не читается.

Всё ниже выписано по коду: `src/graphrag_proto/eval/metrics.py` (метрики),
`infra/eval/run_eval.py` (сборка артефакта), `retrieval/pipeline.py` и `retrieval/context.py`
(поля ответа). Форма можно сверить с реальным прогоном:
`prototype/reports/slice-control/`.

---

## 1. Из чего состоит прогон

| файл | что в нём |
|---|---|
| `run_manifest.json` | **кто, чем и по каким данным мерил**: коммит, дерево, домен, ревизия, корпус, настройки, флаги |
| `qa_log.jsonl` | по одной строке на вопрос: выдача, метрики, тайминги |
| `lift_report.json` | сводка по двум рукавам, `delta` между ними и `verdict` |
| `lift_report.md` | та же сводка для чтения глазами |
| `qa_review.md`, `PASSPORT.md` | разбор и паспорт прогона |
| `failures.jsonl` | вопросы, которые не были посчитаны; **пустой файл и отсутствующий файл — разные вещи** |
| `preflight.log`, `run_state.json` | состояние до и после прогона |

**Два рукава.** `baseline` — ось графа выключена. `target` — ось включена. Всё, что называется
«вкладом графа», есть разница между ними при прочих равных; поэтому конфигурация обязана
совпадать, и это проверяется отдельно (см. `config_drift`).

---

## 2. Идентичность прогона — `run_manifest.json`

Без этого блока остальные числа не привязаны ни к чему.

| поле | что означает |
|---|---|
| `run_id` | идентификатор прогона |
| `code_commit` | коммит, из которого мерили |
| `code_tree` | состояние рабочего дерева: замер с незакоммиченной правкой не воспроизводится по коммиту |
| `started_at`, `finished_at` | границы по времени |
| `domain` | домен профиля |
| `revision` | отпечаток среза данных, по которому считалось |
| `revision_source` | откуда взяли ревизию: `auto`, `none` или иное |
| `datasets` | путь к набору вопросов |
| `corpus_documents`, `corpus_documents_count` | что именно было загружено |
| `k` | глубина, по которой считаются метрики ретрива |
| `graph_enabled` | была ли ось графа включена в этом прогоне |
| `components`, `config`, `timeouts` | состав стенда и настройки |
| `projection` | путь конфигурации проекции, источник лизы |
| `projection_observed` | что проекция сообщила по факту |
| `golden_coverage` | покрытие золотого набора: `mode` + доли |
| `parity` | совпала ли ревизия до и после прогона |
| `flags` | флаги командной строки, фактически применённые |
| `note` | свободное поле для оговорок |

### `golden_coverage` — отдельного внимания

```json
{"mode":"unknown","reason":"corpus_composition_unavailable",
 "questions_total":12,"fully_covered":null,"partially_covered":null,
 "uncovered":null,"fully_covered_ratio":null}
```

Поле сообщает, **можно ли вообще делать вывод** по этому прогону. `mode: "unknown"` с причиной
означает, что состав корпуса не был доступен, и покрытие не вычислялось. Числа здесь — `null`
намеренно. `mode: "known"` означает, что покрытие посчитано и доли действительны.

Пока покрытие `unknown`, **отрицательный результат не является доказательством отсутствия
эффекта**: при неизвестном покрытии золотого набора «ничего не нашлось» и «набор не покрыт
корпусом» неразличимы.

### `parity` — ревизия не должна уехать

```json
{"revision":"stable","reason":null,
 "revision_before":"60b7…","revision_after":"60b7…",
 "projection":"d8fa…","projection_revisions":["d8fa…"]}
```

`revision: "stable"` означает, что данные не менялись, пока шёл прогон. Иное значение с
заполненным `reason` означает, что сравнение недействительно, и причина названа. Молчаливый
дрейф сделал бы `delta` смесью двух разных корпусов.

## 3. Ответ пайплайна — что вообще можно положить в отчёт

`retrieval/pipeline.py`, блок `done`. Это **не** метрики; это то, что система сообщает о
себе, и отчёт берёт значения отсюда.

| поле | что означает |
|---|---|
| `text` | текст ответа |
| `sources` | список источников — **метаданные ответа**, а не то, что читает модель |
| `retrieval_time_s`, `generation_time_s`, `total_time_s` | тайминги |
| `revision` | отпечаток среза, по которому считалось |
| `graph_degraded` | ось графа деградировала (проекция не готова, обход не удался) |
| `projection_status`, `projection_revision` | состояние проекции и её ревизия |
| `profile_fingerprint`, `profile_pinned_at`, `profile_staleness` | какая конфигурация применена и когда; `staleness` — разрешено ли считать её актуальной |
| `effective_retrieval` | **применённые** значения параметров, а не запрошенные |
| `config_fallbacks` | имена параметров, ушедших в значение по умолчанию |
| `usage` | настоящий расход токенов по модели; `null`, если провайдер не отдал, а не `0` |
| `cache_hit`, `cache_lookup_s` | попадание в кэш и время поиска |
| `context` | разбиение бюджета контекста (раздел 6) |

### `sources[]` — что значит каждый элемент

| поле | что означает |
|---|---|
| `source_url` | адрес источника |
| `axis` | какой осью найден: `graph` или `vector` |
| `relevance` | оценка источника в сформированном списке |
| `graph_knowledge` | что ось графа знала об этом источнике: `contributed` / `reachable_unused` / `blind` / `unknown` |
| `graph_knowledge_reason` | почему именно такой вердикт |
| `graph_linked_chunks` | сколько чанков источника связано с найденными сущностями |

Значения `graph_knowledge`:

- **`contributed`** — ось знала об источнике, и его текст попал в ответ;
- **`reachable_unused`** — ось достигла источника, но его текст в ответ не попал;
- **`blind`** — ось о документе ничего не знает;
- **`unknown`** — метрика не вычислялась.

Метка обязательна рядом с осью. Без неё «граф не помог» и «граф про этот документ ничего не
знает» в отчёте неразличимы — а это разные выводы при одном числе.

### `effective_retrieval` — применённое, а не запрошенное

```json
{"max_depth":3,"max_depth_requested":3,"max_depth_effective":3,"depth_clamped":false,
 "max_fanout":8,"max_graph_nodes":5,"graph_boost":0.0,"graph_source_relevance":1.0,
 "expansion_kinds":null,"expansion_direction":"both","graph_search_enabled":false,
 "context_limit":4096,"max_depth_allowed":3,"hops_traversed":0}
```

`max_depth_requested` и `max_depth_effective` разведены намеренно, а `depth_clamped` говорит,
было ли значение зажато ограничением. Иначе «применилось как просили» и «применилось с
ограничением» неразличимы.

## 4. Метрики ретрива — `retrieval`

Считаются по **уникальным** `source_url` из `done.sources`, берутся первые `k` (по умолчанию 5).
Дубли между осями устраняются по первому вхождению: иначе `recall` и `ndcg` способны превысить
1.0 и сместить рукав.

| метрика | определение |
|---|---|
| `recall_at_k` | доля золотых источников, попавших в первые `k`. **Знаменатель — размер золотого набора вопроса** |
| `precision_at_k` | доля релевантных среди первых `k`. Знаменатель — `k` |
| `mrr_at_k` | `1 / позиция` первого релевантного; `0`, если релевантного нет |
| `ndcg_at_k` | бинарная релевантность, идеал — `min(|golden|, k)` |
| `k` | глубина, по которой посчитано |

**Про что важно помнить.** Метрики читают `done.sources` — то есть **метаданные ответа**.
Они не описывают, какие фрагменты текста увидела модель. Модель читает другое: строки связей
и тексты чанков (раздел 6). Поэтому падение `recall@5` при включённой оси означает «список
источников стал хуже», и **не означает** само по себе, что ответ стал хуже.

## 5. Метрики генерации — `generation`

Считаются LLM-судьёй; при `--no-judge` или `--retrieval-only` не вычисляются и равны `null`.

| метрика | определение | знаменатель |
|---|---|---|
| `groundedness` | доля утверждений ответа, подтверждённых контекстом | число утверждений ответа (до 20) |
| `coverage` | доля золотых фактов, отражённых в ответе | число золотых фактов (до 20) |
| `hallucination_rate` | `1 − groundedness` | то же, что у groundedness |

`mode` объясняет, откуда взялись числа: `judge` (судья работал), `n/a` (судьи не было),
`skipped` (генерация отключена), `no_judge`, `empty` (пустой ответ или нет золотых фактов).

**Эти метрики зависят от судьи и от его настроек.** Судья — модель, и она имеет собственные
предпочтения. Известный класс отклонений, который ломает сравнение: **позиционный сдвиг** —
порядок предъявления двух ответов меняет вердикт судьи на десятки процентов, а сравнение
«метод с самим собой» после устранения этого сдвига может дать обратный результат. Поэтому
`groundedness` из разных прогонов нельзя сравнивать, если условия предъявления менялись.

## 6. Разбиение бюджета контекста — `context`

Самое молодое поле: добавлено, потому что без него два разных вреда были неразличимы.

Скелет входит в промпт **первым и не вытесняется**; текст тела получает остаток. Поэтому доля
скелета — это и есть цена, которую платит текст документа.

| поле | что означает |
|---|---|
| `skeleton_count` | сколько строк связей попало в промпт |
| `body_count` | сколько фрагментов текста попало в промпт |
| `dropped_chunks` | сколько фрагментов не поместилось |
| `skeleton_tokens` | оценка токенов в скелете |
| `body_tokens` | оценка токенов в теле |
| `total_tokens` | сумма |
| `max_tokens` | лимит бюджета |
| `skeleton_token_share` | `skeleton_tokens / total_tokens` |

**Как читать.** Если `skeleton_tokens > 0` и `dropped_chunks > 0`, ось графа заняла часть бюджета
и часть текста вытеснила — механизм вреда подтверждён. Если `skeleton_tokens == 0` или
`dropped_chunks == 0`, вытеснения не было, и падение `recall@5` объясняется другим.

**На кэш-попадании весь блок равен `null`.** Кэш отдаёт ранее собранный ответ, и в этом прогоне
контекст не собирался. Ноль означал бы «скелет и тело ничего не заняли», то есть утверждение о
прогоне, которого не было.

### Сводка `context_assembly` по рукаву

```json
{"mode":"measured","questions_measured":12,"questions_unknown":0,
 "avg_skeleton_tokens":…,"avg_body_tokens":…,"avg_skeleton_token_share":…,
 "total_dropped_chunks":…,"questions_with_dropped_chunks":…}
```

Три значения `mode`, которые **нельзя смешивать**:

| `mode` | что означает |
|---|---|
| `measured` | сборка выполнялась хотя бы раз, числа действительны |
| `cache_only` | все ответы из кэша: расход **неизвестен** |
| `not_assembled` | блока нет ни у одного ответа |

`cache_only` и `not_assembled` — это разные причины отсутствия данных, и обе выглядят как
«ноль», если их свести к одному.

## 7. Вклад оси графа — `graph_contribution`

Считается отдельно по каждой оси. Срез целевых вопросов — те, у которых в наборе помечено
`golden_graph_evidence = true`; на остальных вклад **не измеряется**.

| метрика | определение | знаменатель |
|---|---|---|
| `recall_graph` | доля золотых источников, найденных графовой осью | золотой набор вопроса |
| `recall_vector` | то же для векторной оси | золотой набор вопроса |
| `evidence_recall_graph` | `recall_graph`, усреднённая по целевому срезу | целевой срез |
| `necessity` | доля золотых источников, найденных **только** графом | золотой набор вопроса |
| `delta_recall` | `recall(обе оси) − recall(только вектор)` | — |
| `mode` | `measured` / `degraded` / `not_measured` | — |

**`necessity` — главная величина бандла.** Ноль означает: на этот вопрос ось графа не принесла
ничего, чего не принёс вектор. Но ноль на частично наполненном корпусе неоднозначен — он
означает и «ось не помогла», и «оси не было видно этих документов». Поэтому рядом всегда
идут поимённые счётчики:

- `blind_golden`, `blind_golden_count` — золотые документы, которых ось не видела вообще;
- `linked_golden`, `linked_golden_count` — золотые документы, о которых ось знала.

В сводке: `questions_with_blind_golden`, `questions_with_blind_golden_ids`, плюс `per_question`.

### Почему вне среза стоит ноль, а не `null`

Проектная конвенция — «ноль плюс флаг» (ADR-039): число остаётся вычислимым, а измерено ли
оно — читается по отдельному признаку `mode`. Причина практическая: `null` в JSON-артефактах
потребители часто проглатывают молча, и тогда «не измерено» выглядит как ноль. Основание
про обнуление: `test_plan.md` §5 — запуск на основном наборе даёт `necessity = 0`, и это
ложноотрицательный вывод, а не результат.

**Следствие, которое важно помнить:** `necessity = 0.0` вне среза — это не утверждение о том,
что ось бесполезна. Это утверждение о том, что на этом вопросе вклад не измерялся.

## 8. Сводка и вердикт — `lift_report.json`

```json
{"baseline":…,"target":…,"delta":…,"verdict":"n/a","verdict_reasons":[],
 "revision":…,"run_id":…,"created_at":…,"ingest_quality":…,"config":…,
 "parity":…,"manifest":…}
```

`delta` содержит `recall_at_k`, `groundedness`, `coverage`, `necessity`, `delta_recall`,
`evidence_recall_graph`. **Неизмеренная метрика в `delta` попадает как `null`, а не как `0.0`**
— иначе прогон без судьи показывал бы ложные нули.

Внутри рукава: `retrieval`, `generation`, `graph_contribution`, `context_assembly`,
`graph_axis_active`, `graph_axis_sources`, `projection_statuses`, `projection_revisions`,
`question_count`, `config`, `ingest_quality`.

| поле | что означает |
|---|---|
| `graph_axis_active` | ось фактически сработала хоть где-нибудь. Прогон, где проекция «готова», но ничего не дала, без этого флага неотличим от чистого |
| `graph_axis_sources` | сколько источников в выдаче помечено `axis=graph` |
| `projection_statuses` | состояния проекции, встретившиеся в прогоне |
| `question_count` | сколько вопросов посчитано |

### `verdict` — валютное правило

| значение | что означает |
|---|---|
| `pass` | `groundedness` и `coverage` в target не ниже baseline |
| `fail` | хотя бы одна из них ниже |
| `n/a` | судьи не было — валютное правило неприменимо |
| `invalid` | прогон несостоялся; причина обязана быть в `verdict_reasons` |

`invalid` выдаётся в двух случаях: **потеря LLM-слоя при ингесте** и **дрейф конфигурации
между рукавами**.

- Потеря слоя смещена в одну сторону: пропавшие факты нельзя ни найти, ни вспомнить, поэтому
  недооценка оси гарантирована, и «pass» по ней ничего не утверждает. Проверяются оба рукава:
  потеря в baseline смещает базу сравнения так же, как потеря в target смещает цель.
- `config_drift` означает, что рукава измерены разными настройками, и тогда `delta` измеряет
  «вклад графа плюс разницу между конфигами» — разделить эти части нечем.

`ingest_quality`:

```json
{"llm_layer_dropped_documents":0,"llm_layer_lost_entities":0,
 "llm_layer_lost_edges":0,"enrichment_degraded_documents":0,"loss":false}
```

`loss: true` означает, что часть слоя извлечения потеряна, и прогон недействителен для вывода о
качестве.

### `config` — идентичность конфигурации

| поле | что означает |
|---|---|
| `profile_fingerprint` | отпечаток профиля |
| `profile_pinned_at` | когда профиль был закреплён |
| `profile_staleness` | можно ли считать профиль актуальным |
| `config_drift` | разные ли настройки у рукавов |
| `config_fallbacks` | параметры, ушедшие в значение по умолчанию |
| `profile_fingerprints` | отпечатки по рукавам |
| `effective_retrieval` | применённые параметры |
| `modes` | сколько режимов в прогоне |

## 9. Строка вопроса — `qa_log.jsonl`

По одной строке на вопрос. Это детальный слой: сводка выше — среднее по нему.

| поле | что означает |
|---|---|
| `id`, `query`, `revision` | идентификация вопроса и среза |
| `mode` | режим прогона |
| `graph_enabled`, `graph_degraded` | состояла ли ось и деградировала ли |
| `projection_status`, `projection_revision` | проекция на момент вопроса |
| `graph_boost` | **применённый** подъём оценки, взятый из `done`, а не из трейса |
| `effective_retrieval` | применённые параметры этого вопроса |
| `seed_chunk_ids` | чанки, из которых взяты семена обхода |
| `graph_paths`, `graph_depths` | пути и глубины обхода |
| `golden_sources`, `golden_facts` | эталон |
| `golden_graph_evidence` | помечен ли вопрос как целевой для вклада оси |
| `retrieved[]` | выдача по элементам (см. 3) |
| `retrieval`, `generation`, `graph_contribution` | метрики вопроса |
| `blind_golden`, `linked_golden` | поимённые счётчики слепоты |
| `answer` | текст ответа |
| `timings` | `retrieval_time_s`, `generation_time_s`, `total_time_s` |

## 10. Как читать прогон и не сделать неверный вывод

1. **Сначала `verdict` и `verdict_reasons`.** `invalid` или `n/a` означает, что сравнение не
   работает, и никакая метрика ниже не выводится.
2. **Потом `golden_coverage`.** `mode: "unknown"` означает, что отрицательный результат не
   является доказательством отсутствия эффекта.
3. **Потом `parity` и `config_drift`.** Их нестабильность делает `delta` смесью разных корпусов
   или разных настроек.
4. **Метрики ретрива — про `sources`, а не про текст.** Падение `recall@5` говорит о списке
