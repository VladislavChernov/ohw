# Встраивание security wall в агентские среды — карта изучения

> Назначение: понять, **на каком уровне** встраивать защитную стену в агентскую
> среду и чем отличаются два случая — своя среда и готовый чужой инструмент.
> Это не инструкция по OpenCode, Claude Code или Hermes: они взяты как примеры
> разных точек интеграции.
>
> Статус: `Reference` для общей модели; `Runtime` — только там, где указан
> текущий стенд Dz5.
> Дата актуализации: 2026-10-23.

## Как читать

1. **Минимум:** чем wall отличается от прокси и почему одного слоя мало.
2. **База:** уровни L0–L6 и что каждый из них видит.
3. **Два случая:** своя среда и чужой инструмент.
4. **Проекция:** как это выглядит в Dz5.
5. **Углублённо:** политики, отказоустойчивость, антипаттерны и упражнение.

## 1. Минимальное понимание

**Wall — это не прокси и не sandbox.** В текущем стенде `security-wall` — это
Guardrails API, который принимает текст и возвращает `validationPassed`,
`validatedOutput` и `rawLlmOutput`. Прокси — это отдельный шлюз, который решает,
когда и с каким текстом вызвать wall.

Главная мысль:

> Защита ставится не «перед агентом вообще», а на **границы**, через которые
> проходят данные и действия.

У агентской среды обычно есть несколько таких границ:

- вход пользователя;
- запрос к модели;
- ответ модели;
- вызов инструмента;
- результат инструмента;
- доступ к файлам, сети, БД и секретам;
- RAG/MCP/память;
- логи и телеметрия.

Wall полезен на текстовых границах. Для tool execution нужны hooks/permissions,
а для файлов, сети и секретов — sandbox и права доступа. Один wall не заменяет
остальные слои.

### Почему нельзя просто «поставить стену перед агентом»

Если поставить wall только перед UI, можно не увидеть:

- indirect prompt injection из файла, RAG-документа или tool result;
- tool call, который агент сформировал и выполнил локально;
- второй запрос к модели в другом provider или subagent;
- streaming-ответ, который уже показан пользователю;
- запись в БД, которая произошла до следующей проверки.

Поэтому «перед агентом» — это не одна точка, а архитектурное решение о том,
где именно проходит каждый поток данных.

## 2. Ментальная модель: уровни встраивания

| Уровень | Где находится | Что видит | Что может блокировать | Что не видит |
|---|---|---|---|---|
| L0. Периметр | сеть, ingress, egress | кто и куда ходит | запрещённые домены и маршруты | смысл промпта |
| L1. Model gateway | между агентом и моделью | сообщения, tools, ответы | запрос/ответ модели, tool call до возврата агенту | локальное выполнение tool |
| L2. Agent middleware | внутри агента | hooks, сообщения, tool calls | сообщение, tool call, результат tool | syscalls и сеть |
| L3. Tool policy | перед инструментом | имя tool, аргументы, контекст | SQL, shell, URL, файл, параметры | текст, который модель уже показала |
| L4. Runtime sandbox | контейнер/VM/ОС | файлы, процессы, сеть | фактические операции | смысл запроса |
| L5. Data plane | RAG, MCP, память, БД | документы, записи, provenance | отравленные данные и опасные записи | поведение модели |
| L6. Observability | логи, audit, SIEM | события и следы | реакцию после инцидента | то, что не залогировано |

**Практическое правило:** чем ближе слой к действию, тем он надёжнее для
предотвращения ущерба; чем ближе к тексту, тем лучше он понимает намерение.
Поэтому нужна комбинация, а не выбор «или wall, или sandbox».

### Кто что реально защищает

- **Model gateway** ловит явные injection-паттерны и PII в запросе/ответе.
- **Agent middleware** может проверить tool call до выполнения.
- **Tool policy** не даёт выполнить `DROP TABLE`, `rm -rf`, `curl` на
  произвольный домен.
- **Sandbox** ограничивает последствия, если политика ошиблась.
- **Data plane** не даёт отравленному документу попасть в контекст без
  provenance и проверки.
- **Observability** нужна, чтобы отличить «заблокировали» от «не заметили».

## 3. Случай A: разрабатываем свою среду

Когда агент наш, можно проектировать границы сразу.

### 3.1. Контракты, а не «место в коде»

Нужно определить:

1. **Все входы:** пользователь, API, scheduled jobs, webhooks, другие агенты.
2. **Все выходы:** ответ пользователю, tool call, запись в БД, сеть, файлы.
3. **Все контексты:** system prompt, история, RAG, MCP, память, tool results.
4. **Все модели:** основной provider, fallback, embeddings, judge, subagents.
5. **Все инструменты:** кто исполняет — агент, отдельный сервис, MCP-сервер.

Wall встраивается в middleware, а не в один контроллер `/chat`. Иначе второй
endpoint или subagent обойдёт проверку.

### 3.2. Где ставить проверки

Минимальный набор для своей среды:

- **до модели:** проверить пользовательский ввод и **все** добавляемые
  tool/RAG-фрагменты;
- **после модели:** проверить текст и `tool_calls`;
- **перед tool:** проверить имя, аргументы и политику;
- **после tool:** проверить результат на indirect injection и утечки;
- **перед записью:** проверить SQL/команду и права;
- **в sandbox:** ограничить файловую систему, сеть и секреты.

### 3.3. Свой агент: что писать в коде

Не «вызвать wall где-то в chat», а иметь явные интерфейсы:

```text
ValidateInput(text, source) -> allow | block | modified
ValidateOutput(text, source) -> allow | block | modified
ValidateTool(name, args, context) -> allow | block
ValidateToolResult(name, result) -> allow | block | modified
```

Плюс политика отказа:

- `fail-closed`: wall недоступен → block;
- `fail-open`: только для явно некритичных путей, с метрикой и алертом;
- таймаут и размер входа — часть контракта;
- каждое решение логируется с `source`, `policy_version`, `run_id`.

### 3.4. Свой агент: чего не делать

- Не проверять только `system` и `user`, игнорируя `tool` и `assistant`.
- Не считать, что «модель уже отказалась» — это гарантия.
- Не давать агенту прямой доступ к prod-БД, если можно дать read-only.
- Не хранить секреты в environment агента, если он может выполнять shell.
- Не делать wall обязательным только на одном из нескольких provider.

## 4. Случай B: встраиваемся в готовый инструмент

Готовые среды различаются не названием, а **доступными точками расширения**.

### 4.1. Классы интеграции

| Класс | Что есть у инструмента | Что можно сделать |
|---|---|---|
| A. Open | смена `base_url`, hooks/plugins, MCP, permissions | model gateway + tool hooks + sandbox |
| B. Partial | можно сменить provider, но нет hooks | model gateway + sandbox/egress, слабее tool-контроль |
| C. Closed | нет смены endpoint и hooks | сетевой периметр, egress proxy, sandbox, DLP; wall может быть недоступен |

Это важнее конкретного продукта. OpenCode, Claude Code, Hermes и любой другой
агент нужно сначала отнести к A/B/C, а потом выбирать уровень.

### 4.2. Coding-агенты как отдельный случай

OpenCode, Claude Code и похожие среды:

- вызывают модель через API;
- выполняют shell, правят файлы, ходят в сеть;
- читают репозиторий и tool results, где может быть indirect injection;
- могут запускать subagents и MCP-серверы;
- работают с секретами, `.env`, SSH и токенами.

Для них model gateway полезен, но недостаточен. Даже идеальный input guard не
остановит `rm -rf`, если модель уже вернула tool call, а среда его выполнила.
Нужны:

- pre-tool hooks/permissions;
- sandbox с ограниченным FS и egress;
- отдельные credentials с минимальными правами;
- человеческое подтверждение для опасных операций.

### 4.3. Hermes и другие агентские платформы

Если платформа поддерживает OpenAI-совместимый endpoint, ставится gateway.
Если есть middleware/hooks — wall вызывается из них. Если есть только UI/CLI
без API — остаётся adapter или внешний sandbox, а часть проверок становится
black-box.

### 4.4. Чужой инструмент: что нельзя обещать

Нельзя обещать «мы защитили Hermes/OpenCode/Claude Code» только потому, что
поставили wall перед моделью. Корректная формулировка:

> Мы поставили контроль на границе модели и ограничили среду выполнения; для
> tool-level нужны hooks/permissions, иначе остаётся риск локальных действий.

## 5. Где именно ставится wall

### 5.1. Три варианта

| Вариант | Плюсы | Минусы |
|---|---|---|
| Gateway перед моделью | не меняет агент; централизованно; один для многих | не видит локальные tools; нужен протокольный адаптер |
| Middleware внутри агента | видит tools и контекст; точнее | нужно менять агент; легко обойти вторым путём |
| Sidecar/adapter | не трогает агент; можно добавить `/chat`-контракт | дополнительная точка отказа; надо маппить API |

Для своего агента обычно лучше middleware + tool policy. Для чужого — gateway
как минимальный слой, а hooks — если есть.

### 5.2. Что gateway обязан уметь

- принимать OpenAI/Anthropic/собственный формат;
- сохранять streaming и tool calls;
- проверять `system`, `user`, `assistant`, `tool` и RAG-фрагменты;
- не терять `tool_call_id` и порядок сообщений;
- поддерживать несколько provider'ов и fallback;
- возвращать ошибку fail-closed, а не пропускать трафик;
- логировать решение без секретов и PII;
- иметь версию политики и таймауты.

### 5.3. Streaming и tool calls

Это два места, где простые прокси ломаются:

- **streaming:** нельзя показать пользователю текст, который ещё не проверен;
  либо буферизуй, либо проверяй чанки с осторожной политикой;
- **tool calls:** нужно проверить имя, аргументы и контекст **до** выполнения;
  проверка только финального текста уже поздно.

## 6. Что проверять на каждом слое

| Политика | Вход | Выход | Tool | Sandbox |
|---|---|---|---|---|
| Prompt injection | да | да | косвенно | нет |
| PII/секреты | да | да | аргументы | секреты |
| SQL/команды | нет | tool call | да | да |
| Сеть | домены | URL | да | да |
| Файлы | пути | пути | да | да |
| Отравленный RAG | контекст | ответ | tool result | нет |
| Resource exhaustion | лимиты | лимиты | таймауты | cgroups |

Важно: **PII в ответе** и **PII в tool result** — разные проверки. Если
tool result уходит в контекст, его тоже надо проверять, иначе он может утечь
через следующий ответ.

## 7. Проекция на Dz5

В текущем стенде:

- `security-wall/config.py` — input/write/output guards;
- `agent/internal/agentcore/server.go` — вызовы `ValidateInput`,
  `ValidateOutput`, `ValidateSQL`;
- `agent/internal/agentcore/wall.go` — HTTP-контракт wall;
- `agent/fixed/sqlpolicy.go`, `agent/internal/agentcore/db.go` — жёсткие
  ограничения P5, которые не зависят от модели;
- `infra/compose.yaml` — `agent`, `agent-fixed`, `wall`, `ollama`.

Здесь хорошо видно разделение:

- **P4** — wall + встроенные проверки + prompt;
- **P5** — отдельная реализация с SQL allow-list, read-only БД и immutable
  settings;
- **wall не делает P5** и не заменяет tool policy.

Для чужой среды эту же схему можно перенести только частично: wall останется
текстовой проверкой, а tool-level нужно реализовать в самой среде или в adapter.

## 8. Антипаттерны

- **Wall только на UI.** Второй endpoint, subagent или CLI обходят.
- **Проверка только user-промпта.** Indirect injection приходит из tool/RAG.
- **Проверка только финального ответа.** Tool call уже выполнен.
- **Fail-open по умолчанию.** Падение стены становится обходом.
- **Regex как вся политика.** Ложные срабатывания и обходы.
- **Секреты в окружении агента.** Shell/tool может их прочитать.
- **Один provider из трёх.** Остальные идут мимо.
- **Нет audit trail.** Нельзя доказать, что проверка была.

## 9. Чек-пойнт «понял»

**Чек-пойнт:** объясни, почему model gateway не остановит `rm -rf`; назови
границу, на которой это делает tool policy; что изменится, если у агента
появится второй provider или subagent.

## Мини-словарь

- **Model gateway** — шлюз между агентом и моделью.
- **Middleware/hook** — точка внутри агента до/после сообщения или tool.
- **Tool policy** — правила на имя и аргументы инструмента.
- **Sandbox** — ограничение фактических действий процесса.
- **Indirect injection** — инструкция из tool/RAG/файла, а не от пользователя.
- **Fail-closed** — при ошибке проверки блокировать.
- **Choke point** — единственная обязательная точка прохождения трафика.
