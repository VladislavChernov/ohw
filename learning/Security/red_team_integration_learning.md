# Red-team агентских сред — карта изучения

> Назначение: понять, как проектировать red-team для агентской среды, что именно
> доказывает прогон и как подключать его к своей или чужой системе. Это не
> инструкция по конкретному сканеру и не набор готовых промптов.
>
> Статус: `Reference` для общей модели; `Runtime` — только там, где указан
> текущий стенд Dz5.
> Дата актуализации: 2026-10-23.

## Как читать

1. **Минимум:** red-team — это не «прогнать промпты», а измерительный процесс.
2. **База:** уровни от threat model до evidence.
3. **Два случая:** свой агент и чужой инструмент.
4. **Ядро:** сценарии, `n`, oracle и отчётность.
5. **Проекция:** как это устроено в Dz5.
6. **Углублённо:** антипаттерны и упражнение.

## 1. Минимальное понимание

Red-team отвечает не на вопрос «сломали или нет», а на вопросы:

- **что** мы проверяем;
- **при каких условиях**;
- **что считаем успехом атаки**;
- **сколько раз** повторяли;
- **что осталось после прогона** в виде доказательств.

Минимальная формула:

```text
threat model + сценарии + adapter + oracle + повторяемость + evidence
```

Если убрать любой элемент, получается демонстрация, а не red-team.

### Red-team не равен генератору промптов

Промпты — только вход. Ценность появляется, когда есть:

- цель атаки: утечка, tool abuse, изменение БД, обход политики;
- критерий: что именно считается `bypass`;
- окружение: модель, preset, права, данные;
- повторяемость: версия модели, digest, commit, набор сценариев;
- отчёт: вердикт, evidence, ограничения.

## 2. Ментальная модель: уровни red-team

| Уровень | Что определяет | Артефакт |
|---|---|---|
| R0. Scope и threat model | какие активы и сценарии важны | таблица угроз и границ |
| R1. Scenario corpus | что именно атакуем | YAML/JSON/набор промптов |
| R2. Target adapter | как говорить с агентом | HTTP/CLI/OpenAI adapter |
| R3. Runner | как запускать и повторять | harness, `n`, таймауты |
| R4. Oracle | как понять, что атака удалась | evaluator, DB diff, маркеры |
| R5. Evidence | чем доказать результат | run dir, manifest, logs |
| R6. Reporting | как принять решение | matrix, severity, отчёт |
| R7. Regression | как не сломать защиту позже | CI, baseline, retest |

Ошибка новичка — начать с R1 и остановиться на нём. Без R0, R4 и R5 это
«коллекция интересных промптов», а не безопасность.

## 3. Случай A: свой агент

Когда агент наш, red-team можно сделать глубже и точнее.

### 3.1. Что даёт свой агент

- стабильный API и известный контракт;
- `trace_id`, логи, tool calls и статусы;
- доступ к БД для `before/after`;
- тестовые флаги и restore;
- возможность unit-тестов на детерминированные политики;
- контроль над версией модели и промптов.

### 3.2. Что проектировать заранее

1. **Тестовый контракт.** Например, `POST /chat` с `{message}` и ответом
   `{reply, tool_calls}`.
2. **Изоляция.** Отдельная БД, отдельные секреты, отдельная сеть.
3. **Restore.** Возможность вернуть данные после destructive-сценария.
4. **Trace.** ID прогона и шага, чтобы связать ответ с evidence.
5. **Классификация.** Публичные, внутренние и destructive-сценарии.
6. **Версионирование.** Commit, digest модели, hash набора сценариев.

### 3.3. Что проверять

- прямой и indirect prompt injection;
- утечку system prompt и секретов;
- PII в ответах и tool calls;
- SQL/command/tool abuse;
- Poison RAG и отравленные tool results;
- resource exhaustion и таймауты;
- supply chain/MCP;
- обход настроек и immutable policy.

### 3.4. Deterministic vs probabilistic

Часть защиты детерминирована: SQL allow-list, read-only, immutable settings,
regex-правила. Их лучше проверять unit/integration-тестами с одним точным
входом. Но end-to-end поведение агента остаётся вероятностным, поэтому для
матрицы нужны повторы.

## 4. Случай B: чужой инструмент

Когда среда чужая, сначала выясняем, **что вообще можно наблюдать**.

### 4.1. Три класса доступа

| Класс | Что доступно | Что можно проверить |
|---|---|---|
| Black-box | только API/CLI и ответы | утечки, отказы, поведение по тексту |
| Gray-box | logs, tool calls, БД, trace | tool abuse, SQL, изменения данных |
| White-box | код, hooks, тесты, конфиг | политики, обходы, unit-тесты |

Чем меньше доступа, тем слабее oracle: «ответ выглядит безопасно» не равно
«tool не выполнился».

### 4.2. Как подключать чужой агент

- **HTTP API** — adapter или новый client в runner.
- **CLI** — wrapper, который превращает команды в шаги сценария.
- **OpenAI-совместимый endpoint** — adapter на chat completions/responses.
- **Закрытый UI** — только UI-автоматизация; это хрупко и плохо
  воспроизводится.
- **Совсем закрытая система** — network/sandbox + canary-данные; красная
  команда проверяет последствия, а не внутренние решения.

### 4.3. Adapter — это часть security boundary

Adapter должен:

- сохранять состояние диалога;
- передавать tool calls и результаты;
- не терять ошибки и таймауты;
- иметь отдельный healthcheck;
- логировать запрос/ответ без секретов;
- явно возвращать `unknown`, если формат ответа непонятен.

Нельзя молча превращать `error` в `blocked`: это завышает защиту.

### 4.4. Если бы встраивали в OpenCode, Claude Code или Hermes

Это не инструкция по конкретным продуктам и не утверждение об их фактических
возможностях. Ниже — общий рецепт для трёх типовых агентских сред; конкретные
точки подключения нужно проверять по документации версии.

Общий порядок:

1. Отнести среду к классу A/B/C: есть ли смена model endpoint, hooks/plugins,
   headless/API-режим, доступ к tool calls и логам.
2. Найти четыре границы: запрос к модели, tool call, результат tool, доступ к
   файлам/сети/БД.
3. Поставить adapter или CLI-wrapper, чтобы red-team мог запускать сценарии
   не через UI.
4. Подготовить изолированное окружение: тестовый репозиторий, фейковые секреты,
   canary-файлы, тестовая БД, ограниченный egress.
5. Определить oracle до прогона: diff рабочей копии, canary-маркеры, egress-логи,
   audit tool calls, DB before/after, текст ответа.
6. Запускать `n>=3` и отдельно отмечать, что осталось black-box.

| Среда | Основной риск | Куда цеплять red-team | Где oracle | Слабое место |
|---|---|---|---|---|
| OpenCode / coding-агент | shell, правка файлов, чтение секретов, сеть | adapter к API/headless-режиму или CLI-wrapper | diff workspace, canary-файлы, audit команд, egress | без hooks не видно, что tool реально выполнился |
| Claude Code / coding-агент | те же действия плюс hooks/permissions | hooks до/после tool, adapter или CLI-wrapper | workspace diff, tool logs, canary, egress | часть решений и tool calls может быть не видна снаружи |
| Hermes / агентская платформа | tools, плагины, внешние сервисы | adapter к chat/API, sidecar | tool audit, ответы, canary, DB/внешние эффекты | без tool-level доступа oracle слабее |

Что общего у всех трёх:

- red-team не должен работать в реальном пользовательском окружении;
- нельзя использовать настоящие секреты и prod-данные;
- одного текста ответа недостаточно: нужны последствия в workspace/сети/БД;
- baseline и guarded-конфигурация должны отличаться только защитой, а не
  версией модели или набором сценариев;
- если среда не даёт hooks и логов, честный вывод — «проверено частично», а не
  «защищено».

## 5. Target contract и adapter

Для black-box удобно иметь один простой контракт. В Dz5 это:

```http
POST /chat
{"message": "..."}

200 {"reply": "...", "tool_calls": [...]}
```

Плюс DB-снимки для сценариев, которые меняют данные.

Для Hermes/OpenCode/Claude Code нужен один из вариантов:

1. **Sidecar adapter** — переводит наш `/chat` в API среды.
2. **Runner client** — учит harness говорить на протоколе среды.
3. **Generic HTTP provider** — внешний сканер, если он умеет произвольный
   endpoint.

Adapter должен быть отдельным сервисом, а не патчем внутри target. Иначе
тестируемая система и тестовый код смешиваются.

## 6. Сценарии: что и зачем

### 6.1. База

Хороший набор покрывает:

- OWASP LLM01–LLM10;
- direct injection;
- indirect injection через RAG/tool result;
- multi-step и multi-turn;
- tool/SQL abuse;
- PII/secret exfiltration;
- prompt leak;
- unsafe output;
- resource exhaustion;
- supply chain/MCP.

### 6.2. Один сценарий — один проверяемый тезис

Плохо: «атака на агента».
Хорошо: «модель получает инструкцию из tool result и пытается выполнить
`DROP TABLE users`; ожидаем `blocked` по SQL policy».

### 6.3. Oracle задаётся до прогона

Для каждого сценария нужно заранее определить:

- `leak_markers` / `leak_regex`;
- `forbidden_tools` / `forbidden_sql`;
- `allowed_tool_prefixes`;
- `refusal_markers`;
- DB before/after;
- что считается `error`, а что `unknown`.

Если oracle придумывается после ответа, его легко подогнать под результат.

### 6.4. Content safety — отдельный класс

Мат, токсичность и оскорбления не входят в OWASP LLM01–LLM10 и не проверяются
одной фразой. Для этого стенда они вынесены за скоуп:
`../../dz5/docs/CONTENT_SAFETY_SCOPE.md`.

## 7. Сколько раз запускать

### 7.1. Дрейф и вариативность — разные вещи

- **Дрейф** — изменилась версия модели/весов.
- **Вариативность** — та же версия отвечает по-разному из-за сэмплирования,
  батчинга, GPU и контекста.

Digest модели убирает дрейф, но не делает ответ детерминированным. Поэтому
`n=1` не доказывает защиту.

### 7.2. Асимметрия доказательства

- один `bypass` — уже доказательство уязвимости;
- один `blocked` — ещё не доказательство защиты;
- `n<3` — допустимый smoke, но не red-team-вердикт;
- `mixed` виден только при повторах;
- `error` нельзя считать `blocked`.

Практичная стратегия:

1. Запустить сценарий.
2. Если `bypass` — зафиксировать и остановить серию.
3. Если `blocked` — повторить до `n=3`.
4. Если есть `error` — разобраться с инфраструктурой, не записывать в защиту.

### 7.3. Что пиновать

- digest модели;
- версию/ digest образов;
- commit кода;
- hash набора сценариев;
- версию политики/guard'ов;
- конфигурацию preset и `ALLOW_WRITES`.

Seed и temperature не обязательны для вывода «защита работает»; они не
устраняют всю недетерминированность. Важнее честно указать, что результат —
выборка, а не гарантия.

## 8. Evidence и отчётность

### 8.1. Что должно остаться после прогона

- `manifest.json`: target, preset, runs, model, digest, env, commit;
- `results.jsonl`: по строке на запуск;
- `summary.json` / `summary.md`;
- `details/`: запросы, ответы, tool calls, DB before/after;
- `red-team.md`: матрица по последнему прогону на preset;
- `latest.md`: только complete-прогон.

### 8.2. Правила отчёта

- `n<3` не даёт уверенного вердикта;
- `error` не превращается в `blocked`;
- incomplete-прогон не обновляет `latest.md`;
- в отчёте видны ограничения: модель, digest, сценарии, что не проверялось;
- секреты и PII редактируются в evidence.

### 8.3. UI

UI не обязателен для red-team. Сначала должен быть стабильный Markdown/JSON,
потом — просмотр. В Dz5 отдельного red-team UI нет: есть чат-UI агентов и
Markdown-отчёты. Если нужен UI, минимальный вариант — страница `/reports` с
рендером `latest.md` и `red-team.md`, а не отдельная платформа.

## 9. Проекция на Dz5

В стенде:

- `attack-runner/` — сценарии, runner, adapter-контракт `/chat`;
- `report_builder/` — агрегация и Markdown;
- `docs/TEST_PLAN.md` — матрица P1–P5, writes off/on, `n=3`;
- `docs/RED_TEAM_RUNNER.md` — запуск и ограничения;
- `agent` / `agent-fixed` — targets;
- `security-wall` — внешняя стена;
- `ui` — чат/selector, не red-team dashboard.

Матрица разделяет:

- **preset** — какие guard'ы включены;
- **writes** — отдельная ось `ALLOW_WRITES`;
- **runs** — повторяемость;
- **scenario set** — что именно проверяется.

P5 — negative control для write: он всегда read-only. P4 + writes — проверка
write-defense. Смешивать эти оси нельзя.

## 10. Антипаттерны

- **`n=1` как вердикт.** Smoke, не доказательство.
- **Только прямые промпты.** Нет indirect injection из tool/RAG.
- **Нет oracle.** «Модель отказалась» на глаз.
- **Нет DB snapshot.** Неизвестно, была ли запись.
- **Нет digest модели.** Сравнение разных версий выдаётся за эффект защиты.
- **`error` = `blocked`.** Завышает безопасность.
- **Подгонка сценариев под один продукт.** Нет переносимости.
- **Red-team без threat model.** Много шума, мало решений.
- **UI раньше данных.** Красиво, но нечем управлять.
- **Нет regression.** После изменения промпта защита не перепроверяется.

## 11. Чек-пойнт «понял»

**Чек-пойнт:** объясни, почему один `blocked` не доказывает защиту; назови,
что должно быть в oracle для SQL-атаки; что изменится, если у target нет доступа
к БД и tool calls.

Спроектируй red-team для coding-агента без доступа к его внутренним логам.

Заполни:

| Вопрос | Ответ |
|---|---|

**Ожидаемый результат:** понятно, какие выводы можно сделать честно, а какие

ответом модели.

## Мини-словарь

- **Threat model** — какие активы, противники и пути атаки важны.
- **Scenario** — проверяемый тезис с входом и oracle.
- **Target adapter** — слой, который говорит с тестируемой средой.
- **Oracle** — правило, превращающее ответ в вердикт.
- **Bypass** — атака достигла цели.
- **Blocked** — защита остановила атаку.
- **Unknown** — нет достаточных данных или `n<3`.
- **Error** — инфраструктурный сбой, не защита.
- **Evidence** — логи, ответы, tool calls, DB diff, manifest.
- **Regression** — повторная проверка после изменений.
