## 0. Исторический экскурс: кэш старше компьютерных кэшей

Идея «дорогой ответ считаем один раз, дорогой носитель держим рядом» появилась
задолго до RAM-кэшей:

| Годы | Событие | Суть |
|---|---|---|
| Античность-XX век | **Мемуар/справочник как кэш опыта** | «Не пересчитывай таблицу логарифмов» — идея мемоизации руками |
| 1946 | ENIAC: таблицы функций в перфокартах | Программная мемоизация до слова «кэш» |
| 1960-е | **Atlas (Manchester)**: paging, «one-level store» | Аппаратная виртуальная память — первый автоматический кэш страниц |
| 1965 | **Moore's Law** + иерархия памяти | Появился сам конфликт: быстрое память дорогое, дешёвая медленная |
| 1980-90-е | CPU L1/L2/L3 кэши | Локальность доступа (time/space) — теория, на которой стоят все кэши |
| 1995-2000s | Web: прокси-кэши, **HTTP-кэширование** (RFC 2616 → 9111) | Инвалидация как распределённая задача: ETag, max-age, revalidation |
| 2003 | **Memcached** | «Кэш как сетевой сервис» — общий пул RAM для ферм |
| 2009 | **Redis** | Структуры данных (HASH/SORTED SET/...) в памяти — кэш стал «мини-БД» |
| 2010s | CDN повсюду | Кэш на границе сети; инвалидация по подписке/пуржу |
| 2024 | **Valkey** (форк Redis, BSD, Linux Foundation) | Тот же протокол; в Dz4 — именно он |

Сквозная закономерность: каждое новое поколение систем (CPU → web → микросервисы →
LLM) **заново изобретает одни и те же проблемы** — инвалидация, свежесть, stampede,
«что класть в ключ». Различаются только носители.

**Теория:**
- **Wikipedia: Cache (computing)** — https://en.wikipedia.org/wiki/Cache_(computing) —
  обзор иерархии и терминов.
- **DDIA** (Kleppmann), гл. 3 — как хранилища LSM/B-tree уже «содержат» кэш внутри себя.

**Чек-пойнт «понял»:** объясни, чем HTTP-кэш 1999 года принципиально не отличается
от семантического кэша 2024-го — а чем отличается (подсказка: ключ).

## 1. Где вообще кэши в LLM-стеке (карта 2023-2026)

LLM-система кэширует на **пяти разных уровнях** — это разные кэши с разными ключами:

| Уровень | Что кэширует | Ключ | Инвалидация |
|---|---|---|---|
| **KV/prompt cache** (инференс) | attention-состояния префикса | префикс токенов (exact) | вытеснение по VRAM |
| **Provider prompt caching** | префикс промпта на стороне API | префикс | автоматически, скидка на повтор |
| **Embedding cache** | векторы уже эмбеддеренных текстов | hash(text)+модель | по смене модели |
| **Семантический кэш ответов** | готовые ответы | вектор запроса, cos ≥ порога | TTL + epoch-bump ревизии |
| **HTTP/CDN** | ответы API как целое | URL+заголовки | по заголовкам |

Ключевое отличие семантического кэша: **ключ неточный**. Классические кэши —
exact-match; семантический — «похожий запрос» по косинусу. Отсюда уникальные
проблемы: ложные hit'ы, выбор порога, дорогой lookup (скан векторов, а не O(1) хэш).

**Теория:**
- **GPTCache** — https://github.com/zilliztech/GPTCache — первый массовый семантический
  кэш; README честно разбирает пороги и ложные hit'ы.
- **Anthropic: Prompt caching** — https://docs.anthropic.com/en/docs/build-with-claude/prompt-caching

**Чек-пойнт «понял»:** почему prompt caching провайдера — exact-match, а семантический
кэш — fuzzy? Какой безопаснее для корректности ответа и почему?

## 2. Анатомия семантического кэша Dz4 (чтение кода)

`prototype/src/graphrag_proto/retrieval/semantic_cache.py` — минимальная, но полная
реализация канонических решений:

| Решение | Где в коде | Какая боль |
|---|---|---|
| Ключ `query:sc:<rev>:<domain>` | `_key()` | Инвалидация по ревизии: bump → новый слой, старый дочищает TTL (ADR-026) |
| Поле = sha256 вектора запроса | `_field()` | Стабильный id записи без коллизий |
| Payload {embedding, text, sources, ts} | `_payload()` | Hit возвращает `done` без пайплайна; **граф/чанки в кэш не едут** |
| Порог cos ≥ 0.85 | `_DEFAULT_THRESHOLD` | Компромисс hit-rate vs ложные ответы |
| «Плохие ответы не кэшируем» | `should_cache_text()` | Пустые/отказные ответы не закрепляются |
| Fail-open при сбое Valkey | try/except | Сбой кэша ≠ сбой запроса |
| Счётчики в Valkey (`:meta`, HINCRBY) | `_bump()` | Переживают рестарт, общие для воркеров |
| Долг: HGETALL + линейный косинус | `lookup()` | O(N) на hit; план замены — ниже |

**План ухода от линейного скана** (зафиксирован как техдолг прототипа):

1. Бакетирование по coarse-хэшу (LSH-стиль) — скан только своего бакета;
2. Нативный ANN в Valkey 8.x (vector sets);
3. Либо semantic cache на векторной БД (Qdrant/pgvector, фильтр по домену/ревизии) —
   один движок на векторы чанков и запросов.

Замена не затрагивает контракт (`lookup/store/threshold/revision`) — меняется только
реализация, по тому же принципу изоляции, что оси retrieval.

**Чек-пойнт «понял»:** открой `semantic_cache.py`: что попадёт в кэш, если LLM ответил
«контекста недостаточно»? Что вернёт lookup при падении Valkey? Почему COMMIT не
инвалидирует кэш напрямую?

## 4. Сквозные упражнения

1. Сопоставь эры из §0 с уровнями из §1: какой уровень LLM-кэша прямой наследник
   HTTP-кэша? А какой — CPU-кэша?
2. Порог 0.85 в Dz4: придумай два запроса, которые дадут ложный hit при 0.85, но не
   дадут при 0.95. Что изменится в hit-rate при поднятии порога?
3. Почему в payload кэша лежит embedding запроса, а не собранный контекст (скелет+тело)?
   Что бы изменилось, если бы кэшировали контекст?
4. Ревизия домена изменилась (bump): что видит пользователь, обратившийся с тем же
   запросом через 1 минуту после COMMIT? А через 2 часа?
5. Valkey упал на 30 секунд. Что видят пользователи, и какие счётчики врут? Почему
   сбой-пути не увеличивают misses (см. docstring модуля)?
6. Придумай eviction-политику для семантического кэша сверх TTL: когда TTL недостаточно
   и что ограничивать вместо/вместе с ним (подсказка: объём, домены, LRU по полям).
