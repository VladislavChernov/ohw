# Консистентность в распределённых системах — карта изучения (методички)

Всплывает из Вехи 4-хвост: «bounded staleness», «глобальная vs по-доменная
ревизия», доставка ревизии (polling vs events). Это распределённые системы —
область обширная, но нам нужен только прикладной срез: **как читатель видит
данные, которые пишет другой компонент**.

**Как читать:** по порядку; каждый раздел — методичка + чек-пойнт. Многое дублирует
`caching_freshness_learning.md` — не переживай, что пересекается: здесь взгляд
«системный», там — «кэш-центричный».

---

## 1. Один закон, который всё объясняет: CAP

- **Wikipedia: CAP theorem** — https://en.wikipedia.org/wiki/CAP_theorem
  (и «Expanded CAP» из DDIA[^1], глава 9).
- Суть для нас: между *con* (прочитать «окольным путём») и _consistency_ (все видят
  последнее) всегда компромисс. Наш семантический кэш — осознанно «**eventually
  consistent, с окном TTL**»; ревизия сужает это окно без отказа от долгого
  кэширования.

**Чек-пойнт:** сформулируй, что мы выбрали (доступность кэша + ограниченное окно)
и чем это отличалось бы от «сильной консистентности» (инвалидация «как в индексе»).

---

## 2. Модели консистентности: от строгой к eventual

- **Wikipedia: Consistency model** — https://en.wikipedia.org/wiki/Consistency_model
- **DDIA[^1]**, глава 5 (replication lag) и глава 9 — лучший текст, который читается
  последовательно, а не по диагонали.

Термины, которые нужно уметь назвать:

| Термин | Одно предложение |
|---|---|
| Strong consistency / linearizability | все читатели видят результат каждой операции одинаково |
| Eventual consistency | в итоге сойдёмся |
| **Bounded (bounded-loop) staleness** | не старше, чем окно (время/версия) — **наша цель** |
| Read-your-writes / monotonic reads | частные гарантии для отдельного клиента |

**Чек-пойнт:** отметь, где в нашем query-контуре какая модель (registry —
диктование; кэш — eventual + TTL; с появлением `rev` — bounded).

---

## 3. Как доставлять изменения: polling vs push (наша развилка 3)

- **Wikipedia: Push technology** — https://en.wikipedia.org/wiki/Push_technology
- **Wikipedia: Pull technology** — https://en.wikipedia.org/wiki/Pull_technology
- Практикум: сравнение «webhooks vs polling» легко найти в любом приличном
  конспекте API-дизайна (у Stripe/GitHub в доках явно описаны webhooks-модели).

Проекция на наш случай:

| Свойство | Polling (наш `_topology_rebuilder`, и ревизия данных) | Events (Redis Streams) |
|---|---|---|
| Простота доставки | простая (retry, перезапуск = переспроси) | сложнее (потеря событий, компенсация) |
| Задержка | = интервал опроса | малая |
| Работа в inmemory-режиме | да | нет |
| Один механизм на контур | да (уже есть по топологии) | нет (второй транспорт) |

**Чек-пойнт:** объясни, почему для нашей системы (кэш-допущение TTL как нижняя
граница свежести) задержка polling-а приемлема.

## 4. Идемпотентность, fingerprint, сравнение «двух систем» (веха-источник)

- **Content-addressable storage** — https://en.wikipedia.org/wiki/Content-addressable_storage
- **Merkle tree** — https://en.wikipedia.org/wiki/Merkle_tree
- **idempotence** — https://en.wikipedia.org/wiki/Idempotence

Здесь ключевой сдвиг: «ревизия данных» ≠ «счётчик изменений». Счётчик говорит
«изменилось N раз», отпечаток — «вот текущее состояние». Для сравнения двух
окружений (эталон vs прод, до vs после) нужен именно отпечаток.

**Чек-пойнт:** почему «переиндексация того же контента» не должна менять ревизию
(идемпотентность, ADR-014), и какой из двух вариантов это гарантирует.
