# CLAUDE.md — воркфлоу разработки для этого проекта

Адаптированная версия opencode-скиллов `.opencode/` для AI-ассистента (Cline/Claude),
работающего с `light-llm-engine`. Воркфлоу «spec-first»: сначала OpenSpec-пачка,
потом код, потом самопроверка. Код на английском, документация и спеки — на русском.

Этот файл открывает ассистент автоматически, когда пользователь работает в этой
папке. Применяй его для любой работы с проектом.

---

## Конвенции проекта (из `openspec/project.md`)

- Спеки: `openspec/changes/<change>/{proposal,design,tasks}.md` + дельты
  `specs/<capability>/spec.md`. Требования в EARS-стиле: ДОЛЖНА/ОБЯЗАНА + сценарии
  `WHEN ... / THEN ...`.
- Код и комментарии — на английском; README, спеки, коммит-сообщения — на русском
  там, где это уместно.
- Стек: Python 3.13, `uv`, `httpx`, `pydantic`, `pytest`. Exit codes CLI:
  0 — ок, 2 — аргументы/файлы, 3 — ollama недоступна, 4 — не удалось получить ответ.
- Конфиг: `light-llm-engine.toml` + env `OLLAMA_*` + CLI (приоритет именно такой).

## Полный цикл работы над фичей: PROPOSE → APPLY → REVIEW

### Шаг 1. PROPOSE (создать спецификацию раньше кода)

Используй перед началом новой возможности. Создай пачку вручную (без CLI):

1. Имя change — kebab-case, глагол+сущность, напр. `add-request-engine`.
2. Путь: `openspec/changes/<name>/`.
3. `proposal.md` — структура (по образцу `dz2/openspec/changes/*`):
   `# Proposal: <title>` → `## Зачем` → `## Что делаем` → `## Ограничения`
   → `## Изменения` → `## Impact`.
4. `tasks.md` — чек-лист `- [ ]`, задачи мелкие, проверяемые, упорядоченные.
5. `design.md` и `specs/<capability>/spec.md` — только если изменение нетривиально
   (несколько файлов / изменение поведения). Для простых правок хватит `proposal+tasks`.
6. Не создавай код на этом шаге — только спец-пачку.

### 2. APPLY (реализовать по tasks.md)

- Сначала прочитай `openspec/changes/<name>/{proposal,design,tasks}.md`.
- Проверь тулчейн проекта до и после каждой задачи:
  ```bash
  uv run pytest -q
  uv run ruff check .
  uv run mypy src
  ```
- Делай изменения поэтапно, минимально и сфокусированно (одна задача за раз).
- Отмечай `- [x]` только после реальной проверки, не «на глаз».
- Если реализация вскрывает изъян в спеке — остановись и предложи поправить пачку,
  а не угадывай поведение.

### 3. REVIEW (самокритический разбор перед коммитом), а не после

Адаптированный «злой ревьюер» из `agent/reviewer.md` — выполняется на текущем diff:

- Ревьюер **read-only**: смотрит, но не редактирует код и не пушит.
- Ищи evidence-first: подкрепляй каждую претензию фактом (файл:строка, трейс).
- Работает на текущем diff (`git diff HEAD` + staged).
- Проверяет: задачу из tasks.md реально закрыта проверка (`pytest`/`ruff`/`mypy`),
  покрытие тестами, соблюдение конвенций/стеков, отсутствие «волшебных» дефолтов
  и секретов.
- Метки: `[BUG]` — подтверждённый дефект, `[NIT]` — мелочь. Решай `[BUG]` до коммита.

**Порядок завершения работы:** APPLY всё → ПОЛНЫЙ тулчейн → REVIEW diff →
исправить подтверждённые `[BUG]` → перепроверить → коммит → push (только по
запросу пользователя).

## Техника работы

- Не фиксируй `input/`, `output/`, `.venv`, кэши, lock-копии (все в `.gitignore`).
- Переменные/пути в тексте ищи через инструменты, не догадывайся.
- Уважай приоритет конфига: defaults < TOML < env `OLLAMA_*` < CLI.
- Логика первого шага: осмотри `openspec/changes/` и `tasks.md`, дополнительно выбери
  активный change (если один — берём его).
