# ai-testcase-generator

Dz2 — основной проект домашки: CLI-утилита на Python, которая с помощью
локальной LLM через ollama генерирует по файлам требований пять видов
артефактов: тест-кейсы, чек-листы, тест-планы, QA-отчёты и матрицы покрытия
требований. Для каждого входного файла создаётся markdown-отчёт.

Тексты промптов готовит [Dz7](../dz7/): они лежат во внешних шаблонах
`prompts/<type>.txt`, а не в коде; переиспользуемые дополнения к промпту —
в пресетах `presets/*.toml`.

Кроме CLI есть рабочее место на Streamlit: требования → промпт → генерация →
чат-доработка → оценка качества артефакта. Оба фронта вызывают одно ядро
`ai_testgen.service`, поэтому поведение совпадает.

## Как это работает

```
docs/                 output/
├── business-…md ──►   ├── business-….md   # 10 тест-кейсов (6 позитивных, 4 негативных)
└── …                    └── …
        │
        ▼
   ollama (GPU) → валидация ответа → retry при нарушениях → markdown-отчёт
```

- Источник требований по умолчанию — `docs/` (`docs/business-requirements_catalog-courses.md`).
- Каждый файл из `--input-dir` обрабатывается независимо; для батча удобно держать зеркала в `input/` (он в `.gitignore`).
- URL сайта берётся из текста файла; аргумент `--url` переопределяет его для всех файлов.
- Коллизия имён (`auth.md` + `auth.txt`) — ошибка: удалите или переименуйте один из файлов.

## Типы артефактов

Тип артефакта объявляется во front-matter в начале входного файла;
без front-matter файл считается тест-кейсами:

```
---
type: checklist
---
Сайт: https://example.com/catalog
Зоны проверки: навигация, поиск, пагинация...
```

| `type` | Ответ модели | Что проверяется |
|---|---|---|
| `testcases` | JSON `{"cases": [...]}` | каждый кейс проходит pydantic-схему; количество равно `--count`; негативные кейсы появляются всегда, когда запрошено 2 и больше (минимум один), а при N≥5 их должно быть не меньше трети; у каждого кейса поле `requirement` со ссылкой на проверяемое требование |
| `checklist` | Markdown-документ | линт: зоны как `## ` заголовки, под каждой ≥1 пункт списка; пункты завершаются номером требования `(BR-N)` |
| `testplan` | Markdown-документ | линт: обязательные разделы (цели, объём, подход, критерии, риски) непусты; объём перечисляет охваченные BR |
| `qareport` | Markdown-документ | линт: разделы «Введение», «Тестовые сценарии», «Дефекты», «Рекомендации» непусты |
| `coveragematrix` | Markdown-документ | линт: раздел «Матрица покрытия требований» и Markdown-таблица покрытия |

Синонимы в `type`: `testcase`, `qa_report`, `qa-report`, `coverage_matrix`,
`coverage`, `traceability`; регистр и разделители не важны.

Нарушения формата отправляются модели на исправление (`--max-retries`);
после исчерпания попыток — код выхода 4. Для markdown-типов `--count`
игнорируется.

Трассировка: если во входном файле требования пронумерованы (BR-1,
BR-2, …), каждый тест-кейс получает ссылку на проверяемое требование,
пункты чек-листа заканчиваются его номером, а тест-план перечисляет
охваченные требования в разделе объёма.

## Внешние промпты

User-prompt каждого типа собирается из отдельного файла
`prompts/<type>.txt`; в коде текстов промптов нет. В шаблоне доступны
плейсхолдеры:

| Плейсхолдер | Значение |
|---|---|
| `{url}` | URL сайта; если он неизвестен, строка `Target site: {url}` удаляется |
| `{count}` | запрошенное число тест-кейсов |
| `{count_noun}` | `test case` / `test cases` в зависимости от числа |
| `{positive}` / `{negative}` | число позитивных / негативных кейсов |
| `{requirement_rule}` | правило трассировки; пусто, если в требованиях нет `BR-N` |
| `{content}` | текст требований |
| `{extra}` | блок «Additional instructions» из выбранных пресетов; пустая строка, если пресеты не выбраны |

Строки шаблона, начинающиеся с `#`, считаются комментариями и в промпт не
попадают. Литеральные фигурные скобки (пример `{"cases": [...]}`) не
затрагиваются подстановкой.

Каталог шаблонов ищется так: `--prompt-dir` / `[paths] prompt_dir` →
`DZ2_PROMPT_DIR` → `./prompts` → `prompts` в корне репозитория → пакетный
каталог. Явно указанный каталог (CLI или конфиг) проверяется строго: если
его или файла нужного типа нет, утилита завершается с кодом 2 **до**
обращения к Ollama. Молчаливого отката на старый встроенный промпт нет.

Промпты можно подготовить в Dz7. Для штатного каталога `dz2/prompts`
копируются шаблоны как есть — Dz2 подставит требования каждого входного
файла:

```bash
cd ../dz7
python3 generator.py --emit-templates --output-dir ../dz2/prompts
```

Готовый промпт под конкретный файл требований (подстановки уже выполнены)
удобно сложить в отдельный каталог и передать его через `--prompt-dir`:

```bash
cd ../dz7
python3 generator.py --input-dir ../dz2/examples/input \
    --requirements-file login.md --all-types --output-dir output/rendered
cd ../dz2
uv run ai-testgen -n 5 --input-dir examples/input --prompt-dir ../dz7/output/rendered
```

Каталог шаблонов ищется так же, как пресеты: явный аргумент → переменная
окружения → `./prompts` → корневой `prompts` → пакетный каталог.

### Пресеты: готовые примеры запросов

Пресет — это TOML-файл с дополнительными инструкциями по конкретной теме
(граничные значения, негативные сценарии, доступность, валидация ввода,
регрессия, локализация). Выбранные пресеты Dz2 подставляет в `{extra}`:

```toml
id = "boundary-values"
label = "Граничные значения"
types = ["testcases", "checklist", "coveragematrix"]
text = """
Add boundary-value scenarios derived from the requirements: empty result set,
exactly one item, pagination boundaries, the longest input, ...
"""
```

Перед списком инструкций `{extra}` всегда добавляет guard: пресет уточняет
требования, но не добавляет страницы, функции и данные, которых в них нет, и
не меняет обязательный формат вывода. Это защищает от дрейфа вроде
`example.com`/логин/корзина на странице каталога курсов.

```bash
# показать, что есть
uv run ai-testgen -n 10 --input-dir docs --preset boundary-values --preset accessibility
```

- `types` ограничивает применимость: выбрать пресет для неподходящего типа —
  ошибка с кодом 2 **до** обращения к Ollama.
- `id` обязан совпадать с именем файла.
- Если шаблон не содержит `{extra}`, а пресет выбран — тоже ошибка: молча
  игнорировать инструкции нельзя.
- Каталог пресетов: `--presets-dir` / `[paths] presets_dir` →
  `DZ2_PRESETS_DIR` → `./presets` → корневой `presets` → пакетный каталог.
- Источник правды — `dz7/presets`; копируются в Dz2 без изменений:

  ```bash
  cd ../dz7
  python3 generator.py --emit-presets --output-dir ../dz2/presets
  ```

### Явный выбор типа артефакта

Front-matter удобен для батча, но не для разового запуска. Переопределить тип
можно аргументом `--type`, а получить сразу все пять артефактов — `--all-types`:

```bash
uv run ai-testgen -n 10 --input-dir docs --type checklist
uv run ai-testgen -n 10 --input-dir docs --all-types   # 5 файлов на каждый входной
```

Имена файлов в `output/`:

| Режим | Имя |
|---|---|
| тип из front-matter | `<stem>.md` |
| `--type` / `--all-types` | `<stem>.<type>.md` |

Так повторный запуск с другим типом не затирает предыдущий артефакт.

### Матрица покрытия и тест-кейсы

Матрица — единственный артефакт, который ссылается на другой: в колонке
`Test Case IDs` должны стоять реальные номера, а не придуманные. Поэтому
`--all-types` передаёт в промпт матрицы список уже сгенерированных в этом же
прогоне кейсов — `TC-NN (тип, BR-N): заголовок`.

Если матрица запрошена отдельно (`--type coveragematrix`) и кейсов нет, промпт
прямо говорит: «No test cases have been generated for these requirements yet»,
а правило требует поставить `—` и `Not Covered`. Выдуманных `TC-01…TC-14` в
таком прогоне быть не может: в шаблоне нет даже примера с номерами.

В рабочем месте то же правило: матрица берёт кейсы последнего артефакта
`testcases` для этого же файла, а без них показывает подсказку и собирает
промпт с `—`/`Not Covered`.

### Оценка качества промпта (LLM)

Рубрика ДЗ7 ставится не человеком, а отдельным запросом к той же локальной
модели: судья видит **текст промпта** (не артефакт) и возвращает балл 1–5 и
комментарий с цитатой. Запрос идёт с `temperature=0.0`, чтобы повторные прогоны
были сравнимы, и **отдельно на каждый критерий**: один вызов — один критерий со
своей рубрикой. Так модель не может «уравнять» все четыре оценки и не копирует
числа из примера (первая версия с общим JSON-образцом выдавала 3/4/4/3 на всех
десяти промптах).

Перед баллом судья обязан привести 3–5 дословных цитат из промпта. Каждая
цитата проверяется на вхождение в текст: допускаются различия в регистре и
пунктуации, выдуманная цитата отбрасывается, а ответ без единой реальной цитаты
считается ошибкой (код 5). Исключение — балл 1: если элемента в промпте нет,
цитировать нечего, и комментарий называет то, чего не хватает. На ответ без
цитат с баллом выше 1 отводится до трёх попыток с напоминанием копировать
текст. Это не педантизм: без такого шага 7B-модель писала «absent» вместо
чтения и ставила 1 за читаемость всем промптам подряд.

```bash
# пять базовых промптов → output/quality/<type>-<run-id>.json
uv run ai-testgen -n 10 --input-dir docs --all-types --evaluate

# промпт с пресетом → имя файла включает пресет
uv run ai-testgen -n 10 --input-dir docs --type qareport \
    --preset negative-scenarios --evaluate
```

`--evaluate` ничего не генерирует: он только собирает промпт и вызывает судью.
В JSON лежат `scores`, `comments`, `evidence`, `summary`, `average`, `model`,
`presets`, `judge_version`, `judge_temperature`, `prompt_sha256` и
`created_at`; по `prompt_sha256` видно, что оценивался именно текущий промпт, по
`judge_version` — какой рубрикой. В интерфейсе то же делает кнопка «Оценить
через LLM» на вкладке 5; ручная правка остаётся как возможность не согласиться
с моделью.

## Требования

- Локальный запуск: [uv](https://docs.astral.sh/uv/) (сам установит Python 3.13
  при первом запуске) **или** уже установленный Python 3.13+ с pip,
  плюс доступный сервис ollama с моделью
- Запуск через Compose: Docker (для общего ollama — любой; для автономного
  GPU-режима — NVIDIA CUDA или AMD ROCm, см. «Запуск через Docker Compose»)

## Быстрый старт (локально)

```bash
# установка uv, если ещё нет:
curl -LsSf https://astral.sh/uv/install.sh | sh

uv sync --dev
uv run ai-testgen -n 10
```

Пути берутся из конфига по умолчанию (`input_dir = "docs"`,
`output_dir = "output"` в `ai-testgen.toml`): положите файлы требований
в `./docs` (там уже лежит `business-requirements_catalog-courses.md`) —
отчёты появятся в `./output`. Можно переопределить
ключами:

```bash
uv run ai-testgen -n 10 --input-dir my-requirements --output-dir reports
```

В каталоге `examples/input` лежат примеры входных файлов (тест-кейсы
для авторизации и корзины) — это демонстрация формата, не рабочий
материал:

```bash
uv run ai-testgen -n 5 --input-dir examples/input --output-dir output
```

Готовые ответы модели для этих же запросов лежат рядом —
`examples/output/response_auth.md` и `response_cart.md`
(сгенерированы `qwen2.5:7b-instruct`, `-n 5`). Их можно посмотреть
без запуска LLM; при повторной генерации ответы будут отличаться.

Модель и адрес ollama берутся из `ai-testgen.toml` в корне репозитория;
при необходимости переопределите их переменными окружения или CLI-аргументами:

```bash
export OLLAMA_MODEL=llama3.1:8b   # вместо модели из конфига
```

## Рабочее место (Streamlit)

CLI хорош для батча, но чтобы посмотреть и поправить промпт, нужен интерфейс.
`ai-testgen-ui` поднимает локальное рабочее место с пятью вкладками:

| Вкладка | Что делает |
|---|---|
| 1. Требования | загрузка `.md`/`.txt` (один или несколько файлов), выбор файла, правка текста, URL, счётчик `BR-N` |
| 2. Промпт | тип артефакта, `--count`, пресеты, редактируемый текст промпта, скачивание |
| 3. Результат | генерация через то же ядро, что и CLI, просмотр markdown, скачивание, сохранение в `output/` |
| 4. Чат с LLM | доработка артефакта диалогом; ответ становится новой версией только по кнопке «Применить как новую версию» и проходит ту же валидацию |
| 5. Оценка | LLM ставит оценки 1–5 по рубрике ДЗ7 (читаемость, контекстность, чёткость целей, покрытие) → `output/quality/<type>[-<preset>]-<run-id>.json`; если артефакт уже сохранён в `output/`, в оценку попадает ссылка на него (путь, sha256, размер), а в панели его можно скачать; человек может скорректировать и сохранить (`source=human`) |

```bash
uv sync --dev                 # streamlit входит в dev-группу
uv run ai-testgen-ui          # http://localhost:8501
```

Модель и адрес Ollama выбираются в боковой панели, и оба — двумя способами:

- адрес: готовые варианты (`localhost`, контейнер `ohw-ollama`, Docker Desktop
  `host.docker.internal`) либо «Свой адрес» с ручной правкой поля;
- модель: кнопка «Загрузить модели» (`GET /api/tags`) заполняет список
  скачанных, а «Другая модель (ввести вручную)» оставляет обычное поле ввода.

Если модель из конфига на новом адресе не найдена, после загрузки списка
подставляется первая доступная. В свёрнутом блоке «Параметры генерации» —
температура и таймаут запроса: на CPU-инференсе `qwen2.5:7b` одного артефакта
можно ждать несколько минут.

Требования загружаются на вкладке 1 как файлы (`.md`/`.txt`), как в
`QA_RAG_Studio`: каталог указывать не нужно. Можно перетащить несколько
файлов и переключаться между ними; содержимое сразу попадает в редактируемое
поле, а имя файла используется в именах артефактов.

Промпт во вкладке 2 — обычный текст: его можно дописать под конкретную задачу,
и на генерацию уйдёт именно отредактированная версия. Пресеты при этом
пересобирают промпт из шаблона.

## Без uv: системный Python + общий ollama

Если на машине уже стоит Python 3.13+, uv не обязателен — поднимите общий
ollama из [`infra/`](../infra/README.md) и установите пакет через pip:

```bash
# из корня монорепо: поднимает компоненты из dz2/infra.yaml
./infra/up.sh dz2
# или на Windows: .\dz2\scripts\up-cpu.ps1  (поднимет и UI, см. ниже)

pip install ./dz2
ai-testgen -n 10 --input-dir dz2/examples/input --output-dir dz2/output
```

Per-project ollama не нужен: порт `11434` принадлежит общему `ohw-ollama`,
`ai-testgen.toml` уже указывает на `http://localhost:11434`.

## Запуск в Docker

Образ проекта собирается от общего базового образа `ohw-python:3.13`
(`infra/python/`), а не от голого `python:3.13-slim-bookworm`. Один и тот же
образ `ohw/dz2:local` содержит и CLI, и рабочее место: extra `ui` только
добавляет Streamlit, поэтому второй образ не нужен.

```bash
# базовый образ — один раз на машину
../infra/python/build.sh              # ohw-python:3.13

# образ проекта — один раз (кэш переиспользуется)
docker build --build-arg "EXTRAS=--extra ui" -t ohw/dz2:local .
```

Внутри контейнера рабочая папка `/data`: требования монтируются в `/data/docs`,
выход появляется в `/data/output`. Шаблоны промптов и пресеты уже скопированы
в образ (`/app/prompts`, `/app/presets`), а монтирование `./prompts` и
`./presets` позволяет подменить их без пересборки.

Разовая генерация CLI — тем же образом:

```bash
docker run --rm --network ohw_net \
  -v ./docs:/data/docs:ro \
  -v ./output:/data/output \
  -e OLLAMA_BASE_URL=http://ohw-ollama:11434 \
  -e OLLAMA_MODEL=qwen2.5:7b-instruct \
  ohw/dz2:local -n 10
```

## Запуск через Docker Compose

Проект использует **общую инфраструктуру** из каталога
[`infra/`](../infra/README.md): компоненты (сейчас — `ollama`) описываются
один раз в [`infra/compose.yaml`](../infra/compose.yaml) и поднимаются по мере
надобности. Объявление проекта лежит в [`infra.yaml`](infra.yaml):
`components: [ollama]`. Compose проекта поднимает **только приложение** и
переиспользует один образ `ohw/dz2:local` для `app` и `ui`.

Стенд запускается скриптами из `scripts/` — они сами проверяют Docker (и
NVIDIA для GPU), собирают базовый образ при необходимости, поднимают
компоненты из `infra/` с нужным оверлеем, собирают проект и ждут health.

```powershell
# Windows: CPU или GPU (NVIDIA)
.\scripts\up-gpu.ps1          # GPU, рекомендуется
.\scripts\up-cpu.ps1          # CPU, медленно
.\scripts\up-gpu.ps1 -Rebuild # принудительная пересборка образа проекта
.\scripts\down.ps1            # остановить UI; -Infra — ещё и общий ollama
```

```bash
# Linux / macOS: CPU или GPU (NVIDIA)
./scripts/up-gpu.sh           # GPU, Linux; на macOS предупредит и поднимет CPU
./scripts/up-cpu.sh           # CPU, любой Linux/macOS
./scripts/up-gpu.sh --rebuild # принудительная пересборка образа проекта
./scripts/down.sh             # остановить UI; -i — ещё и общий ollama
```

После старта: UI — `http://localhost:8501`, ollama — `http://localhost:11434`.
`./docs` монтируется только на чтение, `./output` — на запись (артефакты и
JSON рубрики), `./prompts` и `./presets` — на чтение.

GPU-оверлей — [`infra/compose.gpu.yaml`](../infra/compose.gpu.yaml) (NVIDIA
CUDA). Без него инференс идёт на CPU (qwen2.5:7b ≈ 2–4 токена/с) — при полной
генерации поднимите таймаут запроса в UI или `timeout` в `[ollama]`
(например, до 600 секунд). На macOS Docker Desktop не пробрасывает NVIDIA GPU
в Linux-контейнеры: скрипт предупредит и поднимет стенд на CPU; для Metal
поставьте родную сборку [Ollama](https://ollama.com/download) и запускайте
через uv.

Полезные варианты:

```bash
docker compose -f ../infra/compose.yaml ps  # статус общего ollama
docker compose run --rm app -n 5            # разовая генерация с другим количеством
```

- Модель хранится в общем volume `ohw_ollama_models` и переживает перезапуски;
  скачивается один раз для всех проектов.
- Имя модели задаётся в `infra/.env` (`OLLAMA_MODEL=...`).
- Адрес службы: хост `http://localhost:11434`, devcontainer
  `http://host.docker.internal:11434`, compose (сеть `ohw_net`) — `http://ohw-ollama:11434`.

## Конфигурация

Параметры складываются из четырёх слоёв (нижний имеет наименьший приоритет):

```
defaults  <  ai-testgen.toml  <  переменные окружения OLLAMA_*  <  аргументы CLI
```

Файл `ai-testgen.toml` ищется в текущем каталоге автоматически (или укажите
`--config <path>`); отсутствие файла ошибкой не считается.

```toml
[ollama]
base_url = "http://localhost:11434"
model = "qwen2.5:7b-instruct"
timeout = 180.0

[paths]
input_dir = "docs"
output_dir = "output"
prompt_dir = "prompts"
presets_dir = "presets"

[generation]
temperature = 0.7
max_retries = 3
```

| Переменная | По умолчанию | Описание |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` (хост, из `ai-testgen.toml`) | адрес сервиса ollama; для devcontainer `http://host.docker.internal:11434`, для compose-сервиса `http://ohw-ollama:11434` |
| `OLLAMA_MODEL` | — (или `model` в конфиге) | имя установленной модели |
| `DZ2_PROMPT_DIR` | — | каталог шаблонов промптов; приоритетнее `./prompts`, но ниже `--prompt-dir` и `[paths] prompt_dir` |
| `DZ2_PRESETS_DIR` | — | каталог пресетов; приоритетнее `./presets`, но ниже `--presets-dir` и `[paths] presets_dir` |

### Аргументы CLI

| Аргумент | По умолчанию | Описание |
|---|---|---|
| `-n`, `--count` | — (обязательный) | тест-кейсов на каждый файл типа `testcases`; для чек-листов, планов, QA-отчётов и матриц игнорируется |
| `--config` | `./ai-testgen.toml` | путь к TOML-конфигу |
| `--input-dir` | из конфига (`./docs`, `/data/docs`) | папка с файлами требований (.md/.txt) |
| `--output-dir` | из конфига (`./output`, `/data/output`) | папка для markdown-отчётов |
| `--prompt-dir` | `./prompts` | папка с шаблонами `<type>.txt` |
| `--type` | из front-matter | сгенерировать указанный тип для всех файлов (переопределяет front-matter) |
| `--all-types` | выкл. | сгенерировать все пять типов для каждого файла |
| `--preset` | — | id пресета из каталога пресетов; можно указывать несколько раз |
| `--presets-dir` | `./presets` | папка с TOML-пресетами |
| `--url` | из текста файла | URL тестируемого сайта |
| `--max-retries` | из конфига (`3`) | повторные попытки при невалидном ответе модели |
| `--temperature` | из конфига (`0.7`) | температура сэмплирования |
| `--testcases-file` | — | файл со списком уже существующих кейсов (`- TC-07 (positive, BR-3): …`); нужен промпту матрицы покрытия, чтобы ссылаться на реальные номера. В `--all-types` кейсы и так передаются автоматически |
| `--evaluate` | выкл. | не генерировать артефакты, а попросить LLM оценить собранный промпт по четырём критериям и сохранить JSON в `output/quality/<type>[-<preset>]-<run-id>.json` (судья вызывается отдельно на каждый критерий, `temperature=0.0`, обязан привести 3–5 дословных цитат из промпта); если рядом уже лежит `<stem>.<type>.md`, в JSON попадает ссылка на него с sha256 |

`--type` и `--all-types` взаимоисключающие.

## Коды выхода

| Код | Значение |
|-----|----------|
| 0 | успех |
| 2 | ошибки аргументов, конфига или входных файлов (нет папки, пусто, коллизия имён, битый `--config`, модель не задана ни в env, ни в конфиге, нет шаблона/пресета, пресет выбран для неподходящего типа) |
| 3 | сервис ollama недоступен |
| 4 | не удалось получить валидный артефакт (кейсы/чек-лист/план/QA-отчёт/матрица) за все попытки |
| 5 | судья вернул ответ, который не разбирается как рубрика 1–5 (`--evaluate`) |

## Разработка

VS Code: откройте проект и выполните «Dev Containers: Reopen in Container» —
окружение (Python 3.13, uv, доступ к Docker) настроится автоматически.

```bash
uv sync --dev                      # установка зависимостей
uv run pytest -m "not integration" # unit-тесты (включая UI на Streamlit AppTest)
uv run pytest -m integration       # интеграционные (нужен живой ollama,
                                   # модель — в OLLAMA_MODEL; иначе skip)
uv run ruff check . && uv run mypy src tests
```

UI-тесты не требуют ни Ollama, ни браузера: `AppTest` прогоняет скрипт
приложения, а `OllamaClient.chat_messages` подменяется в тесте.
