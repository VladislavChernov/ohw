# Design: детерминированная нормализация требований

## Поток данных

```
docs/<file>.md ──bytes──► decode_bytes ──► split_front_matter
                              │                    │
                              ▼                    ▼
                       кодировка (utf-8,      текст без front-matter
                       utf-16, cp1251, cp866)
                                                   │
                                                   ▼
                                             normalize_text
                                    (заголовок → URL → требования)
                                                   │
                                                   ▼
                                    NormalizationResult
                                    (text, url, encoding,
                                     requirements, warnings)
                                                   │
                     ┌─────────────────────────────┴────────────┐
                     ▼                                          ▼
      CLI: --normalize-only / --normalize            UI: вкладка «Требования»
      output/normalized/<stem>.md                     предпросмотр + переключатель
                     │                                          │
                     └──────────────► RequirementDoc ◄──────────┘
                                            │
                                            ▼
                              prompt.py / handlers.py (BR-N)
```

Нормализация стоит **до** сборки промпта: шаблоны и валидаторы не меняются,
они получают уже канонический текст.

## Канонический документ

```markdown
# <заголовок>

**URL:** https://example.com/path

<вступление: всё, что было до первого требования, кроме заголовка и URL>

## Requirements

### BR-1
<текст требования>

### BR-2
<текст требования>
```

Почему так:

- `## Requirements` — на этот раздел ссылается правило `_requirement_rule` и
  шаблоны («from the Requirements section»);
- `### BR-N` — заголовки того же вида, что и во входных примерах
  (`examples/input/login.md`), и нормализатор их же распознаёт при повторном
  прогоне, поэтому результат идемпотентен;
- вступление сохраняется: цель, аудитория и контекст полезны модели, а
  выбрасывать их — терять контекст;
- если URL не найден, строка `**URL:**` не пишется, а в предупреждениях
  появляется «URL не найден».

## Порядок извлечения

Стратегии пробуются по порядку; используется **первая**, давшая хотя бы одно
требование. Смешивать источники нельзя: документ с таблицей-сводкой и
подробными `## BR-N` разделами должен читаться по разделам, а не задваиваться.

| # | Что распознаём | Пример | Источник текста |
|---|---|---|---|
| 1 | заголовки `BR-N` | `## BR-1 Вход по email` | остаток заголовка + тело до следующего заголовка |
| 2 | Markdown-таблица с ID | `\| ID \| Описание \|` | остальные ячейки строки через ` — ` |
| 3 | список под разделом «Требования»/«Requirements» | `- вход по email` | пункт списка (+ вложенные строки) |
| 4 | строки, начинающиеся с `BR-N` | `- BR-1: вход` | текст после ID |
| 5 | абзацы (fallback) | обычный текст | абзац целиком, с предупреждением |

Правила идентификаторов:

- явные `BR-N` сохраняются как есть — на них уже могут ссылаться артефакты;
- если у части требований ID нет, им выдаются следующие свободные номера
  (`BR-1`, `BR-2`, …) в порядке появления;
- дубли ID отбрасываются (остаётся первое вхождение), в предупреждениях
  перечислены отброшенные;
- требование с пустым текстом отбрасывается с предупреждением.

## Определение кодировки

1. BOM: UTF-32 (`FF FE 00 00`, `00 00 FE FF`), UTF-16 (`FF FE`, `FE FF`),
   UTF-8 (`EF BB BF`).
2. Строгий UTF-8.
3. cp1251 и cp866 — обе декодируют любые байты, поэтому выбирается вариант с
   большим числом русских букв и меньшим числом «мусорных» символов
   (`¤`, `®`, `„`, `Є` и т. п.). При равенстве — cp1251.

Эвристика нужна именно из-за пары cp1251/cp866: байты `84 AE AA E3 AC A5 AD
E2 A0 E6 A8 EF` в cp1251 дают `„®Єг¬Ґ­в жЁп`, а в cp866 — `документация`.
Именно так был испорчен `dz7/docs/NORMALIZER.md` в ветке `normalizer`.

UTF-8 остаётся поведением по умолчанию для `load_docs`; определение кодировки
включается флагом `--normalize` и всегда работает в UI.

## Детерминизм

- Никаких LLM, времени, случайности и обращений к сети: одинаковые байты и
  аргументы дают одинаковый результат.
- Порядок требований — порядок появления в документе; нумерация — по этому же
  порядку.
- Нормализация не переписывает формулировки: только раскладка, пробелы,
  переводы строк, регистр заголовков не меняется.
- `normalize(normalize(x)) == normalize(x)` — проверяется тестом.

## CLI

| Флаг | Поведение |
|---|---|
| `--normalize` | декодировать и нормализовать каждый входной файл в памяти; в модель уходит канонический текст; на диск ничего не пишется |
| `--normalize-only` | только нормализовать и записать файлы, без обращения к Ollama; `-n` не требуется |
| `--normalized-dir DIR` | куда писать при `--normalize-only` (по умолчанию `<output-dir>/normalized`) |

Почему `--normalize` не пишет на диск: выходной каталог — это артефакты
прогона; неожиданные файлы ломают ожидания `output/*.md`. Кто хочет сохранить
нормализованный вход — запускает `--normalize-only`.

Почему не отдельная подкоманда: CLI исторически одноуровневый (`ai-testgen -n
10`), и добавление подкоманд ломает существующие вызовы и скрипты стенда.
Флаги расширяют контракт, не меняя его.

## Рабочее место

На вкладке «Требования» после полей ввода:

- кнопка «Нормализовать» — запускает `normalize_text` на текущем тексте и URL;
- результат хранится в `st.session_state["normalization"]` вместе с sha256
  исходного текста: если пользователь правит текст после нормализации,
  предпросмотр помечается устаревшим и не подставляется в промпт;
- показываются определённая кодировка, число требований, стратегия и
  предупреждения;
- предпросмотр — две вкладки `st.tabs(["Исходный", "Нормализованный"])` с
  `st.code`, поэтому существующие `text_area`-индексы не сдвигаются;
- переключатель «Использовать нормализованный текст в промптах» (по умолчанию
  выключен) определяет, какой текст уходит в `RequirementDoc.content`;
- если в тексте нет ни одного `BR-N`, показывается предупреждение о потере
  трассировки — это и есть основной сценарий, ради которого нужна кнопка.

Почему не автоматом: нормализация меняет текст, который пользователь видит и
правит; скрытая подмена входа в промпт противоречит принципу «видно, что ушло
в модель». Кнопка и предпросмотр делают изменение явным.

Почему не заменяем редактор: ручная правка требований остаётся главным
способом исправить формулировку; нормализация лишь раскладывает её по
канонической структуре.

## Отклонённые альтернативы

- **LLM-нормализатор.** Недетерминирован, переписывает формулировки, и тогда
  трассировке нельзя доверять: непонятно, то ли требование, что было в
  источнике.
- **Нормализация всегда включена.** Молча меняет вход и ломает сравнение
  прогонов «до/после»; хуже, скрывает ошибки формата вместо того, чтобы их
  показать.
- **Запись нормализованных файлов в `input_dir`.** Следующий запуск подхватил
  бы их как новые входы и задвоил требования.
- **Перенумерация всех ID подряд.** Ломает ссылки в уже сгенерированных
  артефактах и внешних документах.
- **Отдельный формат без `## Requirements`.** Шаблоны и правило `BR-N` уже
  завязаны на этот раздел; менять контракт ради нормализатора — лишний риск.
