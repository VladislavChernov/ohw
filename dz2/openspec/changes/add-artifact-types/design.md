# Design: типы артефактов и форматы ответа

## Контекст

Пайплайн: input_doc → prompt → ollama_client → validator → renderer.
Сегодня всё жёстко JSON. Нужно протащить понятие «тип артефакта + формат
ответа» через все звенья, не сломав 54 существующих теста и обратную
совместимость.

## Решения

1. **Front-matter в входном файле, а не имя файла или CLI-флаг.**
   Имена ненадёжны, флаг не работает для батча со смешанными типами.
   Парсится в `input_doc`: блок `---` ... `---`, единственный ключ `type`.
   Отсутствие → `testcases`; неизвестное значение/битый блок → `InputError`.

2. **Формат — свойство типа, а не настройка.**
   `testcases` = JSON (машинная проверка полей кейсов), `checklist` и
   `testplan` = markdown (документ читает человек). Пользователь не
   выбирает формат вручную — он следует из сущности.

3. **Реестр хендлеров вместо if-цепочек.**
   `HANDLERS: dict[ArtifactType, ArtifactHandler]`, хендлер несёт:
   `build_prompt`, `validate_response`, `render_section`, `wants_json`
   (флаг для клиента). Новый тип = новая запись. cli плоский: хендлер →
   цикл retry → рендер.

4. **Markdown-валидация — структурный линт, а не парсинг AST.**
   Полноценный markdown-парсер не нужен; проверяем контракт, который сами
   диктуем промптом:
   - срез ограждений ```` ```markdown ... ``` ```` (модели их любят);
   - ответ не является JSON (иначе — «wrong format» issue, частый отказ
     модели от роли);
   - обязательные заголовки разделов присутствуют и имеют непустое
     содержимое до следующего заголовка;
   - у чек-листа под каждой зоной ≥1 пункт списка `- `/`* `.
   Список обязательных заголовков живёт в хендлере типа и ТОЙ ЖЕ
   константой вставляется в промпт — промпт и линт не могут разойтись.
   Семантику текста линт не оценивает (это за пределами автоматики) —
   финальный арбитраж за человеком.

5. **Клиент ollama: `format="json"` только для JSON-типов.**
   Сейчас клиент всегда шлёт `format:"json"` — для markdown это ломало бы
   вывод на корню (ollama принудительно генерировал бы валидный JSON).
   Хендлер объявляет `wants_json`; параметр запроса собирается из него.
   temperature/max_retries остаются общими.

6. **Рендер документов — passthrough.**
   Тело markdown после успешного линта вставляется в отчёт под общей
   шапкой без перекройки (мы его уже структурировали промптом). Сводная
   секция отчёта печатает тип артефакта; count — только для testcases.

7. **`--count` игнорируется молча для нетест-кейсовых типов** (батч со
   смешанными типами — штатный сценарий).

## Риски

- Модель может прислать план с «примерными» заголовками («Цели» вместо
  «Цели тестирования») → линт вернёт issue, retry-промпт перечислит
  недостающие заголовки по именам — на практике qwen исправляется.
- Линт пропустит бессмысленный, но структурно верный текст — осознанный
  компромисс: автоматика проверяет форму, смысл проверяет человек.

## Альтернативы

- Всё через JSON-схемы (первая версия этого change) — отвергнуто: документы
  в JSON вырождаются, маленькая модель чаще ломает большой JSON, чем короткий
  markdown-контракт из 5 заголовков.
- Определение формата по содержимому ответа LLM — отвергнуто: недетерминизм,
  лишний запрос, тип и так известен из front-matter.
