# Delta Spec: testcase-generator

## ADDED Requirements

### Requirement: CLI-запуск с указанием количества тест-кейсов

Программа ДОЛЖНА запускаться из командной строки и принимать обязательный
аргумент — количество генерируемых тест-кейсов (целое число больше нуля).

#### Scenario: Генерация 10 тест-кейсов

- **WHEN** пользователь запускает `ai-testgen --count 10`
- **THEN** программа запускается и целевое количество кейсов принимается равным 10

#### Scenario: Отрицательное или нулевое значение количества

- **WHEN** пользователь запускает программу с `--count 0` или `--count -3`
- **THEN** программа завершается с кодом 2 и сообщением об ошибке, не обращаясь к LLM

### Requirement: Входная и выходная папки

Программа ДОЛЖНА читать файлы требований из входной папки (`--input-dir`,
по умолчанию `./input`, в контейнере `/data/input`) и записывать результаты
в выходную папку (`--output-dir`, по умолчанию `./output`, в контейнере
`/data/output`). Пути к отдельным файлам вручную не указываются.

#### Scenario: Значения по умолчанию

- **WHEN** пользователь запускает `ai-testgen --count 10` в каталоге проекта
- **THEN** программа читает `./input` и пишет в `./output`

#### Scenario: Входная папка отсутствует или пуста

- **WHEN** каталог `--input-dir` не существует или не содержит файлов .md/.txt
- **THEN** программа завершается с кодом 2 и понятным сообщением об ошибке

### Requirement: Пакетная обработка файлов требований

Программа ДОЛЖНА обрабатывать каждый файл (.md/.txt) из входной папки как
отдельный независимый запрос: для каждого файла генерируется свой выходной
документ. Аргумент `--count` применяется к КАЖДОМУ файлу.

#### Scenario: Три файла во входной папке

- **WHEN** входная папка содержит `auth.md`, `cart.txt`, `search.md`
  и запуск выполнен с `--count 10`
- **THEN** в выходной папке появляются `auth.md`, `cart.md`, `search.md`,
  каждый ровно с 10 тест-кейсами

#### Scenario: Именование выходных документов

- **WHEN** входной файл называется `cart.txt`
- **THEN** выходной документ создаётся как `<output-dir>/cart.md`
  (расширение источника заменяется на .md)

### Requirement: Разрешение коллизий имён входных файлов

Если во входной папке обнаружены файлы с одинаковым именем, но разными
поддерживаемыми расширениями (например, `auth.md` и `auth.txt`), программа
ОБЯЗАНА завершиться с ошибкой, не выполняя генерацию: такие файлы претендуют
на один и тот же выходной документ, и выбор за пользователя остаётся явным.

#### Scenario: Дубли имени с разными расширениями

- **WHEN** входная папка содержит одновременно `auth.md` и `auth.txt`
- **THEN** программа завершается с кодом 2 и перечисляет конфликтующие файлы,
  предлагая удалить или переименовать один из них

#### Scenario: Файлы неподдерживаемых расширений

- **WHEN** во входной папке есть `notes.pdf` рядом с корректными .md/.txt
- **THEN** неподдерживаемые файлы пропускаются с предупреждением в лог

### Requirement: Чтение файла запроса

Каждый входной файл ДОЛЖЕН содержать требования к тестированию и адрес
тестируемого сайта в формате markdown (.md) или обычного текста (.txt).
Адрес сайта МОЖЕТ быть также передан общим аргументом `--url`; он имеет
приоритет над значением из любого файла пакета.

#### Scenario: URL задан во входном файле

- **WHEN** входной файл содержит URL сайта и `--url` не указан
- **THEN** программа использует URL из этого файла при формировании промпта

#### Scenario: Входной файл в формате .txt

- **WHEN** входной файл — текстовый документ с тем же содержимым по смыслу
- **THEN** программа разбирает его так же, как markdown-вариант

#### Scenario: URL задан аргументом CLI

- **WHEN** указаны URL в файлах и аргумент `--url https://example.com`
- **THEN** все документы пакета используют `https://example.com`

#### Scenario: URL не найден

- **WHEN** ни в файле, ни через `--url` адрес сайта не указан
- **THEN** программа сообщает об ошибке по конкретному файлу пакета;
  остальные файлы продолжают обрабатываться

### Requirement: Генерация тест-кейсов через локальный ollama

Программа ДОЛЖНА подключаться по HTTP к существующему ollama-сервису
(адрес — переменная окружения `OLLAMA_BASE_URL`, модель — `OLLAMA_MODEL`)
и отправлять промпт на генерацию тест-кейсов.

#### Scenario: Успешный ответ модели

- **WHEN** ollama доступна и модель отвечает корректным JSON со сценариями
- **THEN** программа разбирает ответ в структуру тест-кейсов без ошибок

#### Scenario: Ollama недоступна

- **WHEN** сервис по `OLLAMA_BASE_URL` недоступен
- **THEN** программа завершается с кодом 3 и сообщением о недоступности сервиса

### Requirement: Состав тест-кейсов — позитивные и негативные сценарии

Набор сгенерированных тест-кейсов ОБЯЗАН содержать как позитивные,
так и негативные сценарии. При N < 5 допускается минимум один негативный;
при N ≥ 5 доля негативных должна быть не менее трети набора.

#### Scenario: Только позитивные сценарии в ответе модели

- **WHEN** модель вернула N кейсов, но все помечены как positive
- **THEN** программа выполняет повторный запрос с указанием на нарушение состава

### Requirement: Точное соответствие количества тест-кейсов

Количество тест-кейсов в выходном документе ДОЛЖНО быть равно значению,
переданному в CLI. Если модель вернула иное количество, программа ДОЛЖНА
повторить запрос (не более `--max-retries`, по умолчанию 3) с обратной связью.

#### Scenario: Модель вернула меньше кейсов, чем запрошено

- **WHEN** модель вернула 8 кейсов при запросе 10 и попытки не исчерпаны
- **THEN** программа делает повторный запрос, требуя добрать недостающие кейсы

#### Scenario: Попытки исчерпаны

- **WHEN** после `--max-retries` попыток для файла так и не получен валидный набор
- **THEN** программа завершается с кодом 4; выходной документ этого файла
  не создаётся, обработка остальных файлов пакета не выполняется

### Requirement: Выходной markdown-документ

Программа ДОЛЖНА записывать результат каждого входного файла в отдельный
markdown-документ в выходной папке, структурированный по тест-кейсам:
идентификатор, тип (позитивный/негативный), название, предусловия, шаги,
ожидаемый результат. Выходная папка создаётся автоматически; существующие
документы перезаписываются.

#### Scenario: Успешная запись результата

- **WHEN** валидный набор из N кейсов получен
- **THEN** выходной документ содержит ровно N пронумерованных тест-кейсов
  с разделением позитивных и негативных сценариев

### Requirement: Запуск приложения в контейнере

Приложение ДОЛЖНО иметь Dockerfile и запускаться контейнером, получая
входную и выходную папки через монтируемые каталоги.

#### Scenario: Запуск через docker run

- **WHEN** пользователь запускает контейнер образа с
  `-n 10 -v ./input:/data/input -v ./output:/data/output`
- **THEN** программа обрабатывает файлы из `/data/input` и пишет результаты
  в `/data/output`

### Requirement: Dev Container для разработки

Проект ДОЛЖЕН содержать конфигурацию VS Code Dev Container с Python актуальной
версии, установленным uv и доступом к Docker для интеграционных проверок.

#### Scenario: Открытие проекта в VS Code

- **WHEN** разработчик открывает проект через «Reopen in Container»
- **THEN** окружение готово к работе после `uv sync --dev`, тесты запускаются
