# Change (advanced): JSON-план тестов вместо генерации кода + ядро-исполнитель

> Целевой проект: **advanced-вариант Dz3**. Simple-вариант не изменяется
> (он остаётся «LLM пишет pytest-код → прогон»). Требования пользователя,
> высокий уровень:
> 1. есть **ядро**, которое умеет ТОЛЬКО посылать запросы в API;
> 2. у LLM просится не код автотестов, а **JSON** с названием теста (в отчёт),
>    эндпоинтом, глаголом, телом (если нужно) и критериями приёмки.

## Почему

Simple-подход («LLM пишет python-код, пайплайн его исполняет») имеет
фундаментальные издержки: исполнение недоверенного кода, зависимость рантайма
от pytest, необходимость ретраев на синтаксически кривой код, невоспроизводимые
ассерты. Advanced решает это сменой контракта: LLM выдаёт **данные** (план
тестов), исполняет их детерминированное **ядро**. LLM-код никогда не запускается.

## Архитектура (верхний уровень)

```
документация (слои: страница API / Spec-XYZ / Spec-XXX)
        │  промпт-сборка (секции из шаблона)
        ▼
   LLM ──► JSON-план тестов ──► валидатор плана (покрытие, схема JSON)
        │                            │ не прошёл ──► feedback-луп (ревизия JSON)
        ▼                            ▼ прошёл
   ЯДРО (только HTTP): исполняет каждый request, проверяет expect-критерии
        ▼
   отчёт (имя теста, каждая проверка, результат; FAILURES в человекочитаемом виде)
```

- **Ядро** не содержит LLM-логики и не исполняет код — только HTTP-клиент
  + оценщик критериев + сборка отчёта.
- **LLM** только проектирует план: какие эндпоинты, что проверять.
- **Валидатор** проверяет план ДО исполнения: (а) JSON валиден и соответствует
  схеме; (б) покрытие обязательных ресурсов×глаголов (из спек аналитиков —
  автогенерация, как в слое контрактов; без спек — по глаголам / вручную).
- **Feedback-луп** сохраняется, но работает на уровне плана: «в плане нет
  покрытия DELETE/users — перегенерируй JSON».

## Драфт контракта JSON v3 (после ревью пользователя: cleanup вынесен на уровень теста)

Ключевые решения: (1) **тест = сценарий из шагов** — CRUD-операции с проверкой
и возвратом состояния не выражаются одиночным запросом; (2) общее состояние
шагов через **переменные** (`extract` → подстановка `{var}`); (3) **отделение
уборки от сценария**: `cleanup` — отдельный массив шагов на уровне теста
(аналог fixture-finalizer), в основной сценарий идут только «деловые» шаги;
(4) валидатор требует cleanup у мутирующих сценариев.

```json
{
  "service": "jsonplaceholder",
  "tests": [
    {
      "name": "update_post_roundtrip",
      "description": "PUT-обновление поста 1 с возвратом исходного состояния",
      "vars": { "post_id": 1 },
      "steps": [
        { "name": "получить исходный пост",
          "request": {"method": "GET", "path": "/posts/{post_id}"},
          "extract": {"orig_title": "$.title", "orig_body": "$.body"},
          "expect": {"status_code": 200} },

        { "name": "обновить пост (PUT)",
          "request": {"method": "PUT", "path": "/posts/{post_id}",
                      "body": {"id": "{post_id}", "title": "changed", "body": "changed", "userId": 1}},
          "expect": {"status_code": 200,
                     "checks": [{"op": "eq", "path": "$.title", "value": "changed"}]} },

        { "name": "проверить, что изменение применилось",
          "request": {"method": "GET", "path": "/posts/{post_id}"},
          "expect": {"checks": [{"op": "eq", "path": "$.title", "value": "changed"}]} }
      ],
      "cleanup": [
        { "name": "вернуть исходное состояние",
          "request": {"method": "PUT", "path": "/posts/{post_id}",
                      "body": {"id": "{post_id}", "title": "{orig_title}", "body": "{orig_body}", "userId": 1}},
          "expect": {"status_code": 200} }
      ]
    }
  ]
}
```

Механизмы:
- `vars` — переменные теста; `extract` — сохранение значений из ответа шага
  (JSONPath) в переменные; подстановка `{var}` — в `path`, `headers`, `body`
  (в т.ч. `id`, созданного POST'ом). Переменные, извлечённые в `steps`,
  **видны в `cleanup`** — поэтому «сфотографировать до» делается в шагах,
  а откат в cleanup использует те же `{orig_title}` и т.п.;
- `cleanup` — массив шагов на уровне теста: выполняется **всегда** после
  `steps` (и при падении сценария, и при abort), если был начат хотя бы один
  шаг сценария; шаги cleanup выполняются в порядке объявления;
- cleanup **не влияет на статус теста**: упавший cleanup — раздел «Cleanup
  warnings» в отчёте (сервис остался в изменённом состоянии — об этом надо
  кричать, но тестом это не является);
- `on_fail` шага: `abort` (по умолчанию) | `continue`;
- `provisional: true` на create-шаге — «объект создан тестом, cleanup не
  обязателен» (DELETE-сценарий: POST → DELETE → GET 404);
- `expect` шага — `status_code` + `checks` (мини-DSL `op` по JSONPath);
- READ-тесты — вырожденный сценарий из одного шага, без cleanup;
- статус теста в отчёте — по шагам (видно, на каком шаге упало).

Требования валидатора: **(а)** мутирующий сценарий обязан иметь `cleanup`
с возвратом состояния либо пометку `provisional` у create — иначе план
отклоняется, модель уходит на доработку с фидбеком; **(б)** переменные,
используемые в cleanup, должны извлекаться в steps (`extract`) — битых
ссылок быть не может. Для фейковых API (JSONPlaceholder) проверка отката
неактивна по сути, но контракт пишется под настоящие API.

Прежняя плоская форма v1 (один request + expect на тест) сохраняется как
сокращение для одношаговых READ-сценариев — ядро нормализует её к `steps`.

- `path` — JSONPath в тело ответа; `op` — минимальный набор:
  `eq`, `len_eq`, `contains`, `fields_eq`, `type` (покрывает статус/схему/
  семантику без скриптования);
- `name` идёт в отчёт как есть (человекочитаемо, по договорённости с промптом);
- схема JSON версионируется (`schema/v1.json`), ядро и промпт ссылаются на
  одну версию.

## Слои документации и комбинации (из прежней редакции — без изменений по сути)

Источники собираются в слои; страница API — «Контекст» (не контракт),
Spec-XYZ — «Контракт», Spec-XXX — «Дополнение» (XXX побеждает при конфликте,
конфликты помечаются). Хранение — `input/contracts/{base,supplements,examples}`,
шаблон промпта с плейсхолдерами `{docs_context}`, `{contracts_base}`,
`{contracts_supplements}`. Комбинации:

| Случай | Сборка промпта | Валидатор плана |
|---|---|---|
| API + XYZ | Контекст + Контракт | маркеры автогенерируются из XYZ |
| API + XXX (без XYZ) | Контекст + Дополнение («базовая спека недоступна») | по перечисленному в XXX, иначе по глаголам |
| API + XYZ + XXX | Контекст + мердж XYZ+XXX | маркеры из смерженного контракта |
| Только API (без спек) | только Контекст; режим best effort | по глаголам / ручной `--required-resources` |

## Отчёт

- Имя теста из JSON-плана (`name`/`description`) — человекочитаемо;
- по каждой проверке (`checks`): `op`, `path`, ожидание vs факт;
- FAILURES — по буллету на упавший тест с конкретной несработавшей проверкой
  (не сырой трейсбек — его нет по определению);
- в шапке — модель, параметры, режим документации (какая комбинация слоёв).

## Использование ohw-kit (правило харнесса)

По конвенции «Reuse only through the kit, never by copying» advanced обязан
зависеть от `../kit` (`uv add ../kit`) и использовать:

- **`ohw_kit.ollama_client.OllamaClient`** — весь доступ к LLM (`chat`,
  `json_mode=True` для плана; transport-инъекция `httpx.MockTransport` —
  для тестов фидбек-лупа). **Свой `ollama.py` не пишется** — в отличие от
  simple, где собственный клиент остаётся как часть замороженной истории
  прогонов (см. «Замечание о simple»);
- **`ohw_kit.io.load_input` / `register_reader`** — чтение контрактов из
  `input/contracts/`: built-in ридеры `.txt`/`.md`, при необходимости
  OpenAPI-ридер регистрируется **в проекте** (`.yaml`/`.json`), не в ките;
- **`ohw_kit.checks`** — **эталонный JSONPath-оценщик** (создан в kit по
  подтверждению пользователя): `evaluate(checks, status_code=..., body=...)`
  → `list[CheckResult]` с DSL `eq / len_eq / contains / fields_eq / type` и
  минимальным JSONPath-подмножеством без внешних зависимостей (`$`, `.key`,
  `[i]`, `[*]`, `..key`). Ядро advanced **не пишет собственный оценщик** —
  использует этот; `CheckResult.as_line()` даёт человекочитаемые строки для
  отчёта;
- **`ohw_kit.jsonreply`** — извлечение JSON из ответа модели
  (`extract_json`, снятие markdown-ограждений, ошибки с готовым текстом
  для feedback-лупа) + общий тип `ValidationResult(ok, issues)`;
- **`ohw_kit.render.render_markdown`** — обёртка для markdown-отчёта ядра.

Домашне-специфичное (ядро-исполнитель шагов, валидатор плана, слои
документации/мердж) — в проекте: это выходной контракт домашки, кит его не
фиксирует. Эталонные блоки с кросс-домашним потенциалом (оценщик, парсинг
ответа) уже подняты в kit.

**Замечание о simple:** в simple дублирование клиента kit'а — осознанный
исторический факт (домашка в git как рабочая память прогонов). Advanced
дублирования не допускает; рефакторить simple под kit не планируется.

## Отклонённые альтернативы

- «LLM пишет python-код» (simple-путь) — исполнение недоверенного кода;
- «свободный текст критериев, оценивает LLM» — недетерминизм, ядро не автономно;
- «всегда OpenAPI» / «сырой HTML» / «LLM-суммаризация доки» — как в simple-редакции.

## Влияние

- Проект: advanced-вариант Dz3 (скелет создаётся под эту задачу).
- Код: `core/` (HTTP-исполнитель + оценщик expect + отчёт), `plan/` (валидатор
  JSON-плана, схема v1), `docs.py` (слои, детектор, мердж), `prompt.py`
  (сборка секций), `ollama.py`/`config.py`/`cli.py` (feedback-луп по плану,
  флаги), `tests/`.
- pytest в рантайме advanced **не нужен** (в отличие от simple).
- Зависит от утверждения JSON-контракта пользователем (раздел «Драфт»).
