# Design: AI-генератор тест-кейсов

## Context

Существующая инфраструктура пользователя:

- Windows + Docker Desktop (WSL2), GPU NVIDIA RTX 2070 SUPER (8 GB VRAM).
- Контейнер ollama **уже запущен/настроен**, модель предустановлена.
  Приложение не управляет его жизненным циклом — только подключается по HTTP.

## Goals / Non-Goals

**Goals**

- Простой одноразовый CLI: вход → LLM → валидация → выходной markdown.
- Гарантии результата: ровно N кейсов; есть позитивные и негативные.
- Работа как на хосте (uv run), так и в контейнере.

**Non-Goals**

- Управление ollama (pull моделей, старт/стоп контейнера).
- Реальное выполнение тестов против сайта — только генерация сценариев.
- UI/API поверх CLI.

## Архитектура

```
input-dir/*.md|*.txt ──► CLI ──► PromptBuilder ──► OllamaClient ──► ResponseValidator
                                                          │ (retry ≤ K на файл)
                                                          ▼
                        output-dir/<имя>.md ◄── MarkdownRenderer ◄─ TestCases
```

Модули пакета `ai_testgen`:

| Модуль | Ответственность |
|---|---|
| `cli.py` | разбор аргументов, конфиг из env, оркестрация |
| `input_doc.py` | скан входной папки, детект коллизий имён, чтение .md/.txt, извлечение требований и URL |
| `prompt.py` | сборка системного+пользовательского промпта под JSON-схему |
| `ollama_client.py` | HTTP к Ollama `/api/chat`, таймауты, обработка ошибок |
| `validator.py` | проверка количества и состава кейсов |
| `renderer.py` | markdown-отчёт с секциями позитивных/негативных кейсов |

## Ключевые решения

### D1. Структурированный ответ модели — JSON

Модель просим вернуть JSON-массив объектов:

```json
[{"id": "TC-01", "type": "positive", "title": "...",
  "preconditions": ["..."], "steps": ["..."], "expected": "..."}]
```

Ollama поддерживает `format: "json"` — включаем. JSON надёжнее парсить, чем
свободный markdown, поэтому финальный markdown рендерим сами из структуры.

### D2. Валидация + retry с обратной связью

`ResponseValidator` проверяет: количество == N; есть ≥1 positive и ≥1 negative;
непустые steps/expected. При нарушении — повторный запрос с сообщением об
ошибке («вернул 8 вместо 10, добери ещё»), максимум `--max-retries`
(по умолчанию 3). Если после лимита кейсов меньше N — ошибка выхода (код ≠ 0).

Распределение типов: целевое соотношение ≈ 60% positive / 40% negative
(при N < 5 — минимум один негативный). Точное распределение задаём в промпте.

### D3. Подключение к существующему ollama

- URL по умолчанию: `http://host.docker.internal:11434` (контейнер приложения →
  порт ollama на хосте Docker Desktop). Переопределяется `OLLAMA_BASE_URL`.
- Альтернатива для продвинутых: подключение приложения к docker-сети ollama
  напрямую (`http://ollama:11434`) — поддерживаем через ту же переменную.
- Имя модели: `OLLAMA_MODEL` (обязательно, без дефолта — модель у каждого своя).
- GPU не трогаем из приложения: инференс уже настроен в ollama-контейнере.

### D4. CLI-интерфейс

```
python -m ai_testgen --count 10 \
    [--input-dir ./input] [--output-dir ./output] \
    [--max-retries 3] [--temperature 0.7] [--url https://...]
```

- `--count/-n` — обязательный, int > 0; применяется к **каждому** файлу пакета.
- `--input-dir` — папка с файлами требований (.md/.txt); дефолт `./input`
  (в контейнере `/data/input`).
- `--output-dir` — папка результатов; дефолт `./output`
  (в контейнере `/data/output`); создаётся при отсутствии.
- Пакетный режим: каждый файл → отдельный выходной документ `<имя>.md`.
  Файлы независимы, у каждого свой URL в тексте; `--url` при задании
  переопределяет URL для всех файлов пакета.
- Коллизия имён (`auth.md` + `auth.txt`) → exit code 2 со списком конфликтов:
  оба претендуют на один выходной документ, молчаливая перезапись недопустима.
  Неподдерживаемые расширения пропускаются с warning.
- Стратегия «fail fast»: ошибка любого файла прерывает пакет с ненулевым кодом
  (упрощает диагностику; частичная запись результатов допустима).
- Выходные документы перезаписываются; каталог создаётся автоматически.
- Exit codes: 0 — успех; 2 — ошибки аргументов/входных файлов (нет папки,
  пусто, коллизии имён); 3 — недоступен ollama;
  4 — не удалось получить валидный результат за отведённое число попыток.

### D5. Python + uv

- Python 3.13 (актуальный стабильный), управление версией через `uv`.
- Зависимости: только stdlib + `httpx` (HTTP) + `pydantic` (валидация схемы
  ответа) + `pytest`/`pytest-mock` (dev-группа). Минимум внешних пакетов.
- `pyproject.toml` — единственный источник правды; `uv.lock` коммитится.

### D6. Контейнеризация

- Мультистейдж `Dockerfile`: builder с uv (копируем lock → `uv sync --frozen`)
  → runtime на `python:3.13-slim`.
- Приложение запускается контейнером рядом с хостовым ollama:
  `docker run --rm -v ./input:/data/input -v ./output:/data/output image -n 10`
  — вход/выход через смонтированные каталоги.
- GPU приложению не нужен — он нужен только ollama-контейнеру.

### D7. Dev Container (VS Code)

- База: официальный devcontainer-образ Python + feature `ghcr.io/astral-sh/devcontainer-features/uv:1`.
- Features: `docker-outside-of-docker` (чтобы из dev-контейнера видеть ollama),
  расширения VS Code: Python, Pylance, Ruff, Even Better TOML.
- Post-create: `uv sync --dev`; задачи/launch.json для запуска CLI и pytest.
- Внутри devcontainer `OLLAMA_BASE_URL=http://host.docker.internal:11434`.

## Риски / Trade-offs

- **Качество генерации**: локальная модель ~8B может путать формат — смягчается
  JSON-режимом, retry и pydantic-валидацией.
- **VRAM 8 GB**: держим температуру/num_ctx умеренными; длинные требования
  пользователь сокращает сам.
- **Парсинг входного файла**: URL ищем по шаблону ссылки в любом формате
  (.md/.txt); если не нашли — требуем `--url`.

## Migration Plan

Новый проект — миграций нет. Инфраструктура проверена: контейнер `ollama`
(образ 0.32.15, `--gpus=all`, volume `qa_rag_studio_ollama-models`,
`--restart unless-stopped`), модель **qwen2.5:7b-instruct** в VRAM,
скорость генерации ~66 tok/s. Значение по умолчанию для `OLLAMA_MODEL`
в примерах — `qwen2.5:7b-instruct`.
