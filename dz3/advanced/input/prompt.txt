## Формат ответа

Выведи ТОЛЬКО JSON-объект (без текста и без markdown-ограждений), соответствующий схеме
план-схемы v3 ({schema_version}):

- `service` — имя сервиса;
- `tests` — массив тестов-сценариев. Каждый тест:
  - `name` — короткое имя (пойдёт в отчёт);
  - `description` — что проверяем;
  - `vars` — стартовые переменные (например {"post_id": 1});
  - `steps` — упорядоченные шаги:
    - `name` — человекочитаемое описание шага;
    - `request` — `{method, path, headers?, body?}` (в path/headers/body можно подставлять {var});
        ВАЖНО: имя плейсхолдера обязано совпадать с ключом в `vars` или именем из `extract`
        (vars: {"id": 1} + path: "/albums/{id}" — верно; vars: {"album_id": 1} при "{id}" в path — ошибка).
        Никаких строковых заглушек вида "{post_data}" вместо реального тела запроса.
    - `extract` — `{имя_переменной: JSONPath}` для сохранения значений из ответа;
    - `expect` — `{status_code?, checks?}`; `checks` — массив `{op, path, value}`;
    - `on_fail` — `abort` (по умолчанию) или `continue`;
  - `cleanup` — шаги отката (выполняются всегда после steps, не влияют на статус);
  - `provisional: true` — только для create-шага, если cleanup не нужен.

Допустимые операции `op` в `checks`: `eq`, `len_eq`, `contains`, `fields_eq`, `type`.
JSONPath-подмножество: `$`, `.key`, `[i]`, `[*]`, `..key`.

## Требования

- Покрой ресурсы, перечисленные в контракте/дополнениях (по крайней мере один шаг на ресурс).
- Если сценарий мутирует (POST/PUT/PATCH/DELETE), добавь `cleanup` с возвратом состояния
  либо пометь шаг как `provisional: true` (только create).
- Переменные, используемые в cleanup через {var}, должны быть заданы в `vars` или
  извлечены через `extract` в `steps`.
- Для CRUD: проверяй статус-код и ключевые поля тела (ассерты на реальные данные API).
