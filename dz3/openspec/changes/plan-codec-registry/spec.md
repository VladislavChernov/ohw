# Спека: PlanCodec — версионированный доступ к формату JSON-плана

## Контекст

`json_testgen_advanced` получает от LLM JSON-план автотестов. Формат плана
версионируется (`schema/v3.json`). Данная спека определяет, КАК ядро выбирает и
использует версию формата, чтобы (а) замена версии была локальной, а не
размазанной по коду, и (б) стала возможна поддержка нескольких версий и выбор
на лету.

## Публичный контракт

### `PlanCodec` (Protocol)

- `version: str` — идентификатор версии формата (строка вида `"v3"`).
- `schema_file: Path` — путь к JSON-схеме этой версии.
- `matches(raw: object) -> bool` — вернуть `True`, если сырой план относится
  к этой версии (по полю `version` плана либо по сигнатуре структуры).
- `decode(raw: object, *, doc_mode: str = "unknown") -> TestPlan` — привести
  JSON к единой внутренней модели `TestPlan`. Бросает `PlanParseError`
  на структурно неверный ввод.
- `validate(raw: object) -> ValidationResult` — структурная валидация именно
  этой версии (проверка полей `service`/`tests`/`name`/`steps`, а также плоской
  v1-формы `request`/`expect`, которую кодек v3 нормализует).

### `get_codec(version: str | None = None, raw: object | None = None) -> PlanCodec`

Выбор версии формата:
1. если `version` задана — использовать её;
2. иначе, если `raw` содержит поле `version` — использовать его;
3. иначе — **`DEFAULT_VERSION`** (сейчас `"v3"`).

- Запрошенная версия не зарегистрирована → поднять `ValueError`
  («unknown plan schema version: …»). **Никакого тихого fallback.**
- Реестр версий заполнен по умолчанию кодеком текущей версии (`v3`); функция
  регистрации позволяет добавить будущие версии.

### Инварианты

- **Единая внутренняя модель.** Все версии декодируются в один и тот же
  `TestPlan` (dataclass). Ядро-исполнитель, семантический валидатор
  (`validate_plan`), отчёт и `docs` работают только с `TestPlan` и не зависят
  от версии формата. Версия-специфична только граница «JSON → модель».
- **`validate_plan_schema(raw)` и `load_plan(text, ...)`** — сохраняют
  публичные имена, делегируют в выбранный кодек. `schema_version()` возвращает
  `DEFAULT_VERSION`, что сохраняет `{schema_version}` в промпте и шапке отчёта.
- **Изменение структуры = новый кодек + схема + регистрация.** Правок в
  `core`/`report`/семантическом валидаторе не требуется; существующие версии
  продолжают работать (кодеки остаются в реестре).

## Является текущей версией

**`v3`** — кодек `PlanCodecV3`, схема `plan_schema/v3.json`. Поддерживаемые
ключи на уровне теста: `service`, `tests[].{name, description, vars, steps,
cleanup, provisional}`; на уровне шага: `request.{method,path,headers,body}`,
`extract`, `expect.{status_code, checks}`, `on_fail` (abort|continue). Плоская
v1-форма (`request`/`expect` прямо на тесте) принимается как сокращение
одношаговых READ-сценариев и нормализуется к `steps`.

## Вне спецификации (границы)

- **`input/prompt.txt`** — версионированная человекочитаемая инструкция модели;
  НЕ является кодом и НЕ входит в codec. При смене версии переписывается
  вручную — это законная и единственная неизбежная ручная правка.
- **Семантический валидатор** (`validate_plan`: покрытие, cleanup, переменные)
  работает над `TestPlan` и потому версия-агностичен; в codec не переносится.
- **ohw-kit** не изменяется; `ValidationResult` используется как есть.
