# Proposal: PlanCodec — реестр версионированных декодеров JSON-плана

> Целевой проект: **advanced-вариант Dz3** (`json_testgen_advanced`).
> Simple не изменяется. Это небольшой, но архитектурно важный шаг: сейчас
> «версия схемы» размазана по `plan.py` (константа `SCHEMA_VERSION`, путь
> `_SCHEMA`, парсер `TestPlan.from_dict`, структурный валидатор
> `validate_plan_schema`), и замена версии = правка кода в этих точках.
> Мечте «брать схему/контракт на лету (RAG, требования аналитиков)» нужно
> ядро-абстракция: **реестр codec'ов**, где каждая версия — отдельная,
> регистрируемая единица.

## Почему

1. **Ручная смена версии сейчас размазана.** Чтобы перейти `v3 → v4`
   (изменение структуры), приходится править: `SCHEMA_VERSION`, `_SCHEMA`,
   `TestPlan.from_dict`/`StepSpec.from_dict`/`ExpectSpec.from_dict`,
   `validate_plan_schema`, плюс переписывать `input/prompt.txt`. Это хрупко:
   одна точка, где что-то забыли, ломает соответствие «промпт ↔ ядро ↔ схема».
2. **Нет способа поддерживать несколько версий одновременно.** Сейчас вариант
   «схема берётся на лету» невозможен в принципе: ядро жёстко связано с одним
   набором ключей. При подключении РАГ / динамических требований аналитиков
   это станет блокером.
3. **Три роли слиты в одном модуле.** Сейчас в `plan.py` всё вперемешку:
   (а) редакция формата (какие ключи), (б) приведение к внутренней модели
   `TestPlan`, (в) структурная валидация. При новой форме их нельзя поменять
   независимо. Отсюда и весь риск правок в «НЕ в том месте».
4. **Единственная неизбежная ручная работа при любой смене версии — промпт.**
   Инструкции модели отражают формат, поэтому `input/prompt.txt` переписывается
   всегда. Задача codec'а — сделать так, чтобы **промпт был единственной**
   точкой правки при смене структуры, а не одной из пяти.

## Что делаем

1. Вводим абстракцию **`PlanCodec`** (Protocol) в `plan.py` (или новый модуль
   `codec.py`):
   - `version: str` — идентификатор версии формата (например `"v3"`);
   - `schema_file: Path` — путь к JSON-схеме этой версии;
   - `matches(raw: object) -> bool` — детект, относится ли сырой план к этой
     версии (по полю `version` в плане либо по сигнатуре структуры);
   - `decode(raw: object, *, doc_mode: str) -> TestPlan` — перевод JSON в
     внутреннюю модель (инкапсулирует сегодняшние
     `TestPlan/TestSpec/StepSpec/RequestSpec.from_dict`);
   - `validate(raw: object) -> ValidationResult` — структурная валидация этой
     версии (инкапсулирует `validate_plan_schema`).
2. Реестр **`get_codec(version: str | None, raw: object) -> PlanCodec`**:
   - `DEFAULT_VERSION` выбирает версию по умолчанию, если не указана;
   - поддержка нескольких зарегистрированных версий;
   - неизвестная версия → явная ошибка (не тихий fallback).
3. Первый и единственный сейчас кодек — **`PlanCodecV3`**, **без изменения
   поведения**: в нём ровно нынешняя логика `v3` (ключи `service/tests/steps/
   extract/expect/cleanup/vars/provisional/on_fail`, плоская v1 нормализуется к
   одному шагу).
4. **Точки подключения** (заменяют сегодняшние прямые вызовы):
   - `load_plan(text, *, doc_mode)` → `get_codec(None, raw).decode(raw)`;
   - `validate_plan_schema(raw)` → `get_codec(None, raw).validate(raw)`;
   - `schema_version()`/`SCHEMA_VERSION` → `DEFAULT_VERSION` (для `{schema_version}`
     в промпте и шапки отчёта). Публичные имена сохраняются как точечные
     обёртки, чтобы `docs.py`/`generator.py`/`cli.py`/`report.py` не меняли
     своих вызовов сверх необходимости.
5. `input/prompt.txt` — правки только если это необходимо для сохранения
   смысла (промпт уже описывает v3; здесь не трогаем формат, только если нужно
   уточнить, что версия приходит в ответе).
6. **Тесты:** существующие остаются зелёными (поведение не меняем); добавляем
   юнит-тесты на: `matches` по полю `version`, `get_codec` по явной версии и по
   умолчанию, ошибка на неизвестную версию, что `PlanCodecV3` даёт тот же
   результат, что старый прямой парсинг (паритет без регрессий).

## Спека

Закрепляет поведение в `spec.md`:
- контракт интерфейса `PlanCodec` (version/schema_file/matches/decode/validate);
- правила выбора версии: `get_codec` по явной `version`, иначе `DEFAULT_VERSION`,
  неизвестная версия → ошибка;
- какой кодек считается текущим (v3) и какие ключи он понимает;
- инвариант: внутренняя модель `TestPlan` едина для всех версий, codec — только
  переводчик «формат → модель»;
- границы: промпт остаётся версионированной человекочитаемой инструкцией;
  изменение структуры = новый кодек + схема + регистрация (без правок ядра).

## Проверка

1. `uv run pytest -q` в `advanced/` — существующие 39 тестов зелёные + новые
   юнит-тесты codec-реестра.
2. `uv run ruff check src tests` и `uv run mypy src` — чисто.
3. `uv run python -c "from json_testgen_advanced.plan import ..."` — snipe:
   `get_codec(None, {"service":"s","tests":[{"name":"t","steps":[]}]})`
   возвращает `PlanCodecV3`; явная `version:"v3"` — тоже; несуществующая версия —
   бросает `ValueError`.
4. Прогон пайплайна `--no-run` не должен измениться в поведении (тот же план,
   та же валидация).
