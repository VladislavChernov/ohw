# Артефакты прогонов

Каждый каталог — один запуск оптимизатора. Полный комплект — три файла:

- `<stem>_optimized_tests.py` — то, что вернула модель (или fallback);
- `<stem>_code_review_report.md` — ревью от модели (или fallback);
- `<stem>_optimization_report.md` — отчёт инструмента: метрики, валидация,
  измеренные изменения.

## Почему у трёх первых прогонов нет отчёта инструмента

Отчёты были построены версией анализатора с дефектами разбора: часть метрик
считалась неверно, а раздел «Проделанные оптимизации» был фиксированным
текстом шаблона. Такие числа не должны оставаться в репозитории, поэтому
отчёты удалены; история — в git. Код в `*_optimized_tests.py` от этого не
пострадал: анализатор читает исходник и не меняет ответ модели. Все три файла
являются ответами модели, а не подставленным демо-кодом — проверено по
признакам fallback (`/items`, `created_item`, `BASE_URL = os.getenv("BASE_URL"`).

Отчёт прогона `15-41-01` пересобран текущей версией анализатора по сохранённым
артефактам: код модели, ревью и таблица приоритизации не менялись, обновлены
только производные строки (метрики и «Что изменилось»).

## Что показывает прогон 15:41

Этот прогон — пример того, зачем нужна ручная проверка: статическая валидация
прошла (`ast.parse` OK, `test_*` есть, запрещённых паттернов нет), но модель
объединила валидные и невалидные данные в один цикл и ждёт `201` от невалидных,
добавила «тест на таймаут» без таймаута и оставила два захардкоженных URL.
Отчёт честно показывает `Жёстко заданных URL: 1 → 2`,
`Таймаут в запросах: нет → нет` и `Teardown в фикстурах: нет → нет`.
