# Артефакты прогонов

Каждый каталог — один запуск оптимизатора. Внутри три файла:

- `<stem>_optimized_tests.py` — то, что вернула модель (или fallback);
- `<stem>_code_review_report.md` — ревью от модели (или fallback);
- `<stem>_optimization_report.md` — отчёт инструмента: метрики, валидация,
  измеренные изменения.

## Почему старым отчётам нельзя доверять

Регулярка `extract_test_blocks` склеивала все тесты в один блок, поэтому
дубли всегда были `0`, а читаемость зажималась в `0.0`. Раздел «Проделанные
оптимизации» был фиксированным текстом и не зависел от кода. Подробности — в
`../MODEL_COMPARISON_REPORT.md` §7 и
`../../learning/TestOptimization/llm_autotest_optimization_learning.md` §10.8.

Код в этих прогонах не пострадал: анализатор читает исходник и не меняет
ответ модели. Проверка трёх старых артефактов на признаки fallback (`/items`,
`created_item`, `BASE_URL = os.getenv("BASE_URL"`) не нашла совпадений — все три
файла являются ответами модели, а не подставленным демо-кодом.

## Что показывает прогон 15:41

Этот прогон — пример того, зачем нужна ручная проверка: статическая валидация
прошла (`ast.parse` OK, `test_*` есть, запрещённых паттернов нет), но модель
объединила валидные и невалидные данные в один цикл и ждёт `201` от невалидных,
добавила «тест на таймаут» без таймаута и оставила два захардкоженных URL.
Отчёт честно показывает `Жёстко заданных URL: 1 → 2` и
`Таймаут в запросах: нет → нет`.

Метрик-блок этого отчёта посчитан предыдущей ревизией анализатора:
`Близких дублей (пар): 7` и `Средняя длина теста: 4.6 → 8.0` — старые значения,
текущая ревизия даёт `1` и `7.2`, а формулировка про фикстуры теперь содержит
слово «локальными». Строки, которые цитирует документация (`URL 1 → 2`,
`Таймаут: нет → нет`, `Teardown: нет → нет`), не изменились.
