# Как проходит проверка автотестов

Документ описывает, что скрипт `src/test_optimizer.py` делает с входным файлом
автотестов: какие шаги выполняет, что измеряет по AST, где подключается LLM и
чего эта проверка не делает. Требования к поведению — в `TZ.md` §3.1–3.3.

Главное, что стоит держать в голове: **тесты не запускаются**. Стенда с
тестируемым API в проекте нет, поэтому проверка статическая: измерение кода по
AST, ревью и переписывание моделью, статическая валидация результата. Слово
«проверка» здесь означает «измерить и переписать», а не «прогнать».

## Общий поток

Точка входа — `run()` в `src/test_optimizer.py`:

1. **Скан каталога.** `find_test_files` рекурсивно ищет `.py` и `.txt`, в тексте
   которых встречается `def test_`. Фильтр текстовый, а не по AST. Каталог
   задаёт `INPUT_DIR` (по умолчанию `input/`), глубину рекурсии — параметр
   `max_depth`.
2. **Клиент Ollama — один на весь прогон.** Доступность проверяется запросом
   `GET /api/tags` с таймаутом 5 с. Недоступная Ollama не роняет прогон: она
   только переключает все шаги на fallback. Таймаут генераций задаёт
   `OLLAMA_TIMEOUT` (по умолчанию в коде 120 с, в `compose.yaml` — 600 с:
   7B на CPU отвечает медленно).
3. **Каталог прогона.** `output/<YYYY-MM-DD_HH-MM-SS>/` (время контейнера,
   UTC), чтобы прогоны не перезаписывали друг друга.
4. **Цикл по файлам.** Для каждого найденного файла вызывается
   `process_single_file`; шаги `[1]`–`[6]` ниже — это его вывод в консоль.

## Шаги обработки одного файла

### [1] Чтение исходника

Файл читается в UTF-8 (`read_source`). Путь и размер (в символах) печатаются в
консоль, чтобы было видно, что именно попало в анализ.

### [2] Статический анализ по AST

`static_analysis` вызывает `analyze_code`: один `ast.parse`, дальше либо ошибка
разбора, либо измерения. При ошибке метрики остаются `unknown`, а в список
проблем попадает запись уровня `critical` — ноль вместо «не измерено» не
подставляется.

| Что | Как считается |
|---|---|
| Число тестов | функции `test_*` (`ast.walk` + фильтр по имени), сортировка по `lineno` |
| Дубли | тело каждого теста нормализуется и сравнивается как строка: `_DataNeutralizer` заменяет строковые литералы на `"STR"`, но сохраняет ключи словарей, срезы вида `body["name"]` и куски f-строк; числа не трогаются. Затем `ast.unparse` и группировка по точному совпадению |
| Near-duplicate | Jaccard по множеству `\w+`-токенов нормализованных тел, порог `> 0.7` |
| Параметризация | декоратор, имя которого оканчивается на `parametrize` |
| Фикстуры | декоратор `pytest.fixture` / `fixture`; использование — по совпадению имён аргументов теста с именами фикстур, а при `autouse=True` засчитываются все тесты |
| Слабые тесты | нет `assert`, `pytest.raises` или `pytest.fail` |
| URL | строковые константы по шаблону `https?://...`; URL во **втором** аргументе `os.getenv(...)` считается не хардкодом, а значением по умолчанию, и показывается отдельной строкой |
| Таймаут | только у вызовов, чьё имя оканчивается на `get/post/put/patch/delete/head/options/request`, и только при наличии keyword `timeout` |
| Teardown | `yield` с кодом после него, `try/finally` вокруг `yield`, `request.addfinalizer` в фикстуре |
| Читаемость | формула: 10 − 0.5 за каждую строку средней длины теста сверх 8 − 1.0, если самый длинный тест длиннее 30 строк − до 3.0 за отсутствие docstrings; результат зажимается в 1–10 |

По результатам измерений формируется список проблем (`ReviewIssue`) с уровнем
`critical/high/medium/low`: группы дублей, пары near-duplicate, захардкоженные
URL, отсутствие фикстур или их частичное использование, тесты без assert,
слишком длинные тесты, низкая читаемость.

Покрытие требований намеренно `unknown`: сопоставления «тест → требование» в
проекте нет, и ноль здесь означал бы измеренный ноль (комментарий в
`static_analysis`).

### [3] Проверка Ollama

Печатается адрес, модель и доступность. Ничего не измеряется — это точка, где
становится видно, пойдёт прогон через модель или через fallback.

### [4] Ревью моделью

`llm_review` отправляет исходный код с промптом `prompts/review.md` и
system-промптом `prompts/system_review.md`. Ответ сохраняется как
`<stem>_code_review_report.md`.

Если Ollama недоступна, вернула пустой ответ или запрос упал, берётся
`FALLBACK_REVIEW_REPORT`, а в отчёте явно пишется `**fallback** — причина`
(«Ollama недоступен», текст ошибки HTTP, «модель вернула пустой ответ»).
Шаблонный текст не выдаётся за ответ модели.

### [5] Оптимизация и валидация до сохранения

`llm_optimize` отправляет код с промптом `prompts/optimization.md`, который
требует вернуть только готовый Python в блоке ` ```python `. Блок извлекается
`_extract_python_code`. Ответ без markdown-обёртки принимается только если он
сам разбирается `ast.parse`; иначе — fallback с причиной «ответ модели не
является Python-кодом».

До записи на диск результат проходит `validate_generated_tests`:

- `ast.parse` — синтаксис;
- хотя бы одна функция `test_*`;
- запрещённые конструкции ищутся по узлам AST, а не по тексту: `assert True`
  (литерал `True` в `ast.Assert.test`), вызов `time.sleep(...)`, `except:` без
  типа.

Проверка не останавливает прогон: файл сохраняется в любом случае, но при
провале получает шапку `# ЧЕРНОВИК:` с перечнем причин, статус `**ЧЕРНОВИК**` в
отчёте и `[WARN]` в консоли.

### [6] Приоритизация и сводный отчёт

`llm_prioritization` получает исходный код и текст требований из
`requirements_with_priorities.md` (`REQUIREMENTS_PATH`), ответ идёт в раздел
«Приоритизация по требованиям».

`build_optimization_report` собирает `<stem>_optimization_report.md`:

- источник каждого из трёх ответов (`LLM` или `fallback` с причиной);
- результат статической валидации сгенерированного кода;
- метрики «до оптимизации» и найденные проблемы;
- таблицу приоритизации;
- раздел **«Что изменилось»**: повторный `analyze_code` по сгенерированному
  коду и дельта по тестам, дублям, параметризации, фикстурам, docstrings,
  assert'ам, URL, таймауту, teardown и средней длине теста;
- список критериев «плохих» автотестов и имена получившихся файлов.

## Чего эта проверка не делает

- **Не запускает тесты** — ни исходные, ни сгенерированные. В отчёте это
  сказано прямым текстом: «факты о коде, а не подтверждение поведения».
- **Не измеряет реальное покрытие** — ни строк кода, ни требований. Для
  покрытия требований нужен RTM (сопоставление тестов с требованиями),
  которого в проекте нет, поэтому значение остаётся `unknown`.
- **Не гарантирует качество ответа модели.** Пригодность локальной 7B измерена
  отдельно и вручную: `LOCAL_VS_SUBAGENT_REPORT.md` (0/3 против 3/3 у
  субагента).
- **Guard-тесты в `tests/` проверяют инструмент, а не автотесты:** что метрики
  считаются по отдельным функциям, что `unknown` не превращается в `0`, что
  битые символы не попадают в документы, что лаунчеры соблюдают режимы
  CPU/GPU.

## Где смотреть

- `src/test_optimizer.py` — `run`, `process_single_file`, `static_analysis`,
  `analyze_code`, `validate_generated_tests`, `build_optimization_report`.
- `prompts/*.md` — тексты запросов; `${source_code}` и `${requirements_text}`
  подставляются при отправке.
- `output/<YYYY-MM-DD_HH-MM-SS>/` — результат одного прогона: код, ревью,
  сводный отчёт.
- `TZ.md` §3.1–3.3 — требования к этим шагам; `output/README.md` — статус
  лежащих в репозитории артефактов.
