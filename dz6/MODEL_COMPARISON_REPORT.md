## 1. Зачем

Скрипт отправляет один и тот же запрос в локальную модель. Три прогона дали
результат, который нельзя было использовать. Нужно было отделить две гипотезы:

- **H1:** виноват промпт — он просит слишком много за один раз;
- **H2:** виновата модель — она не удерживает семь ограничений одновременно.

Если тот же текст получает сильная модель и справляется, H1 не подтверждается.

## 2. Метод

1. Промпт отрендерен тем же кодом, что и в рабочем запуске
   (`render_prompt` из `src/test_optimizer.py`), без ручных правок.
2. Слабая модель: `qwen2.5:7b-instruct`, 7.6B, Q4_K_M, digest `845dbda0ea48`,
   Ollama на CPU, ~7.4 токена/с, 4.5–8.5 минуты на прогон, 3 прогона.
3. Сильная модель: агент общего назначения, 3 прогона. Запрет на чтение файлов
   проекта и на инструменты, `requirements_with_priorities.md` не предоставлялся.
4. Критерий успеха зафиксирован **до** просмотра ответов:
   - статическая валидность (`ast.parse`, `pytest --collect-only`);
   - дубли исходного файла устранены параметризацией;
   - нет `assert True`, `time.sleep`, проглоченных исключений;
   - URL и таймаут не захардкожены;
   - teardown касается только данных, созданных тестом;
   - нет выдуманных полей и сценариев, противоречащих требованиям.

## 5. Выводы

1. **Промпт не является узким местом.** Тот же текст, те же семь требований —
   сильная модель удержала их три раза из трёх. Гипотеза H1 не подтвердилась.
2. **Статическая валидность ничего не различает.** Все шесть файлов проходят
   `ast` и `--collect-only`, включая тот, где негативные тесты ожидают `201`.
   Зелёная сборка — необходимое условие, а не доказательство качества.
3. **Разброс у 7B — самостоятельный результат.** Три прогона дали три разные
   стратегии, а не три версии одного решения. Это нестабильность на одном входе.

## 6. Ограничения

- Вход один, промпт один, из малых моделей проверена одна. Утверждение
  «малые модели не годятся вообще» этими данными не подтверждается.
- Сильная модель тоже не эталон: третий прогон добавил сценарии, которых не
  было ни во входе, ни в требованиях.
- Повторяется метод, а не конкретные файлы: генерация стохастическая.
- Контрольные ответы сильной модели получены агентом, а не через Ollama; это
  верхняя граница «что возможно с таким промптом», а не сравнение на равных.

## 7. Дефект инструмента, обнаруженный по ходу (исправлен)

Раздел «Проделанные оптимизации» в `*_optimization_report.md` был фиксированным
текстом шаблона в `src/test_optimizer.py`, одинаковым во всех прогонах и не
совпадающим с кодом. Это дефект инструмента, а не модели.

При разборе нашлись ещё три дефекта того же класса:

- регулярка `extract_test_blocks` склеивала все тесты в один блок (5 → 1),
  поэтому дубли всегда были `0`, а читаемость зажималась в `0.0`;
- `tests_with_fixtures` и `tests_with_docstrings` считали вхождения в файле,
  а не тесты; `hardcoded_urls` ловил только `http://localhost:ПОРТ`;
- `llm_optimize` молча возвращал fallback, написанный про `/items`, хотя вход
  описывает `/users`.

Исправлено в том же коммите: разбор на `ast`, невычислимые метрики —
`unknown`, раздел «Что изменилось» собирается из AST исходника и артефакта,
валидация (`ast.parse`, наличие `test_*`, запрещённые паттерны) до сохранения,
пометка `# ЧЕРНОВИК`, явная причина fallback. Guard-тесты —
`tests/test_static_analysis.py`. Артефакты прогонов выше оставлены как есть:
они показывают поведение моделей, а не состояние анализатора; в их отчёты
добавлена пометка о дефекте, статус каталогов описан в `output/README.md`.

### 7.1. Контрольный прогон после исправления

Чтобы проверить, что «0 из 3» — свойство модели, а не сломанного инструмента,
после исправления сделан ещё один прогон на том же входе и промпте:
`output/2026-10-27_15-41-01/`. Критерии те же, оценка ручная по артефакту,
не по метрикам инструмента.

| Критерий | Результат |
|---|---|
| 1. `ast.parse` + `--collect-only` | OK, 6 тестов |
| 2. Дубли устранены параметризацией | нет: три создания объединены в цикл, а не в `parametrize` |
| 3. Нет `assert True` | да |
| 4. URL и таймаут не захардкожены | нет: `BASE_URL`, `http://invalid-url/users`, ни одного `timeout=` |
| 5. Teardown только своих данных | нет: teardown отсутствует |
| 6. Нет сценариев, противоречащих требованиям | нет: цикл гоняет невалидные данные и ждёт от них `201` |
| **Пригоден без переписывания** | **0/1** |

Это одно наблюдение, а не четвёртая точка в таблице 0/3: критерий и размер
выборки зафиксированы до прогонов, и задним числом менять знаменатель нельзя.
Но оно показывает главное: после устранения дефекта отчёт стал честным
(`Жёстко заданных URL: 1 → 2`, `Таймаут: нет → нет`, `Teardown: нет → нет`),
а результат модели остался непригодным. Валидация при этом прошла — значит,
статическая проверка ловит синтаксис и явные заглушки, но не подмену смысла.

Отдельно в этом прогоне видно, зачем нужен явный fallback: запрос ревью упал
с HTTP 500, и отчёт пометил ревью как fallback, а не выдал шаблон за ответ
модели (в отчёте той версии причина записана как «модель вернула пустой
ответ»; после этого код различает сбой запроса и пустой ответ).

## 8. Воспроизведение

Промпт рендерится функцией `render_prompt()` из `src/test_optimizer.py`
(шаблоны — `prompts/*.md`, подстановка `${source_code}`). Готовый текст можно
получить маленьким скриптом, запущенным в образе с примонтированным `input/`:

```python
import pathlib, sys
sys.path.insert(0, "/data")
from src.test_optimizer import render_prompt
src = pathlib.Path("/in/example.py").read_text(encoding="utf-8")
print(render_prompt("optimization", source_code=src))
```

Прогон слабой модели и проверка ответа:

```bash
docker compose run --rm app
pytest output/<каталог>/example_optimized_tests.py --collect-only -q
```

Синтаксис проверяется через `ast.parse` (см. `pytest --collect-only` — он же
ловит ошибки импорта и декораторов). Запрещённые паттерны проверяются по AST
функцией `validate_generated_tests`; teardown и остальные критерии качества
по-прежнему требуют чтения кода — статический гейт их не заменяет.
