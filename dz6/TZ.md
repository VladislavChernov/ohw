## 1. Цель и контекст

В проекте лежит файл `input/example.py`, содержащий исходный код автотестов на Python (pytest + requests).

Необходимо:
1. Написать скрипт на Python 3, который с помощью ЛЛМ (Ollama) оптимизирует код автотестов и генерирует их оптимизированный вариант.
2. Подготовить отчёт с результатами ревью кода автотестов (что сделано хорошо, что — плохо).
3. Провести исследование того, как подобные задачи решаются в реальной жизни, и какими тестовыми площадками можно пользоваться; оформить отчёт в корне проекта.
4. Провести исследование оптимизации: поиск дубликатов шагов, поиск похожих тестов, расстановка приоритетов по требованиям, оценка качества (читаемость + покрытие требований), критерии "плохих" тестов, тестовые запросы для оптимизации.
5. Обеспечить подъём инфраструктуры из папки `/infra` (Ollama).
6. Написать ТЗ и все отчёты.

## 3. Требования к решению (what)

### 3.1. Скрипт оптимизации (`src/test_optimizer.py`)
- Язык: Python 3.9+.
- Взаимодействует с Ollama через HTTP API (`/api/generate`, `/api/chat`).
- Читает исходные автотесты из `input/example.py` (каталог задаётся `INPUT_DIR`).
- Выполняет статический анализ (поиск дублей, подсчёт метрик, читаемость).
- Проверяет сгенерированный код до сохранения: `ast.parse`, наличие функций
  `test_*`, запрещённые паттерны (`assert True`, `time.sleep`, bare `except`).
  Непрошедший проверку файл сохраняется с пометкой `# ЧЕРНОВИК`, причина
  указывается в отчёте.
- Генерирует в каталоге прогона `output/<YYYY-MM-DD_HH-MM-SS>/`:
  1. `<stem>_optimized_tests.py` — оптимизированный вариант автотестов (код).
  2. `<stem>_code_review_report.md` — отчёт ревью (хорошо / плохо).
  3. `<stem>_optimization_report.md` — сводный отчёт оптимизации.
- Поддерживает демо-режим (fallback), если Ollama недоступен.
- Параметры настраиваются через переменные окружения: `OLLAMA_BASE_URL`, `OLLAMA_MODEL`, `OLLAMA_TIMEOUT`.

### 3.2. Ревью кода (что хорошо / что плохо)
Отчёт должен содержать:
- Положительные моменты (что сделано хорошо).
- Проблемы и антипаттерны (что сделано плохо), в т.ч.:
  - дублирующие тесты и шаги;
  - похожие (near-duplicate) тесты;
  - отсутствие фикстур и изоляции;
  - жёстко заданные данные и URL;
  - отсутствие параметризации;
  - слабые assert'ы;
  - отсутствие обработки ошибок / таймаутов.
- Общую оценку качества и рекомендации по приоритетам.

### 3.3. Оптимизация (что делает ЛЛМ)
- Устранение дублирующих шагов и тестов через `@pytest.mark.parametrize`.
- Добавление фикстур (клиент API, подготовка/очистка тестовых данных, изоляция).
- Вынос базового URL и тестовых данных в переменные окружения / конфиг.
- Усиление assert'ов (проверка полей ответа, структуры JSON, заголовков).
- Добавление docstrings и осмысленных имён тестов.
- Обработка ошибок сети, таймаутов, ретраев.
- Сохранение покрытия всех исходных сценариев.

### 3.4. Исследование оптимизации (отчёт)
Включает:
1. Поиск дублирующих шагов в тестах.
2. Поиск дублирующих (похожих) автотестов.
3. Расстановка приоритетов согласно приоритетам из требований (P0–P3).
4. Оценка качества автотеста: читаемость, процент покрытия требований.
5. Что ещё оптимизируют (список).
6. Критерии "плохих" автотестов (список).
7. Тестовые запросы для оптимизации (промпты).

### 3.5. Инфраструктура (`/infra`)
- Общий каталог `D:\Otus\ohw\infra` поднимает Ollama на порту 11434
  (компонент `ollama`, общая сеть `ohw_net`).
- Проект объявляет зависимость в `infra.yaml`; `run.sh` / `run.ps1` вызывают
  `../infra/up.sh` и затем `compose.yaml` приложения.
- Запуск: `.\run.ps1` (Windows, CPU по умолчанию), `.\run.ps1 -Gpu` (Windows,
  NVIDIA CUDA через `../infra/compose.gpu.yaml`) или `./run.sh` (Linux/macOS,
  только CPU).
- GPU-режим есть только в Windows-скрипте: `run.sh` не предполагает наличия
  NVIDIA-рантайма на машине и оверлей не подключает. `run.ps1 -Gpu` до запуска
  контейнеров проверяет, что в Docker зарегистрирован рантайм `nvidia`.

### 3.6. Отчёты (в корне проекта)
- `TZ.md` — настоящее техническое задание.
- `RESEARCH_REPORT.md` — исследование реальных практик, площадок, оптимизации.
- `LOCAL_VS_SUBAGENT_REPORT.md` — сравнение локальной 7B и субагента на одном
  промпте: метод, критерии, результаты прогонов, ограничения.
- `VERIFICATION_PIPELINE.md` — как проходит проверка автотестов по шагам: что
  измеряется по AST, где подключается LLM, чем проверка не является.
- `optimization_requests.md` — тестовые запросы (промпты) для оптимизации.
- `requirements_with_priorities.md` — требования с приоритетами.
- `README.md` — инструкция по развёртыванию и запуску.
