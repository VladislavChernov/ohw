# DZ6 — оптимизация автотестов с помощью LLM (Ollama)

Скрипт читает код автотестов на Python, выполняет статический анализ, отправляет
код в локальную LLM через Ollama и складывает результат прогона в отдельный
каталог: оптимизированный вариант тестов, отчёт ревью и сводный отчёт
оптимизации. Если Ollama недоступен, скрипт работает в демо-режиме и отдаёт
заранее подготовленный результат.

## Что делает скрипт

1. Находит файлы с автотестами в `INPUT_DIR` (по умолчанию `input/`).
2. Считает статические метрики по AST: тесты, дубли и near-duplicate, фикстуры,
   docstrings, захардкоженные URL, длину функций, читаемость.
3. Отправляет код в Ollama: ревью, оптимизация, приоритизация по
   `requirements_with_priorities.md`.
4. Проверяет сгенерированный код до сохранения: `ast.parse`, наличие
   `test_*`, запрещённые паттерны (`assert True`, `time.sleep`, bare `except`).
   Если проверка не прошла, файл всё равно сохраняется, но помечается
   комментарием `# ЧЕРНОВИК`, а причина попадает в отчёт.
5. Создаёт каталог прогона `output/<дата>_<время>/` (время UTC, как в
   контейнере) и сохраняет туда три файла с префиксом имени входного файла.

Метрики, которые измерить нельзя (код не разбирается, нет сопоставления
тестов с требованиями), печатаются как `unknown`, а не как ноль. Раздел
«Что изменилось» в отчёте собирается из AST исходника и артефакта: количество
функций, параметризация, фикстуры, docstrings, URL, таймауты, teardown.
Источник каждого артефакта (`LLM` или `fallback`) и причина fallback указаны
в отчёте явно.

Тексты запросов к модели не зашиты в код: они лежат в `prompts/*.md`, а
`${source_code}` и `${requirements_text}` подставляются при отправке. Правка
промпта — это правка файла, а не строки в Python.

Каждый запуск пишет в свой каталог, поэтому прогоны не перезаписывают друг
друга и их можно сравнивать.

## Запуск

Ollama — общий компонент каталога `D:\Otus\ohw\infra`; проект объявляет его в
`infra.yaml`. Одна команда (Windows), режим по умолчанию — CPU:

```powershell
cd D:\Otus\ohw\dz6
.\run.ps1
```

Если PowerShell блокирует локальный скрипт (политика выполнения по умолчанию):

```powershell
powershell -ExecutionPolicy Bypass -File .\run.ps1
```

Тот же стенд на NVIDIA GPU (CUDA-оверлей `../infra/compose.gpu.yaml`):

```powershell
.\run.ps1 -Gpu
```

`-Gpu` требует NVIDIA Container Toolkit и включённую GPU-поддержку в Docker
Desktop. Скрипт проверяет наличие рантайма `nvidia` и, если его нет,
останавливается до запуска контейнеров с подсказкой, что делать.

Linux / macOS / WSL — только CPU:

```bash
cd /path/to/ohw/dz6
./run.sh
```

Скрипт запуска поднимает общий `ohw-ollama` (через `../infra/up.sh` в bash и
`../infra/compose.yaml` в PowerShell), собирает образ приложения и запускает
оптимизатор. Флаги: `-Gpu` (только Windows, NVIDIA), `--rebuild` / `-Rebuild`,
`-i FOLDER` / `-InputFolder FOLDER` (другой каталог с тестами). В `run.sh`
GPU-режима нет: он рассчитан на машины, где наличие NVIDIA-рантайма не
предполагается.

Запуск без Docker:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements/requirements.txt
python src/test_optimizer.py --no-interactive
```

Для этого варианта Ollama должна быть доступна на `http://localhost:11434`.

## Параметры окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` | Адрес Ollama |
| `OLLAMA_MODEL` | `qwen2.5:7b-instruct` | Модель |
| `OLLAMA_TIMEOUT` | `120` с | Таймаут запроса к LLM |
| `INPUT_DIR` | `input/` | Каталог с автотестами |
| `OUTPUT_DIR` | `output/` | Корень для каталогов прогонов |
| `PROMPTS_DIR` | `prompts/` | Шаблоны запросов к LLM |
| `REQUIREMENTS_PATH` | `requirements_with_priorities.md` | Требования для приоритизации |

## Проверка результатов

Стенда с тестируемым API в проекте нет, поэтому сгенерированные тесты
проверяются статически. Скрипт делает это сам до сохранения; ту же проверку
можно повторить вручную:

```bash
pytest output/<дата>_<время>/example_optimized_tests.py --collect-only -q
```

`--collect-only` не обращается к API: он проверяет, что файл импортируется и
декораторы вычисляются. Если файл помечен `# ЧЕРНОВИК`, статическая проверка
не прошла — смотрите раздел «Валидация сгенерированного кода» в отчёте.

Guard-тесты анализатора:

```bash
docker compose build app
docker run --rm -v "$PWD:/data" -w /data --entrypoint pytest dz6-app:latest tests -q
```

## Известные ограничения

- Для контейнерного запуска нужен Docker Desktop / Docker Engine с compose.
- Без Ollama скрипт работает в демо-режиме (fallback); такие результаты —
  демонстрационные, и это явно написано в отчёте вместе с причиной.
- Сгенерированный код требует ручной проверки и утверждения перед влитием.
- Модель 7B на CPU отвечает несколько минут; таймаут в контейнере — 600 секунд.
- Проверка сгенерированного кода статическая: `ast.parse`, наличие `test_*`,
  запрещённые паттерны. Она не подтверждает, что тесты пройдут или проверяют
  правильные поля ответа.
- Читаемость — честно объявленная формула от длины тестов и docstrings, а не
  оценка качества набора; дубли, покрытие и изоляция считаются отдельно.
- Дубли считаются по структуре: строковые значения игнорируются, а имена ключей,
  срезы и числовые литералы (коды ответов, пороги) — нет. Поэтому тесты,
  различающиеся только числом, дублями не считаются.
- Near-duplicate ищется по Jaccard-сходству нормализованных тел с порогом 0.7;
  на коротких тестах метрика шумная.
- Процент покрытия требований не вычисляется: сопоставления «тест → требование»
  в проекте нет, поэтому в отчёте `unknown`.
- Генерация стохастическая: повторный прогон даст другой текст при том же
  промпте и входе.
