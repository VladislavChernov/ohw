## 1. Как подобное делают в реальной жизни (промышленная практика)

### 1.1. LLM для ревью и генерации автотестов
В современной индустрии QA Automation large language models (GPT-4, Claude, Codellama, DeepSeek Coder, Llama-3) активно применяются для:

| Задача | Как применяют LLM | Инструменты / подходы |
|--------|-------------------|-----------------------|
| Генерация автотестов | Пишут тест-кейс-код по требованиям / user-story / API-спецификации (OpenAPI/Swagger) | GitHub Copilot, Cursor, Tabnine, Ollama (локально), CodeLLama |
| Ревью кода тестов | Анализируют PR с автотестами, находят дубли, хрупкие селекторы, слабые assert'ы | CodeRabbit, Amazon CodeWhisperer, GitLab Code Suggester, SonarQube + LLM |
| Рефакторинг / оптимизация | Убирают дубли, выносят фикстуры, параметризуют, выносят конфиг | Локальные Ollama-модели (codellama, deepseek-coder-v2) для конфиденциальности |
| Генерация тестовых данных | Создают валидные/невалидные payload, граничные значения | Faker + LLM, prompts к LLM |
| Анализ покрытия требований (RTM) | Сопоставляют тесты с требованиями (ID), находят пробелы | Traceability matrix, Jira + Xray, TestRail, custom скрипты |

### 1.2. Почему Ollama локально
- Конфиденциальность: код тестов и требования не улетают в публичное облако.
- Бесплатно и без rate-limitов.
- Можно выбирать специализированные модели кода (codellama:7b/13b, deepseek-coder-v2, llama-3.1-8b).
- Работает в офлайне / закрытом контуре компании.

### 1.3. Типичный workflow (реальный процесс)
1. Разработчик пишет или правит автотест, открывает PR.
2. LLM-бот CodeRabbit / GitHub Copilot автоматически ревьюит diff, оставляет комментарии.
3. QA-инженер раз в спринт запускает скрипт оптимизации: сканирует репозиторий тестов, находит дубли, генерирует отчёт.
4. На основе отчёта рефакторят тесты: параметризация, фикстуры, удаление мёртвых тестов.
5. Обновляют traceability matrix (покрытие требований).
6. Проверяют на тестовой стенде (staging / playground).

### 2.1. Как на этих площадках решают проблемы дублей и оптимизации
- **Параметризация:** одни и те же запросы с разными наборами данных (пользователи, товары) выводятся в `@pytest.mark.parametrize` или Data Provider.
- **Фикстуры:** создание сущности (бронирование, пользователь, товар) перед тестом и удаление после (изоляция, нет мусора).
- **Page Object Model (UI):** вынос локаторов и действий в отдельные классы страниц — убирает дубли шагов.
- **API Client:** один сессионный клиент с базовым URL, таймаутами и ретраями вместо дублирующих `requests` в каждом тесте.
- **Конфиг:** base URL, учётные данные, таймауты выносятся в `.env` / YAML / JSON, не хардкодятся.
- **Отчёты:** `pytest-html`, `allure` — приложение логов, скриншотов, запросов/ответов к прогонам.

## 3. Исследование оптимизации автотестов

### 3.1. Поиск дублирующих шагов в тестах
Что считается дублем шага:
- Одинаковая последовательность действий (открыть страницу → залогиниться → перейти в раздел) повторяется в нескольких тестах.
- Одинаковые HTTP-запросы с телом и assert'ами.

Как ищут:
- Статический анализ AST-кода тестов (поиск одинаковых блоков кода).
- Нормализация кода (замена литералов на плейсхолдеры) и сравнение структур (Jaccard-сходство, как реализовано в `test_optimizer.py`).
- Поиск повторяющихся строк/фрагментов через diff-инструменты.

Как устраняют:
- Вынос в вспомогательные методы / хелперы.
- Фикстуры pytest (`@pytest.fixture`) с setup/teardown.
- Page Object Model (для UI).
- `@pytest.mark.parametrize` для одинаковой логики с разными данными.

### 3.2. Поиск дублирующих (похожих) автотестов
Что считается дублем теста:
- Разные имена, но идентичная логика (например, `test_create_user_Alice`, `test_create_user_Bob`).
- Тесты, проверяющие одно и то же требование одними и теми же способами.

Как ищут:
- Нормализованное сравнение тел тестов (упорядочение токенов, удаление имён/строковых литералов).
- Cosine/Jaccard сходство векторов эмбеддингов кода (в продвинутых решениях — CodeBERT / embeddings).
- Метрики покрытия: два теста покрывают одинаковые строки кода продукта.

Как устраняют:
- Объединение в один параметризованный тест.
- Удаление мёртвых/избыточных тестов (не покрывают новые требования).
- Оставляют только один представительный тест на эквивалентный класс.

### 3.3. Расстанов приоритетов согласно требованиям
Требования заранее описываются с приоритетами (P0–P3):

| Приоритет | Значение | Пример |
|-----------|----------|--------|
| P0 — Критический | Обязателен к авто-покрытию, блокирует релиз | Создание пользователя (201), изоляция тестов |
| P1 — Высокий | Обязателен, небольшая задержка допустима | Невалидный email → 400, дубликат email |
| P2 — Средний | Желательно покрыть | Получение списка, удаление пользователя |
| P3 — Низкий | Опционально | Получение несуществующего пользователя → 404 |

Каждому автотесту сопоставляют:
- ID требования (RTM).
- Приоритет требования.
- Флаг "включить в регрессионный набор".
- Пробелы в покрытии (требование без теста = риск).

### 3.4. Оценка качества автотеста
Оценивают по двум основным измерениям:

**1. Читаемость (Readability):**
- Длина функции теста (рекомендуется ≤ 10–15 строк).
- Наличие docstrings / описания сценария.
- Осмысленные имена (`test_create_user_valid` vs `test_1`).
- Нет магических чисел и строк (вынесены в константы/данные).
- Структура Arrange-Act-Assert видна невооружённым глазом.

**2. Процент покрытия требований (Requirements Coverage %):**
```
Coverage % = (количество требований, покрытых хотя бы одним автотестом)
           / (общее количество требований) * 100
```
Также считают покрытие по приоритетам: P0/P1 должны быть покрыты на 100%.

**Комбинированная оценка:** читаемость (1–10) + coverage % + наличие фикстур/изоляции = итоговый скор качества теста.

### 3.5. Что ещё оптимизируют (список)
- Время выполнения тестов (параллельный прогон `pytest -n auto`, выборка по приоритетам).
- Устойчивость к сбоям (ретраи, таймауты, ожидания вместо `time.sleep`).
- Поддержку тестовых данных (фабрики, фикстуры, очистка БД между прогонами).
- Чёткость отчётов (Allure / pytest-html с вложениями запросов-ответов).
- Синхронизацию с документацией (OpenAPI/Swagger → автогенерация тестов по спецификации).
- Интеграцию в CI/CD (запуск по PR, блокировка мержа при падении P0-тестов).
- Мониторинг флейков (flaky tests) и их устранение.

### 3.6. Критерии "плохих" автотестов (список)
- **Дублируют** другие тесты без добавления новой ценности.
- **Нет изоляции:** оставляют данные в системе, зависят от порядка выполнения, от состояния БД.
- **Жёстко заданные данные и URL** в теле теста (хардкод base URL, логинов, паролей).
- **Нет assert'ов или слабые assert'ы** (проверяют только HTTP-статус, не тело ответа).
- **Нет обработки ошибок сети** (нет таймаутов, ретраев, обработка connection error).
- **Непонятные, неконсистентные имена** тестов (`test_1`, `test_create_user_new_new_name`).
- **Нет документации** (docstrings, комментарии к сложным моментам).
- **Смешивают несколько сценариев** в одном тесте (нарушение принципа "один тест — одна проверка").
- **Зависят от внутренней реализации** (хрупкие селекторы, привязка к порядку полей в JSON).
- **Не покрывают требования с высоким приоритетом** (пробелы в RTM).
- **Долго выполняются** (без параллелизма, с лишними `sleep`).
- **Флейкати:** проходят нестабильно (зависят от времени, сети, порядка).
- **Отсутствуют негативные сценарии** (только happy path).
- **Сложно поддерживать:** любое изменение API ломает десятки тестов (нет абстракций).

## 5. Вывод
В реальной жизни оптимизация автотестов с помощью LLM — это сочетание статического анализа (поиск дублей, метрик), LLM-генерации и ревью, фикстур/параметризации, RTM и интеграции в CI/CD. Локальный Ollama позволяет делать это конфиденциально и бесплатно. Инструменты вроде CodeRabbit, GitHub Copilot, SonarQube и тестовые площадки (JSONPlaceholder, ReqRes, Restful Booker) используются наряду с кастомными скриптами, таким же, как `src/test_optimizer.py` в этом проекте.
