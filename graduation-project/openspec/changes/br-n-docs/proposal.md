# Предложение: документировать `BR-N` и уточнить эвристику

## Зачем

`BR-N` — единственный сквозной идентификатор между требованиями, промптом,
тест-кейсами и метриками. Правила его использования были разбросаны по README,
`docs/metrics.md` и SDD, а эвристика консистентности при `--runs 1` выдавала
нейтральные `0.5`, когда в тексте не было двух ссылок — то есть оценивала то,
чего оценить нельзя.

## Что меняется

1. Отдельный раздел README с правилами `BR-N`: формат, регистр, уникальность,
   влияние на `scenario_coverage` и поле `requirement` тест-кейса.
2. `assess_internal_consistency` возвращает `None`, если ссылок меньше двух;
   `0.8` и `0.5` сохраняются для двух и более идентификаторов.
3. Спека `openspec/specs/quality/spec.md`, `docs/metrics.md` и SDD синхронизированы.
4. Тесты: одна ссылка и текст без ссылок дают `None`; `assess_quality` с одним
   `BR-N` сохраняет `overall` из остальных метрик.

## Что не меняется

- `scenario_coverage`, `clarity`, `readability`, веса и порог `0.5`.
- Поведение при `--runs ≥ 2`: там консистентность — Jaccard повторов.
- `PIPELINE_VERSION = "0.1.0"` и версия проекта `0.3.0`.
- Форматы файлов: ключи и структура `generation.json`/`quality-metrics.json`
  не меняются.

## Критерии приёмки

- Правила `BR-N` описаны в README и согласованы со спекой и SDD.
- При одной ссылке `consistency = n/a`, а не `0.5`.
- При двух и более ссылок без пропусков результат прежний — `0.8`.
