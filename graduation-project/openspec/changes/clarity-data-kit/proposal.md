# Предложение: инструменты для сбора данных по clarity

## Зачем

`clarity` — единственная метрика проекта, которая не опирается на смысл текста:
она считает долю из пяти регулярных категорий. Равные веса `0.2` и сам набор
категорий выбраны без эмпирической проверки. Менять их по ощущениям нельзя:
это будет подгонка под один прогон.

Нужно подготовить корпус с человеческой разметкой и воспроизводимый анализ,
после которого решение о смене формулы можно будет обосновать.

## Что меняется

1. `src/quality/clarity_kit.py` — выгрузка фрагментов, разбор аннотаций,
   Cohen's kappa, корреляции, детерминированный split train/holdout.
2. Публичный аксессор `clarity_signals()` в `src/quality/assessor.py`: он
   возвращает имена сработавших категорий. Формула `assess_clarity_goals`
   не меняется — только устранено дублирование перебора паттернов.
3. Скрипты `scripts/export_clarity_sample.py` и `scripts/analyze_clarity.py`.
4. Гайд `docs/clarity-annotation.md` с определением измеримой цели,
   описанием категорий, шкалой 1–5 и правилами работы двух разметчиков.
5. Тесты экспорта, kappa, корреляций, split и обоих CLI.

## Что не меняется

- Формула `clarity` и веса `0.2` остаются как есть.
- `openspec/specs/quality/spec.md`, `docs/metrics.md` и SDD описывают ту же
  формулу; в гайд добавляется ссылка на инструменты, а не новое определение.
- Новых зависимостей нет: только stdlib и уже используемый `pydantic`.
- Артефакты `examples/live-run/` не перезаписываются.

## Критерии приёмки

- Из снимка выгружается JSONL с фрагментами, категориями текущей метрики
  и пустым полем `annotation`.
- Два файла разметки объединяются по `id`; считаются kappa и совпадение.
- Анализ печатает связь категорий с измеримостью и сравнение равных весов
  с весами, выведенными на train, на отложенной выборке.
- Ни один тест не требует Ollama.
