# Дизайн: инструменты для сбора данных по clarity

## Контекст

`assess_clarity_goals` перебирает пять паттернов и добавляет `0.2` за каждый.
Чтобы анализировать вклад категорий, нужны их имена и сами фрагменты. Метрика
при этом должна остаться прежней.

## Поток

```text
generation.json
  │ export_clarity_sample.py
  ▼
sample.jsonl  (id, text, метаданные, signals, clarity_score, annotation: null)
  │ два разметчика заполняют annotation
  ▼
alice.jsonl + bob.jsonl  (id + annotation)
  │ analyze_clarity.py
  ▼
analysis.md  (kappa, таблица категорий, train/holdout)
```

## Фрагменты

- Секция Markdown (заголовок + тело) — основная единица.
- Если заголовков нет, текст режется по пустым строкам.
- Фрагменты короче `--min-words` (по умолчанию 8) отбрасываются.
- `id` — первые 12 символов SHA-1 от `source|scenario|run_index|text`.
  Он стабилен между прогонами скрипта и служит ключом соединения разметок.
- Для каждого фрагмента сохраняются `signals` и `clarity_score` текущей метрики,
  но гайд запрещает разметчику на них смотреть.

## Доступ к категориям

В `src/quality/assessor.py` добавляются `CLARITY_SIGNAL_NAMES` и
`clarity_signals(text)`. `assess_clarity_goals` считает ту же сумму
`sum(0.2 for _ in clarity_signals(text))`: порядок паттернов и арифметика
не меняются, меняется только источник перебора. Тест проверяет равенство
старой формулы и нового аксессора на типовых текстах.

## Аннотация

```json
{
  "id": "a1b2c3d4e5f6",
  "annotation": {
    "annotator": "alice",
    "measurable": true,
    "signals": ["modality", "result"],
    "rating": 4
  }
}
```

- `measurable` — бинарная оценка измеримости цели.
- `signals` — подмножество из пяти категорий, реально использованных по смыслу.
- `rating` — целое 1–5.
- Разметка может лежать в выборке или в отдельном JSONL; для двух разметчиков
  используются `--annotator-a` и `--annotator-b`.

## Анализ

- `Cohen's kappa` и доля совпадений по `measurable`; `n/a` при отсутствии пары.
- По каждой категории: сколько раз она есть в тексте, доля измеримых фрагментов
  при её наличии и отсутствии, сколько раз её отметил разметчик.
- Корреляция Пирсона текущей оценки с `rating`; precision/recall при пороге
  `clarity_score >= 0.5` относительно `measurable`.
- Train/holdout: детерминированное деление по `id` (70/30 по модулю 100).
  На train выводятся веса из корреляции категории с оценкой `rating`
  (отрицательные обрезаются в ноль, сумма нормируется); на обоих наборах
  сравниваются равные веса и выведенные.
- При нулевой дисперсии корреляция — `n/a`, веса — равные.

## Ограничения

- Это разведочная аналитика, а не автоматическая смена метрики.
- Приемлемое согласие разметчиков — обязательное условие перед изменением
  формулы; порог в гайде — `kappa >= 0.6`.
- Никаких результатов подбора весов в production-код не записывается.
- Выгрузка читает только снимки; `quality-metrics.json` не содержит
  исходного текста генераций.

## Альтернативы

- **Менять веса сразу по одному прогону.** Отклонено как подгонка без данных.
- **Использовать LLM-судью.** Отклонено: проект принципиально не использует
  модель как метрику.
- **Добавить `scikit-learn` для корреляций.** Отклонено: нужны две формулы
  из stdlib, зависимость не оправдана.
- **Хранить разметку в CSV.** Отклонено: вложенные `signals` естественнее
  в JSONL, а формат уже используется для выборки.
