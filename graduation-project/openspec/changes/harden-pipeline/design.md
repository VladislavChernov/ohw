# Дизайн: устойчивый пайплайн (P0 ревью)

## Контекст

Фазы общаются через файлы в `--output-dir`:

```text
generate ──▶ generation.json ──▶ assess ──▶ quality-metrics.json
                                               ├──▶ visualize
                                               └──▶ report
```

Пока контракт не версионирован, а ошибка соединения с Ollama прерывает весь
прогон. Изменение закрывает оба пробела, не меняя формат остальных полей.

## Версия пайплайна

- Источник истины — `PIPELINE_VERSION` в `src/config.py`.
- Версия увеличивается при любом несовместимом изменении `generation.json` или
  `quality-metrics.json`.
- Оба файла получают ключ `pipeline_version`.
- В `quality-metrics.json` остаётся `version` — версия проекта/схемы отчёта;
  `pipeline_version` описывает совместимость стадий.

### Матрица чтения

| Состояние файла | `load_snapshot` / `load_pipeline_data` |
|---|---|
| ключа `pipeline_version` нет | legacy: файл читается, версия не подставляется |
| версия совпадает с `PIPELINE_VERSION` | файл читается |
| версия отличается | `ValueError` с именем файла, версией файла и текущей версией |
| файл отсутствует | `FileNotFoundError` с подсказкой, какую фазу запустить |

Ошибка несовпадения попадает в CLI как ошибка входа (код `2`) и в UI как
`st.error`; это осознанно: молчаливое чтение чужого формата опаснее падения.

### Почему отсутствие версии — не ошибка

`examples/live-run/` и пользовательские `output/` содержат файлы, записанные до
введения версии. Формат `0.1.0` совместим с ними, поэтому отсутствие ключа
трактуется как legacy. После следующего изменения формата такие файлы нужно
будет перегенерировать.

## Ошибки Ollama

`generate_scenarios` различает три класса сбоев:

| Класс | Поведение |
|---|---|
| `GenerationError`, `OllamaResponseError` | ошибка файла в `errors`, остальные файлы обрабатываются |
| `OllamaConnectionError`, `continue_on_error = False` | проброс исключения, прогон прерывается (код `3`) |
| `OllamaConnectionError`, `continue_on_error = True` | ошибка файла в `errors`, остальные файлы обрабатываются |

Флаг хранится в `GenerationRequest.continue_on_error` со значением по умолчанию
`False`, поэтому поведение CLI и UI без флага не меняется.

`_check_model` в CLI при `--continue-on-error` не прерывает прогон: недоступная
Ollama логируется предупреждением, а ошибки фиксируются по файлам. Без флага
ранняя проверка остаётся fail-fast.

## CLI

```text
python -m src.workflow ... [--continue-on-error]
```

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--continue-on-error` | выкл. | продолжать генерацию, если Ollama недоступна для отдельного файла |

Флаг влияет только на `OllamaConnectionError`; ошибки входа и записи файлов
по-прежнему завершают прогон.

## UI

На вкладке «Генерация» появляется чекбокс «Продолжать при ошибке Ollama».
Он передаётся в `GenerationRequest.continue_on_error`. UI использует те же
стадии, поэтому семантика совпадает с CLI.

## Тесты

- `tests/test_workflow.py` — версия в снимке, legacy-снимок, несовпадение,
  `--continue-on-error` в CLI.
- `tests/test_reporting.py` — версия в JSON-отчёте, legacy-отчёт, несовпадение.
- `tests/test_pipeline.py` — fail-fast без флага и продолжение с флагом.
- `tests/test_ui_app.py` — чекбокс передаёт `continue_on_error`.

## Альтернативы

- **Всегда продолжать при ошибке соединения.** Проще, но меняет поведение по
  умолчанию и скрывает полностью недоступную Ollama; отклонено.
- **Строгая проверка версии без legacy.** Ломает уже сохранённые артефакты и
  `examples/live-run/`; отклонено.
- **Миграция старых файлов на лету.** Лишняя сложность для `0.1.0`; вместо неё
  документирован legacy-режим.
