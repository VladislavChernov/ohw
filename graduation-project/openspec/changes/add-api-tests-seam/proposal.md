# Предложение: шов для API-тестов

## Зачем

Сейчас проект закрывает первую половину QA-цикла: требования → тестовая
документация → метрики → отчёт. Следующий шаг — исполняемые API-тесты:
контракт → LLM генерирует данные и шаги → движок выполняет HTTP-запросы →
результаты попадают в общий отчёт.

Ядро для этого уже есть в ДЗ3 advanced: JSON-план тестов, валидация схемы,
HTTP-движок, retry с замечаниями. Оно хорошо стыкуется с ДЗ2: тот же паттерн
«промпт → JSON → валидация → повтор», тот же Ollama-клиент и общий стенд.

Времени на полную интеграцию сейчас нет. Поэтому сначала делаем **шов**:
стабильный контракт фазы, который сегодня ничего не вызывает, а завтра
подключается одним адаптером без переделки workflow, моделей и отчёта.

## Что входит

1. Порт `ApiTestRunner` и модели результата (`ApiTestRequest`,
   `ApiTestReport`, `ApiCaseResult`).
2. Заглушка `DisabledApiTestRunner`: явно сообщает, что адаптер не подключён.
3. CLI-флаги `--api-tests`, `--api-base-url`, `--api-contract`, `--api-cases`.
4. Файл `api-tests.json` — источник правды для раздела API-тестов.
5. Раздел `## API-тесты` в `report.md` только при наличии данных.
6. Unit-тесты шва на фейковом раннере, без сети.
7. Документация: SDD, README, OpenSpec.

## Что сознательно не входит

- Вендоринг ДЗ3 advanced и любые HTTP-вызовы.
- ДЗ6 (ревью автотестов) — другой тип артефакта, вернёмся отдельно.
- Изменение `overall` и существующих четырёх метрик.
- HTTP-фасад самого проекта: он появится вместе с реальным адаптером.
- Embedded Python: вместо вендоринга рантайма используется `uv`.

## Критерии готовности

- Без `--api-tests` поведение, артефакты и коды возврата не меняются.
- С `--api-tests` и подключённым раннером создаётся `api-tests.json` и раздел
  в отчёте; без раннера — код 2 и понятное сообщение.
- `uv run pytest`, `ruff check`, `mypy src` проходят без Ollama.
- Документация описывает контракт, а не гипотетическую реализацию.
