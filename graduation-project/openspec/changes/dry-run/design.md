# Дизайн: режим `--dry-run`

## Контекст

Промпт собирается в `src/generator/pipeline.py`: загружаются требования,
выбирается обработчик артефакта, читаются пресеты, затем handler строит system-
и user-промпты. Вызов Ollama происходит позже, в `generate_artifact`. Чтобы
посмотреть промпт, сейчас нужно дождаться ответа модели.

## Разделение ответственности

```text
CLI --dry-run
  │
  ▼
build_prompt_previews(request)   # без сети
  │  те же load_docs/get_handler/select_extras
  ▼
stages.dry_run(previews, output_dir, model)
  │
  ▼
output/prompts/<stem>.system.txt
output/prompts/<stem>.user.txt
output/prompts/manifest.json
```

Общая подготовка (документы, обработчик, пресеты) выделяется в
`_prepare_generation(request)` и используется и обычной генерацией, и dry-run.
Это исключает расхождение промптов между режимами.

## Формат вывода

Для каждого входного файла пишутся два текстовых файла в UTF-8 без BOM. Имена
берутся из `doc.path.stem`, как у сгенерированных артефактов.

`manifest.json`:

| Поле | Смысл |
|---|---|
| `project`, `version` | идентификация проекта и релиза |
| `artifact_type`, `count`, `runs`, `temperature`, `model` | параметры прогона |
| `prompts[]` | `filename`, `system_file`, `user_file`, `prompt_sha256`, `note` |

`prompt_sha256` считается от пользовательского промпта тем же способом, что и
в `ScenarioResult` обычного прогона. По нему можно сверить режимы без чтения
больших текстов.

## Особенности

- `coveragematrix`: при реальном прогоне в `{testcases}` подставляется индекс
  сгенерированных тест-кейсов; без модели его нет. Dry-run оставляет стандартную
  формулировку шаблона «No test cases have been generated…» и добавляет `note`
  в манифест.
- Пользовательские правки промпта из UI (`request.prompts`) применяются и здесь.
- Нормализация требований и presets работают одинаково в обоих режимах.
- `--quality-weights` не влияет на промпты и в dry-run игнорируется с
  предупреждением, как на фазах `assess`/`report`.

## CLI

- `--dry-run` — отдельный флаг подготовки промптов; он не вызывает
  `list_models`.
- При `--dry-run` выполняется только подготовка промптов; последующие фазы
  не запускаются, потому что снимка не существует.
- `--dry-run` + `--assess`/`--visualize`/`--report` → `parser.error`, код `2`.
- Код `0` означает, что промпты записаны; `generation.json` не создаётся.

## Тесты

- Промпт из dry-run совпадает с `prompt` обычного прогона при тех же входах
  (сравнение SHA-256).
- `OllamaClient.chat` и `list_models` подменяются так, чтобы любой вызов
  считался ошибкой теста.
- CLI без доступной Ollama возвращает `0` и пишет файлы.
- Конфликтующие флаги дают код `2`.
- Для `coveragematrix` манифест содержит пояснение.

## Альтернативы

- **Переиспользовать обычную генерацию с мок-клиентом.** Потребовало бы
  подменять сеть в CLI и всё равно записало бы фиктивный снимок; отклонено.
- **Показывать промпт в stdout.** Удобно для одного файла, но не масштабируется
  и не даёт стабильных артефактов для ревью; отклонено.
- **Вынести сборку промптов в отдельный модуль.** Разрушает связь с handler и
  повышает риск расхождения; выбран общий helper внутри `pipeline.py`.
