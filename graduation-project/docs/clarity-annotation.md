# Гайд по разметке `clarity`

Этот гайд нужен, чтобы собрать данные для пересмотра метрики `clarity`.
Сейчас метрика считает долю из пяти регулярных категорий и не знает, действительно
ли цель измерима. Пока корпус не размечен, формулу и веса менять нельзя.

Инструменты не меняют production-метрику: они только выгружают фрагменты и
считают диагностику по вашим оценкам.

## 1. Что размечаем

Единица разметки — **фрагмент**: секция сгенерированного артефакта (обычно
заголовок плюс его содержимое) или абзац, если заголовков нет. Скрипт экспорта
сам режет текст по заголовкам Markdown, затем по пустым строкам.

В JSONL у каждого фрагмента есть:

| Поле | Смысл |
|---|---|
| `id` | стабильный хеш для сопоставления разметчиков |
| `text` | сам фрагмент |
| `scenario`, `artifact_type` | исходный файл требований и тип артефакта |
| `model`, `generated_at`, `run_index` | метаданные прогона |
| `requirement_ids` | требования из входа |
| `signals` | категории, которые видит текущая метрика |
| `clarity_score` | текущая оценка `clarity` (только для сравнения) |
| `annotation` | сюда пишется ваша разметка |

**Не смотрите на `signals` и `clarity_score` при разметке.** Они нужны скрипту
анализа, а не разметчику: иначе оценка будет подгоняться под метрику.

## 2. Что считать измеримой целью

`measurable = true`, если по фрагменту можно однозначно придумать проверку:
есть объект, действие или состояние, ожидаемый результат и условие, при котором
результат считается достигнутым.

Примеры измеримых формулировок:

- «Система должна показывать сообщение «Неверный пароль» при несовпадении
  паролей» — есть условие и конкретный результат.
- «Пользователь может войти с корректным email и паролем» — есть проверяемое
  действие и критерий успеха.
- «Система не должна принимать пароль короче 8 символов» — есть запрет и
  числовой критерий.

Примеры неизмеримых:

- «Интерфейс должен быть удобным» — нет критерия удобства.
- «Система должна быстро отвечать» — нет порога времени.
- «Проверить корректность работы» — проверка есть, объекта и результата нет.
- Список шагов без ожидаемого результата.

Если сомневаетесь, задайте вопрос «что именно увидит тестировщик и как решит,
пройдена проверка или нет?». Нет ответа — `measurable = false`.

## 3. Категории `signals`

Отметьте те категории, которые **реально использованы по смыслу**, а не просто
встретились как слова. Разрешено ноль, одна или несколько.

| Категория | Признаки |
|---|---|
| `modality` | `должен/должна/должно/должны`, `must`, `shall`, `should` |
| `expectation` | `ожидаем*`, `expected` |
| `verification` | `провер*`, `убеди*`, `верифиц*`, `verify` |
| `prohibition` | `не должен`, `нельзя`, `must not` |
| `result` | `результат*`, `поведени*`, `сообщени*`, `result`, `behavior`, `output` |

Важно: `не должен` содержит и модальность, и запрет. Если фраза действительно
выражает запрет, отметьте обе категории. Если ключевое слово полное, но
смысла нет (например, «результат проверки качества работы» без конкретики),
категорию не ставьте.

## 4. Общая оценка `rating`

Целое число от 1 до 5:

| Оценка | Что значит |
|---:|---|
| 1 | цель не сформулирована, проверка невозможна |
| 2 | есть намёк на проверку, но критерий отсутствует |
| 3 | проверка возможна, но требует домысливания |
| 4 | цель измерима, один критерий не раскрыт |
| 5 | измеримо полностью, результат и условия ясны |

`rating` и `measurable` должны быть согласованы: `measurable = true` обычно
соответствует `4` или `5`, `false` — `1` или `2`. Исключения допускаются, если
вы явно опишете их в комментарии.

## 5. Формат разметки

Добавьте к нужной строке JSONL поле `annotation` (или создайте отдельный файл
с полями `id` и `annotation`):

```json
{
  "id": "a1b2c3d4e5f6",
  "annotation": {
    "annotator": "alice",
    "measurable": true,
    "signals": ["modality", "prohibition", "result"],
    "rating": 4
  }
}
```

Поле `id` копируется из выгрузки и не меняется. Один разметчик — один файл
`annotations-alice.jsonl`, `annotations-bob.jsonl`.

## 6. Порядок работы

```bash
# 1. Выгрузить фрагменты из снимка (можно несколько --input)
uv run python scripts/export_clarity_sample.py \
  --input examples/live-run/generation.json \
  --output output/clarity/sample.jsonl

# 2. Разметить дважды: заполнить annotation в двух копиях файла
#    или сделать два отдельных файла с id + annotation

# 3. Посчитать согласие и диагностику
uv run python scripts/analyze_clarity.py \
  --sample output/clarity/sample.jsonl \
  --annotator-a output/clarity/alice.jsonl \
  --annotator-b output/clarity/bob.jsonl \
  --output output/clarity/analysis.md
```

Если разметка встроена прямо в выборку, `--annotator-a` и `--annotator-b` можно
не указывать: тогда анализируется один разметчик и kappa будет `n/a`.

### Пилотная выборка

Из одного legacy-снимка `examples/live-run/generation.json` получается 21
фрагмент при `--min-words 0`. Для пилота на 30 фрагментов добавьте свежий снимок
из integration-прогона (путь зависит от временной папки pytest):

```bash
uv run python scripts/export_clarity_sample.py \
  --input examples/live-run/generation.json \
  --input <tmp_path>/test_full_pipeline_from_sdd_re0/generation.json \
  --min-words 0 \
  --output output/clarity/all.jsonl
```

Затем отсортируйте записи по `id`, возьмите первые 30 и запишите в
`output/clarity/pilot-sample.jsonl`. Файлы в `output/` не коммитятся: это
рабочие материалы разметчиков. Получившийся пилот содержит по 15 фрагментов
из каждого снимка.

### Сухой прогон на моделях

`scripts/annotate_with_models.py` готовит промпты и проверяет ответы моделей:
режим `prepare` создаёт по файлу промптов на разметчика, `collect` валидирует
ответы через ту же схему аннотации. Это **только проверка инструментов**: две
разные модели могут выдать одинаковый kappa и при этом не быть человеческой
разметкой. На таких данных нельзя менять формулу `clarity` — они нужны, чтобы
проверить контакт гайда, формата и `analyze_clarity.py` до найма разметчиков.

## 7. Что делать с результатом

1. Если `Cohen's kappa < 0.6`, уточните гайд и повторите разметку. Проблема в
   определении измеримости, а не в весах категорий.
2. Посмотрите таблицу категорий: где разметчик видит измеримость, а метрика —
   нет, и наоборот.
3. Сравните корреляцию равных весов и весов, выведенных на train, на holdout.
   Если выигрыша на holdout нет, метрику не меняют.
4. Только после стабильного согласия и подтверждённого выигрыша меняйте
   формулу, тесты, `openspec/specs/quality/spec.md`, `docs/metrics.md` и SDD.

Разделение train/holdout детерминировано по `id`, поэтому повторный запуск даёт
те же группы. Корреляция печатает `n/a`, если дисперсия оценок равна нулю.
