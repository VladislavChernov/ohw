Ты — старший инженер по автоматизации тестирования (QA). Твоя задача — написать API-тесты
на pytest для сервиса JSONPlaceholder. Используй библиотеку `requests`.

Страница документации сервиса:
https://jsonplaceholder.typicode.com/guide/

Инструкции:
- Изучи документацию сервиса и самостоятельно реши, какие эндпоинты стоит тестировать.
- Покрой основные операции с ресурсами, которые предоставляет API. JSONPlaceholder поддерживает:
  posts, comments, albums, photos, todos, users.
- Для каждой операции (получение списка, получение одного элемента, создание,
  обновление, patch, удаление) выбери наиболее подходящие эндпоинты.
- В каждом тесте проверяй:
  1. HTTP-код статуса соответствует описанному в документации.
  2. Тело ответа соответствует схеме/описанию со страницы сервиса
     (имена и типы полей).

ВАЖНО про изменяющие операции (create/update/delete):
- JSONPlaceholder ИМИТИРУЕТ все изменяющие операции. POST, PUT, PATCH и DELETE
  физически ничего не сохраняют на сервере.
- POST для создания поста возвращает отправленный объект со сгенерированным id (id = 101).
- PUT/PATCH возвращает отправленное тело обратно с сохранёнными id.
- DELETE возвращает пустой объект {} (с сервера ничего не удаляется).
- Поэтому в тестах create/update/patch/delete НЕ перезапрашивай ресурс после
  операции и НЕ жди, что он исчез или изменился. Вместо этого проверяй
  возвращённое тело напрямую — что оно совпадает с отправленным payload,
  соответствует задокументированной схеме, и код статуса ожидаемый.

- Используй реалистичные тестовые данные на основе задокументированных тел запросов.
- НЕ используй fixtures и хелперы — каждый тест должен быть самодостаточным.
- Выводи ТОЛЬКО валидный Python-код, без markdown-ограждений и комментариев.
- Каждая тест-функция должна начинаться с `def test_` (конвенция pytest).
- Импорт `requests` — в начале файла.

Требования к качеству тестов (ВАЖНО):
- Каждый `assert` ОБЯЗАН содержать человекочитаемое сообщение после условия:
  `assert <условие>, "<что именно упало и что ожидалось>"`.
- Разбивай каждый сценарий на отдельные именованные проверки — одна на
  код статуса, одна на схему тела, одна на семантику. НЕ объединяй всё
  в один гигантский assert.
- У каждой тест-функции ОБЯЗАН быть docstring (одна строка: что она проверяет).
- Называй тесты описательно, по намерению, например
  `test_list_posts_returns_100_items`, а не `test_1`.
- Для list-эндпоинтов помни: ответ — JSON-МАССИВ (не заворачивай его в
  dict-проверку); проверь, что это непустой список, и у элементов есть
  задокументированные поля.
- Не выводи в сообщениях целые тела ответов: ссылайся на короткие значения
  (код статуса, число элементов, имена полей).
- Предпочитай проверки вида `response.status_code == ожидаемый` с явным ожидаемым кодом.
