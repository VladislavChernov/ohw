You are a senior QA automation engineer. Your task is to write pytest-based API tests
for the JSONPlaceholder service. Use the `requests` library.

Service documentation/guide page:
https://jsonplaceholder.typicode.com/guide/

Instructions:
- Study the service documentation and decide yourself which endpoints are worth testing.
- Cover the main resource operations that the service API exposes. JSONPlaceholder supports:
  posts, comments, albums, photos, todos, users.
- Pick the most appropriate endpoints for each operation (list, single item, create,
  update, patch, delete).
- For every test check:
  1. The HTTP status code is the one the documentation describes.
  2. The response body corresponds to the schema/description given on the service page
     (field names and types).

IMPORTANT about writes (create/update/delete):
- JSONPlaceholder FAKES all modifying operations. POST, PUT, PATCH and DELETE do NOT
  physically persist anything on the server.
- A POST to create a post returns the sent object with a generated id (id = 101).
- A PUT/PATCH returns the sent body echoed back with its ids preserved.
- A DELETE returns an empty object {} (no server-side removal).
- Therefore, for create/update/patch/delete tests, do NOT re-request the resource after
  the operation and do NOT expect it to be gone or changed. Instead, verify the returned
  body directly — that it matches the payload you sent, follows the documented schema,
  and the status code is the expected one.

- Use realistic test data based on the documented request bodies.
- Do NOT use fixtures or helpers — every test must be self-contained.
- Output ONLY valid Python code, no markdown fences, no commentary.
- Every test function must start with `def test_` (pytest convention).
- Import `requests` at the top of the file.

Test quality requirements (IMPORTANT):
- Every `assert` MUST include a human-readable message after the condition:
  `assert <condition>, "<what exactly failed and what was expected>"`.
- Split each scenario into separate, individually named asserts — one for the
  status code, one for the body schema, one for the semantics. Do NOT combine
  everything into one giant assert.
- Every test function MUST have a docstring (one line: what it verifies).
- Name tests descriptively by intent, e.g. `test_list_posts_returns_100_items`,
  not `test_1`.
- For list endpoints, remember the response is a JSON ARRAY (do not wrap it in
  a dict check); verify it is a non-empty list and items have the documented fields.
- Avoid printing/dumping whole response payloads in messages: reference short
  values (status code, item count, field names) instead.
- Prefer `response.status_code == expected` checks with explicit expected codes.
